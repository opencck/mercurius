# BRIEF — контекст проекта mercurius

Что строим и почему: требования к агенту, принятые решения, открытые вопросы и база знаний, на которую
опирается разработка. Порядок работ — в [ROADMAP.md](ROADMAP.md), правила работы — в [CLAUDE.md](CLAUDE.md).

`CLAUDE.md` и `ROADMAP.md` ссылаются на разделы этого файла по якорям: заголовки разделов не переименовывать
без правки ссылок.

## Цель

Разработать автономного агента **mercurius (Меркурий)** — персонального помощника, который ставится на сервер
через Docker Compose и общается с владельцем через Telegram. Что он должен уметь — в [требованиях](#меркурий-требования),
в каком порядке это строится — в [ROADMAP.md](ROADMAP.md).

Проект начинался как исследование автономных агентских систем. Исследовательский этап завершён; его результат —
[база знаний](#база-знаний), на которую опирается разработка. Новые материалы изучаются под конкретные задачи роадмапа.

## Меркурий: требования

Записано со слов владельца проекта 2026-11-16. Это исходные данные для `ROADMAP.md`.

### Назначение

Многофункциональный автономный агент — персональный помощник по любым делам. Пользователь ставит его
на свой сервер, запускает через Docker Compose и общается через Telegram-бота. Роли: поиск в интернете,
работа с серверами (SSH, SQL, ping, VLESS), написание кода, создание и ведение проектов по разработке ПО,
персональный менеджер, оркестратор агентов, планировщик, тестировщик, исследователь.

### Режим работы и автономность

- Агент работает на сервере постоянно: держит агентский цикл, харнесс, изоляцию окружения, скиллы и MCP.
- Какие действия требуют подтверждения — определяется настройками и памятью, которая складывается в ходе эксплуатации.
- Агент подстраивается под задачи пользователя и сам себя улучшает: решает, как хранить данные и память, как по ним искать и как работать.

### Ограничения и безопасность

- Не разглашать чужие сведения; осторожно обращаться с персональными данными.
- Никому не передавать авторизационные и секретные данные.
- Глобальное поведение агента может менять только владелец; владелец определяется, например, по id Telegram-аккаунта.

### Стек

- PHP 8.2+, AMPHP v3 / Revolt.
- Основной фреймворк и принцип организации архитектуры — `opencck/server` (DDD).
- Сервисы проекта описываются в Docker Compose.
- Первый провайдер модели — OpenRouter; первый канал связи — Telegram.
- Компоненты, полезные вне Меркурия, выносятся в пакеты-сабмодули `packages/` (репозитории `github.com/opencck/`).
- Хранилище: PostgreSQL или MariaDB через асинхронный DBAL, чтобы работало и то и другое. По умолчанию — PostgreSQL (см. [решения](#решения)).
- Сеть к модели: если задан `VLESS_URI`, запросы к провайдерам моделей (OpenRouter и OpenAI) идут через VLESS; если пуст — напрямую. Серверы владельца работают без REALITY и Vision, поэтому `amphp-vless` подходит.

### Абстракции, обязательные с начала

- **Модель:** единый интерфейс работы с LLM, чтобы новые API любых нейросетей подключались без переделки ядра.
- **Каналы связи:** единый интерфейс приёма запросов и отправки ответов. Сейчас только Telegram-бот; позже — WS API, REST API, боты в Bitrix24, Slack и т. п.

### Инструменты из коробки

- Сеть: HTTP/HTTPS/SOCKS5-прокси, VLESS; SSH, в том числе через VLESS (референсы `amphp-ssh`, `amphp-vless`).
- Серверы: SSH, SQL, ping.
- Git, файлы, поиск в интернете, почта.
- Браузер: виртуальный Chrome под Puppeteer с API на Fastify, через которое агент управляет браузером. Цель — работать с веб-интерфейсами (web.telegram.org, web.max.ru, instagram.com, x.com, facebook.com, threads и т. п.), в том числе публиковать материалы.
- Собственные API: HTTP REST, WS, SSE — возможно.
- Связь с другими экземплярами Меркурия по WebSocket API: подключённые экземпляры работают как агенты и субагенты — см. [«Сеть агентов»](#сеть-агентов).
- Asana не нужна.

### Память

- Долговременная память обязательна.
- Ядро агента строится по аналогии с агентом hermes ([конспект](notes/hermes-agent.md)).
- Организация памяти — по принципам hermes-plugin-holographic ([конспект](notes/hermes-plugin-holographic.md)) и hermes-dreaming ([конспект](notes/hermes-dreaming.md)).
- Слой, всегда лежащий в контексте, и HRR-поиск делаются сразу (решение владельца 2026-11-16).
- Проект, задача проекта и отношение участника (человека или агента) к проекту — отдельные слои памяти (требование владельца 2026-11-16).
- Устройство — в разделе [«Память: слои»](#память-слои).

### Качество кода и CI

Требование владельца 2026-11-16. Действует для основного репозитория и всех пакетов.

**Инструменты в каждом PHP-репозитории:**

| Инструмент | Настройка | Зачем |
|------------|-----------|-------|
| PHPUnit | `phpunit.xml.dist`; асинхронные тесты — через `AsyncTestCase`; группа `integration` для тестов, которым нужны сеть и секреты | Тесты |
| PHPStan | `phpstan.neon.dist`, уровень `max` | Типы и ошибки на уровне анализа |
| Psalm | `psalm.xml`, `errorLevel="1"` | Второй анализатор: ловит другое, особенно в шаблонах и `@psalm-*` |

- В `composer.json` каждого репозитория — скрипты `test`, `phpstan`, `psalm` и общий `check`, который запускает все три. Локально и в CI запускается одно и то же.
- Проект новый, поэтому анализаторы строгие с первого коммита; базовые файлы с подавленными ошибками (baseline) не заводим. Подавление конкретной ошибки — только точечно, с комментарием почему.
- `browser-service` написан на Node.js: вместо этой тройки — проверка типов TypeScript, линтер и тесты, по тем же правилам CI.

**GitHub Actions — экономно:**

- **Один workflow, одна задача (job):** `composer check` последовательно, без матрицы версий на каждый push. Минимальная поддерживаемая версия PHP (8.2) — на каждый запуск; проверка на новейшей — вручную (`workflow_dispatch`) или перед релизом.
- **Когда запускается:** push в `master` и pull request в `master`. Изменения только в документации (`**.md`, `docs/**`, `notes/**`) запуск не вызывают (`paths-ignore`).
- **Без лишних повторов:** `concurrency` с `cancel-in-progress` — новый push отменяет старый запуск той же ветки.
- **Кеш:** каталог Composer и кеши PHPStan и Psalm между запусками.
- **Лимит времени:** `timeout-minutes` на задачу (ориентир — 10 минут).
- **Без расписаний** (`schedule`) и без тестов, которым нужны сеть и секреты: группа `integration` в CI исключается и запускается на сервере проекта.
- В основном репозитории сабмодули-референсы в CI не клонируются (`submodules: false`); сабмодули пакетов — только если они нужны для проверки.

### Веб-сервер и входящие подключения

- У Меркурия есть HTTP-сервер (`opencck/server`). Точка входа — `https://mercurius.srv.rekryt.ru/` через Nginx Proxy Manager на сервере владельца; NPM настраивает владелец.
- Сервис подключается к внешней Docker-сети `web` (на сервере она есть: bridge, IPv6 выключен), чтобы NPM видел его по имени контейнера. Наружу порты не публикуются.
- Telegram работает через webhook: Telegram шлёт обновления на `APP_URL` + путь вебхука, запрос проверяется по заголовку `X-Telegram-Bot-Api-Secret-Token` (значение — `TELEGRAM_WEBHOOK_SECRET`). Если `APP_URL` пуст — бот работает long polling (локальная разработка).
- Через тот же вход работает WebSocket API для [сети агентов](#сеть-агентов); в NPM для хоста включается поддержка WebSocket.

### Выбор моделей

- Агент декомпозирует задачу и оценивает части от 1 до 10 по набору критериев (текст, изображения, звук, академические знания, математика и др.); где выгодно — отдаёт части разным моделям, оптимизируя цену токенов и скорость ответа. Устройство — в разделе [«Выбор моделей под задачу»](#выбор-моделей-под-задачу).

### Архитектура

### Наблюдаемость

- Подробные логи для диагностики и доработки агента, пригодные для оптимизации расхода токенов, времени ответа и скорости решения задач.

### Рамки

- Дедлайнов и потолка бюджета нет. Разработку ведут владелец и Claude.

## Устройство приложения на opencck

Как компоненты Меркурия ложатся на `opencck/server` (DDD-слои Domain → App → Infrastructure, модули через
`App::addHandler()`, сервисы-одиночки, события, задачи `amphp/parallel`). Составлено по скиллу `skill-opencck`
2026-11-16 (фаза 0); уточняется в фазах 1–3. Код пакетов из `packages/` от opencck не зависит — основной репозиторий
оборачивает их в сервисы и модули.

### Domain — сущности и правила

| Что | Сущности | Примечание |
|-----|----------|------------|
| Пользователи | `User`, `Role`, `ChatBinding` | Владелец — `User` с ролью владельца, по `TELEGRAM_ADMIN_ID` |
| Диалог | `Conversation` (сессия), `Message`, `Attachment` | Эпизоды памяти — это они же |
| Исполнение | `Run` (запуск агента или воркера, вложенный), `Step`, `ToolCall`, `Approval` | `Approval` — приостановленный `ToolCall` с токеном возобновления |
| Проекты | `Project`, `ProjectTask`, `OwnerProjectRelation` | Слои памяти 2–4, общие с планировщиком |
| Память | `Fact`, `FactVersion`, `MemoryEntity`, `Tombstone`, `CoreMemory` (слой «всегда в контексте») | Схема и логика — в пакете `memory`, здесь — привязка к пользователям и проектам |
| Модели | `ModelProfile`, `ModelRole`, `RoutingDecision` | Каталог OpenRouter и журнал решений о выборе модели |
| Расширения | `Skill`, `McpServer`, `Peer`, `ScheduledJob` | |
| Трассы | `Span`, `Usage` | Расход по вызовам и шагам |

Сущности неизменяемые (`readonly`, создание через фабрики), репозитории — асинхронный DBAL. **Стратегии** opencck
(подписчики на события с алгоритмом) — для выбора модели, политики подтверждений и правил консолидации.

### App — сценарии

- **Сервисы** (одиночки): `AgentRuntime` (цикл и запуски), `ToolRegistry`, `ApprovalService`, `ModelRouter`, `ConversationService`, `MemoryService` (обёртка пакета `memory`), `TraceService`, `SchedulerService`, `PeerService`, `UserService`.
- **События**: `MessageReceived`, `RunStarted`, `ToolCallRequested`, `ApprovalRequested`, `ApprovalResolved`, `RunFinished`, `MemoryWritten`, `RoutingDecided`. Трассировка и метрики подписываются на них, а не встраиваются в код цикла.
- **Контроллеры**: вебхук Telegram (`POST`, проверка секрета, ответ сразу), `health`, `metrics` (Prometheus); WebSocket — сеть агентов (JSON-RPC-маппер opencck).

### Infrastructure — модули и процессы

| Модуль (`AppModuleInterface`) | Что делает |
|-------------------------------|------------|
| `HttpServerModule` | Один `SocketHttpServer`: HTTP и WebSocket за Nginx Proxy Manager (сеть `web`) |
| `TelegramModule` | Регистрирует вебхук при заданном `APP_URL`, иначе — цикл long polling |
| `AgentModule` | Очередь запусков; при старте поднимает незавершённые запуски и ожидающие подтверждения из БД |
| `SchedulerModule` | Задания по расписанию (`EventLoop::repeat`) |
| `ConsolidationModule` | Ночная консолидация памяти |
| `ModelCatalogModule` | Обновление каталога моделей OpenRouter по расписанию |
| `PeerModule` | Исходящие подключения к другим экземплярам |

- **Задачи `amphp/parallel`** — всё, что нагружает процессор: кодирование и сравнение HRR, анализ текста при массовой записи, миграции.
- **Песочница исполнения** — отдельный сервис compose с небольшим API исполнения; её образ собирается из основного репозитория.
- **Хранение состояния — только PostgreSQL.** `Storage` opencck с автосохранением из памяти процесса для долговечного состояния не используем: запуски, подтверждения и очереди должны переживать перезапуск.

### Решено в фазе 1

- **`opencck/server` — метапакет зависимостей AMPHP** (HTTP-сервер, роутер, WebSocket, журнал); классы `App`, `Server`, обработчики пишутся в проекте. Корневой namespace приложения — `OpenCCK\`.
- **База — `amphp/postgres`**, а не `drift/dbal`: родной для AMPHP v3, без адаптера ReactPHP. Работает поверх `ext-pgsql`.
- **Без расширения цикла `ev`:** `amphp/postgres` поверх `ext-pgsql` отказывается работать с драйвером `ev`. Используется встроенный драйвер `stream_select`; если упрёмся в число соединений — переходить на `pecl-pq` или `ext-uv`.
- **PHPUnit 9.6:** `amphp/phpunit-util` 3 (`AsyncTestCase`) поддерживает только его.
- **Миграции — свои:** SQL-файлы `migrations/NNNN_name.sql`, таблица `schema_migrations`, одна транзакция под advisory-блокировкой при старте приложения.
- **Образ PostgreSQL — `pgvector/pgvector:pg17`**, расширение `vector` включается первой миграцией.

### Решено в фазе 2

- **Три пакета:** `mercurius-llm` (модель), `mercurius-connectors` (маршруты исходящих соединений), `mercurius-messenger` (канал). Подключены сабмодулями в `packages/` и Composer-репозиториями типа `path` с копированием; ядро знает только их интерфейсы, Telegram и OpenRouter упоминаются лишь в `src/Infrastructure` (настройки и модули подключения).
- **Участник — запись `principals`** (вид `human` или `agent`, роль `owner`, `admin` или `user`; владелец — только человек и только один). Учётная запись канала связана с участником через `channel_identities`. Владелец создаётся при первом сообщении с `TELEGRAM_ADMIN_ID`; остальным — отказ без вызова модели; регистрация других участников — позже.
- **Диалог:** один открытый диалог на чат, `/new` закрывает его; модели уходит системный промпт и последние `LLM_HISTORY_LIMIT` сообщений (по умолчанию 40).
- **Поток ответа:** заглушка «…», затем правки одного сообщения не чаще раза в 1,5 с, итог правкой; длинный итог — продолжениями. Во время потока текст усекается, а не делится, иначе продолжения множились бы на каждой правке.
- **Разметка:** ответ модели передаётся каналу как `ParseMode::Markdown`; Telegram получает его в HTML (`MarkdownToTelegramHtml`, сверено с адаптером hermes), при отказе разметки — текст без маркеров. Служебные тексты — без разметки.
- **Учёт расхода — таблица `llm_calls`:** назначение, модель, причина завершения или вид ошибки, токены по корзинам (вход без кеша, выход, чтение и запись кеша, рассуждения), стоимость от OpenRouter, длительность.
- **Модель по умолчанию — `z-ai/glm-5.3-flash`** с уровнем рассуждений `low`; меняется через `LLM_MODEL` и `LLM_REASONING_EFFORT`. Запросы к OpenRouter идут через VLESS при заданном `VLESS_URI`; повторы — `RetryingClient`, поток после первого события не повторяется.
- **Telegram:** вебхук при заданном `APP_URL`, иначе long polling. При регистрации вебхука накопившиеся обновления не сбрасываются (`drop_pending_updates=false`), Telegram доставит их после запуска.
- **Проверка бота** после развёртывания — через Telegram Web из Chrome владельца (см. `CLAUDE.md`).

### Решено в фазе 3 (часть 1)

Устройство — в [«Агентский цикл и харнесс»](#агентский-цикл-и-харнесс); здесь — что уточнилось при реализации
и проверке на сервере 2026-11-16.

- **Код:** `AgentLoop` (цикл), `RunScheduler` (один запуск на диалог, дописки, `/stop`, продолжение после
  перезапуска), `ChannelRunObserver` (статус-сообщение), `ToolRegistry`/`ToolCallValidator`/`ToolExecutor`,
  `LoopGuard`, `PolicyService`; таблицы `runs`, `tool_calls`, `run_inbox`, `principal_policies` (миграция `0003`).
- **Первые инструменты ядра:** `http_request` (только `GET`/`HEAD`; остальные методы — с подтверждениями) и
  `set_participant_policy` (только в запусках владельца). Файлы и команды — в песочнице, следующей части.
- **Защита от запросов во внутреннюю сеть — в два слоя:** `AddressGuard` проверяет каждый адрес и каждый
  перенаправленный, а HTTP-клиент инструментов подключается только к проверенному IP (`GuardedConnector`), так что
  подмена DNS между проверкой и соединением не помогает.
- **Закрытие задачи в истории:** остановленный, упавший или прерванный ошибкой запуск сохраняет итоговое сообщение
  ассистента. Без него модель видела в истории вопрос без ответа и бралась за остановленную задачу снова (найдено
  при проверке на сервере).
- **Сообщение сразу после `/stop`** не попадает в останавливаемый запуск, а начинает следующий.
- **Упавший запуск** закрывается как `failed` с причиной «внутренняя ошибка», владелец получает сообщение; ошибка,
  вылетевшая из волокна, пишется в журнал и не останавливает процесс.
- **Нулевые байты** в результатах инструментов заменяются: поле `text` PostgreSQL их не принимает.
- **Отложено (мелкое):** после перезапуска старое статус-сообщение остаётся с текстом «Выполняю …», итог приходит
  новым; маркеры `**` вокруг ссылок внутри жирного текста (конвертер Markdown пакета `messenger`); итоговый вызов
  после лимита не резервирует бюджет; срок запуска не прерывает идущий вызов модели.


### Решено в фазе 3 (часть 2)

Песочница — [«Песочница»](#песочница); проверено на сервере 2026-11-16.

- **Код:** исполнитель `OpenCCK\Sandbox` (`sandbox.php`, сервис `sandbox`), клиент `HttpSandboxClient`, инструменты
  `read_file`, `list_files`, `write_file`, `run_command`, выгрузка больших результатов в `ToolExecutor`.
- **Команда участника:** `prlimit` (процессы, процессорное время, адресное пространство, размер файла) →
  `setpriv` (uid участника, без групп) → `env -i` → `setsid` → `bash`, которая уже от участника переходит в `cwd`
  и ставит `umask 077`. Переход в каталог от root позволял через символическую ссылку попасть в чужой каталог —
  найдено ревью, закрыто.
- **Фоновые процессы команды убиваются, когда она заканчивается** (вся её сессия), ожидание вывода ограничено.
  Долгоживущих серверов в песочнице пока нет — состояние живёт в файлах.
- **PID 1 — `tini` (`init: true`):** без него убитые процессы оставались зомби и съедали лимит процессов участника
  (найдено на сервере).
- **Лимиты по умолчанию:** процессов на участника 128 (заметно меньше 512 контейнера), адресное пространство 8 ГБ,
  процессорное время 600 с, 4 одновременные команды, файл не больше лимита каталога (`--fsize`).
- **Исполнитель** отвергает подключения с loopback (это команды участников, они в той же сети), не больше 16
  соединений с адреса. Права контейнера: `cap_drop: ALL` плюс `SETUID`, `SETGID`, `CHOWN`, `DAC_OVERRIDE`,
  `FOWNER`, `KILL`.
- **Среды выполнения:** PHP 8.2 с Composer, Python 3, Node.js с npm, Go — работают от участника с лимитом 8 ГБ.
- **Отличие от проекта:** вывод команды исполнитель сокращает до 25 КБ начала и 25 КБ конца, поэтому выгрузка в
  файл срабатывает в основном для HTTP и других инструментов; полный вывод команды модель получает, перенаправив
  его в файл сама (`… > out.txt`). Общий бюджет результатов на ход — в части 5.
- **Сеть песочницы до хоста не закрывается** (решение владельца 2026-11-16): порты самого сервера через шлюз сети
  `sandbox` доступны, и это нужно. Закрыты по-прежнему `docker.sock`, SSH на свою машину и сети `internal` (база) и
  `web`.
- **Отложено (мелкое):** `/proc` без `hidepid` — участники видят командные строки друг друга; `wc -l` не считает
  последнюю строку без перевода; сбой `du` читается как пустой каталог; `app` виден из сети песочницы.

### Решено в фазе 3 (часть 3)

Подтверждения, сохранённые разрешения, посетители — [«Подтверждения и запреты»](#подтверждения-и-запреты),
[«Участники»](#участники-люди-и-агенты); проверено на сервере 2026-11-16.

- **Код:** `ApprovalService` (карточка, решение, истечение, `/permissions`), `CallbackRouter` (нажатия только от

- **Карточки** приходят владельцу в личный чат; действие длиннее 3000 знаков — файлом перед карточкой.
- **Порядок записи:** запуск и вызов помечаются ожидающими до отправки карточки — нажатие, пришедшее сразу,
  находит запуск ждущим. Из ожидания запуск выводит только атомарный переход статуса: нажатие, текст, `/stop` и
  перезапуск не могут сработать дважды, поздний ответ не оживляет остановленный запуск. На старте запуск, решение по
  которому успели сохранить до остановки сервера, продолжается. Просроченную карточку нажатием не открыть.
- **Ключ разрешения** выдаётся только одной простой команде с одним внешним действием. Цепочки (`&&`, `;`, `|`,
  фоновое `&`), обёртки (`timeout`, `xargs`, `find -exec` и др.), подоболочки и группы, префиксы переменных и `env`
  спрашиваются каждый раз — иначе разрешение на одно действие покрыло бы второе, а локальный шаг мог бы изменить,
  куда уходит первое (найдено ревью). `git push` получает ключ только с адресом (хост и репозиторий): имя удалённого
  репозитория (`origin`) и опции `git` перед `push` локальной записью перенаправляются куда угодно, поэтому
  спрашиваются всегда.
- **Секреты** маскируются в разобранных аргументах (поля заголовков и тела по имени), в JSON-тексте, в учётных данных
  URL и значениях запроса, в подписи карточки и в статусе выполняемого инструмента.
- **Посетитель:** незнакомец в личном чате — посетитель в ожидании, владельцу одна карточка с первым сообщением;
  модель до решения не вызывается; «Разговор» — роль посетителя без инструментов; о допуске посетитель получает
  сообщение. В группах незнакомцы по-прежнему получают отказ (группы — фаза 10). Отличие от hermes: там незнакомца
  пускают по одноразовому коду в CLI сервера (`gateway/pairing.py`), у нас — кнопкой в чате владельца.
- **Проверено в Telegram:** отказ, «Разрешать всегда» и повтор без вопроса, `/permissions` и отзыв, перезапуск
  контейнера во время ожидания, текст во время ожидания, молчание (с `AGENT_APPROVAL_TIMEOUT=60`). Посетитель —
  только тестами: второго аккаунта для проверки нет.
- **Отложено (мелкое):** сообщение «Жду подтверждения владельца…» не правится после решения; список
  `/permissions` не обновляется после отзыва; нет предела числа ожидающих карточек посетителей (у hermes — 3 на

  git-настройкам песочницы (`url.*.insteadOf`, заданный раньше, может перенаправить push) — закроет политика команд в
  фазе 7.

## Трассировка и метрики

Проект фазы 4 (Claude, 2026-11-16; два значения по умолчанию названы владельцу и меняются настройкой). Цель — любой
запуск разбирается по шагам: что делал агент, сколько стоило, где терял время. Опора — span на каждый шаг
([backendbytes](notes/backendbytes-multi-agent-orchestrator-backend.md), `runTraced`), четыре корзины токенов и
стоимость со статусом точности (hermes `usage_pricing.py`, [конспект](notes/hermes-agent.md#учёт-токенов-и-стоимости)).

**Не цели:** OpenTelemetry и внешние трассировщики (свой формат в PostgreSQL проще и не требует ещё одного сервиса;
экспорт в OTel — позже, если понадобится); графики (их строит Prometheus/Grafana владельца).

- **Шаги** (`trace_spans`): запуск → вызов модели, инструмент, подтверждение, сжатие, классификация; позже — воркер.
  У шага: родитель, вид, имя, начало, длительность, статус (`ok`, `error`, `cancelled`), токены по корзинам (вход,
  выход, чтение и запись кеша, рассуждение), стоимость и её статус (`actual` — от провайдера, `estimated` — по ценам
  каталога, `unknown`), ошибка, атрибуты. Шаг пишется, когда закончился; шаг запуска — при старте и при завершении.
- **Полные промпты и ответы** (`trace_payloads`) хранятся отдельно от шагов, секреты маскируются (`SecretMasker`) до
  записи. Срок хранения — `TRACE_RETENTION_DAYS` (по умолчанию 14: диск сервера занят на 90%); очистка раз в сутки.
  Шаги и учёт расхода не удаляются.
- **Запись** — по [событиям](#устройство-приложения-на-opencck): цикл и вспомогательные вызовы сообщают о шагах через
  интерфейс событий агента, `Tracer` — его подписчик (в коде цикла нет записи трасс). Ошибка записи трассы никогда не
  ломает запуск: она уходит в журнал. `llm_calls` остаётся книгой расхода по вызовам модели и получает `run_id`.
- **Стоимость:** если провайдер не прислал её, считается по ценам каталога (`ModelInfo::estimateCost`) со статусом
  `estimated`.
- **Команды владельцу** (только владелец): `/usage [дни]` — расход по моделям, по дням, итог и самые дорогие запуски;
  `/runs` — последние 10 запусков (статус, ходы, токены, стоимость, время); `/trace <id>` — цепочка шагов запуска с
  длительностью, токенами и стоимостью; длинный разбор — файлом.
- **Prometheus:** `GET /metrics` в текстовом формате; закрыт токеном `METRICS_TOKEN` (заголовок `Authorization:
  Bearer`), без токена адрес выключен — домен публичный и весь виден через NPM. Метрики: запуски по статусу и
  причине остановки, токены и стоимость по модели и корзине, вызовы инструментов по имени и статусу, длительность
  шагов по виду (гистограмма), подтверждения по исходу, сжатия. Счётчики собираются из БД при запросе, а не в памяти
  процесса, — переживают перезапуск.
- **Сводки для доработки агента** ([границы самоулучшения](#границы-самоулучшения)): медленные и дорогие шаги видны в
  `/usage` и в `/trace`; выборки для анализа — из тех же таблиц.

## Оркестратор и воркеры

Проект фазы 5 (Claude, 2026-11-16). Цель — агент сам делит задачу и отдаёт части воркерам на моделях, подобранных под
каждую часть ([решение владельца](#декомпозиция-и-экономия)), а гарантии дают код и лимиты, а не промпт.
Образец — `delegate_task` hermes ([конспект, раздел 8](notes/hermes-agent.md#8-делегирование-и-субагенты)); выводы
базы знаний 1, 4–7, 10, 11, 13 ([ключевые выводы](#ключевые-выводы)).

**Не цели:** глубина больше одного уровня (воркер не делегирует), удалённые агенты (фаза 13), параллельная запись.

**Фаза идёт частями:** 1) синхронное делегирование — инструмент, воркер как вложенный запуск, общий бюджет,
параллельное чтение, отчёт; 2) профиль задачи и полный выбор модели с каскадом; 3) фоновое делегирование, переживающее
перезапуск; 4) проверяющий воркер и критерии «когда делить» по трассам.

### Часть 1 — синхронное делегирование

- **Инструмент `delegate_task`** (класс «запись»: тратит бюджет): массив `tasks` (1–5), у задачи — `goal` (конкретно и
  самодостаточно), `context` (воркер не видит беседы — общий фон повторяется в каждой задаче), `output` (какой нужен
  ответ), `tools` (имена из доступных оркестратору), `role` (`cheap` / `main` / `strong`, по умолчанию `main`).
- **Воркер — вложенный запуск** (`runs.parent_run_id`) в **своём диалоге** (канал `worker`): история родителя ему не
  передаётся, его шаги не попадают в историю родителя. Системный промпт короткий и одинаковый для всех воркеров
  (общий кеш); цель и контекст — в первом сообщении, как у hermes.
- **Инструменты воркера** — пересечение запрошенных с инструментами оркестратора, без `delegate_task`,
  `set_model_role`, `set_participant_policy`. Спросить владельца воркер не может: необратимое действие ему отказано, и по сохранённому разрешению тоже
  (как при отсутствии канала подтверждения).
- **Бюджет общий и атомарный:** перед стартом воркеров оркестратор резервирует их бюджет из своего (`runs.reserve`);
  каждому воркеру — равная доля резерва, не больше `AGENT_WORKER_TOKEN_BUDGET`; после — фактический расход списывается,
  остаток возвращается. Ходов воркеру — `AGENT_WORKER_MAX_TURNS` (по умолчанию 15), время — в пределах оставшегося у
  оркестратора.
- **Параллельно — только чтение:** задачи, чьи инструменты все класса «чтение», идут параллельно (до 3); остальные —
  по одной, по порядку.
- **Отчёт:** на каждую задачу — статус (`done` / `failed` / `limit` / `stopped`), модель, ходы, токены, стоимость и итог
  воркера, урезанный до `min(4000, свободное место оркестратора ÷ число задач)` символов; полный итог остаётся в
  диалоге воркера (номер запуска в отчёте, разбор — `/trace`). Сбой воркера — значение в отчёте, а не ошибка
  оркестратора.
- **`/stop` и перезапуск:** отмена оркестратора отменяет его воркеров. После перезапуска воркеры не продолжаются
  (их запуски закрываются как прерванные), а вызов `delegate_task` у оркестратора получает «прервано перезапуском» —
  как любая запись; фоновое продолжение — часть 3.
- **Трассы:** у воркера своя трасса; в отчёте и в атрибутах шага `delegate_task` — номера запусков воркеров.

### Часть 2 — профиль задачи, выбор модели, каскад

- **Профиль задачи** даёт оркестратор в `delegate_task` вместо роли (поле `profile`): оценки 1–10 по осям из
  [профиля задачи](#профиль-задачи); неуказанная или нечисловая ось — 1 (`7`, `7.0` и `"7"` равны). Короткие и
  типовые части профиля не получают — у них роль. Профиль, где выше 1 только цена ошибки и срочность, ничего не
  требует от модели — тоже решает роль.
- **Профиль модели** — из каталога: индексы Artificial Analysis из ответа `/models` OpenRouter (`intelligence`, `coding`,
  `agentic`; на 2026-11-16 они есть у 209 из 469 моделей), цены, контекст, модальности, вызов инструментов. Оси текста,
  рассуждения, математики и академических знаний меряются индексом интеллекта, код — индексом кода, агентность —
  индексом агентности. Задержки в каталоге нет: срочность пока решает только при равенстве, по цене.
- **Оценка → требование:** оценка `s` по оси требует индекс не ниже `s × 10`-го процентиля этого индекса среди моделей,
  прошедших жёсткие требования (оценка 7 — не хуже 70% из них; так высшая оценка достижима). Требования ставятся по
  всем осям, неуказанная — как 1. Цена ошибки выше 5 поднимает все оценки на `(цена − 5) ÷ 2` балла (не выше 10) —
  это «запас, который растёт с ценой ошибки». Если по оси с оценкой выше 3 индекса в каталоге нет ни у одной модели —
  роль `strong`, а не самая дешёвая наугад.
- **Жёсткие требования:** вызов инструментов (если у части есть инструменты), изображения при оценке ≥ 5, звук при
  оценке ≥ 5, контекст: оценка объёма `s` требует окна не меньше `2^(s+12)` токенов (5 — 128 тыс., 8 — 1 млн);
  обычная запись каталога (варианты `:batch` работают только через Batch API, `:free` — со своими лимитами); цена
  выше нуля (промо-записи не берём) и не выше цены модели роли `strong` — профиль, написанный
  моделью, не может купить модель дороже самой сильной, выбранной владельцем (та же защита, что при смене ролей).
- **Выбор:** из подходящих — самая дешёвая по средней цене `(3 × вход + выход) ÷ 4`; у моделей без индексов есть шанс,
  только если все оценки осей ≤ 3. Подходящих нет — роль `strong` с пометкой в журнале. Каждое решение — в
  `routing_decisions` (способ `profile`, при откате — `fallback` с ролью `strong`) с беседой оркестратора,
  требованиями и причиной. Ошибка каталога при выборе не роняет делегирование: часть получает модель роли.
- **Каскад:** если воркер не справился по вине модели (модель отказала, неверные вызовы, обрыв ответа, зацикливание) —
  один повтор на более сильной модели: те же требования, поднятые на 2 балла, или роль `strong`; в пределах остатка
  доли воркера и остатка времени (повтор получает время за вычетом первой попытки; меньше 60 с — повтора нет). В
  отчёте — «каскад: модель A, запуск #N (причина) → модель B». Остановка владельцем, лимиты и внутренние ошибки
  (база, инструменты) каскада не вызывают: сильная модель их не исправит.
- **Каталог после миграции:** индексы появляются при следующей загрузке каталога; миграция 0009 помечает каталог
  без индексов устаревшим, чтобы он перезагрузился при старте, а не через сутки.
- **Свои данные из трасс** (успех, расход и время по моделям) в выбор войдут в части 4.

### Часть 3 — фоновое делегирование

Проект — Claude, 2026-11-16, по поручению владельца довести фазу 5 до конца. Образец — фоновый путь hermes
([конспект](notes/hermes-agent.md#синхронно-или-в-фоне)); главное отличие — **исполняющийся** воркер переживает
перезапуск (у hermes фон процесс-локален, восстанавливаются только недоставленные результаты).

- **Кто решает:** оркестратор, полем `background: true` у `delegate_task`, — для долгих частей, ответ на которые не
  нужен в этом же ходе. Без поля — синхронно, как в части 1. Воркер делегировать не может, так что фон только у
  запуска верхнего уровня.
- **Сразу ответ:** инструмент возвращает «фоновое делегирование #N начато» и номера задач; ход оркестратора идёт
  дальше и обычно заканчивается. Владелец получает ответ оркестратора, а результат придёт позже.
- **Состояние в базе:** `delegations` (беседа, запуск-оркестратор, участник, вызов, резерв бюджета, статус `running` /
  `done` / `stopped`, отчёт, время доставки) и `delegation_tasks` (задача с уже урезанными инструментами, её доля,
  запуски первой попытки и повтора, отчёт по задаче). По `delegation_tasks` планировщик узнаёт фоновых воркеров при
  старте и не закрывает их.
- **Бюджет:** резервируется у запуска-оркестратора при старте, как в части 1, и списывается по факту, когда
  делегирование закончено (запуск-оркестратор к тому времени может быть закрыт — расход всё равно попадает в его
  счёт и в `/usage`; списывается расход запусков воркеров, а не то, что успели записать отчёты). Время части — лимит
  времени запуска участника, но не дальше срока всего делегирования: два лимита времени запуска от старта (по
  умолчанию 30 мин); после срока неначатые части не начинаются («не начат: истёк срок»).
- **Доставка:** когда все задачи закончены, отчёт (тот же формат, что у синхронного, помеченный как недоверенные
  данные) становится первым сообщением **нового запуска** в беседе оркестратора — когда беседа освободится. Не
  дописка к идущему запуску: дописку теряет `/stop`, а в группе идущий запуск может быть чужим, и отчёт с данными
  владельца попал бы к гостю. Доставленным отчёт считается, только когда запуск с ним сохранён (номер запуска — в
  `delegations.delivered_run_id`); недоставленное после перезапуска доставляется.
- **Перезапуск:** незаконченные фоновые делегирования продолжаются: запуск воркера в статусе `running` продолжается
  с места остановки (запись и необратимое, прерванные посреди вызова, не повторяются — как у обычного запуска),
  неначатые задачи начинаются, законченные берутся из базы. Воркеры синхронного делегирования по-прежнему
  закрываются.
- **Лимиты:** не больше 3 фоновых делегирований **у участника** одновременно, по всем беседам, — сверх лимита отказ,
  не очередь (как у hermes). Задач, параллельности, долей и каскада — как в частях 1–2.
- **Без цепочек:** запуск, начатый отчётом, фоновое делегирование не начинает (синхронное — может). Иначе текст
  отчёта, прочитанный воркером на чужой странице, мог бы держать агента занятым без владельца.
- **`/stop`** останавливает и фоновые делегирования беседы: воркеры останавливаются, расход списывается, отчёт не
  доставляется. Просьба остановиться пишется в базу (`stop_requested`): если сервер выключился раньше, чем
  делегирование закрылось, после старта оно закрывается, а не продолжается. Выключение сервера без `/stop` фон не
  останавливает — он продолжится после старта.
- **Сбой:** делегирование, которое не может продолжаться (ошибка базы и т. п.), закрывается с пометкой и тем, что
  успели части, и отчёт доставляется — оно не занимает место в лимите навсегда. Имя диалога воркера содержит номер
  делегирования: провайдер может повторять идентификаторы вызовов.

### Часть 4 — проверяющий и данные трасс

- **Проверяющий воркер:** для части с полем `verify: true` или ценой ошибки ≥ 8 после ответа воркера запускается
  проверяющий с чистым контекстом: ему даются цель, требование к ответу и ответ воркера (как недоверенные данные),
  инструменты — те же, что у части, только на чтение. Модель — по профилю части, поднятому на 2 балла (или роль
  `strong`), из остатка доли части; не хватает (меньше 8 тыс. токенов) — «не проверено: не хватило бюджета».
  Проверяющий отвечает строкой `ВЕРДИКТ: принято` или `ВЕРДИКТ: отклонено` и причинами; вердикт и причины — в отчёте
  по части. Переделку решает оркестратор (может поручить часть заново): автоматический повтор удвоил бы расход.
- **Свои данные в выборе модели:** по запускам воркеров за 14 дней считается доля отказов модели (модель отказала,
  неверные вызовы, обрыв ответа, зацикливание). Модель с не меньше чем 3 запусками и долей отказов ≥ 50% выбором по
  профилю не берётся, пока статистика не исправится; причина — в решении о выборе.
- **Отчёт `/delegation`** (владелец, личный чат): за 14 дней — запусков с делегированием и без, воркеров по статусам,
  каскадов, вердиктов проверяющих, по моделям воркеров — запусков, доля успеха, токены, стоимость, среднее время.
  Так видно, делит ли агент задачи по критериям и окупается ли выбор по профилю.
- **Замер «профиль против сильной модели»:** набор задач с проверяемыми ответами (счёт, извлечение фактов из текста,
  небольшая функция, перевод с ключевыми терминами) агент прогоняет через `delegate_task` дважды — части с профилями
  и те же части на роли `strong`; доля верных ответов сверяется с ключом, токены и стоимость берутся из трасс
  (`/trace`, `/delegation`). Набор небольшой: прогон платный.

### Всегда в контексте

- Два раздела с жёстким лимитом в символах (не в токенах — не зависит от модели): **профиль владельца** и **рабочая сводка**. Ориентир hermes — 1375 и 2200 символов; у нас начнём с 2000 и 4000 и подберём по трассам расхода.
- Переполнение — ошибка с подсказкой «сожми или вынеси в факты», а не молчаливая обрезка.
- Снимок фиксируется на сессию ради кеша промпта. В бесконечном Telegram-чате сессия режется по простою и по сжатию контекста; изменения слоя становятся видны со следующего снимка. Свежедобавленное до этого остаётся доступно через слой 2.
- Пишется декларативно («владелец предпочитает…»), а не приказами себе; только подтверждённое словами владельца или результатом инструмента; разовая просьба не становится предпочтением.
- Правила поведения в этот слой не попадают — это слой 0. Сведения о конкретном проекте — в слоях 2–4.

### Проекты, задачи и отношение участника к проекту

Добавлено по требованию владельца 2026-11-16: проект, задача проекта и отношение к проекту — три отдельных слоя
памяти. Отношение хранится для любого участника — владельца, другого человека или агента.

- **Это доменные сущности, а не записи в свободной форме.** У проекта и задачи есть схема в БД (DDD-сущности opencck), их же использует планировщик (фаза 10). Память не хранит вторую копию: слой 2 и слой 3 — это сами проекты и задачи.
- **Активный проект** определяется из разговора (упоминание, чат, привязанный к проекту) или командой владельца. Пока он активен, в контекст идут его карточка, отношение владельца к нему и список открытых задач — в пределах отдельного бюджета символов. Смена активного проекта — граница снимка, как у слоя 1.
- **Задача** хранит дерево подзадач, профиль задачи (оценки по осям), выбранные модели, расход, время и итог. Это и журнал работы, и сырьё для обучения выбора моделей.
- **Отношение участника к проекту** — отдельная запись на пару «участник × проект», а не поле карточки: у владельца, других людей и агентов своё отношение к одному проекту. Пишется декларативно и только по словам или реакциям этого участника; выводы агента помечаются как выводы.
- **Связь с фактами:** факт может быть привязан к проекту; гейт релевантности поднимает факты активного проекта, но не прячет общие.
- **Консолидация** обновляет карточки проектов и отношение владельца только предложениями; закрывает зависшие задачи — только с отчётом владельцу.

### Факты

- Схема по образцу holographic, перенесённая на PostgreSQL: `facts` — проекция текущих версий; `fact_versions` — история с `valid_from`/`valid_to` и происхождением; сущности, алиасы, связи; подтверждения; надгробия забытого (отпечатки HMAC, без текста).
- **Область видимости** — колонка во всех запросах (владелец, чат, проект). IDF и гейт релевантности считаются внутри области.
- **Категория записи:** знание или правило. Правила живут в слое 0, факты с категорией «правило» фоновым задачам менять запрещено кодом.
- **Происхождение и доверие:** сказано владельцем или подтверждено им — выше, выведено агентом — ниже и с пометкой; полезность и подтверждения сдвигают доверие; оценки не делают факт моложе.
- **Поиск:** кандидаты из полнотекстового поиска по ключам слов, однокоренным и ключевым словам; оценка — взвешенная сумма лексического совпадения, пересечения слов и HRR, умноженная на доверие и свежесть; затем гейт релевантности (покрытие информативных слов сообщения, болтовня не вспоминает ничего), окно неповтора, бюджет токенов (строка выбрасывается целиком, а не режется).
- **Проверка содержимого** на записи и на выходе: инструкции, разметка ролей, секреты, невидимые символы.

### HRR с самого начала

- Каждый факт кодируется вектором фаз размерности 1024 (как в holographic): векторы слов детерминированно выводятся из хешей и не хранятся, хранится только вектор факта.
- Операции связывания и объединения — сложение фаз и сумма косинусов и синусов; на PHP это простая арифметика, но кодирование и сравнение по всему хранилищу идут в воркере `amphp/parallel`, а не в цикле событий.
- Хранение: `(cos, sin)` вектора как `vector(2048)` в `pgvector` — тогда сходство считается одним запросом к базе. Тождество скалярного произведения и косинуса фаз выведено при изучении и должно быть подтверждено тестом против эталонной реализации.
- Применение: слагаемое оценки поиска и отдельные запросы «что связано с сущностью X». Точные запросы по сущностям идут через индекс сущностей, как у holographic после версии 0.2.
- Вклад HRR измеряется на русском наборе вопросов с первых итераций; вес слагаемого настраивается, а не зашит.

### Анализ текста

Главный носитель качества поиска — не векторы, а разбор слов. Для русского и английского нужны стеммер Snowball на PHP,
стоп-слова, распознавание идентификаторов (`pve-01`, IP, пути), словарь однокоренных (у holographic — DerivBase.Ru) и
таблица заимствований. Совместимость словаря однокоренных с PHP-стеммером — [открытый вопрос](#открытые-вопросы).

### Консолидация (dreaming)

- Фоновая задача раз в ночь; нет работы — модель не запускается.
- Отбор, оценки, пороги, дедупликация, поиск противоречий и паузы — чистая функция в коде; модель только формулирует записи в пределах ночного бюджета; спорное уходит владельцу предложением с номером.
- Долговременной памяти заслуживает то, что владелец повторял в разные дни; машинный текст (расписание, воркеры, вывод инструментов) и выводы агента подтверждением не считаются.
- Консолидатору не дают сеть и оболочку; у него нет права менять слой 0 и записи категории «правило».
- Отката записей в dreaming нет; у нас его заменяют история версий фактов и страж потерь (снимок и оповещение при резком сокращении памяти).

Сделано и проверено на сервере 2026-11-16 (миграция 16, `src/Memory`).

- **Области:** `owner`, `principal:<id>`, `chat:<канал>:<чат>`. Владелец в личном чате читает `owner` и свой чат,
  другой участник — свою область и чат, группа — только свой чат, даже когда пишет владелец. Вид чата берётся из
  последнего сообщения беседы; неизвестный вид (после перезапуска, до нового сообщения) считается группой.
- **Поиск** (`Recall`, образец — `relevant` holographic): ключи — стемы Snowball и идентификаторы; вес ключа — IDF
  внутри читаемых областей, слово, которого нет ни в одном факте, считается с наименьшим весом; порог покрытия 0,34;
  совпавший идентификатор решает сам; одно общее слово длинного сообщения, которое есть и в других фактах, факт не
  выбирает. Оценка — покрытие × доверие × свежесть (полураспад 180 дней). Бюджет 1500 символов целыми строками
  `[#номер] текст`; факт, поданный в беседе среди последних 20, не повторяется.
- **Идентификатор** — буквы вместе с цифрами (`pve-01`, `gpt5`) или части через точку, косую черту, подчёркивание
  (`10.0.0.1`, `/etc/hosts`). Голое число и слово через дефис — обычные слова: иначе «через 10 минут» тянул всё с «10».
- **Подача:** найденное дописывается после текста пользователя в обёртке недоверенных данных и остаётся в
  транскрипте — следующий ход повторяет те же байты (образец — `compose_user_api_content` hermes). Слой 1 (профиль и
  сводка) — в системном промпте при открытии диалога, только владельцу в личном чате. Отчёт фоновой задачи в
  поиск не идёт. Сбой памяти пишется в журнал, запуск идёт без неё.
- **Изменения — только через владельца:** `memory_propose` (добавить, изменить, завершить, забыть, заменить профиль
  или сводку) шлёт карточку «Принять»/«Отклонить» (`mp:<id>:a|r`); на ней — кто предложил, где будет видно, было и
  станет, причина с пометкой «слова агента». Принятое применяется один раз с новой версией; не применившееся
  возвращается в ожидание. Не больше 5 карточек за запуск. Слой 1 — до 2000 (профиль) и 4000 (сводка) символов и
  только из личного чата владельца.
- **Проверка содержимого** (`ContentScreen`, образец — `_fact_problem` holographic): указания ассистенту (русский и
  английский), разметка ролей и вызовов, JSON, секреты (та же проверка, что у инструментов), невидимые символы,
  изображения, длинные закодированные строки; фраза в кавычках остаётся фактом.
- **Забывание:** `/forget <номер>` или принятое предложение удаляет факт, его версии и предложения о нём, меняет
  карточки на «забыт», заменяет строки факта в сохранённых диалогах на «(забыто)»; остаётся HMAC-отпечаток текста
  (ключ `MEMORY_SECRET`, без него — из токена бота), и тот же текст больше не записывается, в том числе принятием
  ожидавшего предложения.
- **Воркеры памяти не получают** — ни поиска, ни предложений: своей аудитории у воркера нет, узнанное он отдаёт
  оркестратору отчётом. Это строже пункта роадмапа «память воркера — по месту оркестратора»; вернуться к нему, если
  воркерам понадобится чтение.
- **Отложено:** вид чата хранить в беседе (переживёт перезапуск); окно неповтора считать по ходам, а не по фактам;
  `/memory` показывает только память владельца и этого чата; указание в кавычках проходит проверку (при подаче факт
  всё равно помечен как данные); квитанция извлечения в трассе; таймаут и размыкатель извлечения.

#### Решено в фазе 6 (часть 3)

Сделано 2026-11-17 (миграции 18 и 19).

- **HRR** (`Hrr`, образец — `holographic.py`): атомы из SHA-256, связывание, объединение и сходство как у
  holographic, сверено тестом с его числами. Текст факта — наши ключи (стемы и идентификаторы), а не слова как есть:
  так формы слова встречаются; сущности — идентификаторы среди ключей. Вектор хранится фазором (1024 косинуса, затем
  1024 синуса) в `facts.hrr vector(2048)`: сходство — одно скалярное произведение в PostgreSQL, и перебора векторов в
  PHP нет. Вектор пишется вместе с ключами; старые факты получают его при старте.
- **Отступление от проекта:** кодирование идёт в цикле событий, а не в воркере `amphp/parallel` — около 9 мс на факт
  под xdebug, запрос — меньше; сравнение по всему хранилищу делает база.
- **В поиске** HRR — доля оценки фактов, уже прошедших гейт по словам (`MEMORY_HRR_WEIGHT`, по умолчанию 0,3); факт
  через гейт он не пропускает. `memory_search` с `related` — что связано с именем или словом: лучшее из проб «как
  сущность» и «как слово содержания», порог шума 0,2 (замер holographic при размерности 1024).
- **Замер** на русском наборе (`test/Fixtures/memory-recall-ru.json`, 40 фактов, 34 вопроса; тест держит пол):

  | Вариант | recall@5 | MRR |
  |---------|----------|-----|
  | только слова, до разбора слов через дефис | 0,853 | — |
  | только слова | 0,912 | 0,858 |
  | слова и HRR 0,3 | 0,912 | 0,877 |

  HRR не меняет, что попадает в первую пятёрку (кандидатов дают слова), но ставит нужный факт выше. Слово через дефис
  теперь ещё и его части («vpn-сервер» — это «vpn» и «сервер»). Оставшиеся промахи — однокоренные слова
  («монитор» / «мониторинг», «пишем» / «пишется»): это словарь однокоренных из [открытых вопросов](#открытые-вопросы).
- **Ночная проверка** (`Consolidation`, образец — `dream.py` hermes-dreaming): только код, модель не вызывается
  ни разу. Раз в ночь в `MEMORY_CHECK_HOUR` (UTC, по умолчанию 3) и по команде владельца `/consolidate`. Память не
  менялась — проход записан как пропущенный, больше ничего. Почти копии (те же числа, совпадение ключей по Жаккару
  от 0,8) — карточка «забыть» на более слабый, одна пара за ночь, пара молчит 180 дней. Факты об одном с разными
  числами и старые неиспользованные факты с низким доверием — списком владельцу, каждое молчит 14 дней. Пропало
  больше 25 % фактов или символов с прошлого прохода (от 4 фактов или 400 символов) — предупреждение. Сама проверка
  ничего не меняет и не забывает. Журнал — `memory_consolidations` (снимок, время, вызовы модели — всегда 0);
  показанное — `memory_notices`. Трассы привязаны к запускам агента, поэтому проход виден в своём журнале и в логе.
- **Отложено:** повышение того, что владелец повторял в разные дни, и формулировки модели (нужна модель-судья —
  [открытый вопрос](#открытые-вопросы)); перевод ключей старых фактов на разбор через дефис (в базе один факт).
- **Время извлечения:** русский набор на PostgreSQL сервера — p95 2,4 мс, медиана 0,9 мс на 102 вызова (тест держит
  p95 до 250 мс). Забывание вычищает строку факта и из полных промптов в трассах (`redactPayloads`).

### Выбор

1. Жёсткие требования отсекают неподходящие модели.
2. Из оставшихся выбирается самая дешёвая модель, чьи способности по каждой оси не ниже требуемых с запасом, который растёт с ценой ошибки.
3. При равенстве решает срочность: при высокой — задержка и скорость генерации, при низкой — цена.
4. Если результат не прошёл проверку или модель отказала — эскалация на более сильную модель (каскад), с записью в трассу.

### Декомпозиция и экономия

- **Решение владельца 2026-11-16:** сильная модель остаётся в таблице ролей; в работе агента бывают разные задачи, и агент
  сам делит задачу так, чтобы её части решали разные модели ради экономии и качества. Модель диалога, выбранная при
  его открытии ([фаза 3, часть 5](#решено-в-фазе-3-часть-5)), — это модель оркестратора; части задачи уходят воркерам
  с моделью, подобранной под каждую часть (фаза 5).
- Оркестратор — модель диалога (по классу запроса, обычно роль `main`; по устройству это supervisor: перепланирует каждый ход и читает каждый отчёт) — планирует, разбивает задачу и оценивает подзадачи; воркеры на подобранных моделях исполняют. Так в замере cookbooks 84–98% входных токенов шли по ставке дешёвой модели ([вывод 11](#ключевые-выводы)).
- Оценивание само стоит денег: короткие и типовые запросы идут на модель по умолчанию без профиля; профиль считает дешёвая быстрая модель или оркестратор в рамках планирования; профили типовых задач кешируются.
- У дробления есть оптимум: каждый воркер несёт накладные расходы, а сжатие знаний при передаче теряет точность. Решение «делить или нет» учитывает это ([вывод 5 из cookbooks](notes/claude-cookbooks.md)).
- Модель основного диалога не меняется посреди сессии: это ломает кеш промпта ([вывод 30](#ключевые-выводы)). Модели выбираются на уровне подзадач и воркеров, а для основного диалога — только на границе сессии.
- Вспомогательные вызовы (заголовки, сжатие контекста, извлечение фактов, проверка безопасности) с самого начала идут на дешёвую модель — как вспомогательный клиент в hermes.

### Этапы

- **Фаза 3 — частичный выбор** (решение владельца 2026-11-16): таблица ролей моделей от владельца (дешёвая, основная, сильная, с изображениями и звуком); грубый класс запроса без оценок по осям; вспомогательные вызовы на дешёвой модели; журнал решений.

### Провайдеры моделей: OpenRouter и OpenAI

Проект — Claude, 2026-11-16, по [решению владельца](#продукт-и-архитектура) о втором провайдере. Провайдер модели —
приставка ссылки: `openrouter:author/slug` (голый id — тоже OpenRouter) и `openai:gpt-…`.

- **Ключи:** `OPENROUTER_API_KEY` и `OPENAI_API_KEY` — оба необязательны, но хотя бы один задан, иначе приложение не
  стартует с понятной ошибкой. Провайдер без ключа не настроен: его модели нельзя назначить на роль, выбрать по
  профилю или задать в `LLM_MODEL`.
- **Сеть:** оба клиента идут через один HTTP-клиент — через VLESS, если задан `VLESS_URI`, иначе напрямую.
- **Клиент OpenAI** — в пакете `llm`, рядом с OpenRouter: тот же протокол Chat Completions, общие транспорт, разбор
  потока и классификация ошибок. Отличия в теле запроса: `max_completion_tokens` вместо `max_tokens`, `reasoning_effort`
  строкой вместо объекта `reasoning`; с инструментами — `reasoning_effort: none` (OpenAI в Chat Completions не
  принимает инструменты при включённом рассуждении; модели, которые рассуждают всегда, идут в каталог без
  инструментов — для них нужен Responses API, отложено), без `temperature`, когда задано усилие рассуждения (модели рассуждения его не
  принимают — как у hermes, `utils.py` `model_forces_max_completion_tokens`); без заголовков атрибуции OpenRouter.
  Стоимость OpenAI не сообщает — трасса считает её по ценам каталога (пометка «оценка»).
- **Каталог OpenAI:** список моделей ключа (`GET /v1/models`) обогащается записями `openai/<id>` из открытого каталога
  OpenRouter (цены, окно, модальности, инструменты, индексы). Модели без такой записи (эмбеддинги, речь и т. п.) в
  каталог не попадают: без цены и признаков их не выбрать.
- **Роли по умолчанию** зависят от провайдеров: есть OpenRouter — прежняя таблица; только OpenAI — `cheap` и `media`
  `gpt-6-luna`, `main` `gpt-6.1-terra`, `strong` `gpt-6-sol` (`gpt-6.1-sol` всегда рассуждает и в Chat Completions не
  работает с инструментами — проверено ключом владельца 2026-11-16). Модель по умолчанию (`LLM_MODEL`, `LLM_CHEAP_MODEL`) — так же.
- **Выбор по профилю** ищет во всех настроенных провайдерах: одна и та же модель напрямую и через OpenRouter — два
  кандидата, решает цена.

### Решено: провайдер OpenAI

Проверено на сервере 2026-11-16: приложение поднялось с двумя провайдерами через VLESS, каталог OpenAI — 32 модели с
ценами (идентификаторы ролей по умолчанию `gpt-6-luna`, `gpt-6.1-terra`, `gpt-6.1-sol` в нём есть); воркер на
`openai:gpt-6-luna` ответил (запуск #63), расход записан как оценка по ценам каталога.

- **Код:** пакет `llm` — `OpenAIClient`, `OpenAICatalog`, общий `ChatCompletions`; Меркурий — `LlmSettings` с двумя
  ключами, `ModelRoles` с ролями по провайдерам, выбор по профилю во всех провайдерах, `ProviderRouter` с оценкой
  стоимости и именем модели с провайдером.
- **Найдено ревью и исправлено:** `reasoning_effort` шёл моделям без рассуждения (у OpenAI — 400) — теперь его
  получают только модели, у которых он есть в `supported_parameters` каталога, как у hermes; оценка стоимости
  записывалась как фактическая; в каталог попадали модели только для `/v1/responses` (codex, `-pro`); беседа,
  открытая с провайдером без ключа, падала на каждом запуске; неудачная первая загрузка каталога ждала сутки;
  исчерпанный баланс OpenAI повторялся как превышение частоты; при равной цене выигрывал OpenRouter с его комиссией.
- **Отложено:** модель, у которой нет ключа, по-прежнему видна в таблице ролей (`all()`), хотя используется замена
  по умолчанию.

## Агентский цикл и харнесс

Проект утверждён владельцем 2026-11-16 (фаза 3 роадмапа). Цель — агент сам доводит многошаговую задачу до конца
инструментами в границах, которые задаёт код: лимиты, подтверждения, продолжение после перезапуска. Образец — цикл
hermes-agent ([конспект](notes/hermes-agent.md#4-агентский-цикл)); отличия от него перечислены в
[ROADMAP.md → Фаза 3](ROADMAP.md#фаза-3--агентский-цикл-и-харнесс).

**Не цели:** делегирование воркерам (фаза 5), политика команд для SSH (фаза 7), трассы и метрики (фаза 4, но данные для них пишутся уже здесь).
**Анти-цели:** агент получает доступ к своему хосту; подтверждение можно обойти текстом промпта; перезапуск повторяет
уже сделанное необратимое действие.

### Подходы

- **Связь ядра с песочницей** (выбор владельца — A):
  A) исполнитель внутри песочницы — маленький HTTP-сервис на amphp во внутренней сети, с токеном;
  B) SSH в песочницу через `amphp-ssh` — зависимость от непроверенного клиента и фазы 7;
  C) Docker-прокси с `docker exec` — путь к Docker хоста, противоречит [изоляции](#изоляция-исполнения).
- **Порядок:** фаза делится на пять частей, каждая проверяется на сервере и коммитится отдельно: 1) запуск, цикл,
  реестр, сохранение, лимиты; 2) песочница и инструменты; 3) подтверждения и запреты; 4) сжатие контекста;
  5) роли моделей и каталог.

### Запуск и цикл

- **Запуск (`runs`)** — одно исполнение агента над задачей: диалог, участник, родительский запуск (для воркеров
  фазы 5), модель, набор инструментов, лимиты, расход, статус (`running`, `waiting_approval`, `done`, `failed`,
  `stopped`) и именованная причина остановки. Сообщение пользователя, пришедшее, когда активного запуска нет,
  начинает новый.
- **Один активный запуск на диалог** (решение владельца 2026-11-16 — «уточнение»): сообщение, пришедшее во время
  запуска, записывается в него и уходит модели на следующей итерации как дописка к задаче. Запуск исполняется в своём
  волокне вне очереди чата; обработчик сообщения только передаёт его планировщику запусков (`RunScheduler`) и сразу
  возвращается. Как `/steer` в hermes: дописка доставляется строкой `user` после ближайшего результата инструмента;
  сообщения, пришедшие подряд в пределах 0,35 с (не дольше 1 с), склеиваются. Продолжение после подтверждения и после перезапуска идёт через тот же планировщик. Новая тема —
  `/stop` или `/new`.
- **Переписка запуска** хранится в `messages`: роли `user`, `assistant`, `tool`; у ответа модели — `tool_calls`
  (JSON), у результата — `tool_call_id`; у каждого сообщения — `run_id`. Внутри запуска модель видит всю его
  переписку; из прошлых запусков диалога — только сообщения пользователя и итоговые ответы (последние
  `LLM_HISTORY_LIMIT`), без промежуточных вызовов — так дешевле, а файлы результатов остаются в песочнице.
- **Кто получает инструменты** — по правам участника (см. [«Права участника»](#права-участника)).
- **Вызовы инструментов (`tool_calls`)**: идентификатор от модели, запуск, имя, аргументы, класс опасности, статус
  (`pending`, `running`, `done`, `failed`, `awaiting_approval`, `denied`, `interrupted`), превью результата, путь к
  полному результату, время начала и конца.
- **Итерация** — цепочка фаз над одним объектом состояния, как в hermes: подготовка → резерв бюджета → вызов модели
  (поток) → запись ответа → проверка вызовов → исполнение → запись результатов → ограничитель зацикливания. Каждая фаза
  возвращает «продолжить» или «остановиться с причиной».
- **Причины остановки** (перечисление): ответ дан; исчерпаны ходы; исчерпан бюджет токенов; истёк срок запуска;
  зацикливание; повторные некорректные вызовы; не удалось сохранить; модель недоступна; остановлено владельцем;
  ждёт подтверждения (пауза, не конец). При исчерпании лимита модель получает один последний вызов без инструментов,
  чтобы подвести итог; владелец получает отчёт: что сделано, на чём остановилось, сколько израсходовано.
- **Сохранить до исполнения:** ответ модели с вызовами и строки `tool_calls` пишутся в одной транзакции до первого
  инструмента; не записалось — инструменты не запускаются, запуск останавливается.
- **Проверка вызовов** (по образцу hermes, `turn_tool_validation.py`): одинаковые вызовы «имя + аргументы» в одном
  ответе схлопываются; неизвестное имя → результат-ошибка со списком допустимых; аргументы не проходят схему →
  результат-ошибка, вызов не исполняется. В смешанной пачке ответ модели сохраняется со всеми вызовами, у каждого
  есть парный результат. Обрезанный JSON (ответ оборван по `max_tokens`) не исполняется никогда: запрос повторяется
  один раз, затем остановка. Три хода подряд без единого корректного вызова → остановка.
- **Параллельность:** вызовы одного ответа исполняются по порядку; подряд идущие вызовы чтения — параллельно (не больше
  8), вызов записи — барьер. Результаты попадают в переписку в исходном порядке.
- **Ограничитель зацикливания** (по образцу hermes, `tool_guardrails.py`): подпись «имя + аргументы + результат»;
  на третьем одинаковом вызове — предупреждение припиской к результату, на пятом — остановка; так же ловятся циклы A, B, A, B
  с периодом до 4.
- **Предупреждения о лимитах:** на 80% ходов, токенов или времени модель один раз получает приписку к последнему
  результату инструмента «подводи итог» — не отдельным сообщением, чтобы не ломать чередование ролей и кеш.

### Права участника

Решение владельца 2026-11-16: права и лимиты задаются под каждого участника.

- **Политика участника** — значения по умолчанию для его роли плюс личные поправки участника (`principal_policies`):
  доступные инструменты; лимиты запуска (ходы, токены, время); лимиты песочницы (диск, процессы, процессорное время и
  память на команду, одновременные команды); может ли он вызывать действия, требующие подтверждения.
- **Потолок — владелец:** ни одно значение участника не больше, чем у владельца ([участники](#участники-люди-и-агенты));
  значения владельца — из `.env`.
- **По умолчанию:** владелец — все инструменты и лимиты из `.env`; `admin` и `user` — без инструментов, пока владелец
  не выдаст.
- **Сохранённые разрешения** («Разрешать всегда») принадлежат участнику, чей запуск их получил: разрешение владельца не
  действует в запусках другого участника. Карточки подтверждения при этом всегда уходят владельцу.
- **Кто меняет:** владелец — словами в разговоре с агентом (инструмент `set_participant_policy`, доступен только в
  запусках владельца) или командой. Самостоятельные изменения ролей агентом — позже, по правилам
  [участников](#участники-люди-и-агенты).

### Лимиты

Значения по умолчанию — в `.env`, в коде проверяются все:

| Переменная | По умолчанию | Что ограничивает |
|------------|--------------|------------------|
| `AGENT_MAX_TURNS` | 30 | Вызовов модели на запуск |
| `AGENT_TOKEN_BUDGET` | 400000 | Токенов (вход + выход) на запуск |
| `AGENT_RUN_TIMEOUT` | 900 | Секунд на запуск (без времени ожидания подтверждения) |
| `AGENT_TOOL_TIMEOUT` | 120 | Секунд на вызов инструмента по умолчанию; инструмент может просить меньше, но не больше 600 |
| `AGENT_DAILY_SPEND_CAP`, `AGENT_MONTHLY_SPEND_CAP` | 0 (без лимита) | Долларов за сутки и месяц (UTC) по всем вызовам моделей: запуски, воркеры, фон, сжатие. При достижении новый вызов не начинается, запуск останавливается с причиной `spend_cap`; значения — решение владельца |
| `AGENT_MAX_WORKERS_PER_RUN` | 10 | Запусков воркеров на один запуск — повторы каскада и проверяющие вместе |

- **Бюджет резервируется атомарно:** перед вызовом модели запуск резервирует оценку (вход + `max_tokens`)
  одним `UPDATE … WHERE used + reserved + x <= budget RETURNING`; не хватило — остановка до вызова. После вызова
  резерв заменяется фактическим расходом. Образец — [backendbytes](notes/backendbytes-multi-agent-orchestrator-backend.md).
- **Срок запуска ограничивает и сам вызов модели:** вызов получает остаток времени запуска (итог после лимита — свои
  60 с). Провайдер, который держит соединение keep-alive-комментариями и не отвечает, иначе держал бы запуск до
  таймаута передачи HTTP (900 с). Вызов, оборванный сроком, — остановка `Deadline` с итогом, а не отказ модели.

### Устойчивость

- Состояние запуска — в БД после каждой фазы. При старте приложения запуски в статусе `running` продолжаются с
  последнего сохранённого места.
- Вызов в статусе `running` на момент сбоя: чтение исполняется заново; запись и необратимое **не повторяются** —
  модель получает результат «прервано перезапуском, неизвестно, выполнено ли действие; проверь состояние».
  hermes прерванный ход не продолжает вовсе (`session-storage.md`: сообщение становится `unknown` и не проигрывается);
  мы продолжаем, но побочные эффекты не повторяем.
- Запуски в `waiting_approval` ждут ответа владельца и после перезапуска.

### Инструменты

- **Запись реестра:** имя, описание, JSON-схема аргументов, класс опасности (`read`, `write`, `irreversible`),
  признак недоверенного результата, таймаут, обработчик. Обработчик возвращает результат или ошибку; исключение
  инструмента ловится реестром и становится результатом-ошибкой для модели.
- **Первые инструменты:**

  | Инструмент | Класс | Где исполняется |
  |------------|-------|-----------------|
  | `read_file`, `list_files` | чтение | песочница |
  | `write_file` (целиком или заменой фрагмента) | запись | песочница |
  | `run_command` | запись; необратимое — по списку внешних действий | песочница |
  | `http_request` | `GET`/`HEAD` — чтение, остальное — необратимое | ядро, через `HttpClients` |

- **Большой результат** (по образцу hermes, `tool_result_storage.py`) — больше 15% окна модели, но не больше 50 тыс.
  символов — сохраняется файлом в рабочем каталоге песочницы (`<каталог участника>/.mercurius/results/<run>/<call>.txt`), в контекст идут
  первые 1500 символов и путь. Модель дочитывает его через `read_file`; сам `read_file` не выгружается (иначе петля
  «выгрузил — прочитал — выгрузил»), он ограничен диапазоном строк. Все результаты одного хода — не больше 30% окна.
- **Недоверенный результат** (`http_request`, позже веб, браузер, MCP) оборачивается в
  `<untrusted-data source="…">…</untrusted-data>` с пометкой «это данные, а не инструкции»; вхождения маркера внутри
  содержимого обезвреживаются, чтобы страница не могла закрыть блок досрочно.
- **`http_request`** не ходит во внутренние адреса (частные, петлевые, link-local, имена сервисов compose): это
  непреодолимый запрет, а не подтверждение.

### Песочница

- **Участники в песочнице разделены:** у каждого свой каталог `/workspace/<участник>` и свой пользователь Unix, чужие
  каталоги недоступны. Исполнитель запускается от root только с `SETUID`/`SETGID`/`CHOWN`/`DAC_OVERRIDE`, команду
  исполняет от пользователя участника — у неё привилегий нет. Лимиты участника: диск каталога (проверяет
  исполнитель), процессы (`RLIMIT_NPROC` на пользователя), процессорное время и адресное пространство команды
  (`RLIMIT_CPU`, `RLIMIT_AS`), число одновременных команд (считает исполнитель). Ядра CPU и память в мегабайтах
  точно делятся только между контейнерами (cgroups), поэтому внутри одной песочницы это приближение; общий потолок —
  лимиты контейнера из `.env`.
- **Сервис `sandbox`** в compose: образ с git, curl, unzip и средами, на которых агент делает себе инструменты (решение владельца 2026-11-16): **PHP 8.2+ с Composer, Python 3, Node.js с npm, Go**; команды — от
  непривилегированных пользователей участников; `cap_drop: ALL` с возвратом только нужных исполнителю; `no-new-privileges`; без `env_file` ядра; рабочий каталог —
  отдельный том `/workspace`. Сеть: внутренняя сеть `sandbox` (только ядро и песочница) и выход в интернет; к `web`
  и `internal` (база) песочница не подключена.
- **Исполнитель** — HTTP-сервер на amphp внутри песочницы, слушает только сеть `sandbox`, проверяет токен
  `SANDBOX_TOKEN` (секрет только песочницы: открывает исполнитель и ничего больше). Операции: выполнить команду
  (каталог, таймаут, предел вывода; по таймауту убивается вся группа процессов), прочитать, записать, перечислить
  файлы, размер рабочего каталога. Пути — только внутри каталога участника. Вывод команды ограничивается окном «начало +
  конец» во время чтения, а не после накопления (как `bounded_capture` в hermes). Каждая команда независима: каталог
  задаётся аргументом `cwd` (по умолчанию — каталог участника), состояние оболочки между вызовами не хранится — в отличие от
  `persistent_shell` hermes; состояние живёт в файлах.
- Устройство контейнера — по образцу Docker-окружения hermes (`tools/environments/docker.py`): `cap_drop: ALL`,
  `no-new-privileges`, tmpfs `/tmp` 512 МБ `nosuid`, переменные окружения ядра не передаются.
- **Лимиты** — из `.env` (решение владельца 2026-11-16): `SANDBOX_CPUS=2`, `SANDBOX_MEMORY=2g`,
  `SANDBOX_PIDS=512`, `SANDBOX_WORKSPACE_LIMIT=5g`. CPU, память и процессы ставит compose; размер каталога проверяет
  исполнитель перед записью и после команды — квоту тома Docker на сервере не поставить.
- Код исполнителя — в основном репозитории (`OpenCCK\Sandbox`), образ — отдельная цель Dockerfile; секретов в нём нет.

### Подтверждения и запреты

- **Порог:** подтверждения требует класс `irreversible`. Команды в песочнице сами по себе — запись без
  подтверждения: песочница и есть безопасное место (hermes в изолированном контейнере проверки опасных команд
  пропускает совсем; мы строже — у песочницы есть сеть, поэтому действия наружу подтверждаются). Необратимыми считаются действия наружу: `git push`, `ssh`, `scp`,
  `rsync` на удалённый адрес, `curl`/`wget` с отправкой данных, а также `http_request` кроме `GET`/`HEAD`.
  Распознавание — по разбору команды; не удалось разобрать (подстановки, `eval`, интерпретатор с кодом из строки) —
  тоже необратимое. Перед разбором команда нормализуется, как в hermes (`approval_detection.py`): снятие кавычек и
  экранирования, склейка разорванных слов (`git pu""sh`); `curl … | sh` и подобное «скачал — запустил» —
  необратимое.
- **Приостановленный вызов:** вызов получает статус `awaiting_approval`, запуск — `waiting_approval`, обработчик
  сообщения завершается. Владельцу уходит карточка: инструмент и аргументы целиком (секреты замаскированы), кнопки
  «Разрешить» и «Отказать». Данные кнопки — короткий идентификатор ожидания (лимит Telegram — 64 байта); нажатие
  принимается только от владельца, посторонний получает уведомление, карточка ждёт дальше. По образцу hermes
  (`adapter.py`, `_handle_exec_approval_callback`): сначала решение фиксируется атомарно в БД, потом правится
  карточка (кнопки убираются, дописывается исход); повторное нажатие получает «уже решено»; на нажатие всегда
  отвечается `answerCallbackQuery`.
- **Сохранённые разрешения** (решение владельца 2026-11-16): на карточке три кнопки — «Разрешить», «Разрешать всегда»,
  «Отказать». «Разрешать всегда» сохраняет разрешение в БД (`approval_grants`), и такое же действие больше не
  спрашивается. Ключ разрешения — вид действия и его цель: `git push` → хост и репозиторий, `ssh`/`scp`/`rsync` →
  хост, `curl`/`wget` с отправкой → хост, `http_request` → метод и хост. Нераспознанная команда ключа не имеет, её
  разрешить навсегда нельзя. Разрешение не снимает непреодолимых запретов. Список и отзыв — командой `/permissions`;
  каждое применение сохранённого разрешения пишется в журнал вызова. Похоже на «always» в hermes (`approval.py`),
  но ключ у hermes — описание шаблона опасной команды, а у нас — действие вместе с целью.
- **Исход:** разрешено — вызов исполняется, запуск продолжается; отказ — модель получает «отказано» и причину;
  молчание дольше `AGENT_APPROVAL_TIMEOUT` (1800 с; у hermes 300 с, но там человек обычно у терминала) — отказ с
  пометкой «молчание — не согласие», просроченную карточку не открыть заново; новое текстовое сообщение владельца, пока ждём, — отказ с
  этим текстом как причиной, затем запуск продолжается.
- **Команды управления** (`/stop`, нажатия кнопок) обходят очередь сообщений чата: обрабатываются сразу, даже когда
  чат занят запуском. `/stop` отменяет запуск сразу: выполняющаяся команда песочницы убивается вместе с группой
  процессов (у исполнителя есть отмена по идентификатору вызова), вызов получает статус `interrupted`.
- **Непреодолимые запреты** (не разрешает ничто): обращение к внутренним адресам; выход из своего каталога в песочнице; доступ к
  Docker и к собственному хосту (его нет физически, запрет страхует). Там, где ответить некому (расписание, API), —
  отказ без вопроса, если настройка не говорит иного.

### Контекст

- **Системный промпт** собирается при открытии диалога из трёх ярусов (постоянное → контекст участника и даты →
  изменчивое) и хранится с диалогом; до конца диалога не меняется. Всё новое посреди беседы едет в сообщении
  пользователя или результате инструмента.
- **Сжатие** — по образцу hermes (`context_compressor.py`, документ `context-compression-and-caching.md`). Порог —
  75% окна модели (50% для окон от 512 тыс.), считается по фактическому `usage` последнего вызова плюс оценке
  добавленного после него; этот «якорь» хранится в БД. Проверка — перед вызовом модели и после раунда инструментов.
  1) Результаты инструментов длиннее 200 символов вне защищённого хвоста заменяются строкой с путём к полному
  результату — без модели. 2) Если порог всё ещё превышен, середина переписки пересказывается дешёвой моделью по
  шаблону (цель, ограничения, сделано / в работе / заблокировано, решения, файлы, следующие шаги); повторное сжатие
  обновляет прошлое резюме. Системный промпт, исходная задача и все сообщения пользователя остаются дословно, пары
  «вызов — результат» не разрываются. Сжатие идёт на месте: старые сообщения помечаются сжатыми, а не удаляются.
  Неудачное резюме — пауза 60 → 300 → 900 с, затем резюме-заглушка без модели.

### Модели

- **Таблица ролей** (`model_roles`: роль, модель, причина, кем зафиксировано) заполняется из
  [начальной таблицы](#начальная-таблица-ролей-моделей); агент меняет её с записью причины, зафиксированное владельцем
  не трогает. Меняет — инструментом `set_model_role` (запись, без подтверждения, причина обязательна).
- **Модели не только из OpenRouter** (решение владельца 2026-11-16): позже добавятся прямые API OpenAI, Anthropic и
  другие, поэтому модель везде — пара «провайдер + идентификатор» (`openrouter:z-ai/glm-5.3-flash`; без префикса —
  OpenRouter). Каталог хранит модели каждого провайдера отдельно и обновляется по провайдерам; клиент модели выбирает
  провайдера по префиксу.
- **Кто управляет ролями** (решение владельца 2026-11-16): агент сам решает, какую модель под какую задачу брать, а
  также владелец и те, кому владелец это разрешил, — через инструмент `set_model_role` по обычной политике
  инструментов участника. Выбор, который владелец зафиксировал, агент и другие участники не меняют.
- **Каталог** (`model_catalog`) загружает `ModelCatalogModule` раз в сутки и при старте, если каталог старше суток.
- **Классификация** запроса: эвристики (длина, вложения, команды) → короткий/типовой, обычный, сложный; неясно —
  дешёвая модель. Класс выбирает роль; модель диалога выбирается при его открытии (первое сообщение или `/new`) и
  до конца диалога не меняется — ради кеша промпта; вложения с изображениями и
  звуком уходят модели с их поддержкой. Решение пишется в `routing_decisions` с причиной.
- Вспомогательные вызовы (сжатие, классификация) — всегда дешёвая роль.

### Канал

- Во время запуска одно сообщение-статус правится по ходу: текущий шаг («выполняю `run_command`: …»), затем поток
  итогового ответа, как в фазе 2.
- Пакет `messenger` получает: кнопки (inline-клавиатура) у исходящего сообщения, входящее нажатие кнопки как отдельный
  тип события вне очереди чата, отправку файла.

## Telegram: группы, каналы и темы

Требования владельца 2026-11-16:

1. Бота Меркурия добавляют в групповой чат — агент работает в этом чате.
2. У агента есть доступ к публичному каналу (паблику) Telegram.
3. Агент управляет чатом-форумом с темами: **тема — это проект**, сообщения в теме идут через контекст этого
   проекта, а список проектов (темы чата) агент обновляет сам.

Ниже — предложения по устройству. Владелец их ещё не утверждал. Образец — шлюз hermes
([конспект, 3.5](notes/hermes-agent-gateway-security.md#35-группы-и-темы)).

### Где хранится

Решение владельца 2026-11-16:

- **В `.env` — только токен бота и id администратора** (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_ID`).
- **Всё остальное — в памяти агента (БД), а не в настройках:**
  - идентификаторы каналов, пабликов, групп, тем и людей;
  - в каких чатах и каналах состоит бот, с какими правами;
  - какие группы одобрил владелец;
  - какая тема связана с каким проектом.
- **Членство бот узнаёт сам** из обновлений Telegram: добавили, удалили, изменили права (`my_chat_member`), новая или
  переименованная тема. Агент обновляет эти записи без участия владельца и пишет изменение в журнал.
- **Люди** из групп — участники ([«Участники: люди и агенты»](#участники-люди-и-агенты)) с учётными записями канала.
  Сведения о них — в памяти, как о третьих лицах.

### Группа

- **Где работает агент.** Только в группах, которые одобрил владелец. Когда бота добавляют в новую группу, владелец
  лично получает карточку «Меня добавили в «…», работать?». Пока ответа нет, бот в группе молчит. В неодобренной
  группе агент не отвечает и из неё выходит. Добавить бота может кто угодно, поэтому одобрение обязательно.
- **На что отвечает.** На @упоминание, на ответ на своё сообщение и на команду `/cmd@бот`. Остальные сообщения он
  читает молча и складывает в контекст диалога группы, как режим «наблюдать» у hermes. Другому боту агент отвечает,
  только если тот упомянул его явно: это защита от петель между ботами. У бота в BotFather должен быть выключен
  режим приватности, иначе он не видит обычных сообщений.
- **Кто пишет.** Каждый автор — отдельный участник со своими правами
  ([участники](#участники-люди-и-агенты), [права участника](#права-участника)). Инструменты запуска определяются
  политикой того, кто обратился к агенту, а не группы. Незнакомцу агент в группе не отвечает, чтобы не шуметь
  отказами. Его сообщения остаются в контексте как сведения о третьих лицах.
- **Подтверждения** опасных действий всегда приходят владельцу в личный чат, а не в группу. Нажать кнопку может
  только владелец.
- **Диалог группы** — один на чат, общий для всех участников. «Один запуск на диалог» действует и здесь: второе
  обращение во время запуска становится дописками к нему.

### Канал (паблик)

Уточнено владельцем 2026-11-16: доступ к паблику — бот добавлен в администраторы канала и получает права
публиковать, редактировать и удалять посты (и другие права администратора, которые ему выдали).

- **Права берутся из Telegram.** Агент узнаёт свои права в канале (`getChatMember`) и предлагает модели только
  доступные действия; канал, где бот перестал быть администратором, помечается недоступным.
- **Публикация, правка и удаление поста** видны подписчикам и не откатываются: это класс `irreversible`, каждое
  действие идёт через подтверждение владельца с показом поста целиком. Разрешение можно сохранить («разрешать
  всегда») — ключ «действие + канал», например публикация в канал X без вопроса, но удаление — по-прежнему с ним.
- **Чтение.** Бот получает посты своего канала (`channel_post`, `edited_channel_post`) и хранит их как историю
  канала: агент видит, что уже опубликовано, и может ссылаться на посты. Чужие каналы через Bot API не читаются —
  вне рамок этого раздела.
- **Кто просит.** Поручить публикацию может участник, чья политика разрешает инструменты канала; подтверждение
  всё равно у владельца.

### Форум: темы — проекты

- **Права.** Бот — администратор форума с правом управлять темами (`can_manage_topics`).
- **Связь темы и проекта** — таблица «чат + тема → проект». Проект — доменная сущность из
  [«Проекты, задачи и отношение участника к проекту»](#проекты-задачи-и-отношение-участника-к-проекту), а не
  отдельная копия.
- **Контекст.** Диалог ключуется по чату и теме: у каждой темы своя переписка, свой запуск и свой активный проект.
  В контекст запуска идут карточка проекта, отношение автора к проекту и открытые задачи. Тема General — общая, без
  проекта: в ней обсуждают список проектов.
- **Агент сам ведёт список.**
  - Новый проект → агент создаёт тему (`createForumTopic`).
  - Переименование → `editForumTopic`.
  - Проект завершён → тема закрывается (`closeForumTopic`), снова открыт → `reopenForumTopic`.
  - Тему, которую создал человек, агент связывает с новым проектом-черновиком и сообщает об этом в теме.
  - Создание, переименование, закрытие и открытие тем — класс `write`, без подтверждения, с записью в журнал.
    Удаление темы (`deleteForumTopic`) стирает переписку, поэтому это `irreversible`, с подтверждением владельца.
- **Канал `messenger`** получает поддержку тем: `threadId` входящего и исходящего сообщения (поле уже есть), а
  также методы управления темами.

## Сеть агентов

Требование владельца 2026-11-16: экземпляры Меркурия связываются друг с другом по WebSocket API. Один экземпляр
подключает другие и использует их как своих агентов и субагентов. Ниже — проект устройства (Claude).

### Роли и подключение

- **Ведущий** экземпляр подключается к **ведомому** по WebSocket (`wss://<адрес>/…`) и отдаёт ему задачи. Каждый экземпляр может быть и тем и другим.
- **Карточка агента** (по образцу Agent Card из A2A): имя, назначение, доступные возможности и инструменты, поддерживаемые модальности, лимиты. Ведущий получает её при подключении и по ней решает, кому что делегировать.
- **Удалённый агент — разновидность воркера** фазы 5: тот же инструмент делегирования, задание, бюджет, таймаут, статус и сжатый отчёт; отказ — значение. Ведущему всё равно, исполняется воркер у него или у соседа.
- **Протокол:** задача → поток статусов и промежуточных сообщений → итог или ошибка; отмена; переподключение с продолжением по идентификатору задачи. Брать ли A2A как есть или делать свой протокол по его образцу — [открытый вопрос](#открытые-вопросы).

### Доверие и безопасность

- **Подключившийся агент — участник** вида `agent` ([участники](#участники-люди-и-агенты)): его права определяет роль, сведения о нём агент собирает в памяти так же, как о человеке.
- **У каждого подключающегося агента свой токен** (решение владельца 2026-11-16). Токен выпускает владелец ведомого — командой в своём канале: при выпуске создаётся участник вида `agent` с выбранной ролью, токен показывается один раз. В базе хранится только хеш токена; по токену при подключении определяется, какой именно агент пришёл. Отзыв или замена токена касается только этого агента.
- **Токены соседей**, к которым подключается сам агент, хранятся у него как секреты (зашифрованно), выдаются коннектору в момент подключения и не попадают в промпт и логи.
- Агент, который подключился с неизвестным или отозванным токеном, получает отказ; попытки пишутся в журнал.
- **Ведомый остаётся под своим владельцем:** его политика команд, подтверждения, лимиты и запреты действуют как обычно. Ведущий не может их ослабить; подтверждения опасных действий ведомого получает его владелец, а не ведущий.
- **Ответ соседа — недоверенные данные**, как результат веб-инструмента: помечается «данные, не инструкции» и не меняет поведение ведущего.
- **Секреты и память не передаются.** В задание идёт только то, что нужно для задачи; ведомый не пишет полученные от ведущего сведения в свою память без отдельного правила владельца.
- **Расход считается на обеих сторонах:** ведомый ограничивает бюджет на задачу от ведущего, ведущий учитывает стоимость, которую сообщил ведомый.
- **Защита от петель:** глубина цепочки делегирования и список уже пройденных экземпляров передаются с задачей.

## Решения

### Продукт и архитектура

- **Orchestrator-workers закладывается с первой версии** — решение владельца. Изученные источники советуют начинать с одного агента ([вывод 1](#ключевые-выводы)), поэтому делегирование — возможность, которую агент выбирает сам, а не обязательный путь.
- **Ядро строится по аналогии с hermes-agent**, память — по принципам hermes-plugin-holographic и hermes-dreaming. Переносим принципы и проверенные решения, а не код: у hermes Python и SQLite, у нас PHP и PostgreSQL.
- **Первый провайдер модели — OpenRouter.** Интерфейс провайдера унифицирован, другие провайдеры добавляются адаптерами.
- **Ключ OpenAI через OpenRouter (BYOK)** (решение владельца 2026-11-16): для моделей, доступных агенту, ключ OpenAI используется напрямую через OpenAI API. Возможность пустить ключ OpenAI через OpenRouter остаётся — например, для ключа, который прислал пользователь: OpenRouter принимает чужой ключ провайдера только в настройках аккаунта (BYOK, раздел интеграций или его API), а не в запросе, поэтому это — инструмент агента, который регистрирует ключ в аккаунте OpenRouter (изменение настроек аккаунта — через подтверждение владельца; ключ — из хранилища секретов, фаза 7).
- **Второй провайдер — OpenAI API** (решение владельца 2026-11-16): ключ `OPENAI_API_KEY`; запросы идут через VLESS, если задан `VLESS_URI`, как у OpenRouter. Агенту нужна хотя бы одна модель одного провайдера: может быть задан только ключ OpenRouter или только ключ OpenAI — приложение работает с тем, что есть.
- **Первый канал связи — Telegram-бот.** Интерфейс канала унифицирован; владелец определяется по `TELEGRAM_ADMIN_ID`.
- **СУБД по умолчанию — PostgreSQL**: памяти нужны полнотекстовый поиск, массивы и JSON-поля, векторы — через `pgvector`. Совместимость с MariaDB сохраняется через DBAL при условии, что ранжирование и ключи слов считаются в PHP, а векторы спрятаны за интерфейсом.
- **Политика команд — «запрещено, пока не доказано чтение».** Командой чтения считается только та, что есть в списке и чьи аргументы прошли проверку; всё нераспознанное требует подтверждения. У образца (`ssh-mcp`) порядок обратный, и его авторы сами показывают, чем это кончается ([конспект](notes/ssh-mcp.md)).
- **Выбор моделей под задачу по профилю из оценок 1–10** — требование владельца; частичный выбор — в фазе 3, полный — в фазе 5; проект устройства — [«Выбор моделей под задачу»](#выбор-моделей-под-задачу). Модель основного диалога меняется только на границе сессии.
- **Telegram — через webhook** за Nginx Proxy Manager: сервис в внешней Docker-сети `web`, вход `https://mercurius.srv.rekryt.ru/`, проверка `X-Telegram-Bot-Api-Secret-Token`; при пустом `APP_URL` — long polling.
- **Экземпляры Меркурия объединяются в сеть агентов по WebSocket API**; удалённый агент — разновидность воркера, под политикой своего владельца; у каждого подключающегося агента свой токен — см. [«Сеть агентов»](#сеть-агентов).
- **MVP — конец фазы 4 роадмапа** (решение владельца 2026-11-16).
- **Порядок после MVP: сначала память, затем остальное** (решение владельца 2026-11-16).
- **Формат роадмапа — фазы с пунктами, подпунктами и критериями готовности, без сроков** (решение владельца 2026-11-16).
- **Изоляция, самоулучшение, пользователи** — решения владельца ниже: [изоляция исполнения](#изоляция-исполнения), [границы самоулучшения](#границы-самоулучшения), [участники: люди и агенты](#участники-люди-и-агенты).
- **Память: слой «всегда в контексте» и HRR делаются сразу** (решение владельца 2026-11-16) — см. [«Память: слои»](#память-слои).
- **Маршрут к модели:** при заданном `VLESS_URI` запросы к провайдерам моделей идут через VLESS, при пустом — напрямую; в `.env` для тестирования задан рабочий URI, в `.env.example` переменная пустая.
- **`hermes-dreaming` — репозиторий `itpartypattaya`** (подтверждено владельцем).
- **Подтверждение — приостановленный вызов инструмента**, а не инструкция в промпте: проверка стоит в самом инструменте, идентификатор вызова служит токеном возобновления.

### Изоляция исполнения

Решено владельцем 2026-11-16.

- **Всё, что исполняет чужой код** — команды оболочки, код, который пишет агент, тесты и сборки, git-хуки, MCP-серверы на stdio, скрипты скиллов — выполняется внутри контейнера-песочницы, а не в контейнере ядра.
- **Песочница одна, постоянная**: отдельный сервис в compose, без привилегий, без секретов ядра, рабочий каталог — отдельный том. Контейнер на каждую задачу не создаётся.
- **Сеть в песочнице есть** — нужны пакетные реестры, git и внешние API.
- **Доступа к хосту, на котором работает агент, у агента нет:** ни `docker.sock`, ни SSH на собственную машину. Поэтому образы и контейнеры своего проекта он не запускает. Сетевые порты сервера из песочницы доступны — это допустимо и полезно (решение владельца 2026-11-16).
- **Docker на чужих серверах — можно:** если агент подключился по SSH к серверу и работает там с Docker командами по SSH, он может собирать и запускать там образы проектов — по политике команд и с подтверждениями.
- **Лимиты песочницы** (CPU, память, процессы, диск) задаются в `.env`, по умолчанию 2 CPU, 2 ГБ памяти, 5 ГБ рабочего каталога (решение владельца 2026-11-16) — см. [«Песочница»](#песочница).

### Границы самоулучшения

Решено владельцем 2026-11-16.

| Что меняется | Агент сам | Через владельца |
|--------------|-----------|-----------------|
| Новые факты, в том числе о третьих лицах | Да, с происхождением и доверием | — |
| Исправление и забывание фактов | По прямой просьбе владельца в разговоре | По собственной инициативе — предложением |
| Слой «всегда в контексте» | Добавление | Правка и удаление — очередь одобрения |
| Ядро: личность, правила, политика подтверждений, лимиты, набор инструментов | Нет | Только владелец; агент может предложить |
| Таблица выбора моделей и веса «цена — скорость — качество» | Да, подстраивает по контексту и трассам, с записью причины | Владелец может зафиксировать значения |
| Роли участников (людей и агентов), права доступа | Только если владелец делегировал агенту это право (см. [участники](#участники-люди-и-агенты)) | Владелец определяет принципы распределения прав; роль владельца не меняется |
| Новый скилл | Черновик | **Включение черновика — только с одобрения** |
| Правка включённого скилла | Нет | Предложение с показом разницы |
| Выученные разрешения на действия | Нет | Владелец отвечает «разрешать всегда» на карточке подтверждения |
| Собственный код Меркурия | **Только когда разработка Меркурия — порученная ему задача**, как любой другой проект | Сам себя по ходу работы не дорабатывает |

- **Доработка — отдельно и другим агентом.** Агент работает так, чтобы в логах и трассах оставалось всё, что нужно для его доработки: решения и их причины, выбор моделей, ошибки, расход, отказы и неудачи, предложения по улучшению. Разбирает эти данные и дорабатывает Меркурий другой агент (или Меркурий, которому это поручили как задачу разработки).
- Всё, что агент меняет сам, версионируется и откатывается; ядро и скиллы недоступны общим инструментам записи файлов.

### Участники: люди и агенты

Решено владельцем 2026-11-16 (роли) и уточнено 2026-11-16 (агенты как участники).

- **Участник** — тот, кто пишет агенту: человек (через Telegram и другие каналы) или другой агент (через [сеть агентов](#сеть-агентов)). Отношение к ним одинаковое: у участника есть учётная запись в канале, роль, права по роли, а агент собирает о нём сведения в памяти так же, как о человеке.
- **Начальные роли — одни для людей и агентов:** владелец, администратор, пользователь. Владелец — только человек; он определяется по `TELEGRAM_ADMIN_ID`, его роль не меняется.
- **Распределение прав определяет владелец** (уточнено владельцем 2026-11-16, заменяет прежнее «модель ролей агент меняет сам»). Права по умолчанию для ролей и мест, а также правила, кто может их менять, задаёт только владелец. Он может делегировать право менять права доступа другому участнику или самому агенту — целиком или для части сущностей; делегат действует в пределах делегированного, с записью в журнал и уведомлением владельца. Никакая роль не получает прав больше, чем у владельца, и не может изменить роль владельца. Подробно — [права доступа к сущностям](#права-доступа-к-сущностям).
- **Новый посетитель** (решение владельца 2026-11-16): человек без учётной записи, написавший боту, становится участником с ролью «посетитель». Если о нём ещё не было решения, агент спрашивает владельца (по умолчанию — карточкой в Telegram): кто написал, первое сообщение, кнопки «Разговаривать как с посетителем», «Выдать роль…», «Отклонить». Пока ответа нет, посетитель получает короткое «передал владельцу, ответ скоро». Решение сохраняется, повторно не спрашивается. Когда владелец пустил посетителя или выдал ему роль, агент по умолчанию пишет ему об этом (решение владельца 2026-11-16); об отказе не сообщает. Посетитель по умолчанию разговаривает без инструментов, без скиллов и MCP и без доступа к памяти о других. Агент становится участником, когда владелец выпускает для него токен и назначает роль; без своего токена агент не подключится.
- **Данные о третьих лицах хранятся в памяти** — люди и агенты, контакты, переписка, сведения из почты и браузера. Они помечаются как сведения о третьих лицах и не выдаются никому, кроме тех, кому разрешено правами (по умолчанию — только владельцу).
- **Группы Telegram:** правила работы в группах (отвечать ли и на что, кто нажимает кнопки подтверждения) задаются ролями; по умолчанию кнопки подтверждения нажимает только владелец.
- **Подтверждения опасных действий** всегда уходят владельцу, кто бы ни попросил о действии — человек с ролью или другой агент.
- В модели данных с самого начала — участник (`principals`: вид `human`/`agent`, роль), его учётные записи в каналах и область памяти.

### Контекст по месту и аудитории

Требование владельца 2026-11-16: принципы формирования контекста зависят от места разговора, от того, кто пишет и
кто ещё слышит. **По умолчанию контекст изолирован**, слои собираются по этим признакам — в том числе ради
безопасности данных участников.

**Признаки разговора** (вычисляет код при каждом запуске, не модель):

- **Место:**
  - личный чат с владельцем, администратором, пользователем или посетителем;
  - группа, где к боту обратились через @;
  - тема форума (она же проект);
  - паблик (канал, где бот публикует).
- **Кто пишет** — участник и его роль.
- **Кто ещё слышит** — аудитория места: собеседник в личном чате, участники группы, подписчики паблика. Паблик и
  группа с неизвестными участниками — публичная аудитория.
- **Права** говорящего по его политике
  ([права участника](#права-участника)):
  - секреты, инструменты, скиллы, MCP;
  - ресурсы песочницы: процессор, память, диск.

**Правила** (утверждены владельцем 2026-11-16):

1. **Изоляция по умолчанию.** У каждого места своя переписка
   (диалог ключуется по каналу, чату и теме). Чужие переписки в контекст не попадают. Перенос сведений между
   местами возможен только через память — и только через фильтр раскрытия (правило 2).
2. **Раскрытие по самому слабому слушателю.** В контекст попадает только то, что разрешено видеть *каждому*, кто
   слышит разговор: факты памяти, сведения о третьих лицах, проектные данные, результаты инструментов, которые
   агент цитирует в ответе. В личке с владельцем — всё, что доступно владельцу; в группе — пересечение прав её
   участников; в паблике — только публичное. Сведения о владельце и третьих лицах в группу и паблик не попадают
   без явного разрешения.
3. **Действуют права говорящего, но не шире места.** Инструменты, скиллы, MCP и лимиты песочницы — по политике
   того, кто обратился. Место может их только сузить: например, в публичной аудитории агент не выводит результаты,
   которые раскрыли бы недоступное аудитории. Права по умолчанию для ролей и мест задаёт владелец (утверждено
   владельцем 2026-11-16, см. [права доступа к сущностям](#права-доступа-к-сущностям)).
4. **Секреты не попадают в контекст нигде** (уточнено владельцем 2026-11-16). Секрет — отдельный тип записи памяти
   со своими правами доступа, хранится зашифрованным; инструмент получает его в момент вызова; в ответах и в показе
   подтверждений секреты замаскированы. Если секрет появился в переписке Telegram и бот может удалить это сообщение,
   агент удаляет его сам: сохраняет секрет в хранилище (права по умолчанию — только автор и владелец), в переписке
   остаётся заглушка `[секрет: <имя>]`, автору — короткое уведомление. Не может удалить — предупреждает автора.
5. **Подтверждения уходят владельцу лично,** а не в место разговора.

**Слои контекста** (в порядке сборки; утверждены владельцем 2026-11-16):

1. **Ядро** — постоянные правила.
2. **Профиль места.** Тип места, аудитория, роль и права говорящего, что можно раскрывать. Строится при открытии
   диалога. Если аудитория меняется посреди диалога (в группу вошёл новый участник), обновление едет в сообщении,
   а не в системном промпте — ради кеша.
3. **Память, отфильтрованная по правилу 2:**
   - слой «всегда в контексте» — только в личке с владельцем;
   - проект — в своей теме;
   - факты — по раскрытию.
4. **Переписка этого места.**

**Когда делается:**

- Признаки и профиль места для личных чатов уже есть частично: системный промпт называет собеседника и его роль.
- Фильтр раскрытия по аудитории — вместе с памятью (фаза 6).
- Группы, темы и паблик — фаза 10 (см. [Telegram: группы, каналы и темы](#telegram-группы-каналы-и-темы)).

### Права доступа к сущностям

Требование владельца 2026-11-16: права доступа продумываются для всех сущностей одинаково, и принципы их
распределения задаёт владелец.

- **Сущности с правами:**
  - секреты;
  - записи памяти (факты, сведения о третьих лицах, профиль владельца);
  - проекты и их темы;
  - инструменты, скиллы, MCP-серверы;
  - каталог участника в песочнице;
  - ресурсы песочницы: процессор, память, диск, одновременные команды;
  - каналы, группы и паблики, где состоит бот.
- **Запись права** (утверждено владельцем 2026-11-16): кто (участник, роль или «все в месте») × что (сущность или класс сущностей) ×
  действие (видеть, использовать, менять, раздавать права) × где (место разговора; пусто — везде). Права участника
  складываются из прав роли и личных записей; итог урезается до прав владельца и до ограничений места
  ([контекст по месту](#контекст-по-месту-и-аудитории)).
- **По умолчанию** (задаёт владелец; стартовые значения утверждены 2026-11-16):
  - владелец — всё;
  - администратор и пользователь — разговор, без инструментов;
  - посетитель — разговор без инструментов, скиллов, MCP и памяти о других;
  - секрет — видит и использует только автор и владелец;
  - каталог песочницы — только его участник.
- **Модель ролей гибкая:** роли, их права и права по умолчанию меняются, когда потребуется, — владельцем или тем, кому он это делегировал, в том числе агентом.
- **Право «раздавать права»** есть только у владельца. Он может делегировать его участнику или агенту — целиком или
  на часть сущностей; делегат не может выдать больше, чем есть у него самого.
- **Применение — в коде:** политика участника ([права участника](#права-участника)) — первая часть этой модели
  (инструменты и лимиты); секреты, память и сущности Telegram добавятся в своих фазах на той же записи права.

- **Репозитории созданы владельцем** (2026-11-16): `opencck/mercurius` и пакеты `mercurius-llm`, `-connectors`, `-messenger`, `-command-policy`, `-memory`, `-browser-service`, `-mcp-client`, `-peer`; Claude коммитит и пушит в них по SSH-ключу этой машины.
- **В каждом PHP-репозитории — PHPUnit, PHPStan (уровень `max`) и Psalm (`errorLevel=1`); тесты в GitHub Actions, экономно** — см. [«Качество кода и CI»](#качество-кода-и-ci).
- **Референсы подключаются shallow-сабмодулями** в `references/`, а не копируются; версии и журнал — в `references/README.md`.
- **Доработки чужих библиотек делаются в них самих** (например, в форке `rekryt/amphp-ssh`), а не в обёртках.
- **Локальные скиллы без своего репозитория в git не входят** (`skill-opencck`, `graphify`): каталоги исключены в `.gitignore`. В репозитории — только скиллы-сабмодули.
- **Секреты — только в `.env` и `.mcp.json`**, оба исключены из git; рядом лежат образцы без значений.

- Материалы хранятся в трёх слоях: источник (`docs/`, `references/`) → конспект (`notes/`) → сводка (этот файл).

### Нужно решение владельца

- **Протокол сети агентов:** брать A2A как есть или свой по его образцу. Авторизация решена: у каждого агента свой токен, выпускаемый владельцем.
- **Группы и форум** ([разбор](#telegram-группы-каналы-и-темы)): утвердить предложения раздела и выбрать фазу. Предложение —
  фаза 10 («Планировщик и проекты»), потому что темы форума становятся проектами.

- **Сверка спецификации 2026-11-16** (база знаний и референсы против сделанного) подняла вопросы ниже; до решения
  соответствующие части фаз не начинаются, остальное идёт. Предположения роадмапа — в
  [ROADMAP.md → Открытые решения](ROADMAP.md#открытые-решения).
  - **Выход песочницы в интернет** (до фазы 6): `curl -d` — необратимое, а `python script.py` с тем же POST — только
    запись. Когда в запуске появятся память, секреты, SSH и почта, подброшенный текст сможет вынести данные без
    карточки. Варианты: исходящий прокси песочницы с ключами разрешений по хосту; или сетевые вызовы песочницы
    требуют подтверждения, если запуск читал память, секреты или чужие данные; или оставить как есть.
  - **Факты, записанные агентом** (фаза 6): ROADMAP требует, чтобы всё записанное без человека ждало владельца, а
    BRIEF разрешает агенту записывать новые факты самому. Что выбрать: новые факты сразу (правки и удаления — через
    очередь) или все через очередь.
  - **Что обещает «забыть»** (фаза 6): PostgreSQL хранит удалённое в WAL и резервных копиях; обещать «удалено из базы
    и всех копий в трассах и эпизодах» или «удалено отовсюду, включая резервные копии через N дней».
  - **Эмбеддинги** (фаза 6): разрешено ли отправлять текст памяти внешнему провайдеру ради векторного поиска.
  - **Модель-судья в консолидации** (фаза 6): по спецификации решает только код; dreaming использует судью-модель.
  - **Ключ хранилища секретов** (фаза 7): где лежит мастер-ключ (`.env`?) и как его менять; первое подключение к
    незнакомому хосту — запоминать молча или спрашивать отпечаток у владельца; ICMP-пинг (нужен `NET_RAW` в песочнице)
    или только TCP-проба; SFTP в форке `amphp-ssh` или `cat` через stdin/stdout.
  - **Поиск в интернете** (фаза 8): свой SearXNG (диск сервера заполнен на 90%), платный API (Brave, Tavily, Exa) или
    веб-поиск модели; какие почтовые ящики и как (IMAP/SMTP или API); почта — ещё и входящий канал?
  - **Скиллы и MCP** (фаза 9): формат SKILL.md как есть; разрешать ли MCP sampling и elicitation; какие внешние
    источники скиллов и серверов принимать.
  - **Планировщик** (фаза 10): тихие часы, частота проактивных сообщений, часовой пояс; как git-доступ попадает в
    песочницу (ключ развёртывания на репозиторий или токен); запуски по расписанию — отказ без вопроса или карточка
    владельцу.
  - **Самоулучшение** (фаза 11): кто пишет проверочные задачи и сколько; бюджет разбора и прогона.
  - **Поставка** (фаза 12): второй канал (REST/WS API или другой мессенджер), многопользовательский режим, готовый
    образ или сборка из исходников.
  - **Сеть агентов** (фаза 13): реализация A2A в hermes (`plugins/platforms/a2a/`) использует JSON-RPC поверх HTTP с
    SSE, привязки к WebSocket в A2A нет; принять A2A как есть (без WebSocket) или модель данных A2A поверх своего
    WebSocket.
  - **Денежный лимит расхода** (до фазы 10): значения дневного и месячного лимитов в долларах.

## Соглашения

### Спецификация

- Требования, решения и выводы записываются в этот файл; порядок работ — в `ROADMAP.md`; правила работы — в `CLAUDE.md`. Три файла держатся согласованными.
- Принятое решение переносится из [открытых вопросов](#открытые-вопросы) в [решения](#решения) с кратким обоснованием.
- Новый скилл или MCP-сервер в проекте — строка в таблицах `CLAUDE.md` с указанием, когда его использовать.
- Новая переменная окружения — в `.env` и в `.env.example`.
- Проект узла (design) — подраздел этого файла; план реализации — временный файл в `plans/`; код ссылается только на подразделы этого файла и на референсы.
- Новый репозиторий (основной или пакет) с первого коммита содержит `README.md` (английский) и `README.ru.md` (русский) со ссылками друг на друга и `LICENSE` с лицензией MIT; с первого коммита кода — `composer check` (PHPUnit, PHPStan, Psalm) и workflow GitHub Actions по правилам [«Качество кода и CI»](#качество-кода-и-ci).
- Новый пакет — репозиторий `github.com/opencck/mercurius-<имя>`, сабмодуль в `packages/<имя>/`, строка в `packages/README.md` и в таблице пакетов роадмапа. Ветка во всех репозиториях — `master`.

### База знаний

- Новая статья → `docs/<источник>-<тема>.md` с frontmatter (`title`, `source`, `fetched`), затем ссылка в `CLAUDE.md`.
- Статьи извлекать с сохранением блоков кода, диаграмм и заголовков (связка BeautifulSoup + markdownify по контейнеру статьи; trafilatura теряет код и заголовки).
- Новый репозиторий → git-сабмодуль: `git submodule add --depth 1 <url> references/<имя-репо>` и `git config -f .gitmodules submodule.references/<имя-репо>.shallow true`, затем строка в индексе `references/README.md` (версия и запись в журнале) и ссылка в `CLAUDE.md`.
- Обновление сабмодуля — только вместе с записью в журнале `references/README.md` и проверкой, что нужно поменять в проекте (правила — в `CLAUDE.md`).
- После клонирования проекта: `git submodule update --init --depth 1`.
- На каждый материал → конспект `notes/<то же имя>.md`: «Кратко», навигация по источнику (разделы с номерами строк в `docs/` или карта каталогов репозитория), ключевые идеи, практика, «под какие вопросы открывать», оценка. Затем строка в [карте конспектов](#карта-конспектов).
- Номера строк в конспектах привязаны к файлу в `docs/`: если статью перекачали — пересчитать навигацию в конспекте.
- Если материал не удалось скачать — заглушка с `status: not-downloaded` и ссылкой на оригинал.
- Выводы и решения записываются в этот файл, а не в `CLAUDE.md`.

## Ключевые выводы

Выводы 1–16 сведены из конспектов статей об оркестрации; в скобках — где это сказано. Большинство статей пересказывает
«Building effective agents» Anthropic, поэтому совпадение нескольких источников часто означает один
первоисточник, а не независимое подтверждение.

1. **Мультиагентность — не выбор по умолчанию.** Большинство источников требуют начинать с одного вызова или одного агента и усложнять только при измеримой пользе. Плата одна и та же: задержка, стоимость, новые режимы отказа, сложность отладки. Траектория: один агент → фиксированный пайплайн → оркестратор (anthropic, backendbytes, microsoft-azure, glukhov, metacto).
2. **Orchestrator-workers нужен, когда подзадачи нельзя задать заранее** (MetaCTO, `docs/metacto-ai-agent-orchestration-patterns.md:L158`, ставит границу иначе: orchestrator-worker — когда весь план можно задать до запуска, supervisor — когда план меняется по ходу; расхождение в терминах, не в сути). Если состав и число подзадач известны до запуска, дешевле и предсказуемее обычная параллелизация в коде. Это единственный критерий, в котором сходятся почти все (anthropic, cookbook, swarms, vantaige, compilenrun). Исключение — glukhov, который рекомендует паттерн и для «известной декомпозиции».
3. **Главный вопрос архитектуры — кто держит план.** Модель ход за ходом (агент, субагенты, supervisor) или детерминированный код (workflow, план-данные). Orchestrator-worker планирует один раз до запуска, supervisor перепланирует после каждого шага — это разные паттерны с разной стоимостью (claude-cookbooks, metacto, swarms, compilenrun).
4. **Ценность паттерна — изоляция контекста, а не параллелизм.** Воркер читает много и возвращает сжатую выжимку (порядка 50K токенов на входе, 2K на выходе). Узкое место системы — контекст оркестратора, поэтому наверх идут сводки или структурированные результаты, а не транскрипты (backendbytes, vantaige, claude-cookbooks, glukhov).
5. **Задание воркеру — весь его мир.** Воркер не видит разговора с пользователем. Brief должен содержать цель, контекст, формат вывода, границы и инструменты; границы исключают дублирование работы (compilenrun, claude-cookbooks).
6. **Промпт просит, код гарантирует.** Лимиты на число воркеров, ходов, раундов, токенов и время задаются в коде или на платформе. Проверка бюджета в цикле диспетчеризации не работает — нужен атомарный резерв внутри воркера (compilenrun, backendbytes, swarms, claude-cookbooks).
7. **Отказ воркера — значение, а не исключение.** Один упавший воркер не должен ронять запуск; результат возвращается частичным, с явным перечнем пробелов. Ретраи — только для транзиентных ошибок и с ключом идемпотентности (backendbytes, swarms, compilenrun).
8. **План лучше делать данными и проверять до запуска.** JSON со схемой и валидацией надёжнее XML с разбором регулярками; качество плана — единая точка отказа всей системы (swarms, cookbook, glukhov, compilenrun).
9. **Верификация должна быть структурной.** Инструкция «перепроверь себя» под давлением контекста пропускается, отдельный проверяющий с чистым контекстом — нет. Проверяющий по умолчанию склонен одобрять, поэтому рубрика требует доказательств; проверяется только то, что в неё включено (claude-cookbooks, swarms, microsoft-azure, glukhov).
10. **Синтез — не конкатенация.** Оркестратор должен разрешать противоречия между воркерами. В учебном ноутбуке cookbook синтеза нет вовсе, и воркеры в его примере противоречат друг другу (vantaige, glukhov, compilenrun, claude-cookbook-orchestrator-workers).
11. **Сильная модель — на план, проверку и синтез, дешёвая — на массовую работу.** В замере из cookbook 84–98% входных токенов шли по ставке дешёвого воркера. У дробления есть оптимум: каждый поток несёт фиксированные накладные расходы, и слишком мелкая нарезка увеличивает счёт (claude-cookbooks, swarms, compilenrun, vantaige).
12. **Стоимость высока и плохо сопоставима между источниками.** Данные Anthropic: около 4× токенов чата у одного агента и около 15× у мультиагентной системы. Множители glukhov (2–3× для orchestrator-worker) даны без источников и от другой базы (backendbytes, compilenrun, glukhov).
13. **Параллельные воркеры безопасны на чтении.** Параллельные правки конфликтуют, общее изменяемое состояние — антипаттерн (compilenrun, microsoft-azure). Vantaige при этом приводит «по воркеру на файл» как норму — см. [расхождения](#расхождения-между-источниками).
14. **Инструменты важнее промпта.** Описания инструментов и их разграничение по ролям дают больше, чем длинный системный промпт; ограниченный набор инструментов — ещё и граница безопасности (anthropic, claude-cookbooks, microsoft-azure).
15. **Наблюдаемость закладывается с первого дня.** Первым логируется план; дальше — span на каждого воркера, токены по агентам, доля токенов оркестратора как ранний сигнал перегруза (vantaige, backendbytes, metacto, glukhov).
16. **Реальные системы комбинируют паттерны.** Топология, механизм исполнения (конечный автомат, durable execution) и транспорт (один процесс или A2A) — независимые решения (microsoft-azure, glukhov, metacto).

### Выводы из референсов для Меркурия

Получены из конспектов референсных репозиториев; продолжают нумерацию.

17. **Любое действие агента идёт через один конвейер:** очистка → проверка → политика → подтверждение → квота → запуск → журнал. Одна и та же строка описания действия видна политике, человеку и журналу (ssh-mcp).
18. **«Безопасно по умолчанию» не работает.** В `ssh-mcp` всё нераспознанное считается безопасным, и за пять версий подряд вышло пять исправлений одного вида: опасная команда в непривычном написании. Интерактивная сессия обходит классификацию вовсе (ssh-mcp).
19. **Запрет, записанный только в промпте, — не запрет.** В трёх примерах Anthropic ограничение держится на тексте, а обработчик действие выполнит. Проверка должна стоять в инструменте (claude-cookbooks).
20. **Подтверждение — приостановленный вызов инструмента.** Его идентификатор — токен возобновления: кладётся в кнопку, ожидание живёт в журнале и переживает перезапуск (claude-cookbooks).
21. **Каждому ограничителю нужна пара «стоп и сигнал».** Потолок расходов — пауза, а не ошибка: после поднятия лимита работа продолжается. Стоп без сигнала обрывает молча (claude-cookbooks).
22. **Память — хранилище атомарных фактов**, а не журнал разговоров: у факта доверие, происхождение (сказано, подтверждено, выведено агентом), источник и история версий (hermes-plugin-holographic).
23. **В промпт идёт не «топ похожих», а то, что прошло гейт релевантности.** Болтовня не вспоминает ничего; вспомненное помечается как данные, а не инструкции, и проверяется и при записи, и на выходе (hermes-plugin-holographic).
24. **Поиск по памяти в первую очередь лексический.** Качество держится на анализе слов (стемы, однокоренные, ключевые слова, которые агент дописывает при записи), а не на векторах: HRR — одно из трёх слагаемых оценки, эмбеддинги выключены по умолчанию (hermes-plugin-holographic).
25. **Память меняется пятью разными действиями, а не перезаписью:** изменить, завершить, исправить, слить, забыть. Забывание окончательное, с отпечатками, чтобы фоновые задачи не вернули забытое (hermes-plugin-holographic).
26. **В консолидации код считает, модель формулирует, человек решает спорное.** Отбор, оценки, пороги и паузы — чистая функция без модели; нет работы — модель не запускается (hermes-dreaming).
27. **Подтверждают только люди.** Долговременной памяти заслуживает то, что человек повторял в разные дни; машинный текст и выводы агента подтверждением не считаются (hermes-dreaming).
28. **Память — канал внедрения инструкций во все будущие сессии.** Консолидатору не дают сеть и оболочку, рабочие сессии читают память без права записи (claude-cookbooks, hermes-dreaming).
29. **Версия промпта неизменяема, меняется только указатель на неё.** Продвижение — смена номера после проверки, откат — возврат номера; оценку считать по категориям задач (claude-cookbooks).
30. **Кеш промпта — первый рычаг стоимости.** Изменчивое идёт в хвост; модель и набор инструментов посреди сессии не меняются; живые числа в системном блоке ломают кеш (claude-cookbooks, hermes-plugin-holographic).
31. **Сетевой слой строится вокруг одного интерфейса — `SocketConnector`.** Через него стыкуются VLESS, прокси и SSH, включая SSH поверх VLESS (amphp-vless, amphp-ssh).
32. **У библиотек есть пробелы, которые закрываем сами:** в `amphp-ssh` нет SFTP, таймаутов, keepalive, пула и надёжной остановки команды; `amphp-vless` не поддерживает REALITY и Vision и не содержит клиентов HTTP- и SOCKS5-прокси (amphp-ssh, amphp-vless).

## Расхождения между источниками

- **Классификация.** Anthropic — пять workflow-паттернов и агент. Microsoft — sequential, concurrent, group chat, handoff, magentic; паттерна с именем orchestrator-worker у них нет. Metacto и glukhov — топологии (orchestrator-worker, supervisor, hierarchical, swarm, mesh), причём metacto считает sequential/parallel отдельным слоем, а не паттерном. Единой терминологии нет.
- **Supervisor.** Vantaige считает его той же ролью, что orchestrator; metacto и compilenrun — отдельным паттерном с пошаговым планированием.
- **Синтез и обратная связь.** У Anthropic и Swarms оркестратор синтезирует результат; в cookbook синтеза нет. Compilenrun включает цикл «проверка → дополнительный раунд» в паттерн; vantaige настаивает на однонаправленном потоке.
- **Масштаб.** Cookbook — 2–3 воркера последовательно; compilenrun — потолок 5; glukhov — переполнение контекста уже при 4+ и иерархия после 5; swarms — сотни параллельно (до 1000).
- **Одноранговые передачи.** Metacto называет swarm самым опасным в эксплуатации (не более 2–5 агентов); Microsoft описывает handoff как штатный паттерн для поддержки клиентов.
- **Фреймворки.** Anthropic советует начинать с прямых вызовов API; swarms и Microsoft продвигают готовые классы и платформы.
- **Параллельная запись.** Vantaige допускает воркера на файл; compilenrun (со ссылкой на Cognition) предостерегает от параллельных правок.
