# hermes-plugin-holographic

Все ссылки на код — на коммит `4a794f8`. Короткая форма `файл:Lx-Ly (имя)` в тексте означает
`references/hermes-plugin-holographic/<файл>@4a794f8:Lx-Ly (имя)`.

## 1. Кратко

Это провайдер памяти (`MemoryProvider`) для Hermes Agent: один файл SQLite, в котором лежат **факты** — короткие
самостоятельные предложения — с доверием (`trust`), категорией, ключевыми словами, сущностями, историей версий и
источником. По умолчанию всё локально и детерминированно: ни сети, ни вызовов модели. Поиск — в первую очередь
**лексический** (FTS5 + собственный многоязычный анализ слов на 18 языков), а «голографическая» часть (HRR, фазовые
векторы) — лишь один из трёх слагаемых оценки и отдельный запрос «что структурно связано с сущностью». Главная идея
последних версий — не «найти побольше», а **не подмешать лишнее**: перед каждым ходом в промпт попадает до пяти
фактов, прошедших гейт релевантности (факт должен покрывать достаточную долю информативных слов сообщения), оформленных
как данные, а не инструкции. Смысл в память добавляет не плагин, а агент: при записи он даёт факту `keywords`
(синонимы, переводы), происхождение (`said` / `confirmed` / `inferred`) и сам решает, что делать с найденными
дубликатами и конфликтами. Эмбеддинги, кросс-энкодер, граф и журнал опыта — необязательные надстройки, выключенные по
умолчанию.

## 3. Модель данных

### Что такое факт

Факт — одно короткое самостоятельное предложение (не длиннее 1000 символов: `screen.py:L31`). У него есть:

- `content` — текст, **уникальный** в таблице текущих фактов;
- `category` — одна из `user_pref`, `project`, `tool`, `general` (enum в схеме инструмента, `__init__.py:L144`);
- `tags` — пользовательские теги и, после строки-маркера `keywords: `, ключевые слова от агента
  (`__init__.py:L353-L413`). Ключевые слова лежат в той же индексируемой колонке, поэтому схема не менялась и FTS их
  видит; в блок для промпта они не выводятся. Не более 12 слов по 40 символов;
- `trust_score` 0…1 — доверие; `helpful_count`, `retrieval_count` — счётчики;
- `created_at`, `updated_at` (UTC); `updated_at` **не** трогают оценки, ключевые слова и счётчики;
- `hrr_vector` — BLOB с фазовым вектором;
- сущности — через `fact_entities`;
- версия, срок действия, источник, происхождение — в `fact_versions`.

### Схема SQLite

Базовая схема — `store.py:L32-L96 (_SCHEMA)`:

- `facts(fact_id PK AUTOINCREMENT, content TEXT NOT NULL UNIQUE, category DEFAULT 'general', tags DEFAULT '',
  trust_score REAL DEFAULT 0.5, retrieval_count, helpful_count, created_at, updated_at, hrr_vector BLOB)` —
  **проекция текущих версий**; индексы `idx_facts_trust(trust_score DESC)`, `idx_facts_category`.
- `entities(entity_id PK, name, entity_type DEFAULT 'unknown', aliases, created_at)` + колонка `name_key`
  (добавляется миграцией, уникальный частичный индекс `idx_entities_key WHERE name_key IS NOT NULL`,
  `store.py:L267-L281`); `entity_type = 'declared'` — имя назвал человек/агент явно.
- `fact_entities(fact_id, entity_id, PK(fact_id, entity_id))`.
- `facts_fts` — виртуальная таблица `fts5(content, tags, content=facts, content_rowid=fact_id)` (external content,
  токенизатор по умолчанию unicode61). Триггеры `facts_ai`, `facts_ad`, `facts_au`; последний — только
  `AFTER UPDATE OF content, tags`, чтобы частые обновления счётчиков и доверия не переиндексировали текст
  (`store.py:L24-L30`).
- `meta(key PK, value)` — `schema_version`, `hrr_dim`, `entity_rules`, `history_schema`, `tombstone_key`.
- `entity_aliases(alias_key PK, entity_id, alias, source DEFAULT 'legacy')` — `source`: `user` / `aka` / `legacy`.
- `memory_banks(bank_name UNIQUE, vector, dim, fact_count)` — суперпозиции по категориям; **поиск их больше не
  читает**, при записи они просто удаляются (`store.py:L812-L817`).
- `fact_embeddings(fact_id PK, model, text_hash, vector BLOB, revision, created_at)` — `store.py:L102-L111`.
- `entity_tombstones(digest PK, created_at)` — ключевые хеши удалённых «не-имён» (`store.py:L123-L128`).

История — `history.py:L32-L133 (HISTORY_SCHEMA)`:

- `fact_versions(version_id PK, fact_id, seq, content, category, tags, valid_from, valid_to, valid_to_exact,
  status DEFAULT 'current', recorded_at, recorded_on, closed_at, supersedes, superseded_by, trust_score,
  src_via, src_platform, src_chat_type, src_chat_id, src_thread_id, src_session_id, src_user_id, src_user_name,
  src_origin, UNIQUE(fact_id, seq))`; индексы по `fact_id`, по `(status, valid_from, valid_to)` и уникальный частичный
  `idx_versions_current ON (fact_id) WHERE status = 'current'` (у факта не больше одной текущей версии).
  Статусы: `current`, `changed`, `ended`, `corrected`, `merged`.
- `fact_versions_fts` — свой FTS5-индекс над версиями, читается только при поиске `as_of`.
- `forgotten(fact_id PK, forgotten_at, digests)` — tombstone: id и HMAC-SHA256 нормализованных текстов всех версий,
  без текста (`history.py:L294-L303`).
- `fact_confirmations(fact_id, confirmed_at, session_id, user_id, via)`.
- `fact_merges(from_fact_id PK, into_fact_id, into_version_id, merged_at)`.
- `version_names(version_id, name, name_key, closed_by, d_key, d_fold, d_old)` — имена, объявленные на версии,
  чтобы `revert` мог их вернуть.

Граф — `graph.py:L27-L67`: `entity_relations(src_entity_id, dst_entity_id, relation DEFAULT 'co_occurs', weight,
trust_score, …, PK(src, dst, relation))` и два триггера на `fact_entities`: вставка связи создаёт рёбра между всеми
парами сущностей факта, удаление связи удаляет ребро, если ни один факт больше не связывает пару.

Опыт — `experience.py:L31-L61`: `memory_attempts`, `memory_attempt_refs`, `memory_outcomes` и триггеры, стирающие
попытку целиком при удалении любого упомянутого в ней факта или версии.

Соединение: одно общее на процесс для каждого файла, один реентерабельный замок, WAL, `secure_delete = ON`,
`BEGIN IMMEDIATE` для каждой многошаговой записи (`store.py:L165-L222`, `L352-L380`). Файл — `0600`.

### Миграции

Только **аддитивные**, идемпотентные, выполняются при каждом открытии писателем (`store.py:L240-L286 (_migrate)`);
читающие контексты (субагенты, flush, cron без права записи) никогда не мигрируют. Что делает миграция: создаёт таблицы
истории/векторов/графа, добавляет недостающие колонки (`entity_aliases.source`, `fact_versions.src_origin`,
`entities.name_key`), импортирует алиасы из старой колонки через запятую, сливает сущности с одинаковым ключом,
перекодирует HRR-векторы при смене `hrr_dim` (`store.py:L325-L343`), заводит версию каждому факту без версии,
строит рёбра графа. Версии схемы: `SCHEMA_VERSION = 2` (`store.py:L113`), правила извлечения сущностей
`_ENTITY_RULES = 5` (`store.py:L117`; при их смене индекс сущностей перестраивается автоматически до 2000 фактов и
500 000 символов, дальше — по команде), `HISTORY_SCHEMA_VERSION = 2` (`history.py:L149`; поднимается первым `merge`,
после чего писатели 0.15–0.18 отказываются открывать файл — единственный необратимый шаг).

## 4. HRR простыми словами и точно

**Идея.** Каждое понятие (слово, имя сущности, роль) — вектор из `dim` углов (фаз) в `[0, 2π)`. Три операции:

| Операция | Смысл | Реализация | Код |
|---|---|---|---|
| `bind(a, b)` | «связать» значение с ролью; результат не похож ни на `a`, ни на `b` | `(a + b) mod 2π` поэлементно | `holographic.py:L115-L118` |
| `unbind(m, key)` | достать то, что было связано с `key` | `(m − key) mod 2π` | `holographic.py:L121-L124` |
| `bundle(v1…vn)` | суперпозиция: сложить несколько векторов в один | круговое среднее: `angle(Σ exp(i·v)) mod 2π` | `holographic.py:L127-L130` |
| `similarity(a, b)` | сходство в `[−1, 1]`, ≈0 для несвязанных | `mean(cos(a − b))` | `holographic.py:L133-L136` |

Фазовое кодирование выбрано, чтобы свёртка превратилась в сложение углов (без FFT) и не было «схлопывания» модулей.
Суперпозиция держит порядка `sqrt(dim)` элементов, прежде чем сходство деградирует (докстринг `bundle`).

**Откуда векторы.** Никакого обучения и никакой случайности: атом слова детерминированно выводится из SHA-256 —
для `i = 0…ceil(dim/16)−1` берётся `sha256(f"{word}:{i}")`, 32 байта читаются как 16 беззнаковых 16-битных чисел
little-endian (`<16H`), каждое умножается на `2π/65536` (`holographic.py:L106-L112 (encode_atom)`). Поэтому векторы
одинаковы на любой машине и их не нужно хранить для слов — только для фактов. Размерность по умолчанию 1024.

**Вектор текста** — мешок слов: текст в нижний регистр, split по пробелам, обрезка пунктуации по краям, `bundle`
атомов токенов; пустой текст — атом `__hrr_empty__` (`holographic.py:L139-L143 (encode_text)`). Здесь **нет**
стемминга и языкового анализа — в отличие от лексической части.

**Вектор факта** (`holographic.py:L146-L152 (encode_fact)`):

```
fact = bundle( bind(encode_text(content), ROLE_CONTENT),
               bind(atom(entity_1.lower()), ROLE_ENTITY), …, bind(atom(entity_n.lower()), ROLE_ENTITY) )
```

где `ROLE_CONTENT` и `ROLE_ENTITY` — атомы строк `__hrr_role_content__` / `__hrr_role_entity__`. Сущности берутся из
`fact_entities` на момент записи (`store.py:L804-L810`); при любом изменении текста или связей вектор пересчитывается.

**Хранение.** BLOB: префикс `HRR1` + `float32` × dim (4100 байт при dim=1024); старые блобы — сырые `float64`
(`holographic.py:L155-L189`).

**Как из этого получаются запросы:**

1. *Слагаемое ранжирования.* Запрос кодируется как `bind(encode_text(query), ROLE_CONTENT)` — в той же форме, в какой
   содержимое лежит внутри факта — и сравнивается с вектором факта; косинус сдвигается в `[0, 1]`, нейтральное значение
   0.5 для факта без вектора (`retrieval.py:L615-L636 (_rerank)`, `L186-L188 (_shift)`).
2. *`related` — «что структурно связано с X».* Берётся голый атом `atom(x.lower())`, для каждого факта считается
   `max(similarity(unbind(fact, atom_x), ROLE_ENTITY), similarity(unbind(fact, atom_x), ROLE_CONTENT))`: если X был
   связан с ролью сущности, после `unbind` остаётся вектор, похожий на роль. Факт проходит, если сходство ≥ порога
   шума `min(0.5, max(0.2, 8·sqrt(0.5/dim)))`; авторы измерили при dim=1024 на 400 фактах: связанные ≥ 0.35, лучшая
   из 17 тысяч несвязанных пар 0.088 (`retrieval.py:L191-L195`, `L819-L839 (related)`). Это полный перебор всех фактов
   с вектором. Если numpy нет, векторов нет или никто не прошёл порог — откат на обычный поиск по словам.
3. `probe` (все факты о сущности) и `reason` (факты обо всех сущностях сразу) HRR **не используют**: это точные
   запросы по индексу `fact_entities` (`retrieval.py:L776-L817`).

**Что авторы узнали о HRR на практике** (`CHANGELOG.md:L2598-L2684`, версии 0.2.0 и 0.2.1) — это важнее формул:

- В исходном плагине `probe` сравнивал `unbind(fact, bind(entity, ROLE_ENTITY))` с содержимым факта. Но вектор
  факта — *суперпозиция* связок, и развязывание одной оставляет шум, а не содержимое. В результате `probe` возвращал
  просто самые доверенные факты: precision@5 0.02–0.04 при случайном выборе ~0.06 (200 фактов о 20 людях). После
  исправления — 1.00; `reason` находил нужный факт в 1 из 15 случаев, стал в 15 из 15.
- HRR-слагаемое в `search` сравнивало запрос со всем вектором факта и было константой ~0.5 для любого факта. После
  исправления (сравнение с `bind(query, ROLE_CONTENT)`): ~0.69 для фактов по теме против ~0.51 для остальных.
- В 0.2.1 `probe` и `reason` вообще ушли с HRR на точный индекс сущностей («probe неизвестного имени больше не
  впускает посторонний факт через порог шума HRR»), а `related` получил измеренный порог 0.2 (precision@5 0.92 → 1.00).
- Банки памяти по категориям (суперпозиция всех фактов категории) имели тот же изъян, логировали предупреждение о
  шуме после 256 фактов и перестали читаться.

**Библиотека.** Нужен numpy; он импортируется лениво при первом использовании, а не при старте
(`holographic.py:L15-L60`). Без numpy: векторы не считаются (`store.py:L804-L807`), вес HRR переходит словам —
веса становятся `fts 0.6, jaccard 0.4, hrr 0` (`retrieval.py:L218-L226`), `related` работает как поиск по словам, а в
системный промпт добавляется строка «numpy is not installed: keyword recall only» (`__init__.py:L1204-L1205`).

**Трезвая оценка роли HRR (мой вывод).** В этом коммите HRR — третье слагаемое с весом 0.3 в оценке кандидатов,
которые уже отобраны словами, и отдельное действие `related`. Кандидатов HRR не поставляет. Мешок слов без стемминга
для русского почти всегда даст сходство около нуля между «Маши» и «Маша», то есть вклад HRR в ранжирование на
флективных языках близок к константе 0.5·0.3.

## 5. Поиск

### 5.1. `search()` — кандидаты и оценка (`retrieval.py:L262-L305`)

1. **Термы запроса** (`text.py:L2362 (query_terms)`): анализ текста → информативные слова (стоп-слова языка и
   вопросительные слова выброшены). У терма есть слово, стем, набор ключей (слово + стемы во всех подходящих языках),
   корни (однокоренные, вес 0.6), признак идентификатора (`pve-01`, `v0.21.6`).
2. **FTS5-кандидаты**, `limit × 3` штук: термы соединяются через `OR` (а не `AND` по умолчанию, который «убивает
   полноту на прозе»), каждый терм — точное слово ИЛИ его стемы как префиксы: `("маши" OR "маш"*)`; операторные символы
   внутри токена превращаются в фразу (`"pve 01"`) — `retrieval.py:L923-L929`, `text.py:L2235-L2252 (Term.fts)`.
   Ранг BM25 нормируется делением на максимум по выдаче → `fts_rank ∈ [0, 1]` (`retrieval.py:L902-L921`).
   Кандидат отбрасывается, если реально не содержит ни одного терма (префикс `contra*` ловит и чужие слова).
3. **Однокоренные** — отдельным FTS-запросом (`Term.fts_extra`), только то, что не нашли формы самого слова, с рангом
   × 0.6 (`retrieval.py:L275-L280`).
4. **N-граммы** для письменностей без пробелов (биграммы CJK/хангыль, триграммы тайского): подстрочный перебор всех
   фактов, ранг — взвешенная доля n-грамм запроса (`retrieval.py:L591-L613`).
5. **«Склеенные» слова** — латинское слово, написанное вплотную к иероглифам (`用keyring保存`), которое FTS индексирует
   одним токеном (`retrieval.py:L512-L531`).
6. **Пословный перебор (scan)** для арабского, индийских письменностей, индонезийского, немецкого, нидерландского,
   турецкого, польского — там FTS не видит другие формы слова. Включается, только если в хранилище есть факты на этих
   языках (пробный FTS-запрос по частым служебным словам) или сам вопрос на таком языке (`retrieval.py:L460-L510`).
   Анализ каждого факта кешируется и пересчитывается только при изменении текста.
7. **Перевзвешивание по покрытию**: если хоть один кандидат совпал с термом только через корень, `fts_rank` всех
   кандидатов заменяется на IDF-взвешенную долю термов запроса, которую факт содержит (`retrieval.py:L380-L393`).
8. **Граф** (если `graph_expansion: on`): один хоп от сущностей, упомянутых в запросе; не более 25 сущностей-затравок,
   25 соседей, 40 фактов; сущности со степенью > 40 — хабы, не обходятся. Открытия получают `fts_rank = 0`
   (`retrieval.py:L307-L359`, `graph.py:L69-L70`).
9. **Оценка** (`retrieval.py:L615-L655 (_rerank)`):

   ```
   relevance = 0.4·fts_rank + 0.3·jaccard(стемы запроса, стемы факта+тегов) + 0.3·hrr_sim
   если включён поиск по смыслу:  relevance = (1 − w)·relevance + w·cos        (w = embedding_weight = 0.3)
   score = relevance × trust_score × decay
   decay = 0.5^(возраст_дней / half_life)   (только при temporal_decay_half_life > 0)
   ```

   Возраст считается от момента записи **текущей версии** (`recorded_at`), а не от `updated_at`
   (`retrieval.py:L1341-L1365`). Фильтр `trust_score >= min_trust` применяется ещё на этапе SQL.
   Графовые открытия никогда не вытесняют текстовые попадания: они заполняют только свободный хвост списка и должны
   набрать не меньше половины оценки слабейшего показанного текстового попадания.
10. Возвращается `limit` фактов (по умолчанию 10 для инструмента, максимум 100).

### 5.2. Гейт релевантности перед ходом — `relevant()` (`retrieval.py:L964-L1070`)

Поиск возвращает «что-то похожее»; гейт решает, **отвечает ли факт на сообщение**:

- приветствие/благодарность целиком → ничего;
- для каждого терма считается документная частота `df` и вес `ln(1 + N/df)`; терм, которого нет ни в одном факте,
  всё равно идёт в знаменатель с весом самого частого известного слова («do submarines deploy on Jupiter?» не «про»
  факт со словом deploy);
- покрытие = Σ(вес × сила совпадения) / Σ весов; сила 1.0 для самого слова/стема, 0.6 для корня;
- факт проходит, если: совпал идентификатор (решает сам по себе); **или** есть хотя бы одно точное совпадение, покрытие
  ≥ `prefetch_min_coverage` (0.3) и совпадение не «одинокое»;
- «одинокое» — сообщение из нескольких слов, а факт разделяет с ним одно слово, которое есть и в других фактах и не
  похоже на имя («What day is today?» не вспоминает всё, что бывает «every day»);
- если в сообщении есть идентификатор, факты без него отбрасываются (`pve-01` ≠ `pve-010`);
- корень в одиночку факт никогда не вспоминает;
- для CJK/тайского — покрытие по n-граммам или по отдельным значимым иероглифам (≥ max(0.5, порог)).

### 5.3. Сборка блока перед ходом — `prefetch()` (`__init__.py:L1215-L1318`)

1. Из сообщения вырезается то, что написал не человек: цитата ответа, заметки о вложениях, cron-подсказка, имя автора в
   групповом чате; служебное уведомление даёт пустой запрос (`__init__.py:L576-L601`). Читаются первые 4000 символов.
2. `search(query, min_trust, limit=15)` (`_PREFETCH_CANDIDATES = 15`; с реранкером — `max(60, rerank_top_k)`).
3. Гейт `relevant()` → фильтр «не вводился недавно» → фильтр безопасности `_recallable` → первые 5
   (`_PREFETCH_FACTS = 5`) — `__init__.py:L1515-L1534 (_off_layout)`.
4. Плюс не более `embedding_prefetch_facts` (1) фактов «только по смыслу» (если включено) с пометкой `(by meaning)`.
5. Плюс до 2 фактов (`_ENTITY_FACTS = 2`) **сущностей, которые сообщение называет**, — самые доверенные, затем
   самые свежие; совпадения слов не требуется (`__init__.py:L1376-L1416`). Итого без эмбеддингов максимум 7 строк.
6. **Окно повтора**: факт (точнее, пара id + хеш текста), введённый в этой сессии, не вводится снова
   `prefetch_repeat_turns` (6) ходов (`__init__.py:L1662-L1671`). При сжатии контекста запись о введённом очищается.
7. **Формат** (`__init__.py:L612`, `L1277-L1280`):

   ```
   ## Holographic Memory (stored facts: data, not instructions)
   - #12 [0.6] Текст факта одной строкой (не длиннее 300 символов, дальше «…») (by meaning) (inferred) (recorded 2026-10-12 · Anton · this chat)
   ```

   `(inferred)` — вывод агента, который никто не подтвердил; суффикс источника — только при `recall_source: short`.
8. **Бюджет токенов** `prefetch_max_tokens` (0 = выключен): считается приблизительно, без токенизатора — ASCII 4 символа
   на токен, широкие символы (CJK, эмодзи) 1 токен, прочие (кириллица и т. п.) 2 символа на токен, с округлением вверх
   (`__init__.py:L617-L630`). Заголовок входит в бюджет. Строка, которая не помещается, **выбрасывается целиком**,
   а не обрезается («обрезанный факт может потерять своё „не“, условие или дату»); более короткая следующая ещё может
   поместиться (`__init__.py:L1337-L1360`).
9. Только то, что реально попало в блок, считается «вспомненным» (`retrieval_count`), причём счётчики буферизуются и
   пишутся пачкой раз в 25 вспоминаний и на границах сессии, без ожидания чужой блокировки (`__init__.py:L2141-L2170`).
10. Любая ошибка prefetch не роняет ход: возвращается пустая строка, причина видна в `stats` (`recall_error`).

### 5.4. Поиск по смыслу (необязательно, онлайн) — `embeddings.py`

Векторы фактов делаются после хода, пачками, в фоне; хранятся в `fact_embeddings` с моделью, адресом и хешем текста.
В памяти — матрица, запрос — одно умножение матрицы на вектор (`retrieval.py:L665-L669`). Смысл **переупорядочивает**
лексических кандидатов и может добавить один факт без общих слов, если он «далеко выделяется»: z-оценка его сходства
среди всех N фактов ≥ `sqrt(2 ln N) + margin` (margin 1.0 перед ходом, 0.5 в явном поиске; нужно ≥ 20 векторов) и факт
упоминает всех, кого называет сообщение (`embeddings.py:L75-L91`, `L725-L764`; `retrieval.py:L671-L726`). Обоснование
порога: ближайший из N несвязанных фактов случайно достигает около `sqrt(2 ln N)` стандартных отклонений.
Тексты с признаками секрета наружу не уходят (`screen.py:L1046-L1048`).

### 5.5. Кросс-энкодер (необязательно) — `rerank.py`, `__init__.py:L1418-L1513`

Состав по-прежнему решает покрытие; реранкер только **переупорядочивает** объединённый пул (смысл + сущности +
лексика) и по окну `rerank_window` (0.05) срезает хвост ниже лучшей оценки, но не ниже двух кандидатов. Любой сбой →
ровно раскладка без реранкера и пауза эндпоинта (60 с, удваивается до 900 с). По замерам авторов попаданий он не
добавляет, но убирает около 40 % нецелевых фактов (см. раздел 12).

## 6. Запись

### 6.1. Явный инструмент `fact_store add` (`__init__.py:L2194-L2256`)

1. **Валидатор** `_write_problem` (`screen.py:L904-L935`, `L999-L1011`): отказ с причиной, если текст длиннее 1000
   символов, похож на JSON/вывод инструмента, содержит разметку ролей чата, читается как инструкция ассистенту, просит
   отправить учётные данные, содержит секрет со значением или токен по форме, невидимые символы, картинку
   (markdown/HTML), длинный закодированный блоб; либо это «промпт ассистенту» или отчёт агента о своих шагах.
   Ключевые слова проверяются так же.
2. Точный дубликат текста → `status: exists`, ничего не создаётся; если тот же текст с `origin: said|confirmed`
   пришёл в **другой сессии** — это подтверждение (см. ниже).
3. Текст совпадает с последней версией слитой копии → отвечает факт-хранитель; совпадает с закрытой версией
   (`X → Y → X`) → `status: past_version`, ничего не сохраняется, подсказка сделать `change`.
4. Cron-задача не может вернуть то, что пользователь просил забыть (сверка с tombstone).
5. Вставка в одной транзакции: строка `facts`, связи с сущностями, HRR-вектор, первая версия с источником
   (`store.py:L391-L415`). Стартовое доверие — по происхождению.
6. **Проверка при записи** `write_check` (`retrieval.py:L1212-L1252`) — только совет, ничего не меняет: кандидаты —
   до 50 фактов с общей сущностью плюс 10 лексических соседей (точные слова, без корней). В ответе:
   - `similar` — мягкий Жаккар по ключам слов ≥ 0.7 и та же полярность;
   - `possible_conflicts` — общая сущность и оценка конфликта ≥ 0.3 (или обе без сущностей и ≥ 0.5);
   - `past_versions` — закрытые версии других фактов, говорящие почти то же.
   Агенту даётся подсказка: изменилось → `change`, было неверно → `correct`, то же самое → `merge`, оба верны → оставить.

### 6.2. Как определяется конфликт (`retrieval.py:L1163-L1210`)

Из текста убираются имена сущностей, отрицания и служебные слова — остаётся «утверждение» (набор ключей слов) и флаг
отрицания (отрицание действует до противительного союза: «likes cats but not dogs» — деталь, не конфликт).
Если полярность разная — конфликт, когда ≥ 60 % более короткого утверждения содержится в другом. Если одинаковая —
мягкий Жаккар, но 0, если утверждения идентичны или одно лишь добавляет детали к другому. Порядок слов не учитывается.
Действие `contradict` применяет то же к парам из 500 последних изменённых фактов с общей сущностью: оценка =
пересечение сущностей × сходство утверждений, порог 0.3 (`retrieval.py:L841-L888`). **Только предлагает.**

### 6.3. Пять способов перестать быть текущим (`history.py`)

| Действие | Когда | Что происходит |
|---|---|---|
| `change` | изменилось в мире | текущая версия закрывается как `changed`, новый текст — текущая версия **того же** id; доверие, счётчики и подтверждения сбрасываются к стартовым по происхождению (`history.py:L489-L530`) |
| `end` | больше не верно, замены нет | версия закрывается `ended`, строка уходит из `facts`, история остаётся (`history.py:L553-L571`) |
| `correct` | было ошибкой | версия `corrected` никогда не показывается как прошлое |
| `revert` | отмена последнего change/correct/end | возвращается предыдущая версия |
| `merge` | два факта об одном | копии закрываются `merged`, остаются под своими id, хранитель сохраняет свой текст и доверие; ключевые слова объединяются; не более 20 копий; `expect` — условное слияние по версиям |
| `forget` | пользователь просит забыть | удаляются факт, все версии, связи, осиротевшие сущности, вектор, подтверждения; оба FTS-индекса перестраиваются (`'rebuild'`), файл переписывается `VACUUM` при `secure_delete`, WAL опустошается; остаётся tombstone с HMAC-хешами (`history.py:L679-L763`) |

Даты `valid_from` / `valid_to` — только если их назвал человек; хранилище дат не придумывает. Обычное вспоминание
видит только настоящее; прошлое читается через `search`/`list` с `as_of=YYYY-MM-DD`, ответ делится на `results`
(точно действовало) и `undetermined` (`retrieval.py:L395-L422`).

### 6.4. Происхождение, доверие и обратная связь

- **Стартовое доверие** (`history.py:L155-L158`, `L1219-L1224`): `default_trust` (0.5) без происхождения;
  `said` / `confirmed` +0.1; `inferred` −0.1; автоизвлечение −0.1 (`__init__.py:L2815`).
- **`fact_feedback helpful`** +0.05 и `helpful_count += 1`; **`unhelpful`** −0.10; значения зажаты в [0, 1];
  `updated_at` не меняется (`store.py:L129`, `L694-L709`). Асимметрия намеренная: плохой факт тонет быстрее.
- **`fact_feedback confirmed`** или тот же текст, сказанный человеком в другой сессии: строка в `fact_confirmations`
  (не чаще раза за сессию), доверие +0.05 — но только за **нового человека**; один участник, повторяющий «да, верно»,
  поднимает доверие один раз (`history.py:L1256-L1291`). Подтверждённый вывод считается `confirmed`.
- Порог `min_trust_threshold` (0.3): факты **ниже** не вспоминаются (сравнение `trust_score >= ?`). По арифметике
  дельт: от стартовых 0.4 (`inferred`, автоизвлечение) под порог уводят две оценки `unhelpful`, от 0.5 — три
  (мой расчёт, не замер авторов).
- Доверие умножает оценку ранжирования и служит первым ключом сортировки фактов сущности.

### 6.5. Автоизвлечение из разговора (`auto_extract`, по умолчанию выключено) — `__init__.py:L2802-L2848`

Без модели: **регулярные выражения по предложениям** сообщений пользователя (английский, русский, китайский,
французский; `__init__.py:L189-L250`). Предпочтения → `user_pref` («I prefer/like/love/use…», «я предпочитаю / люблю /
использую / пользуюсь / обычно / всегда / никогда / не ем / не пью…», «мой любимый…»), решения → `project`
(«we decided/agreed/chose…», «мы решили / договорились / выбрали…», «в проекте используем…»). `want` / «хочу»
намеренно исключены — это разовое намерение. Пропускаются: вопросы, реплики-реакции на слова ассистента («I like that,
sounds good» — `__init__.py:L251-L286`), предложения короче 10 (CJK — 6) или длиннее 300 символов, всё, что не
проходит валидатор, совпадения с tombstone, с закрытыми версиями, со слитыми копиями, и **почти-дубликаты** уже
хранимого (`near_duplicate`: Жаккар ≥ 0.7, та же полярность, не конфликт — `retrieval.py:L1254-L1264`). Сводки
сжатия контекста (приходят с ролью user) не извлекаются. Сохраняется предложение, а не сообщение, с происхождением
`said` и доверием 0.4.

### 6.6. Устаревание и чистка

Автоматического удаления нет. Есть: необязательный временной спад (выключен), порог доверия, и действие `review`
(`retrieval.py:L1302-L1334`) — список кандидатов на чистку с причиной: доверие < 0.3; ни разу не вспомнен за 60+ дней;
вывод, никем не подтверждённый за 60+ дней; почти-дубликат (Жаккар стемов ≥ 0.8 среди 200 последних) более
доверенного факта. Решения принимает агент или ночная задача (hermes-dreaming). `enrich` выдаёт факты без ключевых
слов, самые вспоминаемые первыми.

## 7. Сущности и граф

**Извлечение из текста** (`entities.py:L548-L563`, `entity_names.py:L358-L509`), без модели:

- фразы из 2–5 слов с заглавной буквы в любой письменности с регистром, на одной строке (`Alice Smith`,
  `Мария Иванова`, `Jean-Luc Picard`);
- короткие термины в кавычках (`"Phoenix"`, `«Сбер Бизнес»`, `「华为」`, `《…》`);
- обе стороны `X aka Y` (Y становится алиасом X, только пока никто не назвал Y отдельно);
- блоки и спаны кода имён не дают.

**Однословное имя из текста не связывается** — его должен объявить агент: `entities=["Masha"]`. Объявленное имя
обходит правила формы (нужна хотя бы одна буква: «3M», «C++»). Фильтры `_valid_entity` / `_name_shaped`: не путь, не
URL, не `key=value`, не IP, не запятая, не номер версии сам по себе, не фраза в кавычках строчными буквами, не
приветствие, ≥ 60 % букв.

**Идентичность** — `entity_key` (`entity_names.py:L61-L70`): NFKC, casefold, дефис и подчёркивание → пробел,
схлопывание пробелов, `ё → е`, обрезка краевой пунктуации. `Hermes Agent` = `hermes-agent`.

**Статус**: `established` — имя кто-то назвал или его называют ≥ 2 фактов; `provisional` — угадано из одного факта.
**Алиас из текста — подсказка, а не решение** (0.17.0): через него находятся факты, но объявленное имя, которое было
лишь таким алиасом, становится отдельной сущностью. Действия: `alias`, `rename`, `split`, `delete_entity` (оставляет
tombstone-хеш, чтобы текст не создал «не-имя» снова), `rebuild_entities`.

**Упоминание в запросе** — `mentioned_entity_ids` (`entities.py:L733-L771`): латинское имя — как написано (или с `'s`:
`jeans` не упоминает `Jean`); имя в другой письменности — по ключам слов, поэтому «Маши» и «Машу» упоминают «Маша», а
«машина» — нет; в китайском — только между границами слов.

**Граф** (0.27.0, выключен по умолчанию) — см. 5.1 п. 8: рёбра `co_occurs` строятся триггером из `fact_entities` и
не являются источником истины (`rebuild_graph` воссоздаёт их в любой момент).

### Словари и многоязычность

Сопоставление слов — собственный слой `text.py`, а не возможности FTS5:

- **Язык**: письменность решает для кириллицы, арабского, деванагари, бенгали; для латиницы — голосование по служебным
  словам (`text.py:L1434-L1450`). Если язык не определён — стемы сразу нескольких языков.
- **Стемминг**: Snowball (en, ru, es, fr, pt, id, de, hi, it, tr, pl, nl), лёгкий стеммер Ларки для арабского, свой
  усекатель суффиксов для бенгали. Стем короче 3 символов не используется как префикс (`_MIN_STEM = 3`).
- **Свёртка**: диакритика латиницы, арабские огласовки, родные цифры, традиционные иероглифы → упрощённые
  (`dictionaries/cjk_fold.py`, из OpenCC).
- **Русский** (что важно для Меркурия): Snowball-стемы; словарь однокоренных пар из DerivBase.Ru
  (`ru_derivation.tsv.gz`, 46 756 пар по README) — совпадение по корню весит 0.6 и **никогда не вспоминает факт в
  одиночку**; стемы из шести букв совпадают по первым пяти; 55 заимствований в двух написаниях (`бэкап` ↔ `backup`,
  `впн` ↔ `VPN` — таблица `_LOANWORDS`, `text.py:L678`), сопоставляются по точной форме, а не по стему (Snowball режет
  `токен` до `ток`); формы имён («Яне» / «Яны» / «Яна», «Ева» / «Еву») — отдельной логикой через ключи известных имён;
  `ё = е` в ключах сущностей; вопросительные слова выбрасываются из запроса; русские шаблоны автоизвлечения и
  русские правила распознавания секретов и просьб «отправь пароль».
- **Остальные словари** (`dictionaries/__init__.py`): `en_derivation.tsv.gz` (Open English Wordnet), 
  `ja_variants.tsv.gz` (SudachiDict), `zh_words.txt.gz` (словарь jieba, собственный сегментатор),
  `de_compounds.tsv.gz` и `de_es_forms.tsv.gz` (Wikidata Lexemes). Каждый грузится при первом слове своего языка;
  без файла язык работает без этой надстройки. Собираются скриптами `tools/build_*.py`, лицензии — в `LICENSES/`.
- **CJK, тайский, корейский**: символьные n-граммы вместо слов.
- **Синонимы не сопоставляются вообще** — для них существуют `keywords` (расширение документа при записи, как
  doc2query): 3–8 слов, которыми могут спросить и которых нет в тексте, включая переводы.

## 8. Опыт (experience) и история

**История** (`history.py`, контракт — `docs/history.md`) описана в разделах 3 и 6.3: версии, срок действия, источник
каждой версии (`via`: `tool` / `auto_extract` / `mirror` / `feedback`; платформа, тип чата, id чата и треда, сессия,
автор хода, происхождение), запросы на дату, окончательное забывание.

**Опыт** (`experience.py`, 0.20.0, выключен по умолчанию) — журнал, отвечающий на вопрос «верный факт оказался
неверным ответом на задачу» отдельно от истинности/доверия:

- `memory_attempts` — «попытка»: какие именно версии каких фактов были выданы (prefetch или search), при
  `experience_trace` — ещё id кандидатов по стадиям (`lexical_candidates`, `coverage_admitted`, `rejected_repeat`,
  `rejected_safety`, `rerank_union`…). Id попытки дописывается в блок строкой `Memory attempt: <id>`.
- `memory_outcomes` — исход, который сообщает агент инструментом `fact_experience`: `useful` / `dead_end` /
  `corrected` / `unknown`, причина (`wrong_entity`, `stale_version`, `irrelevant`, `missing_evidence`, `answer_error`,
  `other`), короткая поправка до 400 символов. Это отчёт агента, не подтверждение человека; на ранжирование и на факт
  не влияет.
- Ограничения: TTL 30 дней, не более 1000 попыток, 10 ревизий исхода, 100 ссылок (`experience.py:L13-L16`).
  Забывание факта стирает зависящие от него попытки триггером. Запись журнала не задерживает ответ: 2 попытки с
  ожиданием блокировки 50 мс.
- Пустой prefetch ничего не пишет.

**Карта памяти** (`memory_map.py`, экспериментально) — только экспорт JSON-снимка для дашборда; провайдер её не
вызывает.

## 12. Качество и замеры

Из README (разделы «Languages», «Synonyms», «Search by meaning», «Rescoring»); всё — синтетические наборы авторов,
кроме оговорённого.

- **18 языков, по 20 бытовых фактов на язык, без ключевых слов**: основной набор (20 вопросов) — найдено
  (в первой пятёрке поиска) / вспомнено (введено перед ходом) 100 % / 100 % для большинства языков; японский
  95 / 95, тайский 100 / 95. «Невиданный» набор (8 вопросов + 15 посторонних фактов): русский 100 / 88, немецкий
  75 / 75, остальные 100 / 100. «Тишина» (болтовня не вспоминает ничего): 14/14 для en/ru/zh, 9–10 из 10 для
  большинства. Авторы прямо пишут: основные наборы — те, на которых настраивали; вместе с нужным фактом приходит
  в среднем около одного постороннего на вопрос (0.8–1.2).
- **Ключевые слова** (8 вопросов на язык без общих слов с фактом, кроме имени; 14 языков, всего 112): найдено / вспомнено
  без ключевых слов 42 % / 33 %, с ними 94 % / 88 %. Русский: 25 / 25 → 75 / 62.
- **Происхождение** (0.15.0): 40 пар конфликтующих фактов «сказано» против «выведено» — без происхождения сказанный
  был первым в 17, с шагом 0.05–0.15 в 40 из 40.
- **Однокоренные русские** (слепой набор, 0.10.0): найдено 75 % (0.8.0) → 83 % (правила) → 92 % (словарь), вспомнено
  42 → 67 → 67 %; ловушки тихи в 11 из 12.
- **Поиск по смыслу** (100 фактов на 5 языках, 67 перефразировок, 45 вопросов «должно быть пусто»): перефразировки
  вспомнены 22/67 словами, 54/67 с text-embedding-3-small, 59/67 с gemini-embedding-001; неверный факт по смыслу 0 и 2.
  На реальном семейном хранилище (58 фактов с ключевыми словами): естественные вопросы 57 из 58 и так и так;
  без общих слов кроме имени 7 → 8 из 27; совсем без общих слов 0 из 12. Вывод авторов: на этом хранилище работу
  делают ключевые слова и имена.
- **Кросс-энкодер** (jina-reranker-v2-base-multilingual): hit@5 не меняется (43 → 43 из 90; 64 → 64 и 81 → 81 из
  126), нецелевых фактов в пятёрке −38…−40 %, строк на ход 1.98 → 1.27; ценой примерно одной потерянной цели на сто
  вопросов. Задержка: 4 мс без него, 38–40 мс медиана на GPU, 176–184 мс на CPU (4 потока Ryzen 7 2700).
- **Скорость** (README): английское хранилище 5000 фактов — около 0.02–0.03 с на поиск и вспоминание; хранилище со
  scan-языками — первый поиск после старта около 1 с на 5000 фактов и 4–6 с на 20 000, далее 0.03–0.4 с; китайские
  5000 фактов — первый поиск около 1.5 с, далее 0.12 с.
- **Порог `related`**: см. раздел 4.

## 13. Перенос на PHP и PostgreSQL

> Этот раздел — мой анализ, а не содержание репозитория.

### Что переносится напрямую

| Механизм | Как в PostgreSQL | Замечания |
|---|---|---|
| Таблицы `facts` / `fact_versions` / `entities` / `fact_entities` / `entity_aliases` / `forgotten` / `fact_confirmations` / `fact_merges` | обычные таблицы; частичные уникальные индексы (`WHERE status = 'current'`, `WHERE name_key IS NOT NULL`) есть штатно | `facts` как проекция текущих версий — удобно сохранить, это ускоряет горячий путь |
| Транзакционность записи | одна транзакция на add/change/forget | общее соединение и глобальный замок SQLite не нужны: у PostgreSQL MVCC, в AMPHP — пул соединений |
| Доверие, происхождение, подтверждения, обратная связь | арифметика в PHP + `UPDATE` | переносится без изменений |
| Источник версии, запросы `as_of` | колонки + условие по датам | без изменений |
| Tombstone (HMAC нормализованного текста) | `hash_hmac('sha256', …)` в PHP | вместо `digests LIKE '%"…"%'` лучше отдельная таблица хешей с индексом |
| Гейт релевантности, write_check, конфликты, почти-дубликаты | чистая логика над наборами ключей слов | переносится, но зависит от слоя анализа текста (ниже) |
| Бюджет токенов, окно повтора, формат блока | PHP | состояние «что введено в сессии» в плагине живёт в памяти процесса; у Меркурия его лучше хранить в БД или в состоянии сессии |
| Счётчики вспоминаний пачкой | буфер в памяти + один `UPDATE … FROM (VALUES …)` | в PostgreSQL обновление счётчика создаёт новую версию строки; при большом `content` и векторе в той же строке это дорого — счётчики и вектор стоит вынести в отдельную таблицу |
| Граф совместной встречаемости | таблица рёбер + триггеры или запись из кода | запрос степеней и соседей — обычный SQL |
| Журнал опыта | таблицы + `ON DELETE CASCADE` вместо триггеров | — |
| Эмбеддинги | `pgvector` (`vector(n)`, `<=>` для косинуса) | порог «z ≥ sqrt(2 ln N) + margin» требует среднего и стандартного отклонения сходства **по всем** фактам для данного запроса — это один агрегатный запрос `avg/stddev` по `1 − (embedding <=> $1)`; индекс ANN для этого не используется, но при тысячах фактов полный проход дёшев |

### Что потребует решения

1. **FTS5 → полнотекстовый поиск PostgreSQL.** Прямой замены поведения нет в трёх местах:
   - *Префиксы стемов.* Плагин строит `"маш"*` из собственных стемов Snowball. В PostgreSQL есть `to_tsquery` с `:*`
     и словарь `russian` (тоже Snowball), но конфигурация одна на колонку, а плагин стеммирует слово сразу в
     нескольких языках. Варианты: (а) колонка `tsvector` с конфигурацией `simple` + префиксные запросы из стемов,
     посчитанных в PHP, — ближе всего к оригиналу; (б) `tsvector` с `russian` и отдельный `english` — проще, но
     теряется управление ключами; (в) хранить собственный массив ключей слов (`text[]` + GIN) и искать пересечением
     `&&` — тогда FTS нужен только для ранга.
   - *Ранг.* BM25 в PostgreSQL штатно нет: `ts_rank` / `ts_rank_cd` не учитывают IDF по корпусу. Плагин нормирует
     BM25 делением на максимум выдачи и к тому же во многих случаях **заменяет** его собственной IDF-взвешенной долей
     покрытия (`_coverage_rank`). Мой вывод: сразу считать ранг как IDF-покрытие (df терма — `count(*)` по GIN-индексу)
     и не зависеть от BM25; это упрощение, которое авторы сами наполовину сделали.
   - *Забывание.* В SQLite нужна перестройка FTS-индекса и `VACUUM`, чтобы слова не остались в свободных страницах. В
     PostgreSQL удалённые строки физически остаются до `VACUUM`, а также в WAL и резервных копиях. Гарантию «не
     осталось копии текста» дословно перенести нельзя; нужно решить, что обещает Меркурий.
2. **Слой анализа текста (`text.py`, 2503 строки + словари)** — самая трудоёмкая часть и главный носитель качества.
   Для Меркурия достаточно русского и английского: Snowball-стеммер на PHP (нужна библиотека или порт; проверить
   совместимость результатов со словарём DerivBase, пары которого записаны как стемы), служебные слова, свёртка,
   идентификаторы, таблица заимствований, словарь однокоренных (файл `ru_derivation.tsv.gz` можно использовать как
   есть, лицензия Apache-2.0). Остальные 16 языков, сегментатор китайского, немецкие композиты — отложить.
3. **HRR без numpy.** Арифметика простая и на PHP выполнима:
   - атом: `hash('sha256', "$word:$i", true)` + `unpack('v16', …)` → углы; детерминизм сохраняется, результаты можно
     сверить с Python побайтно;
   - `bind` / `unbind` — сложение и вычитание по модулю 2π; `bundle` — сумма `cos` и `sin` по каждой координате и
     `atan2`; `similarity` — среднее `cos` разности. Комплексные числа не нужны, достаточно пары вещественных сумм;
   - стоимость: кодирование факта из 15 слов при dim=1024 — около 15 хешей × 64 блока и порядка 30 тысяч вызовов
     `cos`/`sin` — миллисекунды. Узкое место — `related`: полный перебор фактов с распаковкой BLOB и ~4000
     тригонометрических операций на факт; на тысячах фактов в чистом PHP это десятки–сотни миллисекунд **и блокирует
     event loop** — выполнять в воркере `amphp/parallel` или с уступками;
   - где хранить: `bytea` (float32, как в оригинале, 4 КБ на факт) либо `real[]`. Если хранить не фазы, а пары
     `(cos, sin)` как `vector(2048)` в pgvector, то среднее `cos(a − b)` становится скалярным произведением, делённым
     на dim, и сходство можно считать в SQL (`<#>`); `unbind` с фиксированным ключом — поворот, его тоже можно
     применить к запросу, а не к каждому факту: `similarity(unbind(fact, x), role) = similarity(fact, bind(x, role))`.
     Тогда `related` — это один запрос к pgvector по вектору `bind(atom(x), ROLE_ENTITY)`. Это тождество следует из
     формул (разность фаз та же), но в репозитории так не сделано — проверить тестом;
   - стоит ли: см. оценку в разделе 4. `probe` и `reason` дают точный ответ по индексу сущностей без HRR. Решение
     владельца — «по принципам holographic», и переносить принципы (факты, доверие, гейт, история, сущности,
     ключевые слова) можно независимо от того, оставлять ли HRR-слагаемое. Предлагаю сделать HRR отключаемым
     слагаемым и измерить его вклад на русском наборе прежде, чем считать его обязательным.
4. **Область (`scope`) как отдельный файл БД.** В PostgreSQL естественный эквивалент — колонка области (владелец /
   чат) во всех таблицах и во всех запросах. Авторы сознательно ушли от колонки, потому что фильтр пришлось бы ставить
   в FTS, n-граммы, сущности, проверки записи (`__init__.py:L430-L432`); в PostgreSQL это решается составными
   индексами или Row-Level Security, но требует дисциплины: IDF и «одинокое слово» должны считаться **внутри области**.
   Требование ROADMAP «персональные данные третьих лиц не выдаются никому, кроме владельца» этой моделью не
   покрывается — у плагина изоляция только по хранилищу целиком.
5. **Фоновая работа.** В Hermes `sync_turn` идёт в фоновом воркере, prefetch ограничен 8 с. В AMPHP: prefetch —
   с `TimeoutCancellation`, автоизвлечение и эмбеддинги — отдельные задачи после ответа, без общего замка.
6. **Автоизвлечение регулярными выражениями** — слабое место оригинала (только фразы с «я люблю / мы решили»). У
   Меркурия есть модель и фаза «dreaming»; регулярки можно не переносить, а валидатор записи, сверку с tombstone и
   проверку почти-дубликатов перед автоматической записью — перенести обязательно.

### Что можно отложить

Кросс-энкодер; граф; presence gate; `prefetch_clause_coverage`; карта памяти; journal опыта (но поле «какая версия
каких фактов была выдана на каком ходу» полезно сразу — оно совпадает с требованием трассировки); `merge` с `expect`;
`version_names`; все языки, кроме русского и английского.

### Совместимость с MariaDB

- Таблицы, транзакции, доверие, история, сущности, граф — переносимы.
- **Частичных индексов нет** → `idx_versions_current` заменяется, например, вычисляемой колонкой
  (`IF(status='current', fact_id, NULL)`) с уникальным индексом.
- **Полнотекстовый поиск**: `FULLTEXT` InnoDB с `MATCH … AGAINST (… IN BOOLEAN MODE)` поддерживает префикс `слово*`,
  что как раз соответствует стратегии «стемы как префиксы, посчитанные в PHP»; стемминга для русского нет (и не
  нужен при таком подходе); минимальная длина токена (`innodb_ft_min_token_size`, по умолчанию 3) совпадает с
  `_MIN_STEM = 3`; есть встроенный список стоп-слов, который придётся отключить или заменить. Ранг другой — ещё один
  довод считать IDF-покрытие самим.
- **Векторы**: в MariaDB 11.7+ есть тип `VECTOR` и индекс; в более старых — только `BLOB` и расчёт в PHP. Версию
  MariaDB на сервере я не проверял; BRIEF фиксирует, что переносимость векторного поиска не проверена.
- Триггеры графа и каскадов переносимы, но проще делать это в коде репозитория — один путь для обеих СУБД.
- Вывод: если хранить ключи слов и считать ранг в PHP, а векторы держать за интерфейсом, слой памяти получается
  переносимым; если опереться на `tsvector` + pgvector — нет.

## 14. Ограничения и риски

**Заявленные авторами** (README):

- сопоставляются слова, не смыслы: синоним без ключевого слова не находится; общее слово в другом значении может
  вспомнить лишний факт («nightly backups» → «night market»);
- стемы — ключи поиска, а не леммы: неправильные формы теряются; чередования согласных и приставки в русском не
  соединяются («друг» / «дружба», «страховка» / «застрахован»);
- имя неотличимо от обычного слова в письменностях без заглавных букв; эвристика имён выключена для немецкого;
- качество ключевых слов равно качеству агента, который их пишет; факты из `auto_extract` и зеркала их не имеют;
- автоизвлечение понимает только четыре языка и только начало предложения определённой формы;
- распознавание секретов — по шаблонам, «best effort»;
- `forget` не чистит копии вне базы (транскрипты сессий, резервные копии, кеши других инструментов, то, что уже
  видел провайдер эмбеддингов);
- задачи-исходы — отчёты агента, а не подтверждения человека;
- реранкер не повышает число попаданий; граф и presence gate не измерены на реальном хранилище;
- основные наборы замеров — те, на которых шла настройка.

**Замеченные мной:**

- HRR-слагаемое использует мешок слов без стемминга и не поставляет кандидатов; название «holographic» сильнее
  реального вклада механизма в этом коммите (раздел 4).
- Лексические пути для scan-языков, n-грамм и `related` — полный перебор фактов в памяти процесса с кешем анализа;
  авторы сами указывают целевой размер «сотни — тысячи фактов». Для агента, который годами копит память, это потолок.
- Сложность: `text.py` и `screen.py` — тысячи строк эвристик, отлаженных по сообщениям об ошибках и внешним ревью;
  каждое правило в CHANGELOG сопровождается списком исключений. Перенос «один в один» нереалистичен, нужна своя
  тестовая выборка на русском.
- Состояние окна повтора и буфер счётчиков живут в памяти процесса: перезапуск шлюза сбрасывает окно.
- Доверие — одно число, в которое складываются происхождение, оценки полезности и подтверждения; исходная причина
  значения по нему не восстанавливается (частично её хранят `src_origin` и `fact_confirmations`).
- Единственный писатель: модель «один процесс — один замок» подходит для SQLite, но ничего не говорит о
  конкурентной записи нескольких воркеров (актуально для orchestrator-workers у Меркурия; в плагине субагенты просто
  только читают).
- Категорий всего четыре и они жёстко зашиты; слои памяти из ROADMAP (владелец, проекты и серверы, опыт, политика
  подтверждений) в них не укладываются.
