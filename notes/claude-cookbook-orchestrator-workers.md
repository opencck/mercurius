# Orchestrator-Workers Workflow (Claude Cookbook) — конспект

## Кратко

Учебный рецепт из Claude Cookbook: минимальная реализация паттерна orchestrator-workers на Python поверх прямых вызовов API. Главный тезис: оркестратор-LLM анализирует конкретную задачу и во время выполнения решает, какие подзадачи отдать воркерам, чем паттерн и отличается от жёстко заданной параллелизации. Демонстрация — генерация нескольких вариантов маркетингового текста для одного продукта. Для разработчиков, которым нужен простой стартовый скелет паттерна и перечень его ограничений. Важно: в локальной копии сам код и тексты промптов не сохранились, остались их описание и вывод прогона.

Автор не указан.

## Ключевые идеи

**Определение (строки 15–19).** Центральная LLM анализирует каждую задачу и динамически определяет лучшие подзадачи для делегирования специализированным воркерам-LLM. Альтернативы, которым паттерн противопоставлен: ручные повторные промпты и «hardcoded parallelization that generates the same variations regardless of context».

**Отличие от параллелизации (строки 39, 63).** Подзадачи не заданы заранее, а определяются оркестратором по конкретному входу; решение принимается во время выполнения.

**Когда использовать (строки 43–45).**
- Задача требует нескольких различных подходов или точек зрения.
- Оптимальные подзадачи зависят от конкретного входа.
- Нужно сравнить разные стратегии или стили.

**Когда не использовать (строки 49–51, повтор в 267–269).**
- Простые задачи с одним результатом — лишняя сложность.
- Критична задержка — несколько вызовов LLM добавляют накладные расходы.
- Подзадачи предсказуемы и могут быть заданы заранее — использовать обычную параллелизацию.

**Две фазы (строки 57–61).**
1. Analysis & Planning: оркестратор получает задачу и контекст, анализирует, какие подходы ценны, и выдаёт структурированные описания подзадач в XML.
2. Execution: каждый воркер получает исходную задачу, тип и описание своей подзадачи и дополнительный контекст.

**Проектные решения (строки 84–87).**
- Промпты — шаблоны с переменными времени выполнения (`task`, `context`).
- XML как формат структурированного вывода (назван надёжным и удобным для языковых моделей).
- Воркеры получают и исходную задачу, и свои инструкции.
- Проверка, что воркер вернул непустой ответ.

**Заявленные преимущества (строки 246–249).** Адаптивность, гибкость (перенос в другой домен сменой промптов), структурированная координация через XML, устойчивость к ошибкам за счёт валидации.

**Где паттерн силён (строки 253–255).** Генерация контента с несколькими точками зрения (маркетинг, документация, художественные тексты); аналитические задачи с разными «линзами»; задачи, где стратегия декомпозиции зависит от самой задачи.

**Цифры.**
- Стоимость: N+1 вызов LLM — 1 оркестратор и N воркеров (строка 261).
- Промпт оркестратора просит 2–3 подхода (строка 107); в прогоне получено 3.
- Модель по умолчанию в `llm_call`: `claude-sonnet-5-5` (строка 73).

## Практика

**Код.** Заявлен Python (класс `FlexibleOrchestrator`, функция `parse_tasks()`, хелперы `llm_call` и `extract_xml`), но в локальной копии ни одного блока кода нет — только словесное описание:

- `llm_call(prompt, system_prompt="", model="claude-sonnet-5-5")` — отправляет промпт и возвращает текст ответа (строка 73).
- `extract_xml(text, tag)` — извлекает содержимое XML-тега регулярным выражением (строка 74).
- `parse_tasks()` — превращает XML оркестратора в список словарей с задачами (строка 91).
- `FlexibleOrchestrator.process()` — основная логика: вызов оркестратора, затем воркеров (строка 92).
- Валидация ответов для отлова пустых выводов воркеров (строка 93).

Полная реализация хелперов — по ссылке на `util.py` в репозитории `anthropics/claude-cookbooks` (строка 76).

**Промпты.** Сами тексты промптов в копии отсутствуют. Сохранились заметки о них (строки 107–109): оркестратору предлагается выдать 2–3 подхода с подсказкой по XML-структуре; воркер получает полный контекст (исходная задача, свой стиль, указания); оба промпта используют XML-разметку ради надёжного разбора.

**Пример вывода (строки 111–236).** Виден формат работы: блок анализа оркестратора, список подзадач вида «ТИП + описание», последовательный лог, затем результат каждого воркера. Полезно как образец того, что возвращает оркестратор.

**Стоимость и задержка (строки 259–263).** N+1 вызов; в этой реализации воркеры выполняются последовательно, по одному; для ускорения предлагается `asyncio` или пул потоков.

**Режимы отказа (строки 273–275).**
- Оркестратор может разбить задачу неоптимально — качество промпта критично.
- Воркеры могут вернуть пустой или некорректный ответ — обрабатывается валидацией.
- Разбор XML может сломаться, если модель не выдержала формат — предложено рассмотреть JSON.

**Что доработать (строки 281–284).** Параллельное выполнение воркеров через `asyncio`; ретраи для упавших воркеров; фаза синтеза, где LLM объединяет выводы воркеров; эксперименты с числом подзадач.

**Оптимизация цены (строка 291).** Claude Opus для оркестратора и Claude Haiku для воркеров.

**Наблюдаемость.** Отдельно не разбирается; единственное средство — печать этапов в stdout, видимая в выводе примера.

## Оценка

- **Первоисточник по реализации, производный по идее.** Официальный пример Anthropic; формулировка «когда использовать» (строка 39) почти дословно повторяет статью «Building effective agents». Ссылки на ту статью в тексте копии нет — связь отмечена мной по совпадению формулировок.
- **Глубина.** Вводная. Заведомо упрощённая реализация: последовательные воркеры, без ретраев, без синтеза результатов. Сам рецепт честно перечисляет это в ограничениях.
- **Маркетинг.** Практически отсутствует; продвижение ограничено тем, что всё построено на Claude и в конце рекомендуются модели Claude.
- **Спорное.**
  - В реализации нет фазы синтеза: оркестратор только планирует, результаты воркеров возвращаются как есть, а синтез вынесен в Next Steps (строка 283). Это уже, чем определение в «Building effective agents», где оркестратор также синтезирует результаты (сопоставление моё).
  - Пример — генерация вариантов текста — по сути близок к обычной параллелизации со стилями; динамичность декомпозиции на нём показана слабо (моя оценка).
  - Выводы воркеров в примере не согласованы между собой: первый описывает бутылку из нержавеющей стали (строка 145), второй — из «100% recycled ocean-bound plastic» (строка 216). Технические характеристики и сертификаты в строках 140–210 сгенерированы моделью, а не взяты из входных данных. Статья это не комментирует; заявленное «coordinated results» (строка 28) примером не подтверждается (наблюдение моё).
  - Заявление об «error resilience» опирается только на проверку непустого ответа.
- **Локальная копия — с существенными пропусками.** Нет блоков кода (раздел Installation пуст, в Implementation нет кода класса, нет текстов промптов и вызова примера). Вывод прогона не оформлен как блок кода, из-за чего заголовки из ответа воркера (строки 140–206) выглядят как разделы статьи; встречаются экранированные символы (`\*\*`, `\[1/3\]`, `\<`). Как справочник по коду копия непригодна.
