# The Orchestrator-Worker Pattern for LLM Agents (Swarms) — конспект

## Кратко

Руководство из блога фреймворка Swarms: краткое объяснение паттерна orchestrator-worker и подробный разбор его реализации в классе `PhasedFanOutWorkflow` (Swarms v17 «InterLink»). Главный тезис: паттерн оправдан, когда ширина работы становится известна только во время выполнения; ведущая модель один раз пишет план как данные, план валидируется до запуска, затем работа веером расходится на сотни свежих воркеров, и ведущая модель собирает ответ. Статья содержит рабочие примеры на Python, таблицу параметров, описание валидатора плана и поведения при сбоях. Для разработчиков, которые используют Swarms или хотят посмотреть на конкретный дизайн «плановой» оркестрации с ограничителями.

Автор — Kye Gomez (указан на странице оригинала; в локальную копию строка с автором при извлечении не попала).

## Ключевые идеи

**Определение (строка 10, повтор в 332).** Паттерн делит работу между одной ведущей моделью, которая планирует, и многими воркерами, каждый из которых делает один узкий кусок. Уместен, когда ширина работы выясняется только во время выполнения: «найти все баги в этих файлах, затем проверить каждый», «разобрать все тикеты в очереди».

**Три хода (строки 16–18).**
1. Decompose — оркестратор решает, какие единицы работы есть, какой воркер берёт каждую и что должно идти по порядку.
2. Fan out — воркеры работают параллельно, у каждого маленький самодостаточный промпт; воркер видит только свою единицу работы.
3. Synthesize — оркестратор читает результаты и пишет один ответ.

**Источник ценности — изоляция и ширина (строка 20).** Один агент на 40 файлов читает всё в одном контексте и начинает просматривать по диагонали; сорок воркеров читают каждый свой файл внимательно и одновременно. Отдельный верификатор на каждую находку проверяет её независимо от агента, который её сделал.

**Критерий выбора (строка 22).** Если всегда запускаются одни и те же пять аналитиков, фиксированный веер (`ConcurrentWorkflow`, `GraphWorkflow`) проще и дешевле, потому что никакой модели не нужно планировать. Паттерн оправдывает лишний вызов планирования, когда число воркеров зависит от входа.

**Четыре стадии `PhasedFanOutWorkflow` (строки 28–31).**
1. Plan — ведущая модель возвращает `WorkflowPlan` в JSON. План — это данные: «The runtime never executes anything the model writes».
2. Validate — проверки до запуска: неизвестные агенты; ссылки на шаги не из более ранней фазы; `{item}` вне веера; `for_each` по полю, не объявленному массивом в `output_schema` исходного шага; шаги без плейсхолдеров; дубли шагов в фазе; статический подсчёт агентов. Отклонённый план возвращается ведущей модели со списком ошибок, до `max_plan_attempts` раз.
3. Execute — фазы идут по порядку; шаги внутри фазы параллельно, с ограничением `max_concurrent_agents`; шаг с `for_each` запускает по одному свежему агенту на элемент списка.
4. Combine — ведущая модель читает только выводы шагов из `return_steps`.

**Структура плана (строки 35–47).** Поля `name`, `description`, `inline_agents` (имя и системный промпт), `phases` (упорядоченный список с `title` и параллельными `steps`), `return_steps`. Шаг: `id`, `agent`, `prompt`, опционально `for_each` (`"<step_id>.<field>"`) и `output_schema` (JSON-схема). Плейсхолдеры: `{task}` — исходная задача дословно; `{item}` — текущий элемент, только в `for_each`; `{step_id}` — вывод шага из более ранней фазы.

**Плановый оркестратор против менеджера, делегирующего по ходам (строка 336).** В `PhasedFanOutWorkflow` план пишется целиком заранее, выводы между фазами переносит код, и ведущая модель промежуточные результаты не читает. Менеджер, делегирующий ход за ходом, может реагировать на каждый результат, но читает каждый результат, и его контекст растёт с шириной прогона.

**Распределение моделей (строки 107, 322).** Ведущая модель делает два вызова за прогон (плюс по одному на каждый отклонённый план) и определяет потолок качества — ей сильную модель. Воркеры делают большинство вызовов — им дешёвую и быструю. Разные провайдеры для ведущей модели и воркеров: всплеск запросов воркеров не расходует лимит ведущей.

**Независимость верификации (строки 204, 324).** Верификатору давать утверждение и исходный материал, просить структурированный вердикт и по возможности ставить его на другого провайдера, чтобы он не разделял слепые пятна модели, сделавшей утверждение.

## Практика

Статья целиком прикладная. Код на Python с библиотекой `swarms`; блоки кода в копии сохранились, перед каждым стоит метка языка (`Python` / `Shell`).

**Примеры кода.**
- **Установка** (строки 53–57, повтор в 354–356): `pip install -U swarms`, опционально `swarms[fast]`.
- **Поиск багов** (строки 67–105): три маленьких файла с заложенными багами, задача «найти, независимо проверить, сообщить только подтверждённые». Ведущая модель `anthropic/claude-opus-5-5`, воркеры `gpt-5.4-mini`, `size_guideline="small"`.
- **Инспекция прогона** (строки 117–129, вывод 133–139): печать фаз и шагов из `last_plan`, счётчик воркеров, упавшие слоты, вердикты, токены.
- **Предопределённые агенты** (строки 155–202): два `Agent` (читатель оговорок о смене контроля на `deepseek/deepseek-v4-pro`, проверяющий на `mistral/mistral-large-latest`), ведущая `gpt-5.4`, `allow_inline_agents=False`.
- **Триаж 200 тикетов** (строки 214–257): ведущая `gemini/gemini-2.5-pro`, воркеры `groq/openai/gpt-oss-120b`, `max_agents=250`, `max_concurrent_agents=64`, `max_retries=1`, обработка `PhasedFanOutWorkflowError`.
- **Валидация плана вручную** (строки 281–309, вывод 313–316): `WorkflowPlan.model_validate` с ошибочным планом и `validate_plan`; без вызовов модели; показаны четыре сообщения об ошибках.

**Промпты.** Системные промпты двух агентов в примере с контрактами (строки 162–165, 172–175) и тексты задач. Планирующий промпт ведущей модели не приводится; цитируется только фраза отказа «Your plan was rejected for these reasons» (строка 318).

**Архитектурная схема.** Диаграмм нет; архитектура описана текстом (четыре стадии, структура плана).

**Стоимость.**
- Если `worker_model_name` не задан, воркеры используют модель ведущего — «usually the expensive choice» (строка 107).
- Воркер, получающий `{task}`, получает всю исходную задачу: 200 воркеров, читающих очередь из 200 тикетов, умножают входные токены на 200. Правильная форма: разделитель возвращает список, каждый воркер получает свой элемент через `{item}` (строка 271).
- `usage` суммирует токены, сообщённые провайдерами, по ведущей модели и всем воркерам (строка 147).

**Ограничители (строка 269).**
- `max_agents` — жёсткий предел: веер, который его превысит, останавливается до старта своих агентов. Приведён пример сообщения при `max_agents=150`.
- `max_concurrent_agents` — дроссель; выставлять по лимиту провайдера для модели воркеров, поскольку все воркеры идут с одного аккаунта.
- `size_guideline` по умолчанию держит ведущую модель в пределах 10 агентов; для настоящей ширины его надо поднимать.

**Ошибки (строки 273, 318, 348).**
- Упавший воркер перезапускается до `max_retries` раз со свежим агентом.
- Слот веера, упавший после ретраев, становится `None`, попадает в `last_run["failures"]` (фаза, шаг, элемент, ошибка), прогон продолжается; ведущей модели сообщают, что null — это упавшие агенты и о пробеле надо сообщить.
- Упавший одиночный шаг (без `for_each`) поднимает `PhasedFanOutWorkflowError`, так как следующим фазам не хватит входа.
- JSON плана, который не парсится или не соответствует схеме, считается отклонённой попыткой; ответ с code fence или строкой прозы после JSON принимается.

**Наблюдаемость (строки 143–147, 326).** `last_plan` (Pydantic-модель, `model_dump_json(indent=2)` для логов и сравнения прогонов), `last_run["outputs"]`, `agent_count`, `agents`, `failures`, `usage`. Совет: логировать план — по нему обычно видно причину плохого ответа (веер по неверному списку; верификатор, не видевший доказательств; `return_steps`, пропустивший проверенные результаты).

**Прочие рекомендации (строки 323, 325).** Не передавать параметры сэмплирования моделям Claude (по утверждению статьи, текущие модели отклоняют `temperature` и `top_p`). Изображения через `run(task, img=...)` попадают только ведущей модели.

**Состояние агентов (строка 206).** Каждое использование предопределённого агента получает новый экземпляр, пересобранный из аргументов конструктора; состояние диалога не переносится между шагами и прогонами.

**Куда идти дальше (строка 358).** Примеры bug-hunt и contract-review лежат в `examples/multi_agent/phased_fan_out_workflow/` репозитория `kyegomez/swarms`; справочная документация — docs.swarms.world.

## Оценка

- **Первоисточник по продукту, пересказ по паттерну.** Общая часть о паттерне занимает один короткий раздел (строки 12–22) и нового не вводит; ценность — в первичном описании конкретного класса `PhasedFanOutWorkflow` в блоге его разработчика.
- **Глубина.** Высокая в инженерных деталях одного инструмента: параметры, значения по умолчанию, семантика сбоев, валидатор, рабочий код. Низкая в сравнении с альтернативами: другие реализации паттерна не рассматриваются.
- **Маркетинг.** Явный. Это пост в блоге вендора: паттерн подаётся через собственный продукт, много внутренних ссылок на другие посты и release notes, раздел «Get started» с призывом к установке, заголовки сформулированы под поисковые запросы (например, строка 61).
- **Не подкреплено.**
  - Результаты («около 14 000 токенов», «3 из 3 прогонов») взяты из собственных release notes вендора; выборка крошечная (три заложенных бага, два контракта), методика не описана.
  - «Every code block below was run against the Swarms 17.0.0 source» — заявление статьи, в тексте не проверяемое.
  - Тезис, что один агент на 40 файлах «начинает просматривать по диагонали», и тезис о несовпадении слепых пятен у разных провайдеров даны без данных.
  - Утверждение о том, что модели Claude отклоняют параметры сэмплирования (строка 323), — со слов статьи, без ссылки.
  - Пример с 200 тикетами синтетический (шесть шаблонов, размноженных через `random`); результаты его прогона не приводятся.
- **Что не обсуждается.** Цена отказа от адаптивности: план пишется заранее, ведущая модель не видит промежуточные результаты и не может перестроиться по ходу. Статья упоминает это в FAQ как свойство (строка 336), но не как ограничение (оценка моя).
- **Локальная копия — в хорошем состоянии.** Заголовки разделов, вопросы FAQ, таблицы и блоки кода на месте. Мелкие артефакты:
  - строка-источник (9) слиплась с вводным абзацем (10) без пустой строки;
  - два примера вывода (строки 133–139 и 313–316) оформлены как многострочный инлайн-код в одинарных обратных кавычках, а не как блоки;
  - блоки кода без указания языка, язык вынесен отдельной строкой перед блоком;
  - нет строки с автором, временем чтения и рубриками, которая была в предыдущей версии копии (строка с автором относится к содержанию страницы; остальное — обвязка).
