## Как вести этот файл

- Файл временный, как и `ROADMAP.md`: **в коде, комментариях, тестах и сообщениях коммитов на него не ссылаемся.**
  Код ссылается только на `BRIEF.md` (`spec:`) и на референсы (`ref:`).
- Последняя фаза — перенос итогов в `BRIEF.md` всех репозиториев проекта и удаление обоих файлов:
  `ROADMAP.md` и `ROADMAP_FINALIZATION.md`.
- Статус фазы: `не начата` → `в работе` → `готова`. Фаза готова, когда выполнены все пункты «Готово, когда» и это
  проверено на сервере.
- У каждого пункта в скобках — откуда он: фаза `ROADMAP.md`, начало текста пункта и важность из сверки. Подробности
  (что у нас, что в статьях, что в референсах, варианты) — в блоке сверки под тем пунктом; здесь они не повторяются.
- Правила разработки прежние: референсы и тест — до кода, `composer check` зелёный перед коммитом, проверка на
  сервере, итог фазы — в `BRIEF.md`.
- Слово владельца получено: пометка **«Решено (номер)»** в пункте отсылает к разделу
  [Решения владельца перед началом работ](#решения-владельца-перед-началом-работ). Новый вопрос по ходу работы
  записывается туда же отдельной строкой и блокирует только свой пункт.

Работа готова к началу: вопросов, блокирующих первый шаг, нет. Порядок первых шагов:

1. **Д1, И1–И3** — `sql_query` и `git` с секретом: исполнение команд и утечка секретов без карточки. Один выпуск.
2. **Д1, И4** — классификатор команд SSH (самая объёмная правка фазы, день-полтора).

## Фаза Д1 — Границы безопасности

**Цель:** закрыть места, где код не гарантирует то, о чём просит промпт: обход карточки подтверждения, права в
группе, отозванные ключи, утечки секретов. Источник — [AUDIT.md](AUDIT.md) (15 находок и 4 ниже порога уверенности)
и пункты сверки роадмапа.

Порядок внутри фазы: сначала исправления по аудиту И1–И16 по убыванию уровня (И1–И7 — высокий), затем пункты сверки. Каждая правка
начинается с теста, который воспроизводит находку и падает; после правки — `composer check`, развёртывание на всех
экземплярах, отметка «закрыто» в `AUDIT.md`.

### Исправления по AUDIT.md

**И1. `sql_query`: мета-команды клиента** (AUDIT 1, HIGH).
- Запрос с обратной косой чертой вне строковых литералов отклоняется в обоих режимах; для psql запрос передаётся
  через `-c`, а не на stdin интерактивного клиента; для mysql отключается `system` (`--skip-system-command` или
  `--execute`).
- `INTO OUTFILE|DUMPFILE` отклоняется в режиме чтения; имена функций из списка побочных действий распознаются и в
  кавычках.
- Режим чтения обеспечивает сервер: `PGOPTIONS='-c default_transaction_read_only=on'` для PostgreSQL, сеансовая
  настройка для MySQL — а не обёртка-транзакция, из которой можно выйти.
- Тест: `\! id`, `\c other`, `commit \g`, `\copy … to program`, `system id`, `select … into outfile` в режиме чтения
  — ошибка инструмента, до сервера ничего не уходит.

**И2. `sql_query`: секрет и хост** (AUDIT 2, HIGH). Решено (Б2, Б3).
- Вызов с `secret` перестаёт быть «чтением»: карточка владельцу; ключ постоянного разрешения — «секрет + сервер +
  хост базы + порт + пользователь», кнопка «Разрешать всегда» есть (Б3). Обычный случай — база слушает только
  локально, и хост базы — `127.0.0.1` на сервере из реестра: такое сочетание разрешается один раз.
- Видов секрета не вводим (Б2): имя свободное. Поэтому защита — только привязка разрешения к хосту; имена
  `setting.*` (секретные настройки агента) в аргументах инструментов отклоняются.
- Точные значения секретов, выданных в ходе вызова, заменяются в выводе инструмента (общая правка с «Маской по
  точному значению» ниже).
- Тест: вызов с `secret` и новым хостом ждёт карточку; с сохранённым разрешением на другой хост — тоже ждёт.

**И3. `git` с секретом** (AUDIT 3, HIGH).

### Пункты сверки роадмапа

- **Права воркера — белый список.** Воркер получает только инструменты с признаком «можно воркеру»; начальный список
  задан кодом, владелец может его менять. Новый инструмент закрыт по умолчанию. (Фаза 5, «Воркер — вложенный
  запуск…», 70%.) Аудит уточнил: неполный список запретов эскалацией не является — воркер получает только то, что
  есть у оркестратора, и не может необратимого; белый список нужен как защита по умолчанию для новых инструментов.
  Какие права дать конкретному воркеру, решает оркестратор в пределах списка (Д5).
- **Скиллы: снимок и проверка.** Снимок перед записью скилла (`skill_save`, `skill_import`); описание для индекса и
  файлы скилла при чтении проходят `SkillGuard`. (Фаза 9, «Защита скиллов», 60%.)
- **Секреты в журнале.** Процессор Monolog в `LoggerFactory` прогоняет сообщение и контекст через `SecretMasker`.
  (Сквозные требования, «Секреты», 45%.)
- **Маска по точному значению.** `SecretMasker` знает значения секретов хранилища и токенов настроек и заменяет их по
  совпадению; из hermes переносятся шаблоны токена Telegram, PEM-ключей и строк подключения к базам, с тестами на
  ложные срабатывания. (Фаза 4, «Полные промпты и ответы…», 40%.) Закрывает и вывод секретов модели в И2, И3, И11.
- **Удаление сообщений с секретами — точнее.** Шаблоны hex и base64 срабатывают только рядом со словом-именем
  секрета: сообщение с хешем коммита не удаляется. (Фаза 7, «Хранилище секретов», 30%.)
- **Разрешение «всегда» на запись файла и SQL.** В ключ разрешения `file-write` и `sql-write` входит sha256
  содержимого или запроса, а для SQL — ещё движок, хост, порт и пользователь (AUDIT 1). (Фаза 7, «Передача файлов»,
  40%; «SQL и диагностика», 45%.) Кнопка «Разрешать всегда» остаётся: владелец хочет, чтобы любое разрешение можно
  было запомнить.
- **Файл ключа SSH** создаётся сразу с правами 600. (Фаза 7, «Ключи из зашифрованного хранилища», 15%.)
- **Забывание вычищает копии.** Слушатель убирает текст факта из отчётов консолидации и аргументов `memory_propose`;
  граница забывания (история разговора, копии, WAL) честно описана в `BRIEF.md` и в ответе `/forget`. (Фаза 6,
  «Дополнения… забывание вычищает копии», 55%.)
- **Счёт отказов подряд.** Три автоматических отказа («карточка не дошла») сейчас блокируют действие на сутки без
  решения владельца. Решено (В2): считаются только отказы, принятые человеком. (Фаза 5а, «Дополнения… после трёх отказов», 30%.)
- **Персональные данные третьих лиц.** Сведения о людях принимаются только в область `owner` — проверка в
  `Proposals::propose()` по флагу модели; колонка `about_person` с показом на карточке и фильтром в `Recall`.
  (Фаза 6, «Персональные данные третьих лиц…», 45%.)
- **Маска почты и телефонов в исходящем агентам.** (Фаза 13, «Дополнения сверки 2026-11-16», 35%, вариант а.)
- **`ffmpeg` в модуле видео** запускается с `-protocol_whitelist file` (замечание аудита, не находка).

**Ход работ пунктов сверки:** 2026-11-18 — сделано: файл ключа SSH открыт только владельцу до записи ключа; `ffmpeg`/`ffprobe` с `-protocol_whitelist file` (media-video `7be2f90`); процессор журнала `SecretProcessor` прогоняет сообщение и контекст через маску; маска знает точные значения секретов (всё, что выдало хранилище, и секреты `.env`) и шаблоны токена Telegram и PEM-ключа из hermes; удаление сообщения с секретом — по `carriesSecret()`, где голые hex и base64 не считаются секретом; ключ разрешения `file-write` — сервер, путь, способ (запись или дописывание) и хеш содержимого; «три отказа подряд» считают только отказы человека (нажатие или ответ владельца текстом), автоматические серию не считают и не обрывают; белый список инструментов воркера — настройка `AGENT_WORKER_TOOLS` с начальным списком в коде; скиллы — снимок перед `skill_save`/`skill_import` (метка `ChangesSandbox`), описание для индекса и каждый файл скилла при чтении проходят `SkillGuard`; забывание вычищает факт из аргументов вызовов и отчётов консолидации; в исходящем соседям скрыты почта и телефоны; сведения о третьих лицах — флаг `about_person` у предложения памяти, только область владельца, пометка на карточке. Отступление: отдельной колонки у факта и фильтра в `Recall` нет — факт о человеке живёт только в области `owner`, и в чужую аудиторию его не пускает правило областей.

**Готово, когда:**
- на каждую находку AUDIT 1–15 есть тест, который падал до правки, и она отмечена в `AUDIT.md` закрытой — либо
  принятой владельцем: находка 8 (открытая сеть песочницы, Б1) и находка 6 при выключенной настройке подтверждений
  браузера (Б6);
- на сервере: `sql_query` с `\!` — ошибка; `git ls-remote` с секретом на новый хост — карточка; `sort --out=…`,
  `ip l s eth0 down`, `git branch <имя>` по SSH — карточка;
- вторым аккаунтом в группе: запуск не получает инструментов сверх прав посетителя;
- на двух экземплярах: после `/apikey revoke` и `/peer revoke` открытое соединение закрыто; на трёх — ретрансляция
  рукопожатия не проходит, а обычная цепочка основной → doorotar → rekryt работает;
- в журнале приложения и в `trace_payloads` нет значения тестового секрета;
- воркер не может вызвать инструмент вне белого списка, даже если оркестратор его назвал.

## Фаза Д2 — Подтверждения и права владельца

**Цель:** владелец может разрешить навсегда всё, что спрашивается, и разрешение действительно запоминается; правила
по умолчанию взяты у hermes; владелец меняет любое из них.

**Состав:**
- **Разбор повторных запросов разрешения.** Найти по журналу и трассам случаи, когда агент просил разрешение на то,
  что уже разрешено навсегда: в каком контексте, с каким ключом разрешения. Итог: каждый вид запроса имеет ключ
  разрешения, «Разрешать всегда» доступно везде и срабатывает при повторе. Тест на каждый вид. (Фаза 6, «Очередь
  одобрения», 45%.)
- **Новые факты агента — одно решение.** В `BRIEF.md` сейчас два противоположных решения («через владельца» и «агент
  сам»). Решено (В3): агент записывает новые факты сам, владелец правит после; правки и удаления
  существующих фактов по-прежнему идут карточкой. (Там же.)
- **Правила по умолчанию — из `HARDLINE_PATTERNS` hermes.** Они становятся начальным набором «опасного»; владелец
  может изменить или снять любое. (Фаза 3, «Владелец решает обо всём», 25%.)
- **Браузер без подтверждений по умолчанию.** Нажатия, ввод и платёжное заполнение — без карточки; владелец может
  включить подтверждение настройкой `BROWSER_CONFIRM`. (Фаза 8, «Публикация и отправка сообщений…», 75%.) Это решение владельца против
  рекомендации сверки: внешняя страница сможет заставить агента отправить сообщение или форму от имени владельца без
  карточки. В `BRIEF.md` записать как принятый риск и назвать настройку, которая его снимает. Решено (Б6): одна настройка,
  по умолчанию выключена для всех, включая не-владельцев и запуски с пометкой внешних данных.
- **Самоизменение — можно разрешить навсегда.** Владелец разрешает самоизменение один раз, без карточки на каждое
  предложение. (Пакеты, «Оркестрация воркеров, планировщик, проекты, самоулучшение», 5%.) Решено (В13): входят заметки к
  промпту, настройки, роли моделей и скиллы; этим же разрешением владелец может отключить ворота набора задач.
- **Файлы памяти, скиллов и промптов доступны инструментам записи.** `BRIEF.md` («Границы самоулучшения») приводится
  в согласие: общие файловые инструменты могут их менять. (Фаза 11, «В hermes самоизменение включено…», 40%.)
  Решено (В4): файловый вид — `MEMORY.md` с пределом размера (Д7).
- **Импорт скиллов — как есть.** Блокируются только находки `critical`; риск чужого скилла с опасной инструкцией
  принят владельцем. Записать в `BRIEF.md`. (Фаза 9, «Скиллы и MCP-серверы из внешних источников…», 50%.)
- **Лимиты запуска по умолчанию — в 10 раз больше.** Ходы, токены, время запуска и воркера: новые значения в коде,
  `.env.example`, `SettingsCatalog::DEFAULTS` и тесте совпадения. (Фаза 3, «Лимиты в коде», 8%.) Решено (В12): 750 ходов запуска и
  375 ходов воркера (в полтора раза больше, чем у hermes), 1 млн токенов на запуск, 8 часов на запуск.
- **Денежные лимиты — по желанию.** По умолчанию их нет; владелец задаёт любой и решает, кто видит и кто меняет.
  (Фаза 5а, «Лимиты в деньгах и числе воркеров», 55%.)
- **Передача владения.** Начальный владелец — из `.env`; владелец может передать владение другому участнику
  командой. (Сквозные требования, «Владелец», 20%.) Решено (В16): прежний владелец становится
  администратором; список ролей владелец может задать свой — отдельным пунктом ниже.
- **Настраиваемый список ролей.** Владелец задаёт свои роли и их порядок (В16); встроенные четыре — начальный
  набор. Делается после передачи владения, отдельным шагом: роли участвуют в политике, памяти и карточках.
- **Сообщение «Жду подтверждения…» правится после решения; `/permissions` обновляется после отзыва.** (Фаза 3,
  «Подтверждения», 8%.)
- **Отказ «карточка не дошла» говорит модели «не повторяй».** (Фаза 5а, «Карточка подтверждения», 10%.)

**Готово, когда:** на сервере действие каждого вида, разрешённое «навсегда», второй раз проходит без карточки;
владелец включает и выключает подтверждения браузера настройкой и это видно в поведении; новые лимиты видны в
`/settings`; передача владения проверена на тестовом экземпляре и возвращена обратно.

**Ход работ Д2:** 2026-11-18 — лимиты по умолчанию: 750 ходов, 1 млн токенов, 8 часов на запуск, 375 ходов и 500 тысяч токенов воркеру (`d31f48f`); отказ «карточка не дошла» говорит модели не повторять действие; `BROWSER_CONFIRM` (по умолчанию 0); правила «никогда» сверены с `HARDLINE_PATTERNS`, у каждого имя, владелец снимает настройкой `SSH_NEVER_OFF`; «Жду подтверждения…» после решения правится на «Решение владельца получено — продолжаю»; список `/permissions` обновляется после отзыва; `sudo` по SSH можно разрешить навсегда (ключ `ssh-sudo`); новые факты агент записывает сам, уведомление с «Забыть»; самоизменение — «Разрешать всегда» по виду изменения (`self-improve:<вид>`), проверка набором задач выключается `IMPROVE_GATE=0`.
Пункты-решения (файлы памяти, скиллов и промптов доступны инструментам записи; импорт скиллов как есть; денежных лимитов по умолчанию нет) записаны в `BRIEF.md` как принятые риски — кода не требуют: `AGENT_DAILY_SPEND_CAP=0` уже означает «без лимита». Осталось: передача владения и свой список ролей — владелец сейчас берётся из `.env` (`TELEGRAM_ADMIN_ID`) по всему коду, передача требует вести владельца из базы; сделать до закрытия Д2.

## Фаза Д3 — Цикл и харнесс

**Цель:** цикл проще читать и менять, а контекст и расход защищены кодом.

**Состав:**
- **Цикл по фазам.** `AgentLoop::iterate()` разнесён на фазы — подготовка хода, вызов модели, раунд инструментов,
  завершение — отдельными классами с вердиктом «продолжить / повторить / остановиться»; поведение не меняется.
  (Пакеты, «Агентский рантайм», 15%; фаза 3, «Цикл», 15%.)
- **Потолок результатов по окну модели.** Один результат — не больше 15% окна модели запуска, все результаты хода —
  не больше 30%, как у hermes (`tool_result_storage.py`, `budget_config.py`); лишнее выгружается в файл по убыванию
  размера. (Фаза 3, «Результаты инструментов», 45%.)
- **Тест-снимок промпта** и определений инструментов; `prompt_cache_key` для OpenAI. (Фаза 3, «Системный промпт
  неизменен», 15%.)
- **Кеш промпта.** Явная метка на системном промпте, без метки у вызова без истории и инструментов;
  `prompt_cache_key` = номер беседы; список семейств расширяется по образцу hermes после замера попаданий по
  `llm_calls`. (Фаза 5а, «Кеш промпта», 45%.)
- **Приведение простых типов аргументов** (строка → число, булево) перед проверкой схемы — как у hermes; сначала
  посмотреть в трассах, как часто встречается ошибка схемы. (Фаза 3, «Проверка вызовов до исполнения», 10%.)
- **Схема инструмента проверяется при регистрации;** негодная (прежде всего от MCP) не регистрируется. (Фаза 3,
  «Реестр инструментов», 12%.)
- **Повторный идентичный результат заменяется ссылкой на первый;** счётчик ограничителя зацикливания хранится в
  `runs`. (Фаза 3, «Параллельность инструментов», 8%.)
- **Индекс якорей при сжатии** — идентификаторы, пути, адреса из сжимаемой части сохраняются регулярками. (Фаза 3,
  «Контекст», 15%.)
- **`search_files`** — инструмент класса «чтение»: агент видит файлы и папки участника и проекта, включая скиллы.
  (Фаза 3, «Первые инструменты», 5%.) Раскладка папок — в Д10.
- **Вызов классификатора запросов пишется в `llm_calls`** (`purpose = classify`). (Фаза 3, «Частичный выбор
  моделей», 35%.)
- **Сроки потока — от запроса.** Сроки до первого события и между событиями передаются в `ChatRequest` и считаются в
  `ProviderRouter` по оценке промпта и признаку рассуждения из каталога. (Фаза 5а, «Зависший поток», 40%.)
- **Пустой и обрезанный ответ.** Меньший бюджет рассуждения для дорогих повторов; без повторов при
  «детерминированной» пустоте. (Фаза 5а, «Обрезанный и пустой ответ», 20%.)
- **Смена модели при отказе.** Не переключаться при `ContentFilter`; выбранная запасная модель хранится в строке
  запуска. (Фаза 5а, «Смена модели при отказе», 35%.)
- **Доставка итога при долгом флуде.** Обязательство остаётся `attempting`, `delivered` ставит таймер после
  реальной отправки. (Фаза 5а, «Доставка итога», 30%.)
- **Реестр и категории инструментов.** Инструменты регистрируются в общем реестре; категории — подкаталоги
  (`Guard` — одна из них: `SecretMasker`, `AddressGuard`, `UntrustedWrapper`, классификатор). (Пакеты, «Встроенные
  инструменты…», 15%.)
- **Номер запуска в каждой записи журнала** — процессор Monolog берёт его из fiber-local хранилища. (Сквозные
  требования, «Логи», 15%.)
- **Сквозные тесты цикла на `OpenRouterClient` поверх `FakeHttp`:** зависший поток, обрыв посреди вызова
  инструмента. (Сквозные требования, «Тесты и анализ», 25%.)
- **`Amp\Parallel\Worker`** для распаковки архивов и пакетного счёта HRR. (Сквозные требования, «Async-first», 30%;
  фаза 6, «HRR с самого начала», 10%.)
- **Извлечение памяти с таймаутом** — `async()` с `TimeoutCancellation` и предупреждением в журнале. (Фаза 6,
  «Дополнения… размыкатель», 30%.)

**Готово, когда:** `AgentLoopTest` и интеграционные тесты зелёные после разбора цикла; восемь параллельных чтений
больших файлов не превышают 30% окна (тест); на сервере длинная задача с рассуждением не обрывается ложным
`no stream events`; доля чтения кеша по `llm_calls` не упала.

**Ход работ Д3:** 2026-11-18 — потолок результатов по окну модели (`ResultBudget`: 15% на результат, 30% на ход, тест на восемь больших чтений); схема инструмента проверяется при регистрации — негодная (имя, корень не объект, `required` без поля) не регистрируется, инструмент MCP с такой схемой пропускается с записью в журнал; вызов классификатора запросов пишется в `llm_calls` (`purpose = classify`, на беседу запуска).

## Фаза Д4 — Модели и провайдеры

**Цель:** один путь к любой модели — с изображениями, повторами и учётом; провайдеры добавляются данными.

**Состав:**
- **Сообщение из частей.** `Message` несёт текст и изображение (затем звук и видео); `MediaModels` переведён на
  `LlmClient` — один путь повторов и учёта. (Фаза 2, «Модель: единый интерфейс…», 40%.)
- **Провайдеры: Anthropic, Bedrock, Codex** — сразу, при необходимости отдельными сабмодулями. (Пакеты, «`llm`»,
  10%.) Перед кодом адаптера Claude — скилл `claude-api`. Владелец в пункте «Провайдер в три слоя» решил «оставить
  до третьего провайдера» — третий провайдер наступает здесь, поэтому объект профиля провайдера (диалект, адрес,
  кеш-метки, параметры рассуждения) вводится в этой же фазе. Решено (В11): адаптеры пишутся и
  проверяются на подставных ответах; живая проверка — когда появятся ключи.
- **Провайдер jev-ai.pro** (`https://jev-ai.pro/docs`) — чтобы выбрать Jev моделью-судьёй. Ключ лежит в `.env`
  (`JEV_API_KEY`), в git не входит. (Фаза 6, «Фоновая консолидация», 35%.)
- **`cost_status` в `llm_calls`** — миграция и поле `Usage`. (Фаза 2, «Единый учёт расхода», 15%.)
- **Выбор модели — как у hermes, по категориям.** Категории: текст, звук, видео, изображения (vision), генерация
  изображений и т. д.; в каждой — несколько моделей или ни одной. Оценки 1–10 по осям могут уйти, если маршрут
  остаётся эффективным. (Фаза 5, «Профиль задачи», 15%.) Решено (В5): категории надстраиваются
  над ролями `cheap`/`main`/`strong` и настройками `MEDIA_*_MODELS`; из нескольких моделей категории агент сам
  выбирает подходящую, если не сказано, как выбирать.
- **Отсев по успешности инструментов.** Для частей с инструментами не брать модели с низкой долей успешных вызовов
  из каталога, если модель не названа прямо. (Фаза 5, «Профили моделей», 30%.)
- **`run_id` в `routing_decisions`** и причина выбора в `/trace` воркера. (Фаза 5, «Каждое решение о выборе
  модели…», 25%.)
- **Замер выбора моделей считается предварительным** — записать в `BRIEF.md`. (Фаза 5, «Выбор модели», 35%.)
- **Судья — модель любого провайдера.** Настройка судьи принимает модель с указанием провайдера. (Фаза 6, «Фоновая
  консолидация».)

**Готово, когда:** картинка от владельца доходит до модели через `LlmClient` и видна в `llm_calls`; один и тот же
запрос проходит через OpenRouter, прямой Anthropic и Jev на сервере; модель-судья из Jev прогоняет набор задач;
`/trace` воркера показывает, почему выбрана модель.

## Фаза Д5 — Оркестратор и воркеры

**Цель:** оркестратор сам решает, что дать воркеру, а код держит границы.

**Состав:**
- **Права воркера задаёт оркестратор.** В задании — инструменты, доступы и режим: «только чтение» или с записью;
  контекст проекта и участника — если нужен, иначе изоляция. Делается как у hermes, но режим «только чтение»
  остаётся выбором оркестратора. Память воркеру — по решению оркестратора, не всегда только чтение. (Фаза 5,
  «Параллельные воркеры — только на чтение», 35%; фаза 6, «Дополнения… `memory_feedback`», 30%.) Граница — белый
  список из Д1.
- **`output_schema` с проверкой**, как у hermes. (Фаза 5, «Инструмент делегирования», 20%.)
- **Потолок отчёта — от свободного места в окне оркестратора.** (Фаза 5, «Отчёт воркера обрезается…», 20%; фаза 5а,
  «Отчёт воркера целиком», 15%.)
- **Проверка `/new` при доставке фонового результата.** (Фаза 5, «Долгое делегирование идёт в фоне», 10%.)
- **Семафор вместо троек** — скользящее окно параллельных воркеров. (Фаза 5, «Параллельный запуск воркеров», 15%.)
- **Непустой `output` у части с проверкой** — иначе ошибка инструмента. (Фаза 5, «Синтез», 15%.)
- **Строка-ориентир в описании инструмента:** одна часть — не делегируй; 2–4 — сравнения; 5 — потолок. (Фаза 5,
  «Критерии „когда делегировать“», 15%.)
- **Срез `/usage` и `/delegation` по `prompt_version`.** (Фаза 5а, «Видимость делегирования», 30%.)

**Готово, когда:** оркестратор на сервере запускает одного воркера «только чтение» и одного с записью в одной
задаче, и трасса показывает их права; отчёт не по схеме возвращается воркеру ошибкой.

## Фаза Д6 — Трассы и метрики

**Цель:** по трассе видно всё, что делал запуск, включая воркеров; метрики собираются.

**Состав:**
- **Вложенные трассы.** `/trace` оркестратора показывает шаги дочерних запусков с отступом; вид шага `worker`
  (миграция, событие); время создания подтверждения передаётся в `approvalDecided`. (Фаза 4, «Трасса запуска», 30%.)
- **Отчёты.** В `/usage` — инструменты (вызовы, ошибки, время) и пять самых долгих шагов; в `/delegation` — доля
  токенов оркестратора. (Фаза 4, «Сводки», 30%.)
- **Команды.** `/runs <число>` с отбором по статусу; `/trace <номер> <шаг>` с файлом промпта и ответа из
  `trace_payloads`. (Фаза 4, «Команды владельцу в канале», 10%.)
- **Prometheus на основном экземпляре.** Включить `/metrics` (`METRICS_TOKEN`) в `/home/rekryt/docker/mercurius/`;
  кеш ответа на 30 с; гистограмма воркеров на запуск. Prometheus на сервере уже стоит: владельцу выдаётся готовый
  фрагмент `scrape_configs` (адрес в сети `web`, заголовок с токеном). Решено (В17): только основной
  экземпляр; владельцу — адрес метрик и токен, `scrape_configs` он пишет сам. (Фаза 4, «Сводки» и «Экспорт метрик», 15%.)
- **Журнал извлечения памяти.** В `memory_recalls` — `run_id` и `version`. (Фаза 6, «Дополнения… квитанция
  извлечения», 35%.)
- **Шаг трассы для консолидации:** строка «ждут решения: N, старейшему D дней» в ночной проверке или ежедневной
  сводке. (Фаза 6, «Дополнения… очередь ожидающих», 35%.)

**Готово, когда:** `/trace` запуска с делегированием показывает шаги воркеров; Prometheus владельца собирает метрики
основного экземпляра (проверено по цели в интерфейсе Prometheus).

## Фаза Д7 — Память

**Цель:** память точнее ищет, честно хранит происхождение и показывает владельцу всё, что помнит.

**Состав:**
- **Правки слоя 1 по записям,** как в hermes, вместо замены всего текста. (Фаза 6, «Слой „всегда в контексте“», 35%.)
- **Файл `MEMORY.md` в промпте.** Запись в `MEMORY.md` попадает в промпт без деления на знания и правила — помимо
  фактов; в `BRIEF.md` записать, что правила живут в заметках к промпту, а категория `rule` не используется.
  (Фаза 6, «Записи делятся на знания и правила», 20%.) Решено (В4): у файла предел размера — значение
  по умолчанию не маленькое, владелец его меняет; при достижении предела файл сжимается до нужного размера скиллом,
  по образцу hermes (перед кодом — изучить, как hermes ведёт `MEMORY.md` и что делает при переполнении; у него
  предел 2200 символов и авто-сжатия нет — у нас сжатие есть). Профиль и сводка слоя 1 остаются в базе.
- **Факты привязаны к проекту** — колонка и область в `Audience`. (Фаза 6, «Слои проектов…», 30%.)
- **Аудитория.** Проверить вторым аккаунтом в группе, что посетитель не получает факт владельца; хранить вид чата в
  `conversations`, чтобы запуск после перезапуска не терял память. (Фаза 6, «Фильтр раскрытия по аудитории», 30%.)
- **Происхождение и ключевые слова.** Настоящее происхождение (сказал владелец или вывел агент) и источник версии;
  ключевые слова от агента при записи. (Фаза 6, «Хранилище фактов», 40%.)
- **Анализ текста.** Таблица заимствований («впн» / «VPN»); однокоренные из `ru_derivation.tsv.gz` с весом 0,6 и
  тестом на наборе; ключевые слова в `memory_propose`. (Фаза 6, «Анализ текста», 45%.)
- **Контракт памяти.** `BRIEF.md` («Интеграция с ядром») — по факту; узкий интерфейс из трёх методов (слой 1,
  извлечение, после запуска) — при выносе пакета в Д16; полный контракт hermes не переносим. (Фаза 6, «Память
  подключается к ядру…», 40%.)
- **До двух фактов по названной сущности без совпадения слов,** как в holographic. (Фаза 6, «Запись в память по ходу
  работы…», 10%.)
- **Повторы считает код.** По сообщениям владельца: на карточке «сказано в N разных днях», как в dreaming; код сам
  отличает устойчивое от разового. (Фаза 6, «Долговременной памяти заслуживает…», 30%.)
- **Журнал выдачи фактов.** Какие версии фактов выданы в ответ и помог ли ответ — и использование этого, как в
  hermes-plugin-holographic. (Фаза 6, «Слои памяти», 15%.)
- **Консолидация.** Формулировка в спецификации — по факту; «показано» — только после доставки отчёта, догон
  пропущенной ночи при старте; отрицания в поиске противоречий по `dream_lang.py`. (Фаза 6, «Фоновая консолидация»,
  35%.)
- **`/memory <слова>`** и постраничный вывод. (Фаза 6, «Владелец может посмотреть…», 40%.) Выгрузка — в Д14.
- **Фоновое предложение фактов.** В промпт — «не бери сбои окружения»; модульный тест `FactNudge`; раз в неделю
  `self-review` показывает факты, ушедшие под порог. (Фаза 11, «Дополнения сверки 2026-11-17», 25%.)
- **Формулировка о соседе в `BRIEF.md`:** о соседнем агенте хранятся история бесед и карточка, фактов нет. (Фаза 13,
  «Подключившийся агент — участник…», 15%.)
- **Недосмотры из сверки:** `Fact::RULE` и категория `rule` убираются из кода вместе с решением выше; замена
  «(забыто)» в `index.php` идёт через i18n.

**Готово, когда:** recall@5 и MRR на русском наборе не хуже прежних, а вопросы с синонимами и заимствованиями находят
факт (новые строки набора); карточка факта показывает происхождение и число дней; проверка вторым аккаунтом в группе
пройдена на сервере.

## Фаза Д8 — Серверы и сеть

**Цель:** реестр серверов правится в диалоге, серии команд идут быстро.

**Состав:**
- **Удаление и правка сервера.** `/server - <имя>` и инструмент `server_remove` через карточку; правка полей
  (секрет, маршрут, группа) со сбросом закреплённого ключа хоста при смене хоста. (Фаза 7, «Реестр серверов», 45%.)
- **Пул SSH-соединений** с уборкой простаивающих: соединение на сервер, 1–2 минуты простоя, проверка живости.
  (Пакеты, «Сверка… кандидаты», 25%; фаза 7, «SSH на `amphp-ssh`», 30%.)
- **Участник в `/audit`;** цепочка хешей проверяется в `doctor` и ежедневной сводке. (Фаза 7, «Журнал всех команд»,
  25%.)
- **Сверка адреса источника при маршруте `vless`** — один раз на сервере командой `who`. (Фаза 7, «Маршрут
  соединения», 10%.)
- **Классы `CommandClassifier` переименованы** (`SshCommandClassifier`, `OutwardActionClassifier`); в `BRIEF.md`
  записано, что пакета `command-policy` не будет. (Пакеты, «`command-policy`», 45%.)

**Готово, когда:** сервер с изменившимся ключом хоста исправляется в диалоге без SQL; пять команд подряд на один
сервер идут по одному соединению (видно в журнале).

## Фаза Д9 — Интернет и браузер

**Цель:** браузер умеет то же, что у hermes, а его профили и файлы лежат рядом с остальными данными участника.

**Состав:**
- **Возможности браузера как у hermes.** Обработчик диалогов (отклонять и возвращать текст), перевод новой вкладки в
  текущую, действия `scroll`, `select`, `back`; сверить список действий с браузерным инструментом hermes. (Фаза 8,
  «Сервис браузера в отдельном контейнере», 45%.)
- **Профиль браузера — в папке участника или проекта,** там же, где контекст в песочнице. (Фаза 8, «Постоянные
  профили браузера», 50%.) Решено (В6): профили остаются в `storage/browser`, с раскладкой по
  участникам и проектам (`p<номер>/<имя>` и `p<номер>/projects/<номер>/<имя>`); том песочницы браузеру не
  подключается.
- **Поиск и чтение.** Вызов `web_search` — в `llm_calls` и в бюджет запуска; `offset` в `web_read`; кеш прочитанных
  страниц. Список запрещённых сайтов и отказ на адрес с секретом не делаем. (Фаза 8, «Поиск в интернете…», 30%.)
- **Почта: вложения.** `mail_attachment` (файл в `inbox/` песочницы с лимитами входящих вложений) и `files` в
  `mail_send`. (Фаза 8, «Почта: чтение и отправка», 30%.)
- **Почта: authserv-id.** `doctor` и ответ `mail_read` называют, с каким authserv-id идёт сверка. (Фаза 8,
  «Дополнения сверки 2026-11-17», 25%.)
- **Модуль браузера на TypeScript;** запись в `BRIEF.md` о проверках модуля — по факту. (Пакеты, «`browser-service`»,
  35%.)
- **Подтверждения в браузере** — в Д2.
- **Остаток находки SSRF** — в Д1 (пункт И16); решено делать (Б9).

**Готово, когда:** страница с `alert` не подвешивает действие; агент выбирает значение в списке и возвращается назад;
вложение письма попадает в песочницу и отправляется обратно письмом; модуль браузера проходит свои проверки в CI.

## Фаза Д10 — Скиллы и MCP

**Цель:** скиллы лежат в одной понятной раскладке, их правки журналируются и откатываются.

**Состав:**
- **Раскладка `.mercurius/skills`.** Скиллы участника — `/<участник>/.mercurius/skills/`, скиллы проекта —
  `/<участник>/projects/<проект>/.mercurius/skills/`; `search_files` (Д3) показывает их вместе с файлами. Перенос
  существующих папок — миграцией данных при старте, с копией. (Фаза 3, «Первые инструменты», 5%.) Решено (В14): каталог участника — `p<номер>`,
  проекта — `projects/<номер>`; существующие папки переносятся автоматически.
- **Индекс скиллов — и запускам заданий.** (Фаза 9, «Скиллы агента: каталог…», 15%.)
- **`/skill <имя> off`** (скрыть из индекса, файлы не трогать) и **`/skill <имя> remove`** (через снимок). (Фаза 9,
  «Управление из канала», 20%.)
- **Журнал правок скиллов с откатом одной записи.** (Фаза 11, «Агент создаёт черновики скиллов…», 45%.)
- **Источник и ревизия при импорте** — в frontmatter `SKILL.md`; **`/skill update`**, если известен адрес
  git-репозитория скилла. (Фаза 9, «Дополнения сверки 2026-11-17 (вечер)», 35%.)
- **Поиск инструментов.** При числе инструментов MCP выше порога модель получает список имён и мост `tool_search`.
  (Там же.)
- **Проверка пакетов MCP** перед `/mcp on` для `npx`/`uvx` — запрос в OSV с кешем и пропуском при сетевой ошибке.
  (Фаза 9, «Дополнения сверки 2026-11-16», 30%.)
- **Учёт использования.** Ключ учёта — «место + имя»; строка при создании скилла; `trace_review` называет
  неиспользуемые скиллы; текст пометки соответствует действию `off`. (Фаза 11, «Дополнения… учёт использования
  скиллов», 45%.)
- **Предел снимков** `.checkpoints/` — `max_snapshots = 20`, как у hermes. (Фаза 10, «Дополнения сверки
  2026-11-16», 35%.)

**Готово, когда:** на всех экземплярах скиллы лежат в новой раскладке и читаются; правка скилла откатывается одной
командой; `/skill update` обновляет скилл, импортированный из GitHub; сервер MCP с сотней инструментов не раздувает
запрос к модели.

## Фаза Д11 — Каналы, Telegram и планировщик

**Цель:** ядро не знает о Telegram, задания доставляют итог туда, где их поставили, webhook не будит агента зря.

**Состав:**
- **Имя канала — из сообщения или настройки,** а не литерал `'telegram'` (четыре места). (Фаза 2, «Канал связи»,
  25%.)
- **Контракт канала.** `supportsButtons` исправлен, флаги возможностей читаются ядром; темы, опрос, контакт,
  геоточка — в необязательных интерфейсах (`ForumChannel` и т. п.). (Фаза 2, «Контракт канала узкий», 45%.)
- **Склейка сообщений,** которые клиент Telegram режет по 4096 символов (hermes `_text_batch_delay_for`). (Фаза 2,
  «Команды управления…», 10%.)
- **Polling перезапускается при падении цикла.** (Фаза 2, «Telegram через webhook», 15%.)
- **`update_id` в PostgreSQL** — без двойного запуска после перезапуска; ответ длиннее 8 частей — файлом. (Фаза 2,
  «Telegram: ограничение частоты…», 25%.)
- **Доставка заданий.** Тема форума хранится в задании, итог идёт в неё; несостоявшаяся доставка повторяется
  (`pending_report`) и называет причину сбоя; запуск задания видит ядро памяти и индекс скиллов. (Фаза 10, «Задачи
  по расписанию и по событиям», 40%.)
- **Webhook.** Фильтр событий по заголовку и полю тела; слияние всплеска; модель задания (роль `cheap` для простых
  проверок). (Фаза 10, «Дополнения сверки 2026-11-17 (конспект)», 30%.)
- **Переименование проекта** с `editForumTopic` для связанных тем. (Фаза 10, «Telegram: группы, каналы, форум», 15%.)
- **Kanban hermes** — изучить и дописать конспект перед следующей доработкой проектов; кода не требует. (Фаза 10,
  «Долгие задачи и проекты», 20%.)
- **Боты в группах — слушать по умолчанию.** (Фаза 13, «Дополнения сверки 2026-11-17 (вечер)», 5%.) Вместе с этим
  обязательно — защита от петель между ботами по образцу hermes `bot_loop_guard.py` (скользящее окно, не больше 4
  переходов): без неё два бота в одной группе будут отвечать друг другу без конца и тратить деньги. Решено (В15):
  бот получает права посетителя; участник может назвать агенту ботов и посетителей, которых надо игнорировать.
- **Белый список инструментов задания `self-review`** — в Д12.
- **Тема форума и адрес сбоя в отчёте задания** — проверить на форуме основного экземпляра.

**Готово, когда:** поиск по `src/` не находит литерала `'telegram'` вне настройки канала; задание, поставленное в
теме форума, присылает итог в ту же тему; push в тестовый репозиторий с неподходящим событием не запускает модель;
два бота в тестовой группе останавливаются защитой от петель.

## Фаза Д12 — Самоулучшение

**Цель:** разбор трасс не искажается проверочными прогонами, а изменения оцениваются по категориям.

**Состав:**
- **Разбор трасс без `eval`.** Канал `eval` исключён из `trace_review`, поиска по истории и отчётов; у задания
  `self-review` — белый список инструментов. (Фаза 11, «Разбор собственных трасс», 55%.)
- **Ревью трасс правилами,** как в cookbooks: правила против выданных прав, «повтор после отказа», вызовы,
  отклонённые политикой участника. (Фаза 11, «Дополнения сверки 2026-11-16», 40%.)
- **Оценка по категориям на версию промпта.** Результаты набора задач хранятся по категориям и по версии заметок;
  отчёт сравнивает версии. (Фаза 11, «Набор проверочных задач», 60%.) Решено (В7): только хранение
  и отчёт; попарное сравнение, расширение набора и ворота для настроек не делаем.
- **Зависшие предложения.** При старте `checking` возвращается в `proposed` с сообщением владельцу; агент видит
  последние отклонённые заголовки и не повторяет их дословно. (Фаза 11, «Изменения глобального поведения…», 45%.)
- **Журнал правок скиллов с откатом** — в Д10. Решено (В8): история ролей моделей с откатом нужна —
  таблица `model_role_history` (роль, модель, причина, кто, когда) и команда отката.
- **Идеи доработок наружу** — через экспорт в Д14. (Фаза 11, «Свой код агент по ходу работы не меняет», 30%.)

**Готово, когда:** после прогона ворот статистика `trace_review` не меняется; отчёт показывает оценку каждой
категории для двух версий промпта; перезапуск посреди прогона ворот не оставляет предложение в `checking`.

## Фаза Д13 — Сеть агентов

**Цель:** протокол задачи полон с обеих сторон, расход и бюджет идут по цепочке.

**Состав:**
- **`a2a_call` и `a2a_orchestrate`** — по подобию hermes: вызов одного агента и раздача частей нескольким. Сначала
  изучить реализацию hermes и дописать конспект. Заодно — проверить на сервере задачу агенту по входящему
  соединению и снять внешний ключ `a2a_outgoing.peer → peers`, если вставка падает. (Фаза 13, «Удалённый агент как
  воркер», 55%.) Решено (В9): `peer_delegate` остаётся; рядом — `peer_call` (вызвать одного агента и дождаться
  ответа) и `peer_orchestrate` (раздать части нескольким и свести).
- **Протокол задачи.** Срок отданной задачи (например, 2 часа → FAILED) и опрос по `updated_at`; `contextId` для
  ответа на вопрос ведомого; отмена ведущим (`CancelTask`). (Фаза 13, «Протокол задачи», 60%.)
- **Расход и бюджет.** `costOf` подключён в сборке — стоимость ведомого в USD видна в `/trace` ведущего; потолок
  токенов в `metadata.mercurius`, который ведомый берёт как минимум со своим лимитом. (Фаза 13, «Учёт расхода на
  обеих сторонах», 60%.)
- **Расширенная карточка** — навыки по политике агента-участника, после входа. (Фаза 13, «Карточка агента», 25%.)
- **Родительская задача и трасса** — `leaderRun` и номер задачи в `metadata.mercurius`, хранятся в `a2a_tasks`; имя
  функции в двух ссылках `ref:` исправлено (`_record_outcome`). (Фаза 13, «Дополнения сверки 2026-11-16», 35%.)
- **Потолок ходов в контексте** остаётся; в `BRIEF.md` записано, что диалог ограничивают глубина и частота. (Фаза 13,
  «Дополнения сверки 2026-11-17», 30%.)
- **Находки аудита по A2A** (ретрансляция рукопожатия, подпись без получателя, путь файлов ответа) — в Д1.

**Готово, когда:** на трёх экземплярах: ведущий отменяет задачу, отвечает на вопрос ведомого в том же контексте,
видит стоимость ведомого в долларах; задача к недоступному соседу закрывается по сроку и не останавливает опрос
остальных; `a2a_orchestrate` раздаёт части двум соседям и сводит ответы.

## Фаза Д14 — Экспорт и импорт агента

**Цель:** агента можно целиком унести в архиве и поднять из него на другом сервере.

**Состав:**
- **Экспорт.** Команда владельца собирает архив: данные базы (дамп), файлы всех участников и проектов, скиллы,
  настройки, память, заметки к промпту, идеи доработок. Секреты — Решено (В10): хранилище секретов и
  мастер-ключ входят в архив; архив шифруется паролем владельца; отправляется и принимается только в личном чате
  владельца.
- **Импорт.** Архив, отправленный агенту, восстанавливается — после этого агент становится тем, из которого архив
  получен. Два пути: полный одним потоком (как `bin/restore.sh`, но из канала) и частичный через агентский цикл
  (например, только память или только скиллы). Перед полным импортом — копия текущего состояния и карточка
  владельцу.
- **Основа — `bin/backup.sh` и `bin/restore.sh`:** формат архива один, чтобы копия перед обновлением и экспорт не
  расходились. (Фаза 6, «Владелец может посмотреть…» и «Дополнения… `/memory`»; фаза 11, «Свой код агент…».)

**Готово, когда:** архив принимается и выдаётся только в личном чате владельца; без пароля не раскрывается; архив
основного экземпляра восстановлен на тестовом экземпляре, и тот отвечает с той же памятью,
скиллами и настройками; частичный импорт только памяти не трогает остальное.

## Фаза Д15 — Поставка

**Цель:** обновление одной командой, образы и память под контролем, README говорит правду.

**Состав:**
- **`mem_limit` для `app` и `postgres`;** образы `php:8.2-cli-bookworm` и `pgvector` закреплены по digest. (Фаза 1,
  «`docker-compose.yml`», 20%.)
- **`bin/update.sh`:** копия → `git pull` → сабмодули → сборка, с остановкой при неудачной копии. (Фаза 12,
  «Дополнения сверки 2026-11-17», 45%.) Ручной порядок развёртывания в `CLAUDE.md` остаётся как описание шагов.
- **Оба README по факту:** статус, возможности, раздел «Несколько экземпляров на одном хосте» с `compose.local.yml`.
  (Фаза 12, «Установка сторонним пользователем», 50%.)
- **Неизвестные ключи сохранённых настроек** — в журнал при старте и в `/doctor`. (Фаза 12, «Дополнения сверки
  2026-11-16», 35%.)
- **Неподключённые репозитории пакетов** — пометка в README «код пока в основном репозитории» (до Д16 — для тех,
  что выносятся). (Фаза 0, «Сделано: ветка `master`…», 10%.)

**Готово, когда:** основной экземпляр обновлён через `bin/update.sh`; README на английском и русском совпадают с
возможностями; `/doctor` называет устаревший ключ настройки.

## Фаза Д16 — Структура кода и репозиториев

**Цель:** точка входа читается как оглавление, самостоятельные подсистемы живут в своих репозиториях.

**Состав:**
- **`index.php` разбит на файлы сборки по подсистемам.** Сам `index.php` — заголовочный файл: написан вручную,
  красиво и читаемо, с блоками phpdoc и комментариями, без ущерба поведению. (Пакеты, «Приложение на
  `opencck/server`», 30%; фаза 1, «Проект на `opencck/server`», 25%.)
- **`memory` — сабмодуль `packages/memory`** (`opencck/mercurius-memory`): своя папка миграций, контрактный тест,
  узкий интерфейс из Д7. (Пакеты, «`memory`», 25%.)
- **`peer` — сабмодуль `packages/peer`** (`opencck/mercurius-peer`). (Пакеты, «`peer`», 25%.) Сеть проверена на
  четырёх экземплярах — вынос делается после Д13 и с повтором живой проверки цепочки.
- **`mcp-client` — сабмодуль `packages/mcp-client`** (`opencck/mercurius-mcp-client`): HTTP-транспорт и клиент
  JSON-RPC; stdio через песочницу остаётся в приложении. (Пакеты, «`mcp-client`», 20%.)
- **Только PostgreSQL.** MariaDB убрана из «Стека» и «Решений» `BRIEF.md`. (Фаза 1, «Доступ к БД…», 35%.)
- **Категории инструментов по каталогам** — если не сделано в Д3.
- **Обязательные файлы новых репозиториев** — `README.md`, `README.ru.md`, `LICENSE`, `composer check`, workflow; запись
  в `packages/README.md`.

**Готово, когда:** `composer check` зелёный в основном репозитории и в трёх новых пакетах; все пять экземпляров
обновлены и здоровы; цепочка основной → doorotar → rekryt проходит после выноса `peer`.

## Фаза Д17 — Спецификация и завершение

**Цель:** спецификация лежит рядом с кодом каждого репозитория; временные файлы удалены.

**Состав:**
- **`BRIEF.md` в корне каждого репозитория проекта** — основного и каждого сабмодуля (`packages/*`, `services/*`,
  `mcp/*`, `skills/*`): что этот репозиторий делает, его решения и устройство. (Фаза 0, «Сделано: устройство
  приложения…», 45%.)
- **`BRIEF.md` основного репозитория разнесён на файлы по подсистемам** с оглавлением; якоря `spec:` во всём коде
  обновлены. (Пакеты, «Спецификация и база знаний», 40%.) Решено (В18): свой `BRIEF.md` — в
  корне каждого сабмодуля, который часть системы; из корневого — ссылки.
- **Ссылочная целостность при переносе** (решение владельца 2026-11-18). Сначала — скрипт проверки: каждая `spec:`
  во всех репозиториях (код, тесты, миграции, SQL, JS, конспекты) ведёт в существующий файл и существующий заголовок;
  путь — от корня основного репозитория (`spec: BRIEF.md#…` или `spec: packages/<имя>/BRIEF.md#…`). Скрипт зелёный до
  переноса; раздел переезжает в бриф сабмодуля вместе с переписью всех ссылок на его якоря (в том числе в коде
  сабмодулей и в основном репозитории), скрипт зелёный после каждого шага. Сейчас ссылок `spec:` — около 700 в
  ~310 файлах.
- **Таблицы «Устройство приложения на opencck» переписаны по фактическим классам;** «Структура репозитория» знает
  `services/`, `mcp/`, `skills/`; «Решения» остаются разделом. (Фаза 0.)
- **Перенос из `ROADMAP.md`:** сквозные требования — в «Соглашения»; «Пакеты и репозитории» — в «Структуру
  репозитория»; итоги сверки, которые стали решениями («оставить как есть» с причиной, принятые риски), — в разделы
  подсистем. Перенос из этого файла: итоги каждой фазы Д1–Д16.
- **Ссылки убраны:** `ROADMAP.md` и `ROADMAP_FINALIZATION.md` не упоминаются в `BRIEF.md`, `CLAUDE.md`, README,
  конспектах; правила `CLAUDE.md` «работа идёт по фазам» переписаны на «задача сверяется с требованиями `BRIEF.md`».
- **Удаление:** `ROADMAP.md`, `ROADMAP_FINALIZATION.md`, `AUDIT.md` (когда все находки закрыты и перенесены),
  каталог `plans/`. Граф знаний обновлён.

**Готово, когда:** в каждом репозитории проекта есть `BRIEF.md`; ни одна ссылка `spec:` не ведёт в пустоту
(проверка скриптом); поиск по всем репозиториям не находит `ROADMAP`; `composer check` и развёртывание зелёные.

## Что решено оставить как есть

49 пунктов сверки с решением «оставить как есть» и ещё несколько, где владелец выбрал не менять: ручной порядок
развёртывания; маршруты соединений и пакеты `llm`/`connectors`/`messenger`; возобновление после перезапуска;
изоляция песочницы; запрос карточки незнакомым агентам без срока. Их причины переносятся в `BRIEF.md` в фазе Д17.

Принятые владельцем риски, которые нужно записать в `BRIEF.md` явно: браузер без подтверждений по умолчанию; импорт
скиллов блокирует только `critical`; денежных лимитов по умолчанию нет; лимиты запуска увеличены в 10 раз; файлы
памяти, скиллов и промптов открыты инструментам записи; боты в группах слушаются по умолчанию.
