# AI Agent Orchestration Patterns: A Production Guide — конспект

## Кратко

Обзорная статья о том, как выбирать топологию взаимодействия нескольких агентов. Описаны четыре паттерна — orchestrator-worker, supervisor, hierarchical, swarm — для каждого даны условия применения, режимы отказа и пример формы задачи. Главный тезис: самая дорогая ошибка — выбрать паттерн по демо фреймворка, а не по форме рабочей нагрузки; неверная топология умножает задержку, стоимость и сложность отладки. Второй тезис: сначала стоит спросить, нужна ли мультиагентность вообще. Написана для инженеров и CTO, выбирающих архитектуру; кода нет, уровень — концептуальный, с рекламой услуг компании.

## Ключевые идеи

**Два независимых слоя «оркестрации»** (строка 19):
1. поток исполнения внутри одного агента или workflow — sequential, parallel, conditional, loop;
2. топология между агентами — кто кого вызывает, кто решает о передачах, кто владеет глобальным состоянием.
Слои комбинируются (супервизор, у которого каждый агент внутри использует параллельный workflow); их смешение даёт неотлаживаемые архитектуры.

**Четыре топологии:**

| Паттерн | Суть | Когда применять | Режимы отказа | Пример формы |
|---|---|---|---|---|
| Orchestrator-Worker | Оркестратор декомпозирует, рассылает, агрегирует; воркеры не общаются между собой | Нагрузка чисто делится на независимые подзадачи; подзадачи можно задать до запуска; 2–6 специалистов без пересечения обязанностей; агрегация простая (склеить, суммировать, оценить-и-выбрать) | Оркестратор — узкое место при высокой конкурентности; плохое решение оркестратора расходится по всем воркерам; обмен контекстом между воркерами идёт через оркестратор и стоит токенов | Сравнение трёх вендоров по цене, поддержке и безопасности |
| Supervisor | Супервизор решает, кто действует следующим, смотрит результат, решает снова | Ветвление зависит от предыдущих результатов; план меняется по ходу; нужна единая точка решения об эскалации человеку; 3–8 подчинённых | Токены супервизора доминируют (он читает каждый результат); over-delegation (ничего не добавляет); under-delegation (делает всё сам) | Триаж клиентской поддержки |
| Hierarchical | Дерево: менеджер → супервизоры → листовые воркеры | 3+ уровня абстракции; задача не влезает в контекст одного супервизора; разные домены требуют разных супервизоров; есть естественная оргструктура | Отказ координатора останавливает всю ветку под ним; потери при пересказе между уровнями; стоимость токенов растёт примерно линейно с глубиной дерева; отказ может быть на любом уровне | Генератор консалтингового отчёта: главред, 3 редактора разделов, дюжина исследователей |
| Swarm | Равноправные агенты передают управление по локальным решениям, координатора нет | Действительно равноправная совместная работа; общая цель при разной специализации; отказ одного агента не должен останавливать систему; есть сильная наблюдаемость и детекция петель; максимум 2–5 агентов | Петли передач; «горячая картошка» (агенты избегают ответственности); эмерджентное поведение вне спецификаций; отладка требует восстановления графа передач из логов | Код-ревью: агенты безопасности, производительности и стиля |

**Различие orchestrator-worker и supervisor** — в моменте планирования: в первом план целиком составляется до запуска и воркеры работают параллельно без дальнейшего участия оркестратора; во втором супервизор «думает между ходами».

**Пять вопросов выбора** (строка 158):
1. Можно ли задать весь план до начала работы? Да → orchestrator-worker; нет → supervisor и выше.
2. Зависит ли следующий шаг от предыдущего результата? Сильно → supervisor; слабо → orchestrator-worker.
3. Удерживает ли один агент всю задачу в контексте? Нет → hierarchical.
4. Есть ли в предметной области ясная иерархия полномочий? Да → supervisor или hierarchical; нет → возможен swarm.
5. Обязательна ли отладка в проде? Да (почти всегда) → избегать swarm без вложений в наблюдаемость передач.

Для типовых нагрузок (операции, финансы, поддержка, внутренние инструменты) ответ — orchestrator-worker или supervisor; hierarchical — для сложной многодоменной аналитики; swarm — для задач исследовательского типа.

**Цифры и количественные утверждения:**
- вступительный кейс: 7 агентов, 47 с среднее время ответа, $1.80 токенов на диалог, закрыт на 3-м месяце;
- orchestrator-worker — «большинство работающих систем» (со ссылкой на Padiso, 2026; без числа);
- в полносвязном swarm поверхность отказов растёт квадратично от числа агентов, выше 8 агентов её не покрыть end-to-end тестами (со ссылкой на Aihola, 2026);
- рекомендуемые размеры: 2–6 воркеров, 3–8 подчинённых, 2–5 агентов в swarm;
- порог-сигнал: доля супервизора в общих токенах выше 60%.

**Слоистость проектирования** (строка 194): 1) выбрать паттерн под форму нагрузки; 2) решить — явный конечный автомат или более свободный промпт-цикл; 3) обернуть в durable runtime; 4) добавить наблюдаемость, evals, guardrails. Шаги 1–2 независимы от 3–4. Durable execution не спасает от петель передач — «будет надёжно зацикливаться до таймаута workflow».

**Инструменты — часть оркестрации** (строка 203): синхронность, таймаут, политика ретраев, ключ идемпотентности — решения уровня оркестрации. В orchestrator-worker отказ инструмента внутри воркера локализован; в swarm вызов внутри любого узла может изменить глобальное состояние, которое следом читает другой.

- **Глубина.** Средняя, концептуальная. Сильные стороны — чёткое различение orchestrator-worker и supervisor, разведение слоёв (поток исполнения / топология / durable execution) и таблица ранних сигналов. Реализация не раскрыта вовсе.

- **Спорное и неподкреплённое.** Вступительный кейс ритейлера анонимен и не подтверждён; вывод «супервизор бы это спас» — утверждение без доказательства. «Большинство работающих систем — orchestrator-worker» — без числа.
