# AI Agent Orchestration Patterns (Azure Architecture Center) — конспект

## Кратко

Справочное руководство Microsoft по паттернам мультиагентной оркестрации. Описаны пять паттернов — sequential, concurrent, group chat (с подвидом maker-checker), handoff и magentic — каждый по единому шаблону: определение, синонимы, когда применять, когда избегать, пример сценария. Главный тезис: использовать наименьший уровень сложности, который надёжно решает задачу (прямой вызов модели → один агент с инструментами → мультиагентная оркестрация), а паттерн выбирать по характеру координации. Вторая половина — сквозные соображения по реализации: контекст и состояние, надёжность, безопасность, стоимость, наблюдаемость, участие человека, антипаттерны. Для архитекторов и разработчиков; кода нет, паттерны заявлены как технологически нейтральные.

## Ключевые идеи

**Три уровня сложности** (строка 23) — брать наименьший, который надёжно работает:

| Уровень | Когда | Соображения |
|---|---|---|
| Прямой вызов модели | Одношаговые задачи: классификация, суммаризация, перевод | Если задача решается промптом — агент не нужен |
| Один агент с инструментами | Разнообразные запросы в одном домене, часть требует динамических инструментов | Часто правильный дефолт для enterprise; проще отлаживать; ставить лимит итераций против бесконечных циклов вызова инструментов |
| Мультиагентная оркестрация | Кросс-доменные задачи; разные границы безопасности у агентов; выигрыш от параллельной специализации | Оправдана, когда один агент не справляется из-за сложности промпта, перегрузки инструментами или требований безопасности |

**Пять паттернов** (сводная таблица статьи, строка 286, дополнена синонимами из разделов):

| Паттерн | Синонимы | Координация | Маршрутизация | Лучше всего для | Риски |
|---|---|---|---|---|---|
| Sequential | pipeline, prompt chaining, linear delegation | Линейный пайплайн, каждый агент обрабатывает выход предыдущего | Детерминированная, заранее заданный порядок | Пошаговое улучшение с ясными зависимостями стадий | Сбои ранних стадий распространяются; нет параллелизма |
| Concurrent | parallel, fan-out/fan-in, scatter-gather, map-reduce | Агенты независимо работают над одним входом | Детерминированный или динамический выбор агентов | Независимый анализ с разных позиций; чувствительность к задержке | Нужно разрешение конфликтов; ресурсоёмкость |
| Group chat | roundtable, collaborative, multiagent debate, council | Агенты пишут в общую ветку | Chat manager управляет очерёдностью | Консенсус, мозговой штурм, maker-checker | Петли разговора; трудно управлять при нескольких агентах |
| Handoff | routing, triage, transfer, dispatch, delegation | Один активный агент в каждый момент | Агенты сами решают, когда передать управление | Задачи, где нужный специалист выясняется по ходу | Бесконечные передачи; непредсказуемые маршруты |
| Magentic | dynamic orchestration, task-ledger-based orchestration, adaptive planning | План–сборка–исполнение; менеджер ведёт task ledger | Менеджер динамически назначает и переставляет задачи | Открытые задачи без заранее известного пути | Медленная сходимость; зависания на неясных целях |

**Уточнения по паттернам:**
- Sequential: какой агент вызывается следующим — определено детерминированно в workflow, это не выбор агентов.
- Concurrent: агрегация необязательна (агенты могут просто параллельно выполнять действия); если нужна — голосование/большинство для классификации, взвешенное слияние для оценок, LLM-синтез для связного текста. Оркестратор должен знать, какие агенты зарегистрированы; возможен и вызов всех, и динамический выбор. Агент может внутри сам запускать свою оркестрацию.
- Group chat: агенты обычно read-only, не меняют работающие системы; человек может взять на себя роль chat manager; рекомендация — не более трёх агентов.
- Maker-checker (синонимы: evaluator-optimizer, generator-verifier, critic loops, reflection loops): требует ясных критериев приёмки, лимита итераций и fallback при его достижении (эскалация человеку или лучший результат с предупреждением о качестве).
- Handoff: агенты обычно не работают параллельно; если нужный агент определяется из исходного входа — использовать детерминированную маршрутизацию или простой диспетчер, который не участвует в обработке.
- Magentic: «в некотором смысле расширение group chat»; отличие — менеджер строит план, а остальные агенты инструментами меняют внешние системы. Менеджер регулярно проверяет, выполнен ли запрос или работа застопорилась, и правит ledger.

**Стоимость по паттернам** (строка 341): sequential и handoff вызывают агентов по одному — ограничивают одновременное потребление, но копят стоимость по шагам; concurrent даёт пропускную способность, но всплески потребления; magentic — наименее предсказуем, так как менеджер итерирует, пока не построит рабочий план.

**Контекст** (строка 306): для следующего агента выбирать между полным сырым контекстом, сжатой сводкой и только новой инструкцией без накопленного контекста — последнее предпочтительно, если агент может так работать.

**Антипаттерны** (строка 362): сложный паттерн там, где хватит sequential/concurrent; агенты без содержательной специализации; игнорирование задержки многошаговой коммуникации; общее изменяемое состояние у параллельных агентов; детерминированный паттерн для недетерминированного процесса и наоборот; игнорирование ресурсных ограничений при concurrent; раздувание контекстных окон.

**Цифр и измерений в статье нет** — единственные числа: «три или меньше агентов» в group chat и размеры команд в примерах.

## Практика

**Кода и промптов в статье нет.** Есть ссылка на примеры Declarative Workflows в репозитории Agent Framework (строка 395).

**Архитектурные схемы.** В оригинале у каждого паттерна и примера есть диаграмма; в локальной копии картинок нет. Текстовые описания (alt-текст) сохранились только для четырёх: общая схема group chat (136), пример с парками (183), общая схема magentic (239), пример SRE (269).

**Пять сценариев-примеров** (состав агентов расписан):
- Sequential (72): выбор шаблона → настройка положений → проверка соответствия регуляторике → оценка рисков.
- Concurrent (115): фундаментальный, технический, сентимент- и ESG-анализ одной акции → сводная рекомендация.
- Group chat (178): агенты по вовлечению сообщества, экологическому планированию, бюджету и эксплуатации + сотрудник департамента в чате.
- Handoff (221): triage → техническая инфраструктура → финансовое урегулирование → человек.
- Magentic (264): менеджер + агенты диагностики, инфраструктуры, коммуникаций, отката; чекпойнты согласования и эскалация инженерам.

**Чек-листы «когда применять / когда избегать»** — по каждому паттерну (строки 51/61, 93/104, 142/159, 202/211, 245/254).

**Надёжность** (строка 318): таймауты и ретраи; graceful degradation при отказе одного или нескольких агентов; показывать ошибки, а не скрывать; валидировать выход агента перед передачей дальше (ретрай, запрос уточнения или остановка); circuit breaker для зависимостей; изоляция агентов (вычислительная; учитывать rate limiting общего MaaS-эндпойнта или общего хранилища знаний при параллельной работе); чекпойнты SDK для восстановления.

**Состояние** (строка 312): для долгих и многосессионных оркестраций хранить прогресс, промежуточные результаты и историю во внешнем долговременном хранилище; объём сохраняемого — минимально необходимый (токены и приватность).

**Безопасность** (строка 332): аутентификация и защищённая сеть между агентами; аудит; least privilege; security trimming в каждом агенте (агент имеет широкий доступ, но не должен отдавать данные, недоступные пользователю); content safety guardrails на входе пользователя, вызовах инструментов, ответах инструментов и финальном выводе.

**Стоимость** (строка 345): модель под сложность задачи агента (для классификации, извлечения, форматирования — меньшие модели); мониторинг токенов по агентам и по запускам; компактизация контекста между агентами.

**Наблюдаемость и тесты** (строка 353): инструментировать все операции и передачи; метрики производительности и ресурсов по каждому агенту; тестируемые интерфейсы агентов; интеграционные тесты со scoring rubrics или LLM-as-judge вместо точного сравнения.

**Human-in-the-loop** (строка 360): определить точки, где нужен человек, обязательны ли они и что означает ответ — одобрение (движение вперёд) или обратная связь (возврат агенту). Обязательные точки делают шаг синхронным — сохранять состояние в этих чекпойнтах. Можно привязывать согласование к отдельным вызовам инструментов, а не ко всему выводу агента.

## Оценка

- **Первоисточник или пересказ.** Первоисточник в жанре вендорского архитектурного руководства: собственная систематизация Microsoft, поддерживаемая названными авторами. Это каталог паттернов, а не отчёт об опыте эксплуатации: измерений и кейсов из практики нет.
- **Глубина.** Самое широкое и систематичное покрытие из трёх статей набора (5 паттернов + 10 сквозных тем), единообразная структура, удобно как справочник и словарь синонимов. На уровне каждого совета — неглубоко: рекомендации перечислены списками без механики реализации, порогов и цифр.
- **Маркетинг.** Умеренный. Основная часть заявлена и действительно написана как технологически нейтральная; продукты Microsoft (Agent Framework, Semantic Kernel, Foundry Agent Service) вынесены в раздел «Implementations», там же названы конкуренты (LangChain, CrewAI, OpenAI Agents SDK). По тексту рассыпаны ссылки на документацию Microsoft (MCP на Azure, guardrails Foundry, HITL в Agent Framework).
- **Спорное и неподкреплённое.** Примеры — вымышленные иллюстрации, а не кейсы. Рекомендация «три или меньше агентов» в group chat дана без обоснования. Название «magentic» не объяснено (от составителя конспекта, не из статьи: вероятно, отсылает к системе Magentic-One от Microsoft Research). Паттерна «orchestrator-workers» под этим именем в классификации нет: динамическая декомпозиция оркестратором распределена между concurrent (с динамическим выбором агентов) и magentic — соотнесение с терминологией других источников читателю придётся делать самому (это наблюдение составителя).
