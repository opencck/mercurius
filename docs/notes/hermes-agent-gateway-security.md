# hermes-agent: шлюз, безопасность, исполнение

Общий конспект репозитория — [docs/notes/hermes-agent.md](hermes-agent.md). Здесь — только шлюз и каналы, подтверждения и безопасность, окружения исполнения, браузер, MCP, логи и развёртывание. Ядро/цикл и память/скиллы — в соседних конспектах.

Ссылки на код даны в формате `references/hermes-agent/<путь>@e96221fa:Lx-Ly (имя)`. Всё, что помечено «**Вывод:**», — моя оценка, а не утверждение из репозитория.

> Конспект составлен по документации и точкам входа в коде; большинство файлов читалось фрагментами. Что именно прочитано, а что нет — в разделе 14.

## 1. Кратко

Шлюз hermes — один долгоживущий процесс, в котором адаптеры платформ превращают сообщения в единое событие `MessageEvent`, а раннер маршрутизирует их по ключу сессии, проверяет доступ и запускает ход агента; обязательных методов у адаптера четыре, всё остальное (правка, кнопки, typing, файлы) — необязательные возможности с текстовым откатом. Опасные команды ловятся чёрным списком регулярных выражений по нормализованному тексту команды; решение принимает вспомогательная LLM или человек через карточку в чате (`once / session / always / deny`), а поток агента на это время блокируется; молчание считается отказом. Сам проект прямо заявляет, что ни подтверждения, ни маскирование, ни сканеры не являются границей безопасности — границей служит только операционная система: либо песочница для команд (docker, ssh, облако), либо контейнер вокруг всего агента. Браузер на этом коммите — один инструмент `browser_exec`, исполняющий код модели поверх CDP; MCP-серверы подключаются по stdio или HTTP, их инструменты попадают в общий реестр под именем `mcp__<сервер>__<инструмент>`. Секреты лежат в `.env`, вырезаются из окружения дочерних процессов и маскируются в логах, выводе инструментов и исходящих сообщениях. Для Меркурия ценнее всего контракт канала, механика подтверждений через канал и накопленные приёмы работы с Telegram; модель изоляции и чёрный список команд переносить один к одному не стоит.

## 2. Шлюз

### 2.1. Процесс и состав

- Шлюз — один долгоживущий процесс (`hermes gateway run`), в котором живут все адаптеры платформ, сессии, планировщик cron и фоновые наблюдатели. Фасад — `GatewayRunner` в `gateway/run.py`, фазы разнесены по примесям `gateway/run_*.py` (startup, adapters, inbound, turn, busy, notifications, shutdown), сессии — `gateway/session*.py`, slash-команды — `gateway/slash_commands_*.py`, авторизация — `gateway/authz_mixin.py`, адаптеры — над `gateway/platforms/base.py`. Источник: `references/hermes-agent/gateway/AGENTS.md@e96221fa:L6-L17`, таблица файлов — `references/hermes-agent/website/docs/developer-guide/gateway-internals.md@e96221fa:L359-L373`.
- Поток сообщения: адаптер нормализует сырое событие в `MessageEvent` → базовый адаптер проверяет «сессия занята?» → `GatewayRunner._handle_message()` строит ключ сессии, проверяет авторизацию, разбирает slash-команду, иначе создаёт/берёт из кеша `AIAgent` и запускает ход → ответ уходит через тот же адаптер (`gateway-internals.md@e96221fa:L679-L693`).
- Адаптеры мессенджеров — плагины в `plugins/platforms/<имя>/adapter.py` (+ `plugin.yaml`); в `gateway/platforms/` остались базовый класс и HTTP-входы (`api_server.py` — REST/OpenAI-совместимый API, `webhook.py`, `msgraph_webhook.py`). Загрузка ленивая: SDK платформы импортируется только при старте шлюза (`gateway-internals.md@e96221fa:L769-L803`).
- Перечень платформ (только названия): Telegram, Discord, Slack, WhatsApp (мост Baileys и Cloud API), Matrix, Mattermost, Email (IMAP/SMTP), SMS (Twilio), DingTalk, Feishu/Lark, WeCom, LINE, Teams, Signal, IRC, BlueBubbles/Photon (iMessage), Weixin, QQ, Google Chat, ntfy, Raft, SimpleX, Home Assistant, Buzz, A2A; плюс `relay` — общий адаптер к внешнему «коннектору» по WebSocket. Таблица возможностей (голос, картинки, файлы, треды, реакции, typing, стриминг) — `references/hermes-agent/website/docs/user-guide/messaging/index.md@e96221fa:L31-L62`.
- Блокировка учётных данных: адаптер с уникальным токеном берёт `acquire_scoped_lock()` в `connect()`, чтобы два профиля не подняли одного бота; при конфликте на старте шлюз выходит с кодом 78, чтобы супервизор не перезапускал его в цикле (`gateway-internals.md@e96221fa:L822-L826`).

### 2.3. Нормализованное входящее событие

`MessageEvent` (`references/hermes-agent/gateway/platforms/event.py@e96221fa:L66-L147`):

- `text`, `message_type` (`TEXT | LOCATION | PHOTO | VIDEO | AUDIO | VOICE | DOCUMENT | STICKER | COMMAND`, `event.py@e96221fa:L46-L56`);
- `source: SessionSource`, `user_id`, `user_name`, `message_id`, `timestamp`, `raw_message`;
- вложения: `media_urls` (локальные пути уже скачанных файлов), `media_types`, `media_filenames` (исходное имя — только для показа, никогда не путь);
- ответ на сообщение: `reply_to_message_id`, `reply_to_text`, `reply_to_author_*`, `reply_to_is_own_message`;
- `platform_update_id`, `edit_revision` — для дедупликации и рестарта;
- `internal: bool` — синтетическое событие (уведомление о фоновом процессе), обходит авторизацию пользователя;
- `allow_gateway_control: bool` — может ли событие вообще быть командой или ответом на карточку; у проактивных событий от плагинов `False`, чтобы недоверенный текст не стал `/approve` (`event.py@e96221fa:L119-L121`);
- `channel_prompt`, `auto_skill`, `channel_context` — привязки канала/темы;
- методы `is_command()`, `get_command()` (отрезает `@botname`, отвергает пути вида `/usr/bin`), `get_command_args()` (чинит автозамену `--` → `—` на iOS) — `event.py@e96221fa:L194-L217`.

`SessionSource` (`references/hermes-agent/gateway/session.py@e96221fa:L69-L111`): `platform`, `chat_id`, `chat_name`, `chat_type` (`dm | group | channel | thread`), `user_id`, `user_name`, `thread_id`, `parent_chat_id`, `is_bot`, `scope_id`, `profile`, `role_authorized`. Признаки доверия (`delivered_via_upstream_relay`) намеренно не сериализуются — чтобы их нельзя было подделать по проводу.

Имена вложений чистятся `clean_attachment_filename`: убираются каталоги, управляющие и bidi-символы, длина ≤ 255 (`event.py@e96221fa:L28-L43`).

### 2.4. Маршрутизация в сессии

- Ключ сессии строит только `build_session_key()` (`session.py@e96221fa:L722-L769`): `<ns>:<platform>:<chat_type>[:<chat_id>][:<thread_id>][:<user>]`, где `ns` = `agent:main` для профиля по умолчанию. Пример из документации: `agent:main:telegram:private:123456789` (`gateway-internals.md@e96221fa:L695-L707`).
- Правила изоляции: личка — по `chat_id`; группа — по умолчанию отдельная сессия на участника (`group_sessions_per_user=True`); тред/тема — общая на всех, если не включён `thread_sessions_per_user` (`session.py@e96221fa:L742-L751`).
- `SessionStore` (`session.py@e96221fa:L826`) хранит соответствие «ключ маршрута → id сессии» и метаданные (переопределение модели, флаг yolo); `/new` и `/reset` выдают маршруту новую сессию (`reset_session`, `session.py@e96221fa:L1206`).
- В системный промпт добавляется блок контекста сессии (платформа, чат, пользователь); значения из платформы проходят через `neutralize_untrusted_inline_text` (`session.py@e96221fa:L286-L295`, `L390`), а при `privacy.redact_pii` идентификаторы хешируются.

### 2.5. Занятая сессия: очередь и прерывание

Два последовательных сторожа (`gateway/AGENTS.md@e96221fa:L19-L27`, `gateway-internals.md@e96221fa:L709-L717`):

1. **Базовый адаптер.** `handle_message` ставит «сессия активна» синхронно, до запуска фоновой задачи, чтобы второе сообщение не проскочило (`base.py@e96221fa:L3901-L3909`). Если сессия уже активна — `_handle_message_while_active` (`base.py@e96221fa:L3933-L4030`):
   - команды обхода (`/stop`, `/new`, `/approve`, `/deny`, `/queue`, `/status`) исполняются **инлайн**, а не через фоновую задачу — иначе `/approve` встал бы в очередь за ходом, который сам ждёт этого `/approve` (взаимная блокировка, PR #4926);
   - если агент ждёт ответа на clarify — текст уходит в перехватчик ответа, а не в очередь;
   - иначе событие получает обработчик занятой сессии раннера; без него — складывается в `_pending_messages` (тексты сливаются, фото-серии копятся без прерывания).
2. **Раннер** (`gateway/run_busy.py`): для каждой команды берёт `CommandDef.busy_policy`; остальное — по режиму `display.busy_input_mode` (`messaging/index.md@e96221fa:L509-L535`):
   - `interrupt` (по умолчанию) — перенаправить текущий ход: генерация модели перезапускается с уже показанным текстом как контрольной точкой, выполняющийся инструмент **не убивается**, поправка применяется на границе результата инструмента; выполняющаяся команда терминала переводится в фон;
   - `queue` — сообщение ждёт и становится следующим ходом;
   - `steer` — текст впрыскивается в текущий ход после ближайшего вызова инструмента.
   - `/stop` — жёсткая остановка всегда.
   - Быстрые подряд сообщения склеиваются: `busy_text_debounce_seconds: 0.35`, потолок `busy_text_hard_cap_seconds: 1.0`.

### 2.6. Доставка ответа

- **Журнал доставки.** Итоговый ответ записывается в `state.db` вокруг отправки. Если шлюз упал между «ответ готов» и «платформа подтвердила», после старта ответ досылается, а не теряется и не пересчитывается. Семантика честно at-least-once: неоднозначная досылка помечается «♻️ Recovered reply — may be a duplicate»; при flood control повтор — после истечения штрафа; иначе backoff 30 с → 2 мин; максимум 3 попытки и 24 часа свежести (`messaging/index.md@e96221fa:L286-L316`).
- **Стриминг, разбиение, файлы** — см. 2.7 и раздел 3.
- **Фоновые уведомления.** `terminal(background=true, notify_on_complete=true)` вооружает наблюдателя на цикле шлюза; по завершении процесса он создаёт **новый ход агента** (внутреннее событие). Подробность — `display.background_process_notifications`: `concise` (по умолчанию) / `all` / `result` / `error` / `off`. Несколько завершений, пришедших во время занятой сессии, складываются в один ход (`gateway-internals.md@e96221fa:L899-L930`).
- **Прогресс инструментов.** `display.tool_progress: off | new | all | verbose | log`, группировка `accumulate` (править один «пузырь») или `separate` (`messaging/index.md@e96221fa:L554-L567`).
- **Домашний канал** и явные цели (`telegram:-100…`) — для cron и `hermes send`; результаты cron не подмешиваются в историю чата (`gateway-internals.md@e96221fa:L828-L837`).

### 2.7. Стриминг и разбиение

**Потребитель потока** — `GatewayStreamConsumer` (`references/hermes-agent/gateway/stream_consumer.py@e96221fa:L106-L118`). Агент работает в отдельном потоке и синхронно вызывает `on_delta(text)`; дельты кладутся в потокобезопасную очередь, асинхронная задача `run()` их копит и с ограничением частоты правит одно сообщение платформы (`send`, затем `edit_message`). Через ту же очередь идут служебные маркеры: конец, новый сегмент, комментарий, прогресс инструмента, итоговый текст, граница подтверждения (`stream_consumer.py@e96221fa:L48-L60`).

- Настройки `StreamingConfig` (`references/hermes-agent/gateway/config.py@e96221fa:L509-L530`): `enabled: false` по умолчанию; `transport: auto | draft | edit | off`; `edit_interval: 0.8` с; `buffer_threshold: 24` символа; курсор `" ▉"`; `fresh_final_after_seconds` — если превью висело дольше, финал уходит новым сообщением, чтобы время сообщения отражало завершение.
- Правка делается, когда прошёл интервал **или** накопилось больше порога символов; при активном штрафе за flood порог не действует — только интервал, запрошенный сервером (`_should_edit`, `stream_consumer.py@e96221fa:L814-L848`). После трёх подряд отказов по flood правки отключаются (`_MAX_FLOOD_STRIKES = 3`, `L111`).
- Если текущий ход сброшен (`/new`, `/stop`), потребитель бросает поток, а не доставляет устаревшие дельты (`stream_consumer.py@e96221fa:L588-L591`).
- Перед карточкой подтверждения поток «закрывается» (`close_for_approval_prompt`, `L405-L428`), чтобы карточка не оказалась посреди редактируемого сообщения.
- **Маскирование секретов в потоке** (`references/hermes-agent/gateway/stream_consumer_redact.py@e96221fa:L1-L16`): в промежуточные кадры попадает только «устоявшийся» префикс — текст, который уже не может оказаться началом секрета (недописанный токен, `Authorization:` без значения, открытый PEM-блок). Иначе ключ сначала показали бы, а потом замаскировали.
- Инварианты для платформ с нативным стримингом («поток и есть сообщение»): кадры — строго префиксы друг друга; финал объявляет потребитель, адаптер не угадывает; сверка — правкой, а не новой отправкой. Каждый инвариант — след реального инцидента с дублями (`gateway/AGENTS.md@e96221fa:L29-L56`).

**Разбиение длинных сообщений** — `chunk_markdown_message(content, max_length=4096, len_fn)` (`references/hermes-agent/gateway/platforms/base_chunking.py@e96221fa:L38-L135`):

- длина считается функцией платформы (для Telegram — в кодовых единицах UTF-16);
- режется по переводу строки, иначе по пробелу;
- разрез внутри блока кода закрывает ограждение и открывает его заново (с тем же языком) в следующем куске;
- разрез не попадает внутрь inline-кода и незакрытой markdown-ссылки;
- таблица переносится целиком, а если не помещается — режется по строкам с повтором заголовка;
- к кускам добавляется `(1/3)`; под индикатор резервируется 12 единиц.

**Файлы в ответе.** Модель пишет в тексте директиву `MEDIA:/путь`; база вырезает её из текста (`extract_media`, `base.py@e96221fa:L3167`) и отправляет файл методом адаптера. Путь проверяется `validate_media_delivery_path` (`base.py@e96221fa:L3105`). Файл отправляет **процесс шлюза**, поэтому путь должен существовать на его стороне: файл, созданный внутри docker-песочницы в `/workspace`, шлюзу не виден — нужен общий том (`references/hermes-agent/website/docs/user-guide/messaging/telegram.md@e96221fa:L345-L372`).

## 3. Telegram-адаптер

Код — `references/hermes-agent/plugins/platforms/telegram/`: `adapter.py` (6641 строка) и около 60 модулей-спутников `telegram_*.py`. Библиотека — `python-telegram-bot` (PTB). Класс `TelegramAdapter` — `adapter.py@e96221fa:L398`.

### 3.1. Получение обновлений

- **Режим** выбирает `connect()` (`adapter.py@e96221fa:L2917-L2975`): задан `TELEGRAM_WEBHOOK_URL` — webhook, иначе long polling.
- **Polling** (`_start_polling_mode`, `adapter.py@e96221fa:L2888-L2915`): сначала снимается старый webhook; ошибки polling разбираются по типам — конфликт 409 (второй процесс с тем же токеном), сетевые, прочие — и запускают восстановление в фоне. Если polling не поднялся, адаптер остаётся «в деградированном режиме»: шлюз жив, повторы идут в фоне. Отдельный цикл-сердцебиение ловит «зависший» long-poll сокет (`_polling_heartbeat_loop`, `adapter.py@e96221fa:L1964`).
- **Webhook** (`_start_webhook_mode`, `adapter.py@e96221fa:L2858-L2886`): порт `TELEGRAM_WEBHOOK_PORT` (8443), `TELEGRAM_WEBHOOK_SECRET` **обязателен** — без него адаптер отказывается стартовать, потому что иначе точка входа принимает поддельные обновления (GHSA-3vpc-7q5r-276h).
- **Очередь на стороне Telegram.** При переподключении накопленные обновления сохраняются всегда; при холодном старте — по `drop_pending_on_cold_boot` (по умолчанию не отбрасывать), решение пишется в лог (`adapter.py@e96221fa:L2843-L2856`).
- **Параллельность.** Стандартный обработчик PTB ждёт каждое обновление по очереди — «один медленный ход глушит все чаты». Здесь обновления разных чатов идут параллельно (пул 32), одного чата — строго по порядку (`adapter.py@e96221fa:L2953-L2956`; `references/hermes-agent/plugins/platforms/telegram/update_admission.py@e96221fa:L29`).
- **Дедупликация `update_id`** (`update_admission.py@e96221fa:L1-L9`, `L29-L35`): последние 4096 принятых id в памяти плюс файл квитанций на бота со сроком 24 часа (дольше Telegram обновление не хранит). Защищает от повторной обработки, когда подтверждение `getUpdates` не дошло. Гарантии exactly-once нет.
- **Блокировка токена:** `_acquire_platform_lock('telegram-bot-token', ...)` (`adapter.py@e96221fa:L2937`).
- **Сеть:** отдельный прокси для Telegram (`telegram.proxy_url` / `TELEGRAM_PROXY`, приоритетнее общего `HTTPS_PROXY`; `telegram.md@e96221fa:L455-L470`), запасные IP (`_fallback_ips`, `adapter.py@e96221fa:L1054`; `telegram_network.py` не читал), свой `base_url` для локального Bot API сервера (`adapter.py@e96221fa:L2942-L2948`).

### 3.2. Типы содержимого

Обработчики регистрирует `_register_handlers` (`adapter.py@e96221fa:L2699-L2722`): текст, команды, геолокация/место, кубик, контакт, медиа (фото, видео, видеозаметка, аудио, голос, документ, стикер), создание темы форума, callback-кнопки, inline-запросы, плюс наблюдатель всех обновлений (группа 99) для событий платформы — реакций и правок.

- **Медиа** (`_handle_media_message`, `adapter.py@e96221fa:L6169-L6223`): авторизация отправителя → построение события → **скачивание в локальный кеш сразу**, потому что ссылки на файлы Telegram живут около часа. Фото — берётся самый крупный размер; голос — кешируется для распознавания речи; аудио/видео — файлом; стикер — описывается vision-моделью.
- **Документы** (`_cache_inbound_document`, `adapter.py@e96221fa:L6091-L6130`): лимит 20 МБ (2 ГБ со своим Bot API сервером, `adapter.py@e96221fa:L597`); проверка размера идёт до ветки «картинка-документ», чтобы её нельзя было обойти. Слишком большой файл превращается в текстовую заметку в событии, а не в ошибку.
- **Альбомы** (`media_group_id`) копятся `MEDIA_GROUP_WAIT_SECONDS = 1.5` с и уходят одним событием (`adapter.py@e96221fa:L413`, `L6219-L6222`).
- **Склейка текста.** Клиент Telegram сам режет длинный текст на сообщения по ~4096 символов. Адаптер буферизует текст с адаптивной задержкой (`_text_batch_delay_for`, `adapter.py@e96221fa:L5975-L5986`; константы `L434-L442`): до 320 символов — 0,18 с, до 1024 — 0,24 с, иначе настроенный потолок (1,5 с); если последний кусок длиной ≥ 4000 — ждать 2,0 с, «продолжение почти наверняка будет».
- Подпись, набранная прямо перед вложением, присоединяется к его ходу (`claim_pending_text` / `absorb_claimed_text`, `adapter.py@e96221fa:L6194`, `L6217`).
- **Ответ на сообщение:** текст и автор цитируемого сообщения кладутся в `reply_to_*` (`_reply_context`, `adapter.py@e96221fa:L6362`). Telegram не возвращает тело собственных сообщений бота в `reply_to_message`, поэтому адаптер сам запоминает отправленный текст (`_record_sent_text`, `adapter.py@e96221fa:L1335`, `L3443`).
- Нормализация в `MessageEvent` — `_build_message_event` (`adapter.py@e96221fa:L6396`).

### 3.3. Команды

- Меню бота собирается из центрального реестра slash-команд плюс команды плагинов и скиллов и регистрируется `set_my_commands` в трёх областях: по умолчанию, все личные чаты, все группы (`_register_command_menu`, `adapter.py@e96221fa:L2486-L2515`).
- Ограничения: Telegram допускает 100 команд, но есть недокументированный предел размера запроса около 4 КБ — потолок по умолчанию 60; описание обрезается до 256 символов; порядок управляется списком приоритетов (`telegram.md@e96221fa:L205-L231`).
- Команды с суффиксом `/cmd@botname` разбирает `MessageEvent.get_command()`.
- Есть inline-режим для поиска по всем командам, без потолка (`_handle_inline_query`, `adapter.py@e96221fa:L4237`).

### 3.4. Кнопки

Диспетчер — `_handle_callback_query` (`adapter.py@e96221fa:L4302-L4336`), маршрутизация по префиксу `callback_data`:

| Префикс | Назначение |
|---|---|
| `ea:<choice>:<approval_id>` | подтверждение опасной команды, `choice` ∈ `once/session/always/deny` |
| `sc:` | подтверждение slash-команды |
| `cl:` | ответ на clarify |
| `mp:`, `mm:`, `mc:` … | выбор модели/провайдера с пагинацией |
| `cp:` | общий выбор (`/reasoning`, `/fast`) |
| `update_prompt:` | подтверждение обновления |

Устройство карточки подтверждения (`_send_exec_approval_prompt`, `adapter.py@e96221fa:L3844-L3861`; обработка — `_handle_exec_approval_callback`, `L4347-L4389`):

- В `callback_data` кладётся **короткий числовой id**, а не ключ сессии: лимит Telegram — 64 байта. Соответствие `approval_id → session_key` и `approval_id → request_id` хранится в памяти адаптера; счётчик уникален между рестартами.
- **Проверка нажавшего:** `_callback_authorized` → полная цепочка авторизации шлюза (`_is_callback_user_authorized`, `adapter.py@e96221fa:L698-L733`); при отсутствии списков — отказ (fail-closed, #24457). Затем `approval_refusal` — имеет ли этот человек право ответить именно на этот запрос; посторонний получает alert-уведомление, карточка остаётся ждать.
- **Порядок «сначала решить, потом рисовать»:** вызывается `resolve_gateway_approval_card`; если разрешено 0 запросов (ожидание уже истекло), карточка правится на «истекло», а не на «одобрено» (#63501).
- Состояние забирается атомарно (`pop`): второе одновременное нажатие получает «уже решено».
- `answerCallbackQuery` вызывается всегда, даже для неизвестного префикса, иначе у пользователя крутится индикатор (#78788).
- После ответа сообщение правится: кнопки убираются, текст дополняется «одобрено пользователем X». Индикатор набора, остановленный на время ожидания, возобновляется.
- Карточки-выборы привязаны к id отправленного сообщения: нажатие на старую карточку после рестарта даёт «устарело, вызовите команду заново».

**Вывод:** соответствие «id кнопки → сессия» живёт в памяти процесса, поэтому после перезапуска шлюза старые карточки подтверждений становятся нерабочими — вместе с самим ожидающим запросом.

### 3.5. Группы и темы

`_should_process_message` (`adapter.py@e96221fa:L5760-L5798`):

- личные сообщения — без ограничений;
- собственные сообщения бота отбрасываются (в супергруппах `getUpdates` может их вернуть);
- группа: жёсткий список `allowed_chats`; затем — отвечать, если чат/тема в списке «свободного ответа», или `require_mention` выключен, или это ответ на сообщение бота, или есть @упоминание (включая `/cmd@botname`), или совпал шаблон-«позывной»;
- другой бот должен упомянуть явно — защита от петель между ботами.

Режим приватности BotFather должен быть выключен, иначе бот не видит обычные сообщения группы (`telegram.md@e96221fa:L253`). Есть режим «наблюдать за группой, не отвечая»: неадресованные сообщения пишутся в общий контекст сессии (`telegram.md@e96221fa:L280`).

Темы: `message_thread_id` попадает в `SessionSource.thread_id` и в ключ сессии — тема форума даёт отдельную сессию, общую для участников (см. 2.4). Тема General имеет id `"1"` (`adapter.py@e96221fa:L415`) и требует особого обращения при отправке. Темы в личном чате (Bot API 9.4) используются как несколько параллельных сессий с одним пользователем, к теме можно привязать скилл и системный промпт (`telegram.md@e96221fa:L852-L1110`, код `telegram_topic_routing.py` не читал).

### 3.6. Отправка

- **Формат.** Основной путь — MarkdownV2: markdown модели конвертируется `format_message` (`adapter.py@e96221fa:L5152`; `telegram_markdown.py`, 792 строки, не читал). Если Bot API отвергает разметку — тот же кусок уходит плоским текстом с вычищенной разметкой (`_send_chunk_markdown_or_plain`, `adapter.py@e96221fa:L3207-L3218`). Есть «богатый» путь Bot API 10.1 (таблицы, списки задач, лимит 32 768 символов) с откатом на MarkdownV2 (`adapter.py@e96221fa:L411`, `L3407-L3411`). Карточки подтверждений идут в HTML.
- **Длина.** 4096 единиц UTF-16 (`MAX_MESSAGE_LENGTH`, `adapter.py@e96221fa:L405`). Длиннее — разбиение; сущности, разрезанные границей, закрываются и открываются заново. Если ответ требует больше 8 сообщений (`MAX_SPLIT_MESSAGES`), он уходит **одним `.md`-файлом** (`adapter.py@e96221fa:L406`, `L3415-L3417`). Подписи к медиа — до 1024 символов (`_caption_1024`, `L4758`).
- **Порядок.** Отправка в один чат идёт под блокировкой на чат, чтобы куски двух ответов не перемешались (`adapter.py@e96221fa:L3380-L3381`).
- **Частичная доставка.** Если отправка оборвалась посреди кусков, результат несёт уже доставленные id и остаток, и доставку можно продолжить (`_with_partial_send`, `adapter.py@e96221fa:L3449`).
- **Правка при стриминге** (`edit_message`, `adapter.py@e96221fa:L3527-L3600`):
  - промежуточная правка **пропускается**, если слот чата занят: её текст всё равно покажет следующая; финальная правка не пропускается никогда;
  - текст длиннее 4096 во время стриминга **усекается**, а не разбивается: разбиение создавало сообщение-продолжение, которое становилось новой целью правки, — бесконечное дублирование (#48648); разбивается только финал;
  - одинаковое усечённое превью повторно не отправляется: визуально это ничего не меняет, а бюджет flood тратит;
  - «message is not modified» считается успехом;
  - превью правится в том же режиме разметки, что и финал, иначе клиент рисует старую вёрстку поверх нового текста (#49536).
- **Черновики** (`sendMessageDraft`) — нативный стриминг, только в личных чатах; в группах откат на правки (`telegram.md@e96221fa:L1186-L1214`).
- **Индикатор набора** — `sendChatAction("typing")` (`send_typing`, `adapter.py@e96221fa:L5105-L5136`); действует ~5 с, база обновляет его каждые 2 с; на время ожидания подтверждения приостанавливается.
- **Статус обработки реакциями** на сообщение пользователя — `on_processing_start/complete` (`adapter.py@e96221fa:L6486-L6495`), опционально.
- **Изображения:** картинки больше 1 МБ перед отправкой сжимаются в JPEG (качество 85, сторона до 1600) — через прокси сырые PNG не успевают загрузиться (`adapter.py@e96221fa:L421-L426`).

### 3.7. Ограничения API и как они обходятся

| Ограничение | Решение | Место |
|---|---|---|
| Общий лимит отправок и правок на чат | один «слот» на чат с шагом 1,0 с: **отправка ждёт** слот, **промежуточная правка пропускается** | `adapter.py@e96221fa:L239`, `L5080-L5103`, `L3394-L3402`, `L3543-L3553` |
| 429 `retry_after` | окно flood на чат (до 300 с): внутри него отправки, правки, typing и удаления отказывают **локально, без вызова API**, потому что Telegram удлиняет штраф, пока в него стучатся; окно пишется в файл и переживает рестарт; более длинные штрафы забирает журнал доставки | `references/hermes-agent/plugins/platforms/telegram/telegram_flood_cooldown.py@e96221fa:L1-L30` |
| Черновики и typing: 20 вызовов за 5 с, 40 за 30 с на чат | общий бюджет на оба | `telegram.md@e96221fa:L1216`; `telegram_draft_budget.py` не читал |
| 4096 символов | разбиение; больше 8 частей — файл | 3.6 |
| 64 байта `callback_data` | короткий id + таблица в памяти | 3.4 |
| Файлы 20 МБ на приём | локальный Bot API сервер (`base_url`, `local_mode`) — до 2 ГБ | `adapter.py@e96221fa:L597`, `L2942-L2948`; `telegram.md@e96221fa:L564-L700` |
| Ссылки на файлы живут ~1 час | скачивать сразу | `adapter.py@e96221fa:L6196` |
| Меню: 100 команд и ~4 КБ | потолок 60, приоритеты | 3.3 |
| Зависание вызова | жёсткий дедлайн 30 с на отправку текста | `adapter.py@e96221fa:L372`, `L3209-L3211` |
| Разрыв связи посреди ответа | `send()` ждёт переподключения до 15 с, иначе ответ уходит в журнал доставки | `adapter.py@e96221fa:L416-L419`, `L3361-L3371` |

**Вывод:** объём адаптера (тысячи строк только на устойчивость polling, flood и разметку) показывает, что «простой Telegram-бот» в продакшене не прост. Для одного владельца в личном чате большая часть этого не нужна; нужны слот на чат, локальный отказ в окне flood, откат разметки на плоский текст, усечение превью при стриминге и дедупликация `update_id`.

## 4. Авторизация пользователей

**По умолчанию — отказ всем, кто не в списке и не сопряжён** (`messaging/index.md@e96221fa:L418-L442`).

Порядок проверки — `_is_user_authorized` → `_principal_authorized` (`references/hermes-agent/gateway/authz_mixin.py@e96221fa:L855-L939`):

1. локальные источники (CLI/Desktop) и доверенные входы (webhook с HMAC-подписью) — пропуск;
2. разрешение на уровне чата (списки групп);
3. нет `user_id` — отказ;
4. `{PLATFORM}_ALLOW_ALL_USERS`;
5. роль, проверенная адаптером (Discord);
6. хранилище сопряжения;
7. списки `{PLATFORM}_ALLOWED_USERS`, `TELEGRAM_GROUP_ALLOWED_USERS` (только группы, без доступа в личку), `GATEWAY_ALLOWED_USERS`; `*` — все;
8. `GATEWAY_ALLOW_ALL_USERS`;
9. иначе отказ.

Сообщение от бота, допущенное списком, дополнительно проходит сторож петель (`gateway.bot_loop_guard`, `max_hops: 4`; `messaging/index.md@e96221fa:L460-L469`).

**Сопряжение (pairing)** — `references/hermes-agent/gateway/pairing.py@e96221fa:L29-L37`, класс `PairingStore` (`L336`); описание — `security.md@e96221fa:L520-L597`:

- незнакомец пишет боту в личку → бот отвечает одноразовым кодом → **владелец подтверждает код в CLI на сервере** (`hermes pairing approve telegram <код>`) → пользователь допущен навсегда;
- код — 8 символов из алфавита в 32 знака без `0/O/1/I`, криптографически случайный; срок 1 час; 1 запрос на пользователя в 10 минут; не больше 3 ожидающих кодов на платформу; 5 неверных попыток — блокировка на час; файлы с правами `0600`; коды не пишутся в лог; в хранилище коды лежат хешами с солью (`_hash_code`, `pairing.py@e96221fa:L491`);
- поведение для неавторизованной лички: `pair` (по умолчанию) / `ignore` / `decline` (одно вежливое «я общаюсь только с владельцем», затем молчание на 24 часа);
- данные — `~/.hermes/pairing/{platform}-pending.json`, `{platform}-approved.json`, `_rate_limits.json`.

Важно: подтверждение идёт **по другому каналу** (CLI на сервере), а не командой в чате. В Docker команду надо выполнять от пользователя `hermes`, иначе файл одобрения создаётся с владельцем root и шлюз его не читает (`security.md@e96221fa:L575-L590`).

**Роли** (`messaging/index.md@e96221fa:L471-L507`; код — `references/hermes-agent/gateway/slash_access.py@e96221fa:L31`, `SlashAccessPolicy`):

- два уровня на каждую область (личка / группа): **админ** — все slash-команды; **обычный пользователь** — только перечисленные в `user_allowed_commands`, минимум `/help` и `/whoami`;
- ключи: `allow_from`, `allow_admin_from`, `user_allowed_commands`, `group_allow_admin_from`, `group_user_allowed_commands`;
- **сейчас уровни ограничивают только slash-команды**; обычный разговор с агентом — а значит и его инструменты — доступен всем допущенным. Документация прямо говорит, что доступ к инструментам «может быть» завязан на роли в будущем;
- если `allow_admin_from` не задан, разделения нет: все допущенные имеют полный доступ;
- ответ на карточку подтверждения приравнен к команде `/approve`.

**Вывод:** понятия «владелец» как отдельной роли в hermes нет — есть список допущенных и необязательный список админов. Требование Меркурия «глобальное поведение меняет только владелец» ближе всего к связке `allow_admin_from` + `approvals.approvers: []`, но закрывает оно только команды, а не то, о чём агента можно попросить текстом.

## 5. Подтверждения опасных действий

### 5.1. Порядок проверок

Точка входа для команды терминала — `check_all_command_guards(command, env_type, approval_callback, has_host_access)` (`references/hermes-agent/tools/approval.py@e96221fa:L1421-L1479`). Возвращает словарь `{"approved": bool, "message": ...}`. Порядок:

1. **Изолированный бэкенд — проверки пропускаются.** Для `docker` без проброшенных путей хоста, `modal`, `daytona`, `vercel_sandbox` опасные шаблоны не проверяются вовсе: «контейнер и есть граница». Docker с bind-mount хоста идёт обычным путём (`_should_skip_container_guards`, `approval.py@e96221fa:L1301-L1315`). Пользовательские запреты `approvals.deny` действуют и здесь.
2. **«Полы», которые не обходит ничто** — ни yolo, ни `mode: off`, ни «разрешить всегда» (`_floor_block`, `approval.py@e96221fa:L1329-L1352`):
   - жёсткий чёрный список `HARDLINE_PATTERNS` (`references/hermes-agent/tools/approval_detection.py@e96221fa:L184-L229`): `rm -rf /`, системные каталоги и домашний каталог, `mkfs`, `dd` на диск, fork-бомба, выключение/перезагрузка, `curl | sh` и т. п.;
   - удаление собственного интерпретатора/venv агента;
   - `sudo -S` с паролем через stdin, когда `SUDO_PASSWORD` не настроен (модель «угадывает» пароль);
   - пользовательские правила `approvals.deny` — fnmatch-глобы без учёта регистра по тексту команды и по каждому «кандидату на исполняемую команду».
3. **Обход:** yolo-режим или `approvals.mode: off` → разрешено (кроме команд, которые сканер не смог дочитать до конца).
4. **Постоянный список разрешённого** `command_allowlist` в `config.yaml`: точный текст команды или глоб. Сокращение не действует для составных команд — с операторами оболочки, `$(...)`, раскрытием в двойных кавычках, незакрытой кавычкой (`_has_allowlist_shell_operator`, `references/hermes-agent/tools/approval_floors.py@e96221fa:L178-L229`).
5. **Нет человека** (не CLI, не шлюз): cron, одиночный запрос `-q`, webhook/API решают мгновенно по `cron_mode` / `single_query_mode` / `unattended_mode` (по умолчанию `deny`) — «никогда не оставлять подтверждение, на которое некому ответить».
6. **Детектирование.** `_command_findings` → все совпавшие шаблоны; каждый уже разрешённый на сессию или навсегда отбрасывается; остаток уходит в один общий запрос.
7. **`_human_decision`** (`approval.py@e96221fa:L1032-L1188`): необязательный шаг «умного» подтверждения, затем вопрос человеку.

### 5.2. Как классифицируются команды

- Это **чёрный список регулярных выражений**, а не разбор команды в дерево. `DANGEROUS_PATTERNS` — список пар `(regex, описание)` (`approval_detection.py@e96221fa:L506-L872`). **Описание шаблона и есть ключ разрешения** (`pattern_key`): «recursive delete», «pipe remote content to shell» и т. п. (`detect_dangerous_command`, `approval_detection.py@e96221fa:L1908-L1921`).
- Что ловится (таблица в документации, `references/hermes-agent/website/docs/user-guide/security.md@e96221fa:L209-L247`): рекурсивное удаление, `chmod 777`, `mkfs`/`dd`, SQL `DROP`/`TRUNCATE`/`DELETE` без `WHERE`, запись в `/etc/`, `~/.ssh/`, `~/.hermes/.env`, `systemctl stop/restart`, `kill -9 -1`, `bash -c` / `python -e`, `curl | sh`, `find -delete`, `xargs rm`, остановка/удаление контейнеров и томов docker, перенаправление docker на другой демон, самоубийство шлюза (`pkill hermes`), загрузка файла с секретами через curl/wget.
- **Нормализация перед сопоставлением.** Шаблоны применяются не к исходной строке, а к набору «вариантов» (`_command_detection_variants`, `approval_detection.py@e96221fa:L1603-L1619`): снятие кавычек и экранирования, деобфускация слов (`git pu""sh`), раскрытие ANSI-C кавычек, отбрасывание тел heredoc, которые являются данными, рекурсивный разбор `sh -c '…'`, пометка начала каждой простой команды после `;`, `&&`, `|`, подстановок. Часть шаблонов сопоставляется по тексту с замаскированными кавычками, чтобы `echo "rm -rf /"` не срабатывал (`_iter_dangerous_descriptions`, `approval_detection.py@e96221fa:L1853-L1905`).
- **Бюджет разбора.** Если разбор превысил бюджет или рекурсию, команда получает ключ «scan incomplete»: её может разрешить **только человек и только на один запуск**; ни yolo, ни allowlist, ни LLM-страж её не пропустят (`approval.py@e96221fa:L1437-L1452`, `L1476-L1478`).
- Невидимые и двунаправленные символы Юникода в команде — отдельная находка (`approval_detection.py@e96221fa:L73`, `L1903-L1905`).
- Отдельные модули под частные случаи: `approval_wrappers.py` (sudo/env/nohup/timeout-обёртки), `approval_fetch_exec.py` (скачал — запустил), `approval_git_options.py`, `approval_applescript.py`, `approval_windows_hardline.py`, `approval_wmic.py` — не читались.

### 5.3. Режимы

`approvals.mode` (`security.md@e96221fa:L28-L61`):

| Режим | Поведение |
|---|---|
| `smart` (по умолчанию) | вспомогательная LLM оценивает риск: `APPROVE` — выполнить (только эту команду), `DENY` — отказ, `ESCALATE`/ошибка/пустой ответ — спросить человека |
| `manual` | всегда спрашивать человека |
| `off` | не спрашивать (равно yolo) |

«Умное» подтверждение — `_smart_approve` (`references/hermes-agent/tools/approval_smart.py@e96221fa:L168-L226`): `temperature=0`, `max_tokens=16`, явный таймаут; ответ — одно слово. Политика оператора добавляется **только в системный промпт**, команда — в блок `<command>` пользовательского сообщения, комментарии оболочки из неё вырезаются (чтобы в комментарии нельзя было уговорить стража). Любой сбой → эскалация человеку. После N подряд отказов стража (`approvals.denial_breaker_threshold`, по умолчанию 3) в текст отказа дописывается «CIRCUIT BREAKER: прекрати подбирать варианты, сообщи пользователю» — меняется только текст результата инструмента, история не правится (`approval.py@e96221fa:L64-L119`).

**Yolo:** флаг `--yolo`, переменная `HERMES_YOLO_MODE=1`, команда `/yolo` (переключатель, действует на одну сессию, сохраняется с ней и переживает рестарт; `/new` возвращает подтверждения) — `security.md@e96221fa:L67-L96`; код — `references/hermes-agent/tools/approval_yolo.py@e96221fa:L31-L111`. Жёсткий чёрный список и `approvals.deny` yolo не отключает.

### 5.4. Запоминание разрешений

Четыре ответа: `once` / `session` / `always` / `deny` (`ExecApprovalPrompt`, `base.py@e96221fa:L1548-L1566`).

- `session` — ключ шаблона кладётся в набор разрешений сессии, в памяти процесса (`approve_session`, `approval.py@e96221fa:L328`).
- `always` — ключ добавляется в `command_allowlist` в `config.yaml` (`_persist_choice`, `approval.py@e96221fa:L514-L527`; `save_permanent_allowlist`, `L583-L600`). Файл правится и руками: запись сливается с тем, что на диске, чтобы удалённое оператором разрешение не «воскресло».
- Запоминается **класс** («recursive delete»), а не конкретная команда. Вручную в allowlist можно вписать и текст/глоб команды (`podman *`).
- Разовыми остаются: отмена отказа LLM-стража, «scan incomplete», рискованный `osascript` — для них `session`/`always` не предлагаются (`approval.py@e96221fa:L1056-L1060`).
- Ответ — белый список: всё, что не входит в `CONSENT_ANSWERS`, считается отказом (`approval.py@e96221fa:L1073-L1083`).
- Есть `hermes approvals suggest` — разбор истории подтверждений с предложениями в allowlist (`security.md@e96221fa:L372`, не читал).

### 5.5. Как подтверждение проходит через канал

1. Поток агента (синхронный) доходит до `_human_decision`. Текст команды и описание для показа проходят маскирование секретов `redact_approval_display` — исполняется при этом исходная команда (`approval.py@e96221fa:L1107-L1112`).
2. `_await_gateway_decision` (`references/hermes-agent/tools/approval_gateway_wait.py@e96221fa:L164-L310`) создаёт запись `_ApprovalEntry` с `threading.Event`, кладёт её в очередь сессии `_gateway_queues[session_key]` и вызывает `notify_cb` — мост из потока агента в асинхронный цикл шлюза, зарегистрированный через `register_gateway_notify` (`approval.py@e96221fa:L128`).
3. Шлюз вызывает `adapter.send_exec_approval(...)`. Если адаптер умеет кнопки — карточка с кнопками, иначе текст «ответьте /approve или /deny». **Запись рождается «только Deny»**: одобрение включается лишь когда карточка показала команду целиком. Если команда не влезла — сначала отдельным сообщением шлётся полная команда; если и это не удалось — остаётся только кнопка «Отклонить»: «никто не одобряет команду, которую не смог прочитать» (`base.py@e96221fa:L2744-L2764`).
4. Поток агента блокируется в `_poll_event` до события, таймаута (`approvals.timeout`, по умолчанию 300 с) или прерывания хода.
5. Нажатие кнопки или `/approve` → `resolve_gateway_approval(session_key, choice, resolve_all, reason, request_id)` (`approval.py@e96221fa:L150-L187`): по `request_id` или самый старый запрос (FIFO), `/approve all` — все. Снятие записи с очереди и фиксация ответа — одна критическая секция с ожидающей стороной, чтобы ответ, пришедший на границе таймаута, не превратился в «таймаут».
6. Одинаковые параллельные запросы (та же команда и набор ключей) **склеиваются** в один запрос; `once` покрывает только первого, остальные спросят снова (`approval_gateway_wait.py@e96221fa:L170-L176`).
7. Поскольку `/approve` приходит, когда сессия занята, он обязан обойти оба сторожа из 2.5.

**Кто может ответить.** `approvals.approvers` (по умолчанию `["*"]` — любой допущенный участник чата); если сужено — только автор запроса, перечисленные id и админы области. Если настроено разделение админ/пользователь, ответ на карточку приравнивается к команде `/approve` и требует права на неё — на всех путях: кнопка, реакция, набранное «yes» (`security.md@e96221fa:L295-L329`).

**Итоги** (`approval.py@e96221fa:L1124-L1146`):

- отказ — инструмент возвращает модели `BLOCKED` с указанием не повторять и не перефразировать; свободный текст `/deny <причина>` передаётся модели дословно, чтобы она могла изменить план;
- таймаут — отказ с пометкой «Silence is not consent»; не считается отказом пользователя, просроченную карточку нельзя переоткрыть — нужен новый запрос от человека (`security.md@e96221fa:L196-L200`);
- запрос отозван (ход прерван) — отказ без приписывания его пользователю;
- уведомление не доставлено — отказ `notify_failed`.

**`execute_code`:** скрипт может вызывать `subprocess`/`os` в обход шаблонов, поэтому в сессиях шлюза подтверждение запрашивается один раз на весь скрипт (`check_execute_code_guard`, `approval.py@e96221fa:L1499`; `security.md@e96221fa:L254-L262`).

**Другие инструменты** входят в ту же механику через `request_tool_approval(tool_name, reason, rule_key=...)` (`approval.py@e96221fa:L1391`) и общий `_run_approval_gate` (`approval.py@e96221fa:L1226-L1245`) — им пользуются защита записи файлов, computer use, правила плагинов.

### 5.6. Слабые места подхода

Признано самим проектом:

- «Deny rules are a shell-command policy, not a complete shell interpreter or an OS capability sandbox»: нормализация не раскрывает произвольные переменные, алиасы, функции, переименованные бинарники, скрипты и программы интерпретаторов (`security.md@e96221fa:L192-L194`).
- В изолированных бэкендах проверки отключены целиком — безопасность там равна качеству изоляции контейнера.

**Вывод (мои оценки):**

- Чёрный список по определению неполон: опасность определяется текстом команды, а не её действием. `python script.py`, где скрипт делает что угодно, не ловится; на этом построено и исключение для `execute_code`.
- Размер модуля детектирования (около 1900 строк регулярных выражений и ручного разбора кавычек плюс 15 модулей-спутников) — следствие гонки с обходами: почти каждый шаблон сопровождается ссылкой на инцидент. Переносить это в PHP один к одному дорого и бессмысленно.
- Ключ разрешения — класс («recursive delete»). «Разрешить всегда» на `rm -r ./build` разрешает и `rm -r ~/проекты`. Гранулярность грубая.
- Режим `smart` по умолчанию передаёт решение вспомогательной LLM. Команда приходит от основной модели, которая могла прочитать внедрённую инструкцию; страж видит только команду и описание и может быть введён в заблуждение её содержимым. Вырезание комментариев — частичная мера.
- Ожидание ответа блокирует поток ОС (`threading.Event`), состояние очереди — в памяти процесса: перезапуск шлюза теряет ожидающие подтверждения и разрешения уровня сессии.
- По умолчанию в групповом чате ответить может любой допущенный участник.

## 6. Окружения исполнения

### 6.1. Интерфейс

Базовый класс — `BaseEnvironment` (`references/hermes-agent/tools/environments/base.py@e96221fa:L285-L290`). Бэкенд реализует всего два метода:

- `_run_bash(cmd_string, *, login=False, timeout=120, stdin_data=None) -> ProcessHandle` — запустить процесс bash (`base.py@e96221fa:L365-L369`);
- `cleanup()` — освободить ресурсы (`base.py@e96221fa:L371-L376`).

Всё остальное даёт база: `execute(command, cwd="", *, timeout=None, stdin_data=None, bounded_capture=False, ...) -> {"output": str, "returncode": int}` (`base.py@e96221fa:L718-L740`), а также долгоживущие процессы `start_process / attach_process / stop_process` (`base_processes.py`, не читал) и `fetch_file` — забрать файл из окружения на хост (`base.py@e96221fa:L379`).

**Модель «процесс на команду + снимок окружения»**, а не постоянная оболочка:

- при создании `init_session()` один раз запускает login-оболочку и сохраняет её окружение в файл-снимок `hermes-snap-<id>.sh` (`base.py@e96221fa:L453-L479`);
- каждая команда оборачивается скриптом: подключить снимок → `cd` в отслеживаемый каталог → выполнить → заново выгрузить экспортированные переменные → напечатать маркер с текущим каталогом (`_wrap_command`, `base.py@e96221fa:L512-L524`);
- текущий каталог извлекается из маркера в выводе и хранится в объекте окружения (`_update_cwd`, `_extract_cwd_from_output`, `base.py@e96221fa:L668-L672`).

Что переживает вызовы (`references/hermes-agent/website/docs/user-guide/configuration.md@e96221fa:L840-L856`): рабочий каталог — всегда; экспортированные переменные — при `persistent_shell` (по умолчанию включено); обычные переменные оболочки, функции и алиасы — нет.

Прочее: таймаут на команду (`terminal.timeout: 180` с); прерывание — через общий реестр живых процессов (`kill_live_foreground_processes`, `base.py@e96221fa:L117`); вывод ограничивается прямо во время чтения окном «голова + хвост» (`bounded_capture`), а не после накопления (#64435); stdin — трубой, полезной нагрузкой SDK или heredoc, смотря по бэкенду (`_stdin_mode`, `base.py@e96221fa:L292-L296`).

Флаг `uses_host_filesystem` (`base.py@e96221fa:L302-L306`) решает, работают ли файловые инструменты прямо с диском хоста (только `local`) или через `execute()` в окружении — «файловые инструменты видят ровно то, что видят команды».

### 6.2. Варианты

Выбор — `terminal.backend` в `config.yaml` (`local | docker | ssh | modal | daytona | vercel_sandbox | <плагин>`, `configuration.md@e96221fa:L263-L279`); фабрика — `_create_environment` (`references/hermes-agent/tools/terminal_tool_backends.py@e96221fa:L295-L320`), неизвестный тип уходит к плагинам (singularity, sprites).

| Бэкенд | Где выполняется | Изоляция | Проверка опасных команд | Файл |
|---|---|---|---|---|
| `local` | на машине агента | нет; из окружения дочернего процесса вырезаются ключи провайдеров и токены шлюза | да | `tools/environments/local.py`, `local_env_policy.py` |
| `docker` | один долгоживущий контейнер, команды через `docker exec` | пространства имён, сброс capabilities, лимиты | **пропускается**, если нет bind-mount с хоста | `tools/environments/docker.py` |
| `ssh` | удалённая машина | граница сети | да | `tools/environments/ssh.py` |
| `modal`, `daytona`, `vercel_sandbox` | облачная песочница | VM / microVM | пропускается | `modal.py`, `daytona.py`, `vercel_sandbox.py` |

Сводные таблицы — `configuration.md@e96221fa:L333-L344`, `references/hermes-agent/website/docs/user-guide/security.md@e96221fa:L650-L661`.

### 6.3. Docker подробно

- **Запуск:** `docker run -d [--init] --name hermes-<8 hex> --label … -w <cwd> <аргументы> <образ> sleep infinity` (`_run_command`, `references/hermes-agent/tools/environments/docker.py@e96221fa:L1022-L1037`). Контейнер просто спит; каждая команда — `docker exec [-i] <id> bash …` (`_run_bash`, `docker.py@e96221fa:L1100-L1126`).
- **Безопасность** (`_BASE_SECURITY_ARGS`, `docker.py@e96221fa:L328-L334`; `_build_security_args`, `L403-L410`): `--cap-drop ALL` и обратно только `DAC_OVERRIDE`, `CHOWN`, `FOWNER`; `--security-opt no-new-privileges` (снимается флагом совместимости со snap-версией Docker); tmpfs `/tmp` 512 МБ `nosuid`, `/var/tmp` 256 МБ `noexec`, `/run` 64 МБ. `SETUID/SETGID` добавляются, только когда контейнер стартует от root и должен сбросить привилегии.
- **Ресурсы** (`_resource_args`, `docker.py@e96221fa:L814-L848`): `--cpus`, `--memory`, `--pids-limit 2048`, `--shm-size 1g`, `--storage-opt size=` (только overlay2 на XFS с pquota — иначе предупреждение и работа без квоты), `--network=none` при `docker_network: false`. Значения по умолчанию из документации: 1 CPU, 5120 МБ памяти, 51200 МБ диска (`configuration.md@e96221fa:L446-L450`).
  - **Расхождение:** документация в двух местах называет `--pids-limit 256` (`security.md@e96221fa:L613`, `configuration.md@e96221fa:L506`), в коде — 2048: 256 не хватало для Chromium внутри песочницы (`docker.py@e96221fa:L336-L343`). Верить коду.
  - Противоречивая настройка (сеть запрещена, но в `docker_extra_args` стоит `--network=host`) — отказ запуска, а не молчаливый выбор (`docker.py@e96221fa:L838-L846`).
- **Файлы** (`_mount_args`, `docker.py@e96221fa:L850-L926`): при `container_persistent: true` (по умолчанию) `/workspace` и `/root` — bind-mount из `~/.hermes/sandboxes/docker/<task>/`; при `false` — tmpfs (`/workspace` 10 ГБ), всё теряется. Каталог хоста монтируется в `/workspace` только по явной настройке `docker_mount_cwd_to_workspace` (по умолчанию выключено). Свои тома — `docker_volumes`, можно `:ro`.
- **Жизненный цикл** (`configuration.md@e96221fa:L471-L500`; `cleanup`, `docker.py@e96221fa:L1284-L1296`): контейнер помечается метками `hermes-agent=1`, `hermes-task-id`, `hermes-profile`, `hermes-environment` (хеш образа, монтирований и домашнего каталога). Новый процесс находит контейнер по меткам и **подключается к нему**; остановленный — запускает заново. По умолчанию выход процесса hermes контейнер **не трогает** — только так переживают сессии фоновые процессы (dev-серверы, длинные тесты). Удаление: при `docker_persist_across_processes: false`; сборщиком простаивающих (`lifetime_seconds: 300`) — только в этом же режиме; сборщиком сирот на старте — завершённые контейнеры старше `2 × lifetime_seconds`.
- **Один контейнер на профиль**: его делят сессии шлюза, cron и субагенты. Параллельные субагенты в одном контейнере мешают друг другу (`cd`, переменные, запись в один путь) — документация это прямо оговаривает (`configuration.md@e96221fa:L501`). Режим «контейнер на сессию» — `container_persistent: false`.
- **Переменные окружения:** по умолчанию из окружения хоста в контейнер не попадает ничего; явный список — `docker_forward_env`, статические значения — `docker_env`. Флаги `-e` передаются **только именами**, значения идут через окружение клиентского процесса docker, чтобы не светиться в `/proc/*/cmdline` (`docker.py@e96221fa:L1112-L1114`).
- **Исходящий трафик:** необязательный прокси-«файрвол учётных данных» (iron-proxy): контейнеру подставляются `HTTPS_PROXY` и корневой сертификат; настройки, способные ослабить или обойти прокси, проверяются на коллизии, при `proxy.enforce_on_docker` полунастроенное состояние — отказ запуска (`references/hermes-agent/tools/environments/docker_egress.py@e96221fa:L1-L37`). Подробнее — `website/docs/user-guide/egress/` (не читал).
- **Образ песочницы** по умолчанию — `nousresearch/hermes-sandbox:desktop` (Python + Node + графический стек, чтобы браузер и computer use работали внутри песочницы).

### 6.4. SSH и local

- **SSH** (`configuration.md@e96221fa:L538-L570`): `ControlMaster` для переиспользования соединения (5 минут простоя), `BatchMode=yes`, `StrictHostKeyChecking=accept-new`; каждая команда — новый `ssh … bash -c` со снимком окружения. Переменные передаются через `SendEnv` — имена в командной строке, значения в окружении клиента; на сервере нужен `AcceptEnv`. Ключи провайдеров не пересылаются, даже если указаны.
- **Local:** из окружения дочерних процессов вырезаются ключи провайдеров, токены шлюза и ключи инструментов (`references/hermes-agent/tools/environments/local_env_policy.py@e96221fa:L78` — `_build_provider_env_blocklist`; `L390` — `_is_hermes_internal_secret`). Список разрешённых сверх этого — `terminal.env_passthrough`; скилл может объявить `required_environment_variables`, и они пропускаются автоматически, пока скилл загружен (`security.md@e96221fa:L663-L676`).

### 6.5. Песочница исполнения кода (`execute_code`)

`references/hermes-agent/tools/code_execution_tool.py`; описание — `references/hermes-agent/website/docs/user-guide/features/code-execution.md@e96221fa:L11-L32`.

- Модель пишет Python-скрипт, который импортирует `hermes_tools` и вызывает инструменты агента как функции. Hermes открывает Unix-сокет и поток-слушатель RPC, скрипт выполняется в дочернем процессе, вызовы инструментов идут по сокету обратно. В удалённых бэкендах транспорт — файлы в каталоге `HERMES_RPC_DIR` (`code_execution_tool.py@e96221fa:L260`, `L345-L349`).
- **Модели возвращается только `print()` скрипта** — промежуточные результаты инструментов в контекст не попадают. Это средство экономии токенов, а не изоляции.
- Разрешённые инструменты: `web_search`, `web_extract`, `read_file`, `write_file`, `search_files`, `patch`, `terminal` (только передний план) — `SANDBOX_ALLOWED_TOOLS` (`code_execution_tool.py@e96221fa:L43`); у `terminal` заблокированы параметры `background`, `pty`, `notify…` (`references/hermes-agent/tools/code_execution_rpc.py@e96221fa:L25`).
- Лимиты (`code_execution_tool.py@e96221fa:L48-L53`): 300 с, 50 вызовов инструментов, 50 КБ stdout, 10 КБ stderr.
- Окружение дочернего процесса — белый список безопасных префиксов (`PATH`, `HOME`, `LANG`, …) плюс отсев всего, в чьём имени есть `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`, `AUTH`, `DSN` (`references/hermes-agent/tools/code_execution_env.py@e96221fa:L25-L33`; `_scrub_child_env` — `L57`).
- Скрипт может вызвать `subprocess` напрямую, минуя шаблоны опасных команд, — поэтому в сессиях шлюза подтверждение запрашивается на весь скрипт (см. 5.5).

### 6.6. Файловые инструменты

- Запись (`write_file`, `patch`) проверяется по списку защищённых путей **без запроса подтверждения** — сразу отказ: `~/.ssh/`, `~/.aws/`, `~/.kube/`, `/etc/sudoers`, `~/.netrc`, а также хранилища секретов самого hermes (`.env`, `auth.json`, `vault/`, `browser-profile/`, `mcp-tokens/`, `pairing/`). Проектные `.env` **нельзя читать**, но можно писать: агент может создать файл, но не прочитать значения обратно (`security.md@e96221fa:L416-L430`).
- `HERMES_WRITE_SAFE_ROOT` — необязательный корень, вне которого запись запрещена жёстко; в официальном образе равен `/opt/data` (`security.md@e96221fa:L448-L462`).
- Проект сам называет это «defense-in-depth, not a hard boundary»: инструмент `terminal` работает от того же пользователя и может прочитать или перезаписать запрещённые пути командой оболочки (`security.md@e96221fa:L468-L470`).

### 6.7. Слабые места

**Вывод (мои оценки):**

- Бэкенд по умолчанию — `local`, то есть без изоляции; безопасность по умолчанию держится на чёрном списке команд из раздела 5.
- Песочница терминального бэкенда покрывает только команды оболочки и файловые инструменты. Исполнение кода (`execute_code`), подпроцессы MCP, плагины и хуки работают в процессе агента или рядом с ним на хосте — это оговорено в модели угроз проекта (см. 9.1).
- Docker-бэкенд требует доступа к демону Docker. Если сам агент работает в контейнере (как в официальном образе), ему нужен проброшенный сокет Docker — а это фактически root на хосте — либо агент выполняет команды `local` внутри собственного контейнера (см. раздел 11).
- Один контейнер на профиль, общий для всех сессий и субагентов: взлом одной сессии через внедрённую инструкцию даёт доступ к файлам остальных.
- Сеть в песочнице по умолчанию открыта (`docker_network: true`).
- Квота диска работает только на XFS с pquota — на типичном ext4 лимита нет.

## 7. Браузер

Описание — `references/hermes-agent/website/docs/user-guide/features/browser.md`; код — `references/hermes-agent/tools/browser_*.py` (около 8 тыс. строк, читал выборочно).

### 7.1. Инструменты

На этом коммите у модели **один основной инструмент — `browser_exec`**: он выполняет написанный моделью Python-код с заранее импортированными помощниками, которые говорят с браузером по Chrome DevTools Protocol. Отдельных инструментов «перейти», «кликнуть», «ввести», «снимок» больше нет (`browser.md@e96221fa:L8-L21`). Движок — CLI проекта Browser Use («browser-harness») (`references/hermes-agent/tools/browser_use_cli.py@e96221fa:L1-L7`).

| Инструмент | Назначение |
|---|---|
| `browser_exec(code)` | навигация, чтение, клики, ввод, скриншоты — блоком Python; возвращается то, что код напечатал |
| `browser_cdp(method, params, target_id)` | одна сырая команда CDP (cookies, сеть, iframe) — доступен только при настроенной точке CDP |
| `browser_dialog(action, prompt_text, dialog_id)` | принять/отклонить нативный диалог `alert/confirm/prompt/beforeunload` |
| `browser_vault(action=list/fill/save_login/enter_code/unlock)` | подставить сохранённые логины, карты, коды 2FA на страницу, не показывая их модели |

Помощники внутри `browser_exec` (`browser.md@e96221fa:L45-L57`): `new_tab(url)`, `goto_url(url)`, `wait_for_load()`, `page_info()`, `js(expr)`, `fill_input(selector, text)`, `click_at_xy(x, y)`, `capture_screenshot()`, `cdp('Domain.method', **kwargs)`, `ensure_real_tab()`.

Смысл такого устройства — тот же, что у `execute_code`: модель упаковывает целую подпроцедуру (перейти, подождать, извлечь, действовать) в один вызов, а не тратит вызов на каждое действие. Сессия браузера между вызовами сохраняется (вкладки, cookies, текущая страница), переменные Python — нет; между вызовами живёт рабочий каталог сессии (`browser.md@e96221fa:L35-L42`). Таймаут вызова — 300 с по умолчанию, от 5 до 1800 (`browser_use_cli.py@e96221fa:L95-L97`).

Без набора инструментов `terminal` браузера нет: `browser_exec` исполняет Python (`browser.md@e96221fa:L672`).

### 7.2. Откуда берётся браузер

`browser.md@e96221fa:L22-L28`; выбор и создание — `_create_session_for_key` (`references/hermes-agent/tools/browser_session.py@e96221fa:L279`):

- **локальный Chromium (по умолчанию)** — запускается самим hermes, headless, **один браузер на сессию**, с чистым одноразовым профилем: агент ни во что не залогинен, после сессии ничего не остаётся (`browser.md@e96221fa:L96-L118`);
- **облачные браузеры** — Browserbase, Browser Use, Firecrawl, подписка Nous, плагины-провайдеры (`browser_session_cloud.py`);
- **Lightpanda** — лёгкий движок без скриншотов, одна страница на сессию;
- **свой браузер по CDP** — `/browser connect [ws://host:port]`, `BROWSER_CDP_URL`, `browser.cdp_url`. Команда — только из интерактивного CLI, через шлюз она не исполняется (`browser.md@e96221fa:L456-L462`);
- **«настоящий профиль»** (`browser.use_real_profile: true`, `browser.md@e96221fa:L298-L332`): hermes **копирует** активный профиль пользователя (cookies, логины) в управляемый снимок `~/.hermes/browser-profile/<browser>/` и запускает на нём настоящий бинарник браузера. Живой профиль напрямую не открывается: иначе борьба за блокировку профиля и запрет Chrome 136+ на удалённую отладку профиля по умолчанию. Файлы авторизации пересинхронизируются при каждом запуске сессии.

### 7.3. Сессии

- Кеш сессий по ключу задачи; создание потокобезопасно, с защитой от гонки «двое создали одновременно» (`get_session_info`, `browser_session.py@e96221fa:L342-L383`).
- Закрытие: после `browser.inactivity_timeout` (120 с) простоя, при выходе процесса и «сборщиком сирот» после падения (`browser.md@e96221fa:L106-L108`; уборщик — `references/hermes-agent/tools/browser_session_lifecycle.py@e96221fa:L318-L350`).
- **Супервизор CDP** — постоянное WebSocket-соединение на задачу, подписанное на события Page/Runtime/Target: ловит диалоги в момент появления, ведёт дерево фреймов, обслуживает vault. Нужен потому, что открытый диалог блокирует поток JavaScript страницы и вся работа встаёт (`browser.md@e96221fa:L584-L598`; `browser_supervisor.py` не читал).
- Политика диалогов `browser.dialog_policy`: `must_respond` (по умолчанию, с автоотклонением через 300 с), `auto_dismiss`, `auto_accept`.

### 7.4. Политика URL

`references/hermes-agent/tools/browser_url_policy.py@e96221fa:L1-L7`, `L108-L142`. Проверки по порядку:

1. **Секрет в URL** — если в адресе (в том числе после URL-декодирования) есть что-то похожее на API-ключ, навигация запрещена: внедрённая инструкция могла бы вынести секрет через адрес (`_secret_url_error`, `L108-L114`).
2. **Метаданные облака** (169.254.169.254, `metadata.google.internal`) — запрещены безусловно.
3. **Частные адреса** — запрещены, если браузер не локальный и не разрешено `browser.allow_private_urls`. Логика: защита нужна тогда, когда браузер достаёт до сетей, до которых не достаёт терминал.
4. **Список запрещённых сайтов** `security.website_blocklist` (`check_website_access`).

Поскольку `browser_exec` выполняет произвольный код, URL нельзя проверить «на входе в инструмент»: вместо этого код **предварительно сканируется на URL-литералы** (`_JS_URL_LITERAL_RE`, `browser_url_policy.py@e96221fa:L34-L46`; `expression_targets_private_url`, `L200`), включая адреса без схемы (`//host`).

Общая SSRF-защита всех веб-инструментов (`references/hermes-agent/website/docs/user-guide/security.md@e96221fa:L819-L833`): RFC 1918, loopback, link-local, CGNAT `100.64.0.0/10`; ошибка DNS = запрет; цепочки редиректов перепроверяются на каждом шаге.

### 7.5. Vault

`browser_vault` отдаёт модели только «ручки» сохранённых записей; значение подставляется в страницу помимо модели. Заполнение отклоняется, если origin страницы не совпадает с сохранённым для записи (`browser.md@e96221fa:L600-L608`). Хранилища — собственное, 1Password, Bitwarden. Код `browser_vault_tool.py` (744 строки) не читал.

### 7.6. Слабые места

**Вывод (мои оценки):**

- `browser_exec` — это исполнение кода модели рядом с браузером. Проверка URL предварительным сканированием литералов — эвристика: адрес, собранный в коде из частей, её обходит. Проект, судя по комментариям, считает границей не сканер, а то, до каких сетей браузер физически достаёт.
- Защита от инструкций, подброшенных на странице, — только обёртка результата в блок «это данные, а не инструкции» (см. 9.2); содержимое при этом не блокируется и не вырезается.
- Профиль по умолчанию одноразовый, поэтому «оставаться залогиненным» можно только через «настоящий профиль» (копия профиля владельца — рассчитано на настольную машину) или через свой Chrome по CDP. Для сервера без рабочего стола, как у Меркурия, годится только второй путь.

## 8. MCP

Описание — `references/hermes-agent/website/docs/user-guide/features/mcp.md`, справочник — `references/hermes-agent/website/docs/reference/mcp-config-reference.md`; код — `references/hermes-agent/tools/mcp_tool*.py` (два десятка модулей, читал точечно).

### 8.1. Конфигурация и транспорты

Раздел `mcp_servers` в `config.yaml` (`mcp-config-reference.md@e96221fa:L15-L74`):

- **stdio:** `command`, `args`, `env`;
- **HTTP:** `url`, `headers`, по умолчанию Streamable HTTP, `transport: sse` — SSE; TLS: `ssl_verify`, `client_cert`/`client_key` (mTLS); `auth: oauth` — OAuth 2.1 с PKCE;
- общие: `enabled`, `timeout` (вызов инструмента), `connect_timeout` (60 с), `keepalive_interval`, `lazy`, `idle_timeout_seconds` / `max_lifetime_seconds` (перезапуск «тяжёлых» stdio-серверов), `supports_parallel_tool_calls` (по умолчанию инструменты одного сервера идут последовательно);
- `tools.include` / `tools.exclude` — белый и чёрный списки по исходным именам инструментов, с fnmatch-глобами; `tools.resources`, `tools.prompts` — включить ли служебные инструменты;
- `trust: full | untrusted`, `tool_costs`, `spend_limit`, `sampling`, `elicitation`.

**Расхождение в документации:** значение `timeout` по умолчанию в одном файле указано и как 120 (пример), и как 300 (таблица) — `mcp-config-reference.md@e96221fa:L34`, `L57`.

### 8.2. Жизненный цикл

- Серверы подключаются при старте и регистрируют инструменты в общем реестре; одновременно не более 4 подключений (`mcp.discovery_concurrency`), иначе все stdio-серверы стартовали бы в один момент; волна — 120 с, весь проход — 300 с (`mcp.md@e96221fa:L749-L764`).
- MCP работает на **собственном фоновом цикле событий в отдельном потоке**; остальные потоки ставят туда корутины (`references/hermes-agent/tools/mcp_tool_loop.py@e96221fa:L1-L4`).
- `lazy: true` — инструменты регистрируются из кеша схем на диске, процесс запускается при первом вызове (`mcp.md@e96221fa:L766-L768`).
- `notifications/tools/list_changed` — список инструментов перечитывается автоматически, под блокировкой (`mcp.md@e96221fa:L770-L776`).
- `/reload-mcp` — перечитать конфигурацию. Команда требует подтверждения: пересборка набора инструментов сбрасывает кеш промпта у провайдера, и следующее сообщение оплачивается полными входными токенами (`security.md@e96221fa:L48`).
- Шлюз сам следит за `config.yaml`: убранный сервер отключается в пределах минуты, добавленный подключается; неудачное подключение повторяется (`mcp.md@e96221fa:L786-L788`).
- Истёкший OAuth-токен в фоне браузер не открывает: сервер «паркуется» с предупреждением в логе, переавторизация — `hermes mcp login <server>`.

### 8.3. Как инструменты попадают к агенту

- Имя: `mcp__<server>__<tool>` (`MCP_TOOL_NAME_PREFIX = "mcp__"`, `references/hermes-agent/tools/mcp_tool_schema.py@e96221fa:L163`); всё, кроме букв, цифр и подчёркивания, заменяется подчёркиванием (`sanitize_mcp_name_component`, `L151`). **Расхождение:** пользовательское руководство всё ещё показывает старый вид `mcp_<server>_<tool>` (`mcp.md@e96221fa:L569-L583`), справочник — новый (`mcp-config-reference.md@e96221fa:L302-L321`). Верить коду.
- Фильтры `include`/`exclude` применяются к **исходным** именам.
- Служебные инструменты на сервер: `list_resources`, `read_resource`, `list_prompts`, `get_prompt` — регистрируются, только если сервер объявил возможность.
- На каждый сервер создаётся набор инструментов `mcp-<server>` (`mcp.md@e96221fa:L792-L800`).
- Результаты: из текста, содержимого ресурсов и **описаний инструментов** вырезаются невидимые символы-теги Юникода U+E0000–U+E007F — канал скрытой передачи инструкций модели; картинки сохраняются в кеш и отдаются как `MEDIA:/путь` (`mcp.md@e96221fa:L587-L596`).

### 8.4. Безопасность

- **Окружение stdio-процесса** — только `PATH, HOME, USER, LANG, LC_ALL, TERM, SHELL, TMPDIR`, переменные `XDG_*` и то, что явно задано в `env` сервера (`_SAFE_ENV_KEYS`, `references/hermes-agent/tools/mcp_tool_config.py@e96221fa:L147`; `_build_safe_env`, `L199-L208`).
- **Маскирование в ошибках** — токены GitHub, ключи `sk-…`, Bearer, параметры `token=`/`password=` заменяются на `[REDACTED]` прежде, чем ошибка попадёт к модели (`_sanitize_error`, `references/hermes-agent/tools/mcp_tool_common.py@e96221fa:L85`).
- **Проверка пакетов** — перед запуском сервера через `npx`/`uvx` делается запрос в OSV на известные вредоносные пакеты (идентификаторы `MAL-*`; обычные CVE игнорируются). Отказоустойчивость в сторону пропуска: сетевая ошибка запуск не блокирует (`references/hermes-agent/tools/osv_check.py@e96221fa:L1-L7`).
- **Уровень доверия.** `trust: untrusted` — каждый вызов инструмента без аннотации `readOnlyHint: true` требует подтверждения через общую механику раздела 5; «всегда» пишется в `command_allowlist` как `mcp:<server>/<tool>`. По умолчанию `trust: full` — без запросов (`mcp-config-reference.md@e96221fa:L71`).
- **Бюджет.** `tool_costs` и `spend_limit` — учёт расхода на чат и сервер, в памяти; вызов, выводящий за лимит, спрашивает даже на доверенном сервере и даже в yolo; там, где ответить некому, — отказ (`mcp.md@e96221fa:L991-L1014`).
- **Sampling** (сервер просит LLM у клиента) — **включён по умолчанию**; ограничения: `max_tokens_cap: 4096`, `timeout: 30`, `max_rpm: 10`, `max_tool_rounds: 5`, `allowed_models` (`mcp.md@e96221fa:L958-L989`).
- **Elicitation** (сервер просит ввод у пользователя) — включено по умолчанию; формы идут через поверхность clarify, URL-режим отклоняется, таймаут 300 с (`mcp.md@e96221fa:L1018-L1032`).
- OAuth-токены — в `mcp-tokens/` домашнего каталога (защищённый от записи путь, см. 6.6).

### 8.5. Слабые места

**Вывод (мои оценки):**

- По умолчанию сервер полностью доверенный: его инструменты вызываются без подтверждений, а опасность инструмента определяется аннотацией `readOnlyHint`, которую выставляет сам сервер.
- Sampling включён по умолчанию: сторонний сервер может тратить токены владельца, пусть и в пределах лимитов.
- Проверка OSV пропускает запуск при сетевой ошибке и ловит только уже известные вредоносные пакеты.
- Сканирования описаний инструментов на текстовые инъекции, кроме вырезания невидимых символов, я не нашёл (результаты вызовов при этом оборачиваются как недоверенные — см. 9.2).
- По модели угроз самого проекта stdio-серверы MCP запускаются из окружения процесса агента и **не ограничены** терминальным бэкендом: docker-песочница для команд их не изолирует (`references/hermes-agent/SECURITY.md@e96221fa:L78-L83`).

## 9. Защита от инъекций и секреты

### 9.1. Модель угроз проекта

`references/hermes-agent/SECURITY.md@e96221fa:L32-L154` — самое важное место для проектирования:

- Hermes — **однопользовательский** персональный агент.
- «**Единственная граница безопасности против враждебной LLM — операционная система.** Ничто внутри процесса агента не является сдерживанием — ни шлюз подтверждений, ни маскирование вывода, ни сканеры шаблонов, ни списки разрешённых инструментов» (`SECURITY.md@e96221fa:L58-L65`).
- Два режима изоляции (`SECURITY.md@e96221fa:L70-L119`):
  - **изоляция терминального бэкенда** — в песочнице только команды оболочки и файловые инструменты. **Не ограничены:** инструмент исполнения кода (дочерний процесс на хосте), подпроцессы MCP, плагины, хуки, загрузка скиллов. Годится, когда опасаются разрушительной команды от модели, а оператор в остальном доверенный;
  - **оборачивание всего процесса** — весь агент в контейнере (собственный Docker-образ и Compose) или в NVIDIA OpenShell. Это **поддерживаемый режим для случаев, когда агент читает содержимое, которым оператор не управляет**: открытый веб, входящая почта, многопользовательские каналы, недоверенные MCP-серверы.
- Шлюз подтверждений, маскирование, Skills Guard названы «эвристиками в процессе»: «denylist over shell strings is structurally incomplete. The gate catches cooperative-mode mistakes, not adversarial output» (`SECURITY.md@e96221fa:L137-L154`).
- **Не считается уязвимостью** (`SECURITY.md@e96221fa:L258-L280`): обход регулярок шлюза подтверждений, обход маскирования, prompt injection сама по себе — без доведённого до конца вредного исхода.
- Внешние поверхности (`SECURITY.md@e96221fa:L198-L234`): авторизация обязательна на каждой поверхности, пересекающей границу доверия; адаптер обязан **отказывать, пока не задан список разрешённых** (поведение «открыто при пустом списке» — баг); идентификатор сессии — ручка маршрутизации, а не право доступа; **внутри допущенного набора все вызывающие равны** — возможности на уровне отдельного пользователя не моделируются; «профили — не арендаторы».

### 9.2. Что сканируется на инъекции

Общий набор шаблонов — `references/hermes-agent/tools/threat_patterns.py@e96221fa:L68-L156`, функция `scan_for_threats(content, scope)` (`L196-L212`). Три области: `all` ⊂ `context` ⊂ `strict`.

| Категория | Примеры (идентификатор находки) |
|---|---|
| классические инъекции (`all`) | `ignore … previous/all … instructions` (`prompt_injection`); `system prompt override`; `disregard your … rules`; `forget …` с защитой от «don't forget to»; `act as if you have no restrictions`; HTML-комментарий со словами ignore/override/system/secret/hidden; `<div style="display:none">`; `translate … into … and execute`; `do not tell the user` |
| подмена роли (`context`) | `you are now a …`, `pretend to be`, `output system prompt`, `respond without restrictions`, `you have been updated to`, `name yourself …` |
| управление извне, C2 (`context`) | `register as a node`, `heartbeat to …`, `pull tasks` |
| невидимые символы | нулевой ширины, bidi-переопределения, изоляты, теги U+E0000–U+E007F (`INVISIBLE_CHARS`, `L157-L160`) — проверяются по сырому тексту до нормализации; три настоящих флага-эмодзи исключены |

Сканируется весь текст кусками с перекрытием (`MAX_SCAN_CHARS = 65 536`, перекрытие 4096), чтобы нагрузка не спряталась за границей.

Где применяется:

- **Контекстные файлы** (AGENTS.md, .cursorrules, SOUL.md, .hermes.md) перед вставкой в системный промпт: `_scan_context_content` (`references/hermes-agent/agent/prompt_builder.py@e96221fa:L84-L111`). Находка → содержимое **заменяется заглушкой** `[BLOCKED: <файл> contained potential prompt injection (…). Content not loaded.]`. Исключение — собственный `SOUL.md` владельца: только предупреждение, файл грузится (иначе документ, который сам описывает атаку, выпадал целиком). `SOUL.md`, пришедший из стороннего дистрибутива профиля, блокируется.
- **Записи памяти** — область `strict`, при записи и при чтении (`references/hermes-agent/tools/memory_tool_store.py@e96221fa:L17-L32`, `L228-L235`).
- **Результаты недоверенных инструментов** — `web_extract`, `web_search`, всё с префиксами `browser_` и `mcp_` (`references/hermes-agent/agent/tool_dispatch_helpers.py@e96221fa:L497-L506`):
  - содержимое длиннее 32 символов **оборачивается** в `<untrusted_tool_result source="…">` с указанием «это ДАННЫЕ, а не инструкции» (`_maybe_wrap_untrusted`, `L585`);
  - вхождения самого маркера внутри содержимого обезвреживаются, чтобы отравленный текст не закрыл блок раньше времени; быстрого пути «уже обёрнуто» нет сознательно — его можно подделать (`L579-L591`);
  - сканирование результата даёт только **внутреннюю метку риска** (`risk: high/low`, список находок) — ничего не блокирует и не вырезает (`_tool_output_risk_metadata`, `L557-L575`).
- **Сообщения из шлюза** не сканируются: это ввод допущенного пользователя. Метаданные платформы (название чата, имя) перед вставкой в промпт обезвреживаются (`neutralize_untrusted_inline_text`, `references/hermes-agent/gateway/session.py@e96221fa:L295`).
- Скиллы (Skills Guard) и промпты cron — отдельные сканеры (`tools/skills_guard.py`, `tools/cronjob_prompt_scan.py`), не читал.

Проект сам называет шаблоны «эвристиками, а не определением намерения» (`references/hermes-agent/website/docs/user-guide/security.md@e96221fa:L929-L932`).

### 9.3. Маскирование секретов

Модуль — `references/hermes-agent/agent/redact.py` (около 2000 строк).

- **Что распознаётся:** префиксы известных ключей (`sk-…`, `ghp_…`, `github_pat_…` и десятки других — `_PREFIX_PATTERNS`, `redact.py@e96221fa:L134`); присваивания переменным с именем, содержащим `KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL/AUTH` (`_ENV_ASSIGN_RE`, `L224-L225`); секретные флаги командной строки и `docker login -p`; строки подключения; поля JSON и YAML с секретными именами; заголовок `Authorization` (`L607-L608`); токен Telegram-бота (`_redact_telegram_token`, `L628`); блоки приватных ключей PEM (`_redact_private_key_blocks`, `L1036`); учётные данные в URL и чувствительные параметры запроса; телефоны.
- **Как:** `mask_secret` — первые 4 и последние 4 символа (`sk-p...7890`), короче 12 символов — `***` (`redact.py@e96221fa:L931-L939`). При чтении файла найденный ключ заменяется **непригодной для повторного использования** меткой `«redacted:ghp_…»` вместо маски «голова/хвост», которую агент мог бы принять за значение (`L1497-L1499`).
- **Где применяется:**
  - логи — `RedactingFormatter` на всех файловых обработчиках (`redact.py@e96221fa:L1973`; подключение — `references/hermes-agent/hermes_logging.py@e96221fa:L420-L433`);
  - вывод терминала перед отдачей модели — `redact_terminal_output` (`redact.py@e96221fa:L1805-L1814`): полный проход по присваиваниям включается только для команд-дампов окружения и чтения секретных файлов, иначе слишком много ложных срабатываний на исходном коде;
  - исходящий текст в чат — `redact_for_egress` (`L1784`), в стриминге — «устоявшийся префикс» (см. 2.7);
  - карточки подтверждений — `redact_approval_display` (`L942`);
  - ошибки MCP — отдельная функция (см. 8.4).
- **Выключатель:** `HERMES_REDACT_SECRETS` / `security.redact_secrets` (`redact.py@e96221fa:L75`); параметр `force=True` — для границ, где сырое значение не должно пройти ни при каких настройках.
- Плагины могут добавлять свои шаблоны; они проходят структурную проверку от катастрофического перебора (`register_redaction_patterns`, `L1921`).

### 9.4. Хранение и выдача секретов

- Секреты — в `~/.hermes/.env`; токены OAuth — в `auth.json`; настройки без секретов — в `config.yaml`. Правило проекта: секреты никогда не кладутся в основной конфиг (`references/hermes-agent/website/docs/user-guide/configuration.md@e96221fa:L57-L68`).
- Внешние источники секретов — 1Password, Bitwarden, произвольная команда (`website/docs/user-guide/secrets/`, не читал).
- Дочерние процессы получают отфильтрованное окружение — у каждой «песочницы» свой фильтр (таблица — `security.md@e96221fa:L744-L753`): `execute_code` — белый список плюс отсев по имени; локальный терминал — чёрный список ключей самого hermes; docker и ssh — ничего, кроме явно перечисленного; MCP — восемь безопасных переменных плюс явный `env`.
- Модель не может прочитать `.env` файловыми инструментами и не может писать в хранилища секретов (см. 6.6).
- Проект оговаривает: фильтрация окружения «снижает случайную утечку, это не сдерживание» — код, работающий внутри процесса агента (скиллы, плагины, хуки), читает всё, что читает агент (`SECURITY.md@e96221fa:L121-L135`).

**Вывод:** секреты в hermes лежат в `.env` открытым текстом и защищены правами файла и фильтрацией окружения дочерних процессов. Шифрования на диске и выдачи секрета инструменту «в момент вызова» как общего механизма я не увидел (исключение — vault браузера). Требование Меркурия «хранятся зашифрованными, выдаются инструменту в момент вызова» строже, чем сделано в hermes.

## 10. Логи и наблюдаемость

### 10.1. Файлы логов

`references/hermes-agent/hermes_logging.py@e96221fa:L1-L7`, настройка — `setup_logging` (`L375-L446`), каталог — `~/.hermes/logs/`.

| Файл | Уровень | Ротация | Что |
|---|---|---|---|
| `agent.log` | INFO+ (настраивается) | 5 МБ × 3 | всё |
| `errors.log` | WARNING+ | 2 МБ × 2 | только предупреждения и ошибки |
| `gateway.log` | INFO+ | 5 МБ × 3 | только компоненты шлюза (фильтр по префиксу имени логгера), в режиме `mode="gateway"` |
| `gui.log` | INFO+ | 10 МБ × 5 | дашборд и TUI |

- Формат строки: `%(asctime)s %(levelname)s%(session_tag)s %(name)s: %(message)s` (`hermes_logging.py@e96221fa:L107`). **Метка сессии** добавляется в каждую запись фабрикой записей (`set_session_context`, `L253`) — по ней фильтрует `hermes logs --session <id>`.
- Все файловые обработчики работают через **одну асинхронную очередь** (`QueueHandler`/`QueueListener`), чтобы запись на диск не блокировала цикл событий, и через `RedactingFormatter`.
- Маршрутизация по компонентам — таблица префиксов `COMPONENT_PREFIXES` (`L330-L342`).
- Уровень и ротация — `logging.*` в `config.yaml`; подробный режим — `setup_verbose_logging` (`L456`).
- Правило для кода шлюза: **на уровне INFO и выше не логируется пользовательское содержимое** — ни тела сообщений, ни имена, ни адреса; только длина текста, идентификатор или хеш; сырое значение — только на DEBUG. Причина: логи уходят в выгрузку для поддержки (`references/hermes-agent/gateway/AGENTS.md@e96221fa:L58-L62`).
- В Docker (`references/hermes-agent/website/docs/user-guide/docker.md@e96221fa:L436-L454`): вывод шлюза дублируется в `docker logs` и в `logs/gateways/<profile>/current` (ротация 10 × 1 МБ); журнал загрузки контейнера — `logs/container-boot.log`.
- Прогресс инструментов можно писать в файл аудита вместо сообщений в чат: `display.tool_progress: log` (`references/hermes-agent/website/docs/user-guide/messaging/index.md@e96221fa:L573`).

### 10.3. Метрики и здоровье

- **Экспорт — OTLP/HTTP (OpenTelemetry), а не Prometheus** (`references/hermes-agent/website/docs/developer-guide/gateway-monitoring.md@e96221fa:L6-L46`), выключен по умолчанию (`monitoring.export.otlp`). Экспортируются показатели шлюза (`hermes.gateway.up/state/busy/active_agents/background_work`, `hermes.platform.up/degraded`), переходы жизненного цикла, показатели cron.

## 11. Развёртывание

### 11.1. Образ

`references/hermes-agent/Dockerfile` (590 строк), описание — `references/hermes-agent/website/docs/user-guide/docker.md@e96221fa:L608-L640`.

- База — Debian 13 (trixie), закреплённая по digest (`Dockerfile@e96221fa:L47`); многостадийная сборка: `sqlite_build` → `runtime_base` → `python_deps` → `frontend_build`/`webapp_build` → `runtime`.
- Внутри: Python 3.14 из `uv.lock`, Node.js, полный Chromium, FFmpeg, ripgrep, Git, OpenSSH, **Docker CLI**, s6-overlay (версии и архивы закреплены контрольными суммами, `Dockerfile@e96221fa:L136-L140`).
- `ENV HERMES_HOME=/opt/data`, `HERMES_WRITE_SAFE_ROOT=/opt/data`, `VOLUME /opt/data` (`Dockerfile@e96221fa:L501-L502`, `L555`); `ENTRYPOINT` — `docker/entrypoint-dispatch.sh` (`L589`).
- **Каталог приложения `/opt/hermes` неизменяем**: принадлежит root и доступен пользователю среды только на чтение. Агент не может править собственный код; самоулучшение ограничено скиллами, памятью, плагинами и конфигурацией в `/opt/data`; ядро меняется только выпуском нового образа (`docker.md@e96221fa:L313-L319`).
- **init — s6-overlay** как PID 1 (`docker.md@e96221fa:L642-L650`): от root выполняются стартовые скрипты (перенастройка UID/GID пользователя `hermes` под `HERMES_UID/GID`, исправление владельца тома, при первом запуске — создание `.env`, `config.yaml`, `SOUL.md`, миграции схемы конфигурации, синхронизация встроенных скиллов), затем каждый сервис сбрасывает привилегии до `hermes` (uid 10000). Запуск шлюза от root в официальном образе отклоняется.
- s6 **перезапускает упавший шлюз** за пару секунд, не роняя контейнер, и **собирает зомби-процессы** (безголовые браузеры, MCP-серверы, помощники git/npm). Если переопределить entrypoint без init, сироты копятся — в одном развёртывании набралось 284 зомби меньше чем за три часа (`docker.md@e96221fa:L77-L79`, `L670-L672`).
- `docker exec` автоматически переходит на пользователя `hermes` (`docker.md@e96221fa:L687`).
- Отдельный образ песочницы — `docker/sandbox-desktop.Dockerfile` (не читал).

### 11.2. Compose

`references/hermes-agent/docker-compose.yml` (76 строк): два сервиса на одном образе —

- `gateway`: `command: ["gateway", "run"]`, `restart: unless-stopped`, **`network_mode: host`**, том `~/.hermes:/opt/data`, переменные `HERMES_UID/GID`;
- `dashboard`: тот же том, привязка к `127.0.0.1` (дашборд хранит ключи; удалённый доступ — только через SSH-туннель или прокси с авторизацией).

Ограничений ресурсов в compose нет; документация рекомендует 2–4 ГБ памяти и 2 CPU, с браузером — не меньше 2 ГБ (`docker.md@e96221fa:L585-L606`). Healthcheck в прочитанных строках Dockerfile и compose не задан; проверка состояния — через `/health` API-сервера.

Сопутствующие сервисы (база, браузерная ферма) документация советует выносить в **отдельные контейнеры в общей сети Docker** и обращаться по имени контейнера (`docker.md@e96221fa:L794-L825`).

Предупреждение: два шлюза на одном каталоге данных запускать нельзя (`docker.md@e96221fa:L325-L327`).

### 11.3. Где выполняются команды контейнерного агента

Документация разделяет два понятия: «hermes в Docker» и «Docker как терминальный бэкенд» (агент на хосте, команды в песочнице) — `docker.md@e96221fa:L12`, `L470-L472`. Упоминаний проброса `docker.sock` в `docker.md` поиск не нашёл. По модели угроз (9.1) контейнер с агентом **и есть** изоляция («оборачивание всего процесса»): внутри него команды идут бэкендом `local`.

**Вывод:** в официальной схеме агент и исполняемые им команды живут в одном контейнере вместе с `.env` и памятью. Изоляция защищает хост от агента, но не секреты и память агента от выполняемого им кода; при `network_mode: host` контейнер к тому же видит все сервисы хоста на loopback.

### 11.4. Слои конфигурации

`configuration.md@e96221fa:L57-L68`, по убыванию приоритета:

1. аргументы командной строки;
2. `~/.hermes/config.yaml` — все несекретные настройки;
3. `~/.hermes/.env` — секреты (и запасной источник переменных окружения);
4. встроенные значения по умолчанию.

Переменные, переданные контейнеру через `-e`, перекрывают `.env` (`docker.md@e96221fa:L456-L468`).

- Шлюз читает YAML **«сырым»**, не через словарь значений по умолчанию CLI, поэтому ключ, видимый CLI, может по-другому вести себя в шлюзе (`gateway/AGENTS.md@e96221fa:L11-L13`).
- Часть настроек подхватывается на лету: конфигурация подтверждений (кеш по времени изменения файла, `security.md@e96221fa:L190`), список MCP-серверов (шлюз следит за файлом).
- **Профили** — отдельные домашние каталоги со своими `.env`, конфигурацией, памятью и песочницей; один процесс шлюза может обслуживать несколько профилей (`gateway.multiplex_profiles`). Профили — не граница безопасности (9.1).

Каталог данных (`configuration.md@e96221fa:L19-L32`, `docker.md@e96221fa:L282-L298`): `config.yaml`, `.env`, `auth.json`, `SOUL.md`, `state.db` (SQLite: сессии, журнал доставки, расход), `sessions/`, `memories/`, `skills/`, `cron/`, `hooks/`, `logs/`, `pairing/`, `sandboxes/`, `home/` (HOME для подпроцессов инструментов), `cache/`.

Замечание про SQLite в контейнере: режим WAL повреждается на bind-mount через границу виртуальной машины (virtiofs, 9p) — hermes определяет тип монтирования и переключает журнал (`docker.md@e96221fa:L300-L311`). К Меркурию с PostgreSQL не относится.

### 12.2. Упростить

- **Один канал, один владелец.** Мультиплексирование профилей, relay-коннекторы, темы в личных чатах, режим наблюдения за группой, сторож петель между ботами — не нужны. Авторизация: сравнение `user_id` с `TELEGRAM_ADMIN_ID`, остальным — отказ. Сопряжение (pairing) пригодится, только если появятся другие пользователи.
- **Не переносить чёрный список регулярных выражений для оболочки.** Вместо него — то, что уже записано в плане разработки: класс опасности у **инструмента** (чтение / изменение / необратимое) и политика по классам; для SSH — классификация команд по образцу `ssh-mcp`. Hermes сам говорит, что его шлюз подтверждений — не граница.
- **Ожидание подтверждения — состояние запуска в БД**, а не заблокированный поток: в hermes перезапуск теряет ожидающие подтверждения и разрешения сессии; Меркурию по фазе 3 это нельзя.
- **Стриминг:** только правка сообщения с интервалом; нативные черновики и «богатые» сообщения Bot API — позже.
- **Конфигурация:** `.env` + БД; слоёв «CLI / YAML / .env / профиль / managed» не нужно.

### 12.3. Спорно

- **«Умное» подтверждение вспомогательной моделью** по умолчанию. Экономит внимание владельца, но переносит решение о безопасности на LLM, которую можно обмануть содержимым команды. Для Меркурия — не раньше, чем появится выученная политика подтверждений, и только как понижение шума, а не как единственный барьер.
- **Отключение проверок в контейнерном бэкенде.** Верно лишь если в песочнице нет ничего ценного и из неё нет пути наружу; у Меркурия агент ходит по SSH на серверы владельца и публикует от его имени — опасность там не в файловой системе песочницы.
- **`browser_exec` — произвольный код модели вместо набора действий.** Экономит ходы, но политика URL и подтверждение публикаций становятся эвристикой по тексту кода. Меркурию с требованием «публикация только с подтверждением» ближе явные действия (навигация, клик, ввод, отправка формы) с классом опасности у каждого — так и запланировано через API на Fastify.
- **Агент и исполнение команд в одном контейнере** (официальная схема hermes). Меркурий в плане разработки выбрал обратное: «команды и код выполняются в песочнице, а не в контейнере ядра». Из hermes стоит взять параметры песочницы (`--cap-drop ALL`, `no-new-privileges`, лимиты pids/памяти/CPU, tmpfs, сеть по настройке — раздел 6.3), но управлять песочницей придётся иначе: проброс `docker.sock` в контейнер ядра равен root на хосте. Варианты — заранее поднятый контейнер-песочница в том же compose с исполнением по SSH (на `amphp-ssh`) или небольшой агент исполнения внутри песочницы. Этого решения в hermes нет.
- **Один контейнер песочницы на всё** (сессии, cron, субагенты) — удобно для фоновых процессов, но параллельные воркеры мешают друг другу. план разработки уже требует «параллельные воркеры — только на чтение».
- **Секреты открытым текстом в `.env`** — в hermes норма; у Меркурия требование строже (шифрование, выдача в момент вызова).
- **`network_mode: host`** в compose — на сервере с сорока другими проектами лучше обычная сеть compose.
