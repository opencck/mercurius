# Устройство и соглашения

## Устройство приложения на opencck

Как компоненты Меркурия ложатся на `opencck/server` (DDD-слои Domain → App → Infrastructure, модули через
`App::addHandler()`, сервисы-одиночки, события, задачи `amphp/parallel`). Составлено по скиллу `skill-opencck`
2026-11-16; таблицы ниже сверены с кодом 2026-11-20. Код пакетов из `packages/` от opencck не зависит — основной репозиторий
оборачивает их в сервисы и модули.

### Domain — сущности и правила

По фактическим классам `src/Domain/` (2026-11-20). Сущности неизменяемые (`readonly`), интерфейсы хранилищ — в
`src/Domain/Repository/`, реализации — PostgreSQL в `src/Infrastructure/Repository/` и в памяти для тестов.

### App — сценарии

Без отдельного контейнера зависимостей: сервисы собираются в `bootstrap/01…11-*.php` (части запуска в одной области
видимости) и передаются конструкторами.

- **Агент** (`src/App/Agent/`): `AgentLoop` и `ToolRound` (цикл, раунд инструментов), `RunScheduler` (очередь запусков
  по беседам), `ApprovalService` и `ApprovalGate` (карточки), `LoopGuard` и `SpendGuard`, `PromptBuilder`,
  `ChannelRunObserver` (статус в канале), `Tool/` — инструменты по категориям и `ToolRegistry`, `Delegation/` — воркеры,
  `Model/` — `ModelRouter`, `ModelRoles`, `Context/` — сжатие контекста, `Sandbox/`, `Media/`, `Trace/`.
- **Канал и команды** (`src/App/Service/`): `ChatService` (сообщения и команды `/…`), `GroupGate`, `VisitorService`,
  `PolicyService`, `OwnerDirectory`, `RoleCatalog`, `SettingsCommands`, `CodexCommands`, `TraceReports`, `Doctor`.
- **Подсистемы**: `Job/` (`JobScheduler`, `HookReceiver`, `DailyDigest`), `Peer/` (`PeerNetwork`, `A2aServer`, `AgentKeys`,
  `AgentRequests`, `A2aFiles`), `Mcp/` (`McpManager`, `McpTool`, `OsvCheck`), `Skill/` (`SkillLibrary`, `SkillImporter`),
  `Server/` (`ServerConsole`), `Vault/`, `Settings/`, `Improve/` (предложения, заметки к промпту, набор задач), `Eval/`,
  `Export/` (архив и импорт), `Api/` (WebSocket API), `Web/`.
- **Событий opencck нет:** трассировка — наблюдатель запуска (`RunObserver`, `Trace/`), а не подписка на события.

| `TraceRetentionModule` | Срок хранения трасс |
| `PeerModule` | Соединения с соседями, которые держатся открытыми |

- **`amphp/parallel` не используется:** по замеру тяжёлых по процессору мест нет (решение в доработках цикла).
- **Песочница исполнения** — сервис compose `sandbox` (`bootstrap/sandbox.php`, `src/Sandbox/`), образ из основного
  репозитория.
- **Хранение состояния — только PostgreSQL.** `Storage` opencck не используется: запуски, подтверждения и очереди
  переживают перезапуск.

### Как сделано: каркас

- **`opencck/server` — метапакет зависимостей AMPHP** (HTTP-сервер, роутер, WebSocket, журнал); классы `App`, `Server`,
  обработчики пишутся в проекте. Корневой namespace приложения — `OpenCCK\`.
- **База — `amphp/postgres`**, а не `drift/dbal`: родной для AMPHP v3, без адаптера ReactPHP. Работает поверх `ext-pgsql`.
- **Без расширения цикла `ev`:** `amphp/postgres` поверх `ext-pgsql` отказывается работать с драйвером `ev`.
  Используется встроенный драйвер `stream_select`; если упрёмся в число соединений — переходить на `pecl-pq` или
  `ext-uv`.
- **PHPUnit 9.6:** `amphp/phpunit-util` 3 (`AsyncTestCase`) поддерживает только его.
- **Миграции — свои:** SQL-файлы `migrations/NNNN_name.sql`, таблица `schema_migrations`, одна транзакция под
  advisory-блокировкой при старте приложения.
- **Образ PostgreSQL — `pgvector/pgvector:pg17`**, расширение `vector` включается первой миграцией.

### Как сделано: канал, модель и участники

- **Три пакета:** `mercurius-llm` (модель), `mercurius-connectors` (маршруты исходящих соединений),
  `mercurius-messenger` (канал). Подключены сабмодулями в `packages/` и Composer-репозиториями типа `path` с
  копированием; ядро знает только их интерфейсы, Telegram и OpenRouter упоминаются лишь в `src/Infrastructure`
  (настройки и модули подключения).
- **Участник — запись `principals`** (вид `human` или `agent`, роль `owner`, `admin` или `user`; владелец — только
  человек и только один). Учётная запись канала связана с участником через `channel_identities`. Владелец создаётся при
  первом сообщении с `TELEGRAM_ADMIN_ID`; остальным — отказ без вызова модели; регистрация других участников — позже.
- **Диалог:** один открытый диалог на чат, `/new` закрывает его; модели уходит системный промпт и последние
  `LLM_HISTORY_LIMIT` сообщений (по умолчанию 40).
- **Поток ответа:** заглушка «…», затем правки одного сообщения не чаще раза в 1,5 с, итог правкой; длинный итог —
  продолжениями. Во время потока текст усекается, а не делится, иначе продолжения множились бы на каждой правке.
- **Разметка:** ответ модели передаётся каналу как `ParseMode::Markdown`; Telegram получает его в HTML
  (`MarkdownToTelegramHtml`, сверено с адаптером hermes), при отказе разметки — текст без маркеров. Служебные тексты —
  без разметки.
- **Учёт расхода — таблица `llm_calls`:** назначение, модель, причина завершения или вид ошибки, токены по корзинам
  (вход без кеша, выход, чтение и запись кеша, рассуждения), стоимость от OpenRouter, длительность.
- **Модель по умолчанию — `z-ai/glm-5.3-flash`** с уровнем рассуждений `low`; меняется через `LLM_MODEL` и
  `LLM_REASONING_EFFORT`. Запросы к OpenRouter идут через VLESS при заданном `VLESS_URI`; повторы — `RetryingClient`,
  поток после первого события не повторяется.
- **Telegram:** вебхук при заданном `APP_URL`, иначе long polling. При регистрации вебхука накопившиеся обновления не
  сбрасываются (`drop_pending_updates=false`), Telegram доставит их после запуска.
- **Проверка бота** после развёртывания — через Telegram Web из Chrome владельца (см. `CLAUDE.md`).

### Как сделано: агентский цикл

Устройство — в [«Агентский цикл и харнесс»](agent-loop.md#агентский-цикл-и-харнесс); здесь — что уточнилось при реализации
и проверке на сервере 2026-11-16.

- **Код:** `AgentLoop` (цикл), `RunScheduler` (один запуск на диалог, дописки, `/stop`, продолжение после
  перезапуска), `ChannelRunObserver` (статус-сообщение), `ToolRegistry`/`ToolCallValidator`/`ToolExecutor`,
  `LoopGuard`, `PolicyService`; таблицы `runs`, `tool_calls`, `run_inbox`, `principal_policies` (миграция `0003`).
- **Первые инструменты ядра:** `http_request` (только `GET`/`HEAD`; остальные методы — с подтверждениями) и
  `set_participant_policy` (только в запусках владельца). Файлы и команды — в песочнице, следующей части.
- **Защита от запросов во внутреннюю сеть — в два слоя:** `AddressGuard` проверяет каждый адрес и каждый
  перенаправленный, а HTTP-клиент инструментов подключается только к проверенному IP (`GuardedConnector`), так что
  подмена DNS между проверкой и соединением не помогает.
- **Закрытие задачи в истории:** остановленный, упавший или прерванный ошибкой запуск сохраняет итоговое сообщение
  ассистента. Без него модель видела в истории вопрос без ответа и бралась за остановленную задачу снова (найдено
  при проверке на сервере).
- **Сообщение сразу после `/stop`** не попадает в останавливаемый запуск, а начинает следующий.
- **Упавший запуск** закрывается как `failed` с причиной «внутренняя ошибка», владелец получает сообщение; ошибка,
  вылетевшая из волокна, пишется в журнал и не останавливает процесс.
- **Нулевые байты** в результатах инструментов заменяются: поле `text` PostgreSQL их не принимает.
- **Отложено (мелкое):** после перезапуска старое статус-сообщение остаётся с текстом «Выполняю …», итог приходит
  новым; маркеры `**` вокруг ссылок внутри жирного текста (конвертер Markdown пакета `messenger`); итоговый вызов
  после лимита не резервирует бюджет; срок запуска не прерывает идущий вызов модели.

### Как сделано: песочница

Песочница — [«Песочница»](agent-loop.md#песочница); проверено на сервере 2026-11-16.

- **Код:** исполнитель `OpenCCK\Sandbox` (`bootstrap/sandbox.php`, сервис `sandbox`), клиент `HttpSandboxClient`, инструменты
  `read_file`, `list_files`, `write_file`, `run_command`, выгрузка больших результатов в `ToolExecutor`.
- **Команда участника:** `prlimit` (процессы, процессорное время, адресное пространство, размер файла) →
  `setpriv` (uid участника, без групп) → `env -i` → `setsid` → `bash`, которая уже от участника переходит в `cwd`
  и ставит `umask 077`. Переход в каталог от root позволял через символическую ссылку попасть в чужой каталог —
  найдено ревью, закрыто.
  Текст команды — не аргумент: `bash` обёртки читает его со своего stdin до нулевого байта, дальше идёт stdin самой
  команды (2026-11-18, аудит безопасности) — аргументы любого процесса видны другим пользователям в `/proc`. Команда
  с нулевым байтом отклоняется.
- **Фоновые процессы команды убиваются, когда она заканчивается** (вся её сессия), ожидание вывода ограничено.
  Долгоживущих серверов в песочнице пока нет — состояние живёт в файлах.
- **PID 1 — `tini` (`init: true`):** без него убитые процессы оставались зомби и съедали лимит процессов участника
  (найдено на сервере).
- **Лимиты по умолчанию:** процессов на участника 128 (заметно меньше 512 контейнера), адресное пространство не
  ограничено (решение владельца 2026-11-19: сборка vite + tailwind падала с «WebAssembly.instantiate(): Out of memory» —
  Node резервирует под WebAssembly ~10 ГБ адресов, а `--as` давал 8 ГБ; настоящую память держит контейнер,
  `SANDBOX_MEMORY` теперь 4 ГБ; `SANDBOX_COMMAND_MEMORY` задаёт предел, если нужен), процессорное время 600 с, 4
  одновременные команды, файл не больше лимита каталога (`--fsize`).
- **Исполнитель** отвергает подключения с loopback (это команды участников, они в той же сети), не больше 16
  соединений с адреса. Права контейнера: `cap_drop: ALL` плюс `SETUID`, `SETGID`, `CHOWN`, `DAC_OVERRIDE`,
  `FOWNER`, `KILL`.
- **Среды выполнения:** PHP 8.2 с Composer, Python 3, Node.js с npm, Go — работают от участника с лимитом 8 ГБ.
- **Отличие от проекта:** вывод команды исполнитель сокращает до 25 КБ начала и 25 КБ конца, поэтому выгрузка в
  файл срабатывает в основном для HTTP и других инструментов; полный вывод команды модель получает, перенаправив
  его в файл сама (`… > out.txt`). Общий бюджет результатов на ход — в части 5.
- **Сеть песочницы до хоста не закрывается** (решение владельца 2026-11-16): порты самого сервера через шлюз сети
  `sandbox` доступны, и это нужно. Локальная сеть сервера тоже доступна — это нормально (подтверждено владельцем
  2026-11-17, для всех четырёх экземпляров); правила брандмауэра для подсетей песочниц не ставим. Закрыты
  по-прежнему `docker.sock`, SSH на свою машину и сети `internal` (база) и `web`.
- **`/proc` с `hidepid=2,gid=0`** (решение владельца 2026-11-19): контейнер песочницы получает `CAP_SYS_ADMIN` и
  `apparmor=unconfined` (профиль Docker по умолчанию запрещает перемонтирование), при старте перемонтирует `/proc`.
  Участник видит только свои процессы, исполнитель (root, группа 0) — все, чтобы снимать то, что оставила команда.
  Команды участников идут без возможностей: `setpriv` со сменой uid и `no-new-privileges`. Проверено на сервере:
  другой участник процессов не видит, root видит и останавливает.
- **Отложено (мелкое):** `wc -l` не считает
  последнюю строку без перевода; сбой `du` читается как пустой каталог; `app` виден из сети песочницы.

### Как сделано: подтверждения и посетители

Подтверждения, сохранённые разрешения, посетители — [«Подтверждения и запреты»](agent-loop.md#подтверждения-и-запреты),
[«Участники»](participants.md#участники-люди-и-агенты); проверено на сервере 2026-11-16.

- **Код:** `ApprovalService` (карточка, решение, истечение, `/permissions`), `CallbackRouter` (нажатия только от
  владельца, по префиксу `ap:` / `pv:` / `pg:`), `VisitorService`, `OutwardActionClassifier`, `SecretMasker`, таймер в
  `AgentModule`, миграция `0004_approvals`. Настройка — `AGENT_APPROVAL_TIMEOUT` (1800 с, не больше суток).
- **Карточки** приходят владельцу в личный чат; действие длиннее 3000 знаков — файлом перед карточкой.
- **Порядок записи:** запуск и вызов помечаются ожидающими до отправки карточки — нажатие, пришедшее сразу,
  находит запуск ждущим. Из ожидания запуск выводит только атомарный переход статуса: нажатие, текст, `/stop` и
  перезапуск не могут сработать дважды, поздний ответ не оживляет остановленный запуск. На старте запуск, решение по
  которому успели сохранить до остановки сервера, продолжается. Просроченную карточку нажатием не открыть.
- **Ключ разрешения** выдаётся только одной простой команде с одним внешним действием. Цепочки (`&&`, `;`, `|`,
  фоновое `&`), обёртки (`timeout`, `xargs`, `find -exec` и др.), подоболочки и группы, префиксы переменных и `env`
  спрашиваются каждый раз — иначе разрешение на одно действие покрыло бы второе, а локальный шаг мог бы изменить,
  куда уходит первое (найдено ревью). `git push` получает ключ только с адресом (хост и репозиторий): имя удалённого
  репозитория (`origin`) и опции `git` перед `push` локальной записью перенаправляются куда угодно, поэтому
  спрашиваются всегда.
- **Секреты** маскируются в разобранных аргументах (поля заголовков и тела по имени), в JSON-тексте, в учётных данных
  URL и значениях запроса, в подписи карточки и в статусе выполняемого инструмента.
- **Посетитель:** незнакомец в личном чате — посетитель в ожидании, владельцу одна карточка с первым сообщением;
  модель до решения не вызывается; «Разговор» — роль посетителя без инструментов; о допуске посетитель получает
  сообщение. В группах незнакомцы по-прежнему получают отказ (группы — [в каналах](channels.md#группа)). Отличие от hermes: там незнакомца
  пускают по одноразовому коду в CLI сервера (`gateway/pairing.py`), у нас — кнопкой в чате владельца.
- **Проверено в Telegram:** отказ, «Разрешать всегда» и повтор без вопроса, `/permissions` и отзыв, перезапуск
  контейнера во время ожидания, текст во время ожидания, молчание (с `AGENT_APPROVAL_TIMEOUT=60`). Посетитель —
  только тестами: второго аккаунта для проверки нет.
- **Отложено (мелкое):** сообщение «Жду подтверждения владельца…» не правится после решения; список
  `/permissions` не обновляется после отзыва; нет предела числа ожидающих карточек посетителей (у hermes — 3 на
  платформу); отклонённый посетитель получает отказ на каждое сообщение; разрешение на адрес `git push` доверяет
  git-настройкам песочницы (`url.*.insteadOf`, заданный раньше, может перенаправить push) — закрывает политика команд
  [на серверах](servers.md#правила-никогда-без-владельца).

### Как сделано: сжатие контекста

Сжатие контекста — [«Контекст»](agent-loop.md#контекст); проверено на сервере 2026-11-16.

- **Код:** `ContextCompactor`, `ContextBudget`, `SummaryPrompt` (`App/Agent/Context`), миграция `0005_context_compaction`.
  Состояние — у диалога: `conversations.summary` (только тело резюме), `summary_upto` (id последнего сжатого
  сообщения), неудачи и пауза; обрезанный текст — в `messages.compact_content`, оригинал остаётся.
- **Модель получает:** системный промпт → сообщение-резюме (роль `user`: пометка «только справка», тело, сообщения
  собеседника сжатой части) → историю и сообщения запуска после `summary_upto`. Пометка взята у hermes вместе с
  оговоркой «инструменты доступны» — без неё hermes видел, как модель после сжатия перестаёт вызывать инструменты.
- **Проверка** — перед каждым вызовом модели; ошибка «контекст переполнен» от провайдера — одно принудительное сжатие и
  повтор. Хвост — `clamp(2,5% окна, 10–25 тыс.)`, но не больше четверти окна (иначе в малых окнах нечего сжимать);
  хвост не начинается с результата инструмента.
- **Сжатие не тратит ходы запуска:** расход резюме идёт в бюджет токенов и в `llm_calls` (`purpose = compaction`), но не
  в счётчик ходов (`settleAuxiliary`) — найдено ревью.
- **Отличие от проекта:** сообщения собеседника сжатой части остаются дословно в базе и в истории, но в контекст идут
  с ограничением — каждое до 2000 символов, все вместе до десятой части окна, сначала новые, с пометкой, сколько
  ранних не показано. Без предела список рос бы с каждым сжатием и сам запускал сжатие на каждом шаге (найдено ревью).
- **Окно и дешёвая модель** пока из `LLM_CONTEXT_WINDOW` (131072) и `LLM_CHEAP_MODEL` (`openai/gpt-5.6-luna`);
  часть 5 заменит их каталогом и таблицей ролей.
- **Отложено (мелкое):** оценка сразу после сжатия не учитывает описания инструментов (поправляется якорем следующего
  вызова); решение ждать паузу берёт оценку до обрезки; после заглушки дешёвая модель снова получает три попытки;
  нехватка бюджета на резюме считается неудачей; на сервере дешёвая модель вернула подозрительно малое число входных
  токенов (3) — проверить учёт `usage` у этого провайдера.

### Как сделано: роли моделей

Роли моделей, классификация, каталог — [«Модели»](agent-loop.md#модели); проверено на сервере 2026-11-16.

- **Код:** `ModelRef`, `ProviderRouter` (`Infrastructure/Llm`), `ModelRoles`, `ModelRouter`, `RequestClassifier`
  (`App/Agent/Model`), `SetModelRoleTool`, `ModelCatalogModule`, миграция `0006_model_roles`.
- **Провайдеры** (решение владельца): модель — `провайдер:идентификатор`, без префикса — OpenRouter (так хранились
  диалоги до этого). `ProviderRouter` отдаёт запрос клиенту провайдера без префикса; подключён OpenRouter, другой
  провайдер — одна строка в сборке. Каталог хранится и обновляется по провайдерам; пустой ответ каталога старый не
  стирает. В `llm_calls` модель пишется с префиксом.
- **Выбор модели** — при открытии диалога по первому сообщению; меняется, только когда меняется модель его роли
  ([«Модели»](agent-loop.md#модели), решение владельца 2026-11-19). Сложными считаются
  только явные просьбы («спроектируй», «составь план», «проанализируй», «сравни варианты», «по шагам»…) и запросы от
  2000 символов; слова вроде «планшет», «планета», «планирую» сильную модель не включают (найдено ревью). Неясное —
  дешёвая модель не дольше 8 с, иначе основная модель.
- **Кто меняет роли** (решение владельца): агент, владелец и участники с инструментом `set_model_role` (по политике
  инструментов). Закрепить роль (`fix`) может только владелец; закреплённую меняет только он, запись владельца без
  `fix` снимает закрепление. Закрепление и более дорогая (или без цены) модель идут через подтверждение владельца —
  иначе прочитанная страница могла бы переключить все диалоги на дорогую модель (найдено ревью).
- **История ролей**: каждое принятое изменение роли пишется в `model_role_history` (роль, модель,
  причина, кто, когда; миграция 81). `/models` — роли и последние 10 изменений, `/models rollback <номер>` (только
  владелец) возвращает роли модель этой записи — обычной записью роли со всеми её проверками; откат — тоже запись.
- **Окно для сжатия** — из каталога, но не больше `LLM_CONTEXT_WINDOW`: окно в 1 млн токенов позволило бы слать сотни
  тысяч токенов на каждом шаге. Дешёвая модель сжатия — роль `cheap`.
- **Сильная модель дорогая** (`anthropic/claude-opus-5`, $5/$25 за млн): сложный первый запрос оставляет её на весь
  диалог. Замена — `set_model_role`.
- **Отложено (мелкое):** вызов классификатора не пишется в `llm_calls`; загрузки каталога не отменяются при остановке;
  сообщение, пришедшее во время классификации, запускает вторую классификацию (модель от этого не меняется);
  `LLM_MODEL` и `LLM_CHEAP_MODEL` теперь только запасные значения.

### Пакеты и репозитории

Основной репозиторий — `github.com/opencck/mercurius`. Части системы, которые имеют смысл вне Меркурия, выносятся
в отдельные репозитории `github.com/opencck/mercurius-<имя>` и подключаются сабмодулями в `packages/<имя>/`.
Репозиторий пакета называется `mercurius-<имя>`, каталог сабмодуля — коротко, `packages/<имя>/`
(например, `github.com/opencck/mercurius-connectors` → `packages/connectors/`). Во всех репозиториях работа идёт в ветке
`master`.

**Когда выносить.** Компонент выносится, если выполнено всё: он полезен без Меркурия; у него узкий интерфейс,
который можно зафиксировать; он не зависит от кода основного репозитория; у него свои тесты. Иначе он остаётся
в основном репозитории — вынести позже дешевле, чем поддерживать преждевременную границу.

**Как подключается.** Пакет — Composer-библиотека (или отдельный сервис со своим образом). В основном репозитории —
сабмодуль в `packages/<имя>/` и Composer-репозиторий типа `path`, чтобы править пакет и приложение одновременно.
Версии сабмодулей пакетов ведутся в индексе `packages/README.md` по тем же правилам, что у референсов.

- `memory`, `peer`, `mcp-client` выносятся в сабмодули; `command-policy` не выносится.
  Решено окончательно (2026-11-19): пакета `command-policy` не будет — политика команд держится на настройках и
  карточках приложения. Два классификатора названы по назначению: `SshCommandClassifier` (команды на серверах по
  SSH, `src/CommandPolicy`) и `OutwardActionClassifier` (действия наружу из песочницы, `src/App/Agent/Tool/Guard`).
- В корне каждого сабмодуля, который часть системы (пакеты, модули, MCP, скиллы; не референсы), — свой `BRIEF.md`;
  корневой `BRIEF.md` ссылается на каждый и разносится на файлы по подсистемам.

## Соглашения

### Спецификация

**Где что хранится**

- Требование и решение — в разделе своей подсистемы в `brief/`; история доработок и проверки вживую — в
  [`history.md`](history.md); правила работы — в `CLAUDE.md`; спецификация сабмодуля — в его `BRIEF.md`; сведения о
  сервере разработки — в локальном `SERVER.md`, в git их нет.
- Одно знание — в одном месте, в остальных — ссылка. Сквозное решение (затрагивает несколько подсистем) записывается
  в [решениях](decisions.md#решения), а в [указателе](decisions.md#где-записаны-решения) — строка о том, где лежит
  решение подсистемы.
- Принятое решение переносится из [открытых вопросов](decisions.md#открытые-вопросы) в раздел подсистемы с кратким
  обоснованием.
- Проект узла (design) — подраздел файла подсистемы; план реализации — временный файл в `plans/`; код ссылается
  только на подраздел спецификации (`spec:`), не на план.

**Разделы и заголовки**

- Заголовок называет тему: без дат, без номеров этапов работ, без слов «решено» и кодов задач. Когда и кем принято
  решение — в тексте раздела.
- Раздел, на который ссылается код, — не больше 8000 символов вместе с подразделами. Вырос — делится на подразделы по
  темам, и ссылки переводятся на них. Список таких разделов — `php bin/spec-links.php --coarse`.
- Уровень заголовка — на один ниже родителя; заголовок файла не повторяет заголовок его первого раздела.
- Новый файл в `brief/` — строка в оглавлении `BRIEF.md`.

**Ссылки**

- `spec: <файл>#<якорь>` в коде ведёт в самый узкий раздел, где описано то, что делает этот код; путь — от корня
  основного репозитория, в том числе из сабмодулей.
- Заголовок переименовывается или раздел переезжает только вместе со всеми ссылками на него, во всех репозиториях,
  в одном изменении.
- Обратный путь, от раздела к коду, — `php bin/spec-links.php --where <якорь>`; списков файлов кода в спецификации нет:
  они устаревают.
- `php bin/spec-links.php` (часть `composer check`) проверяет каждую `spec:` и каждую ссылку между файлами
  спецификации.
- В комментариях кода нет дат решений, номеров этапов, имён экземпляров разработки и рассказа о ходе работ: что и
  почему делает код, плюс ссылка.

**Прочее**

- Новый скилл или MCP-сервер в проекте — строка в таблицах `CLAUDE.md` с указанием, когда его использовать.
- Новая переменная окружения — в `.env` и в `.env.example`.
- Новый репозиторий (основной или пакет) с первого коммита содержит `README.md` (английский) и `README.ru.md` (русский)
  со ссылками друг на друга и `LICENSE` (MIT); с первого коммита кода — `composer check` (PHPUnit, PHPStan, Psalm) и
  workflow GitHub Actions по правилам [«Качества кода и CI»](requirements.md#качество-кода-и-ci). Все репозитории
  ведутся в `master`.
- Новый пакет — репозиторий `github.com/opencck/mercurius-<имя>`, сабмодуль в `packages/<имя>/`, строка в
  `packages/README.md` и в таблице пакетов.

### База знаний

- Новая статья → `docs/<источник>-<тема>.md` с frontmatter (`title`, `source`, `fetched`), затем ссылка в `CLAUDE.md`.
- Статьи извлекать с сохранением блоков кода, диаграмм и заголовков (связка BeautifulSoup + markdownify по контейнеру
  статьи; trafilatura теряет код и заголовки).
- Новый репозиторий → git-сабмодуль: `git submodule add --depth 1 <url> references/<имя-репо>` и `git config -f
  .gitmodules submodule.references/<имя-репо>.shallow true`, затем строка в индексе `references/README.md` (версия и
  запись в журнале) и ссылка в `CLAUDE.md`.
- Обновление сабмодуля — только вместе с записью в журнале `references/README.md` и проверкой, что нужно поменять в
  проекте (правила — в `CLAUDE.md`).
- После клонирования проекта: `git submodule update --init --depth 1`.
- На каждый материал → конспект `docs/notes/<то же имя>.md`: «Кратко», навигация по источнику (разделы с номерами строк
  в `docs/` или карта каталогов репозитория), ключевые идеи, практика, «под какие вопросы открывать», оценка. Затем
  строка в [карте конспектов](knowledge.md#карта-конспектов).
- Номера строк в конспектах привязаны к файлу в `docs/`: если статью перекачали — пересчитать навигацию в конспекте.
- Если материал не удалось скачать — заглушка с `status: not-downloaded` и ссылкой на оригинал.
- Выводы и решения записываются в этот файл, а не в `CLAUDE.md`.

### Сквозные требования

Действуют в любой задаче: новая возможность, исправление, доработка.

- **Async-first.** Никаких блокирующих вызовов: только `amphp/*` и Revolt. Архитектура — DDD-слои opencck (Domain → App
  → Infrastructure).
- **Промпт просит, код гарантирует.** Лимиты ходов, токенов, времени, числа воркеров и права на действия проверяются
  кодом, а не инструкцией модели ([вывод 6](knowledge.md#ключевые-выводы)).
- **Недоверенные данные.** Всё, что агент прочитал извне (страницы, письма, вывод команд, ответы MCP), — данные, а не
  инструкции. Действия по таким данным проходят ту же политику подтверждений.
- **Секреты.** Токены, пароли и ключи не попадают в промпт, логи и ответы пользователю; хранятся зашифрованными,
  выдаются инструменту в момент вызова.
- **Владелец.** Изменения глобального поведения агента принимает только владелец (сейчас — по `TELEGRAM_ADMIN_ID`).
- **Логи.** Каждый шаг агента оставляет запись, достаточную для диагностики и оптимизации (структурные логи и
  [трассировка](operations.md#трассировка-и-метрики)).
- **Тесты и анализ.** Новая логика покрывается тестами (`AsyncTestCase`); вызовы модели в тестах подменяются записанными
  ответами. В каждом PHP-репозитории `composer check` (PHPUnit, PHPStan `max`, Psalm `errorLevel=1`) проходит без
  подавлений; CI в GitHub Actions — по правилам [Качество кода и CI](requirements.md#качество-кода-и-ci).
- **Проверка на сервере.** Задача не закрывается по локальному запуску — только после проверки на сервере разработки
  (локальный `SERVER.md`).
