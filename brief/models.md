# Модели

## Выбор моделей под задачу

Требование владельца 2026-11-16: агент декомпозирует задачу, оценивает каждую часть по набору критериев от 1 до 10
и, где это выгодно, отдаёт части разным моделям — чтобы тратить меньше на токены и отвечать быстрее.
Ниже — проект устройства (Claude); детали уточняются в фазах 3–5 и по трассам.

### Профиль задачи

Оценки 1–10 по осям требований к модели:

| Ось | Что оценивает |
|-----|---------------|
| Текст | Понимание и написание текста, стиль, языки |
| Рассуждение | Многошаговая логика, планирование |
| Математика | Вычисления, математический анализ, доказательства |
| Академические знания | Глубина предметных знаний (наука, право, медицина и т. п.) |
| Код | Чтение, написание и отладка кода |
| Агентность | Длинные цепочки вызовов инструментов, точность аргументов |
| Изображения | Понимание изображений и документов-сканов |
| Звук | Распознавание и синтез речи, анализ аудио |
| Объём контекста | Сколько материала нужно держать сразу |
| Цена ошибки | Насколько дорого обойдётся неверный результат |
| Срочность | Насколько важна скорость ответа |

Кроме оценок — жёсткие требования: нужные модальности, минимальный контекст, вызов инструментов, структурированный
вывод, ограничения на хранение данных у провайдера.

### Профиль модели

- Строится из каталога OpenRouter: цены входа и выхода, контекст, модальности, поддерживаемые параметры, индексы
  интеллекта, кода и агентности, доля успешных вызовов инструментов, задержка и пропускная способность по провайдерам.
  Каталог обновляется по расписанию, а не берётся из памяти модели.
- Дополняется собственной статистикой из трасс: успех, расход и время по типам задач.
- Агент сам определяет и меняет список используемых моделей, роли моделей и веса «цена — скорость — качество» исходя из
  контекста и статистики трасс, записывая причину изменения (решение владельца 2026-11-16). Владелец может зафиксировать
  значения.

### Списки моделей по категориям

Решение владельца 2026-11-20. Агент вызывает только модель, которую владелец назначил в категорию; модель вне
списков не вызывается никогда. В каждой категории — список; среди его моделей агент выбирает сам.

| Категория | Настройка | При установке |
|-----------|-----------|---------------|
| Текст: дешёвая (вспомогательные вызовы) | `LLM_CHEAP_MODELS` | одна стартовая `LLM_MODEL` |
| Текст: основная | `LLM_MAIN_MODELS` | одна стартовая `LLM_MODEL` |
| Текст: сильная (сложные задачи) | `LLM_STRONG_MODELS` | одна стартовая `LLM_MODEL` |
| Веб-поиск | `WEB_SEARCH_MODELS` | пусто |
| Чтение картинок | `MEDIA_VISION_MODELS` | пусто |
| Генерация картинок | `MEDIA_IMAGE_MODELS` | пусто |
| Чтение звука | `MEDIA_SPEECH_MODELS` | пусто |
| Генерация звука | `MEDIA_AUDIO_GEN_MODELS` | пусто (инструмента пока нет) |
| Чтение видео | `MEDIA_VIDEO_MODELS` | пусто |
| Генерация видео | `MEDIA_VIDEO_GEN_MODELS` | пусто (инструмента пока нет) |
| Сон памяти | `MEMORY_SLEEP_MODELS` | пусто: сна нет ([консолидация](memory.md#консолидация-dreaming)); читается при каждом проходе |

- **Зашитых моделей нет.** Стартовая таблица ролей, модель поиска по умолчанию и дешёвая модель по умолчанию убраны:
  до решения поиск шёл через `openai/gpt-5.6-luna`, которую владелец не называл, а выбор по профилю задачи брал любую
  модель каталога. Раздел [Начальная таблица ролей моделей](#начальная-таблица-ролей-моделей) остаётся справкой о том,
  что подбиралось раньше.
- **Пустая категория — возможности нет:** инструмент не предлагается (`web_search`, `image_generate`), вид вложений
  не разбирается. Агент говорит владельцу, какую настройку заполнить, и не подменяет модель другой.
- **Кто назначает.** Списки — настройки владельца. Решение владельца 2026-11-23: менять их можно и словами — агент
  делает это инструментом `model_list` (`list`; `add`, `remove`, `set` для любой категории) только по просьбе
  владельца; другой участник и прочитанный текст списки не расширяют (класс — необратимое). `set_model_role` по
  просьбе владельца сам добавляет названную модель в список роли и ставит её; от другого участника модель вне списка
  по-прежнему отклоняется. Модель текстовой категории проверяется как для роли: ключ провайдера, каталог,
  инструменты (кроме дешёвой); в текстовом списке остаётся хотя бы одна модель, в любом — не больше 20. Владелец
  может и сам — `/set <настройка> <модели через запятую>`.
- **Текстовые списки действуют сразу** (2026-11-23): `LLM_CHEAP_MODELS`, `LLM_MAIN_MODELS`, `LLM_STRONG_MODELS` —
  среди настроек, читаемых при каждом использовании; списки перечитываются не чаще раза в 5 секунд и сразу после
  правки. Веб-поиск и медиа сначала оставались «после перезапуска» — см. следующий пункт. Причина — разбор
  2026-11-23: на двух экземплярах агент на просьбу владельца отвечал «добавьте сами командой и перезапустите» —
  так ему говорили текст отказа `set_model_role` и тема `self_info` `models`; на третьем после `/set` без
  перезапуска ничего не менялось.
- Агент выбирает внутри списка: выбор по профилю задачи, эскалация на сильную и запасная модель при сбое — только
  среди текстовых списков. Сжатие контекста,
  классификация запроса и напоминания берут модель дешёвой роли.
- **Списки поиска и медиа тоже действуют сразу** (решение владельца 2026-11-24): `WEB_SEARCH_MODELS`,
  `MEDIA_VISION_MODELS`, `MEDIA_IMAGE_MODELS`, `MEDIA_SPEECH_MODELS`, `MEDIA_VIDEO_MODELS` читаются при каждом
  использовании (тем же чтением раз в 5 секунд, что и текстовые). Инструмент категории (`web_search`,
  `image_generate`) зарегистрирован всегда, а предлагается, пока в категории есть модель (интерфейс `Available`,
  спрашивается при каждом запросе). Поиск пересобирается, когда его список меняется. Имя, которое категория принять не
  может, при чтении пропускается — остальные работают. Причина: владелец назначил модель картинок словами, а агент
  дважды ответил, что рисовать не может, пока приложение не перезапустили.
- **Модель роли** — выбранная агентом, пока она есть в списке; иначе первая модель списка. Роль `media` упразднена:
  зрение, звук и видео — свои категории.
- **Отчёт о ролях называет модель, которая работает** (2026-11-24): `/models` и ответ `set_model_role` показывают
  действующую модель роли, а не запись таблицы. Если записанной модели в списке роли уже нет, в отчёте — первая модель
  списка с пометкой, какой выбор выбыл. Причина: после замены списка `cheap` отчёт называл модель из начальной
  таблицы, которую агент не вызывал, и это выглядело как модель, взявшаяся ниоткуда.
- **Отказ «модели нет в каталоге» называет похожие идентификаторы** этого провайдера (до пяти, ближайший первым):
  владелец говорит «fable 5.2», а в каталоге подписки она записана `claude-fable-5-2` — без подсказки агент
  перебирал написания и сдавался.
- **Модель без провайдера — OpenRouter, и агент об этом знает** (2026-11-24): тема `models` называет провайдеров с
  доступом и модели каждой подписки. Когда в текстовый список добавляется платная модель, а у подключённой подписки
  есть модель того же семейства (совпали два слова имени, например `claude` и `sonnet`), ответ инструмента называет
  её и просит заменить или уточнить у владельца. Причина: на «добавь claude sonnet» при подключённой подписке агент
  добавил модель OpenRouter.
- **Поиск — только модель провайдера с веб-поиском по ключу** (2026-11-26; с 2026-11-27 не только OpenRouter —
  [Модели поиска](#модели-поиска)). Модель подписки (`claude:`, `chatgpt:`, `antigravity:`) или Vertex он не вызовет. Раньше такая модель молча сохранялась, ответ говорил
  «действует сразу», а поиска не оставалось совсем (на D после перевода ролей на подписку Claude). Теперь `/set
  WEB_SEARCH_MODELS` и `model_list` для `search` отказывают и называют, что подходит. Уже сохранённый неподходящий
  список при старте не сбрасывает остальные настройки — поиск выключен, в журнале `Search providers without settings
  are skipped`. Распознавание картинок модель подписки принимает (проверено на D: `media-vision` через `claude:`).
- Судья набора проверочных задач (`EVAL_JUDGE_MODEL`) задаётся владельцем отдельно и значения по умолчанию не имеет.
- Агент узнаёт категории и их состав темой `self_info` `models`.
- **Открытая беседа уходит с модели, которой больше нет в списках** (2026-11-27). Беседа держит модель, выбранную
  при открытии; смену роли к ней доносит `RoleConversations`, а смену списка не доносило ничто. На B владелец заменил
  три текстовых списка моделями подписки, бот ответил «действует сразу», но ещё двадцать минут отвечал прежней
  моделью, которой не было ни в одном списке, — и на вопрос «какой моделью отвечаешь» назвал новую. Теперь в начале
  запуска модель беседы сверяется со списками: если её нет ни в одном текстовом, запуск выбирается заново, как при
  открытии, и беседа переводится. Работает одинаково для `model_list` и `/set`.
- **Беседа на модели подписки не уходит на модель по умолчанию** (2026-11-27). Планировщик запусков сверял провайдера
  модели беседы со списком провайдеров по ключам, где подписок нет, и каждую беседу на `antigravity:` (как и на
  `claude:`, `chatgpt:`) переводил на `LLM_MODEL` с записью `Conversation model has no provider key`. На B роли стояли на
  подписке, а отвечала модель по умолчанию — к подписке беседы не обращались вовсе. Теперь планировщик берёт
  провайдеров ролей, где подписки есть.
- **Ответ на смену текстового списка называет модель роли** (2026-11-27). Порядок списка модель роли не выбирает: роль
  держит свою модель, пока та в списке, и берёт первую из списка, только когда её модели там нет. На B владелец
  попросил оставить подписку основной, а прежние модели добавить запасными; агент поставил модели подписки первыми и
  сказал «они основные», а роли остались на прежних моделях. Теперь ответ `model_list` на текстовую категорию говорит,
  какой моделью роль отвечает сейчас, и что сменить её — `set_model_role`.

#### Каталог провайдеров для агента

Списки категорий говорят, что выбрано, а не из чего выбирать. Повод (2026-11-27): на B владелец спросил «какие модели
каких провайдеров тебе доступны» и «мне нужен список моделей, из которых выбрать» — агент дважды вызвал `model_list
list` и ответил текущими категориями («провайдер один — OpenRouter»), хотя ключей и подписок было четыре; на вопрос
о модели подписки для чтения картинок ответил «может не сработать», потому что не видел, что модели читают.

У `model_list` два действия чтения (без карточки, как `list`):

- `providers` — провайдеры, у которых сейчас есть ключ или модуль: по ключу или подписка, сколько моделей в каталоге,
  для подписки — команда входа и квоты; провайдер, снятый с выбора (нет входа, окно плана исчерпано, провайдер просит
  владельца аккаунта), так и назван. Затем — провайдеры, которые не подключены, со ссылкой на тему `models`.
- `catalog` — модели одного провайдера полными именами `провайдер:модель`, какими их принимает список категории:
  окно, что модель читает, цена за миллион токенов, вызывает ли инструменты. Отбор — слова из имени (`query`, все
  слова должны встретиться в идентификаторе или названии) и то, что модель должна читать (`input`: `image`, `audio`,
  `video`, `file`). В ответе не больше 40 строк (до 100 по `limit`); если подошло больше — сказано сколько и что
  отбор надо сузить. Пустой отбор говорит, что модели этого провайдера такого не умеют.

Сведения берутся из каталога в базе (он обновляется своим порядком), запросов к провайдеру действие не делает. Что
модель выдаёт (картинка, звук), каталог не хранит — отбора по этому нет. Чужому провайдеру (без ключа) — отказ со
списком подключённых.

#### Модели поиска

Веб-поиск моделью — модель провайдера, у которого есть свой веб-поиск по ключу (решение владельца 2026-11-27: поиск не
только через OpenRouter). Повод: на B владелец перевёл текстовые категории на подписку и попросил перевести поиск —
поиск принимал только OpenRouter.

- `openrouter:автор/модель` (или просто `автор/модель`) — веб-плагин OpenRouter, как раньше.
- `gemini:<модель>` — модель Gemini по ключу Gemini API (`GEMINI_API_KEY` провайдера) с инструментом Google Search
  (`generateContent`); ссылки ответа — переадресации Google, заголовок — имя сайта.
- `openai:<модель>` — модель OpenAI по ключу (`OPENAI_API_KEY`) с инструментом `web_search` Responses API
  (`store: false`).

Список `WEB_SEARCH_MODELS` идёт по порядку: модели с ключом своего провайдера, по первой на провайдера, становятся
запасным порядком поиска; у инструмента `web_search` каждый провайдер выбирается по имени (`openrouter`, `gemini`,
`openai`). В `SEARCH_PROVIDERS` это место называется `model` (прежнее имя `openrouter` работает). `model_list` для
`search` отказывает модели провайдера без ключа и называет подключённых; `/set` проверяет только вид имени.

Чего нет и почему:

- **Подписки** (`chatgpt:`, `claude:`, `antigravity:`) — у них веб-поиск свой, внутри их клиента: у Codex — инструмент
  `web_search` того же Responses API (hermes подставляет его в транспорте Codex), у Claude Code и `agy` — встроенные
  инструменты, которые наши модули запрещают сторожем. Поиск подпиской — отдельная задача.
- **Vertex** — тот же Google Search, но вход сервисным аккаунтом; не сделан, пока Vertex не проверен вживую.
- **Anthropic по ключу** — серверный инструмент веб-поиска есть; не сделан, ключа на проверочных экземплярах нет.

Проверка вживую 2026-11-27 на B: ключ Gemini API из секрета MCP на `generateContent` без поиска отвечает моделями
lite, а большие модели — 503 «high demand»; с `google_search` тот же ключ получает 429 «exceeded your current quota» на
всех моделях — одинаково напрямую и через VLESS, то есть это квота ключа, а не наш маршрут. Ответ OpenAI вживую не
проверен (ключ установки для проверки не брал).

### Категории моделей

Решение владельца (2026-11-18): у моделей есть категории — текст, зрение (картинки), видео, звук (речь), генерация
картинок; в каждой несколько моделей или ни одной. Категории надстраиваются над тем, что уже есть, а не заменяют его
(проект — Claude, 2026-11-19):

| Категория | Откуда модели | Кто выбирает среди нескольких |
|-----------|---------------|-------------------------------|
| Текст | роли `cheap`, `main`, `strong` и выбор по профилю задачи | маршрутизатор и [выбор](#выбор) |
| Зрение | `MEDIA_VISION_MODELS` | порядок списка и принципы `MEDIA_VISION_RULES` и участника |
| Видео | `MEDIA_VIDEO_MODELS` (без неё — кадры зрением и звук речью) | так же, `MEDIA_VIDEO_RULES` |
| Звук | `MEDIA_SPEECH_MODELS` | так же, `MEDIA_SPEECH_RULES` |
| Генерация картинок | `MEDIA_IMAGE_MODELS` | порядок списка и принципы `MEDIA_IMAGE_RULES` |

- **Пустая категория — возможности нет:** по умолчанию все медиакатегории пусты, агент не смотрит и не рисует,
  пока владелец не назовёт модель.
- **Любой провайдер** с профилем: `MEDIA_*_MODELS` принимают `anthropic:`, `bedrock:`, `codex:` наравне с
  `openrouter:` и `openai:`. Модель такого провайдера получает картинку через клиент текстовых моделей этого
  провайдера (те же повторы, учёт и VLESS).
- **Генерация картинок** — модели изображений OpenRouter (`POST /api/v1/images`, картинка приходит base64 в ответе).
  Инструмент `image_generate` (запрос, модель из списка, соотношение сторон, имя) сохраняет картинку файлом в песочнице
  участника (`images/<имя>.png`); отправляет её агент как любой файл — `send_file`. Модели — по порядку, при сбое —
  следующая; модель вне списка не вызывается. Инструмент предлагается, только пока в списке есть модель; расход —
  строка `media-image` в `llm_calls` с ценой от OpenRouter. Другие API картинок (OpenAI `images/generations`, свои
  адреса) не подключены: в списке картинок принимаются только модели OpenRouter.
- Как у hermes: «именованная задача — своя модель» (`auxiliary.<task>`), у нас задача — категория, а моделей в ней
  может быть несколько.
- Категории моделей (текст, звук, видео, изображения, генерация изображений) надстраиваются над ролями и настройками
  `MEDIA_*_MODELS`; из нескольких моделей категории агент выбирает сам. Судьёй может быть модель любого провайдера.

### Выбор

1. Жёсткие требования отсекают неподходящие модели.
2. Из оставшихся выбирается самая дешёвая модель, чьи способности по каждой оси не ниже требуемых с запасом, который
   растёт с ценой ошибки.
3. При равенстве решает срочность: при высокой — задержка и скорость генерации, при низкой — цена.
4. Если результат не прошёл проверку или модель отказала — эскалация на более сильную модель (каскад), с записью в трассу.

- Замер выбора моделей считается предварительным.

### Декомпозиция и экономия

- **Решение владельца 2026-11-16:** сильная модель остаётся в таблице ролей; в работе агента бывают разные задачи, и агент
  сам делит задачу так, чтобы её части решали разные модели ради экономии и качества. Модель диалога, выбранная при
  его открытии ([Как сделано: роли моделей](architecture.md#как-сделано-роли-моделей)), — это модель оркестратора; части
  задачи уходят воркерам
  с моделью, подобранной под каждую часть.
- Оркестратор — модель диалога (по классу запроса, обычно роль `main`; по устройству это supervisor: перепланирует
  каждый ход и читает каждый отчёт) — планирует, разбивает задачу и оценивает подзадачи; воркеры на подобранных моделях
  исполняют. Так в замере cookbooks 84–98% входных токенов шли по ставке дешёвой модели ([вывод
  11](knowledge.md#ключевые-выводы)).
- Оценивание само стоит денег: короткие и типовые запросы идут на модель по умолчанию без профиля; профиль считает
  дешёвая быстрая модель или оркестратор в рамках планирования; профили типовых задач кешируются.
- У дробления есть оптимум: каждый воркер несёт накладные расходы, а сжатие знаний при передаче теряет точность. Решение
  «делить или нет» учитывает это ([вывод 5 из cookbooks](../docs/notes/claude-cookbooks.md)).
- Модель основного диалога не меняется посреди сессии: это ломает кеш промпта ([вывод
  30](knowledge.md#ключевые-выводы)). Модели выбираются на уровне подзадач и воркеров, а для основного диалога — только
  на границе сессии.
- Вспомогательные вызовы (заголовки, сжатие контекста, извлечение фактов, проверка безопасности) с самого начала идут на
  дешёвую модель — как вспомогательный клиент в hermes.

### Этапы

- **Частичный выбор** (решение владельца 2026-11-16): таблица ролей моделей от владельца (дешёвая, основная,
  сильная, с изображениями и звуком); грубый класс запроса без оценок по осям; вспомогательные вызовы на дешёвой модели;
  журнал решений.
- **Полный выбор:** профиль задачи из оценок 1–10, профили моделей из каталога и трасс, выбор по подзадачам и
  воркерам, каскад при неудаче.
- **Обучение выбора** по накопленным исходам — следующий шаг.

### Обучение выбора

Каждое решение — профиль задачи, выбранная модель, расход, время, итог — пишется в слой опыта. Консолидация и разбор
трасс уточняют таблицу выбора; агент применяет поправки сам и пишет причину в журнал ([границы
самоулучшения](self-improvement.md#границы)).

## Провайдеры и подписки

Какие поставщики моделей есть у агента, как подключаются подписки и как устроен каждый.

### Провайдеры моделей: OpenRouter и OpenAI

Проект — Claude, 2026-11-16, по [решению владельца](decisions.md#продукт-и-архитектура) о втором провайдере. Провайдер
модели —
приставка ссылки: `openrouter:author/slug` (голый id — тоже OpenRouter) и `openai:gpt-…`.

- **Ключи:** `OPENROUTER_API_KEY` и `OPENAI_API_KEY` — оба необязательны, но хотя бы один задан, иначе приложение не
  стартует с понятной ошибкой. Провайдер без ключа не настроен: его модели нельзя назначить на роль, выбрать по
  профилю или задать в `LLM_MODEL`.
- **Сеть:** оба клиента идут через один HTTP-клиент — через VLESS, если задан `VLESS_URI`, иначе напрямую.
- **Клиент OpenAI** — в пакете `llm`, рядом с OpenRouter: тот же протокол Chat Completions, общие транспорт, разбор
  потока и классификация ошибок. Отличия в теле запроса: `max_completion_tokens` вместо `max_tokens`, `reasoning_effort`
  строкой вместо объекта `reasoning`; с инструментами — `reasoning_effort: none` (OpenAI в Chat Completions не
  принимает инструменты при включённом рассуждении; модели, которые рассуждают всегда, идут в каталог без
  инструментов — для них провайдер `codex`, см. ниже), без `temperature`, когда задано усилие рассуждения (модели
  рассуждения его не
  принимают — как у hermes, `utils.py` `model_forces_max_completion_tokens`); без заголовков атрибуции OpenRouter.
  Стоимость OpenAI не сообщает — трасса считает её по ценам каталога (пометка «оценка»).
- **Каталог OpenAI:** список моделей ключа (`GET /v1/models`) обогащается записями `openai/<id>` из открытого каталога
  OpenRouter (цены, окно, модальности, инструменты, индексы). Модели без такой записи (эмбеддинги, речь и т. п.) в
  каталог не попадают: без цены и признаков их не выбрать.
- **Роли по умолчанию** зависят от провайдеров: есть OpenRouter — прежняя таблица; только OpenAI — `cheap` и `media`
  `gpt-6-luna`, `main` `gpt-6.1-terra`, `strong` `gpt-6-sol` (`gpt-6.1-sol` всегда рассуждает и в Chat Completions не
  работает с инструментами — проверено ключом владельца 2026-11-16). Модель по умолчанию (`LLM_MODEL`,
  `LLM_CHEAP_MODEL`) — так же.
  Только Anthropic или только Bedrock — роли Claude этого провайдера: `cheap` и `media` — Haiku 5.5, `main` — Sonnet
  5.5, `strong` — Opus 5.5 (2026-11-19; до этого такие экземпляры получали роли OpenAI, которые без ключа OpenAI не
  вызвать).
- **Выбор по профилю** ищет во всех настроенных провайдерах: одна и та же модель напрямую и через OpenRouter — два
  кандидата, решает цена.
- **Третий провайдер — Anthropic** (2026-11-19): `anthropic:claude-…`, ключ `ANTHROPIC_API_KEY`. Клиент
  `Anthropic\AnthropicClient` в пакете `llm` говорит на Messages API (`POST /v1/messages`) поверх HTTP-клиента AMPHP:
  официальный SDK блокирует цикл событий, поэтому не берём его. Заголовки — `x-api-key` и `anthropic-version:
  2026-10-21`. Эта версия API не принимает `temperature`, поэтому температура не отправляется, а усилие рассуждения
  уходит в `output_config.effort`. Системные сообщения передаются блоками верхнего уровня. Реплики одной роли
  сливаются, потому что роли должны чередоваться, а результаты инструментов идут в реплике пользователя. Картинки
  уходят блоками base64; видео API не принимает. Рассуждение возвращается текстом и с историей обратно не
  отправляется: убрать все блоки рассуждения — допустимая правка истории, поэтому подписи не храним. Кеш устроен как у
  Claude через OpenRouter: метка на системном промпте и `cache_control` верхнего уровня. Перегрузка (HTTP 529) — это
  повторяемая ошибка сервера. Каталог: список ключа (`GET /v1/models`) описывается записями открытого каталога
  OpenRouter, где версии пишутся через точку (`claude-opus-5-5` — это `anthropic/claude-opus-5.5`). Если задан только
  этот ключ, модели по умолчанию — `anthropic:claude-sonnet-5-5` и `anthropic:claude-haiku-5-5`. Адаптер проверен на
  подставных ответах (решение владельца); живая проверка ждёт ключа.
- **Четвёртый провайдер — Claude в Amazon Bedrock** (2026-11-19): `bedrock:anthropic.claude-…`, ключ
  `AWS_BEARER_TOKEN_BEDROCK` (так его называют AWS и hermes) и регион `BEDROCK_REGION` (по умолчанию `us-east-1`).
  Bedrock отдаёт Claude по тому же Messages API на адресе `https://bedrock-mantle.{region}.api.aws/anthropic`, поэтому
  клиент тот же — `AnthropicClient::bedrock()`. Вход — только ключом Bedrock API (токен на предъявителя): подпись
  SigV4 требует AWS SDK и пока не нужна. Регион проверяется по форме (`us-east-1`), прежде чем стать именем хоста.
  Своего списка моделей у этого адреса нет, поэтому каталог — модели Claude из каталога OpenRouter в написании Bedrock
  (`anthropic/claude-opus-5.5` → `anthropic.claude-opus-5-5`). Доступ к каждой модели решает Bedrock: недоступная
  падает при вызове, и дальше работает запасная модель. Кеш — как у прямого Anthropic. Если задан только этот ключ,
  модели по умолчанию — `bedrock:anthropic.claude-sonnet-5-5` и `bedrock:anthropic.claude-haiku-5-5`. Проверено на
  подставных ответах.
- **Профиль провайдера** (2026-11-19, решение владельца «оставить до третьего провайдера» — третий наступил):
  провайдер — это данные, `ProviderProfile`: имя (приставка модели), API (`chat_completions`, `responses`,
  `messages`), переменная ключа, способ кеша (`marks` — метки Claude, `key` — `prompt_cache_key` OpenAI, `provider` —
  кеширует сам), модели по умолчанию и начальная таблица ролей. Порядок профилей — порядок предпочтения умолчаний:
  OpenRouter, OpenAI, Codex, Anthropic, Bedrock. Настройки, роли, маршрутизатор (метки кеша), цикл агента (ключ кеша)
  читают профиль; клиенты и каталоги строит `ProviderClients` по профилям с ключом. Новый провайдер — профиль и клиент
  в фабрике. Как у hermes (`providers/base.py`, `ProviderProfile`), без обработчиков входа и флагов зрения — они у
  клиентов и в каталоге.
- **Провайдер `codex` — OpenAI Responses API** (2026-11-19): `codex:gpt-…`, тот же ключ `OPENAI_API_KEY`, поэтому
  есть ключ OpenAI — есть оба провайдера. Через Responses API (`POST /v1/responses`) идут модели codex и `-pro`,
  которых нет в Chat Completions, и модели, которые рассуждают всегда: здесь они принимают инструменты. Каталог —
  список ключа с этими семействами и с инструментами у таких моделей. Запрос: `store: false` (на стороне OpenAI ничего
  не хранится, беседа идёт целиком), системные сообщения — `instructions`, результаты инструментов —
  `function_call_output`, кеш — тот же `prompt_cache_key` беседы. Зашифрованное рассуждение между ходами не
  передаётся: в истории его нет. Вход по подписке ChatGPT (`chatgpt.com/backend-api/codex`, как у hermes) не сделан —
  это вопрос владельцу. Проверено на подставных ответах.
- Провайдеры Anthropic, Bedrock, Codex и jev-ai.pro добавляются сейчас; до появления ключей — на подставных ответах.

### Провайдеры Gemini и Vertex

Решение владельца 2026-11-26: модели Google по ключу — встроенные провайдеры приложения, как OpenAI и Anthropic, без
отдельного сервиса. Это пути, которые Google сам называет для сторонних агентов; риска для аккаунта нет.

| Провайдер | Что это | Вход | Модели |
|---|---|---|---|
| `gemini:` | Gemini API по ключу Google AI Studio | `GEMINI_API_KEY` | `gemini:gemini-3.8-flash` |
| `vertex:` | Gemini в Google Cloud (Gemini Enterprise Agent Platform, бывший Vertex AI) | `VERTEX_CREDENTIALS` — JSON сервисного аккаунта | `vertex:google/gemini-3.8-flash` |

- **Способ.** Оба ходят на адрес Google, совместимый с Chat Completions, клиентами пакета `llm`
  ([Gemini и Vertex](../packages/llm/BRIEF.md#gemini-и-vertex)): там адреса, обмен токена сервисного аккаунта,
  подписи мышления, уровни мышления по семействам, очистка схем, ошибки квоты. Родного клиента (`generateContent`,
  Interactions) нет — см. [Что не сделано](#что-не-сделано-для-провайдеров-google).
- **Настройки.** `GEMINI_API_KEY` и `VERTEX_CREDENTIALS` — секретные настройки по общему правилу
  ([Настройки агента](operations.md#настройки-агента)): значение по умолчанию — в `.env`, значение, заданное в чате
  (`/set`), хранится в хранилище секретов, важнее и действует после перезапуска. JSON сервисного аккаунта кладётся
  одной строкой. `VERTEX_PROJECT_ID` — проект; пусто — проект из JSON. `VERTEX_REGION` — регион; пусто — `global`.
  Проект и регион проверяются по форме: они становятся частью адреса. JSON проверяется при старте: тип
  `service_account`, почта, читаемый закрытый ключ, проект; текст отказа ключ не повторяет.
- **Хватит одного ключа.** Правило «хотя бы один ключ провайдера» выводится из профилей: экземпляр только с ключом
  Gemini или только с сервисным аккаунтом Vertex стартует. Роли по умолчанию для такого экземпляра: дешёвая и
  медиа — `gemini-3.8-flash`, основная — `gemini-4-hydrogen`, сильная — `gemini-4-carbon` (каталог OpenRouter,
  2026-11-26).
- **Каталог.** У `gemini:` — список моделей ключа, описанный каталогом OpenRouter; у `vertex:` списка нет, поэтому
  это текстовые модели Gemini из каталога OpenRouter. Модели, которые отвечают не текстом (картинки, речь, музыка,
  видео), в каталог не входят.
- **Цена** — оценка по ценам каталога OpenRouter: API стоимость не сообщает. Повышенная цена Google для запросов
  длиннее 200 тысяч токенов не учитывается — оценка таких запросов занижена.
- **Кеш промпта** — неявный, на стороне Google; меток кеша приложение не ставит.
- **Подписи мышления в истории.** Подпись вызова инструмента хранится вместе с вызовом в `messages.tool_calls`
  (ключ `signature`) и возвращается модели со следующим запросом; без неё Gemini 3 и новее отвечает 400. Другим
  провайдерам подпись не уходит. Вызов, сделанный другим провайдером, получает заглушку.
- **Сеть.** Общий HTTP-клиент моделей: через VLESS, если задан `VLESS_URI`, иначе напрямую. Обмен токена Vertex
  идёт тем же маршрутом.
- **Медиа.** Модели `gemini:` и `vertex:` можно внести в списки чтения картинок и видео. Звуковой части у запроса
  нет — речь идёт отдельным путём.
- **`Doctor`** называет ключ Gemini и сервисный аккаунт Vertex, JSON на месте ключа и сервисный аккаунт, который не
  читается.
- **Знания агента о себе** — тема `self_info` `models`: как названы провайдеры, какими настройками включаются, что
  значат 403 и 429 бесплатного уровня. В системный промпт ничего не добавлено.
- **MCP `gemini-api`** — инструменты медиа на том же ключе — отдельная часть: ключ ему задаётся секретом агента, а
  не настройкой приложения ([MCP gemini-api](skills-mcp.md#mcp-gemini-api)).

Состояние: сделано и проверено на подставных ответах по документации Google и коду hermes — ключа Gemini API и доступа
к Vertex у владельца пока нет. Первая проверка ключом может потребовать правок; что проверить — в
[«Ждёт владельца»](history.md#ждёт-владельца).

#### Что не сделано для провайдеров Google

- **Родной клиент** (`generateContent`, Interactions). Нужен, если проверка ключом покажет, что совместимый адрес
  не возвращает подписи мышления, не принимает видео или сообщает блокировку безопасности не тем полем. Образец —
  hermes `agent/gemini_native_adapter.py` и `plugins/model-providers/gemini/interactions.py`. Длинный вывод
  (`agent/gemini_long_decode.py`) без родного клиента не берём.
- **Сводки мыслей** не запрашиваются: как совместимый адрес их отдаёт, не проверено.
- **Звук во входе** — вместе со звуковой частью запроса, которой у приложения нет.
- **Учётные данные по умолчанию (ADC) и ключи Vertex express** — вход Vertex только сервисным аккаунтом.

### Codex по подписке ChatGPT

Модели подписки ChatGPT владельца — провайдер `chatgpt:` (`chatgpt:gpt-5.5` и т. п.; `codex:` — это ключ OpenAI API через
Responses). Вход — `/codex login` в личном чате владельца: агент получает код устройства, владелец открывает
`https://auth.openai.com/codex/device` и вводит код (пароль агенту не нужен и не виден); агент ждёт до 15 минут и
кладёт токены в хранилище секретов (`chatgpt-codex-oauth`), обновляет токен доступа за две минуты до конца.
`/codex` — подключена ли, `/codex logout` — убрать токены. Запросы — Responses API на `chatgpt.com/backend-api/codex`
(`CodexClient`) с заголовками аккаунта из токена, только потоком, без `max_output_tokens` и `temperature`; список
моделей — каталог Codex аккаунта (`CodexCatalog`), цена за токен 0 (платит подписка). Пока владелец не вошёл, каталог
подписки не запрашивается: это не сбой, поэтому нет ни предупреждения, ни повтора через 10 минут, как у провайдера,
чей каталог не загрузился. После входа каталог загружается сразу, и модели `chatgpt:` можно выбрать без ожидания.
Без хранилища секретов провайдер
не предлагается. Адрес неофициальный (как у hermes); работает, пока OpenAI его не закроет.

### Claude по подписке

Решения владельца 2026-11-23. Модели Claude по подписке владельца (Pro, Max) — провайдер `claude:`; подписка такое
использование разрешает (слово владельца). Образец — плагин Hermes `claude-subscription-directsdk`
([конспект](../docs/notes/hermes-claude-subscription-directsdk.md)). Состояние: требования записаны, модуль в
разработке.

- **Способ:** на каждый вызов модели запускается неизменённый официальный Claude Code как одноразовый клиент; цикл
  агента, инструменты, подтверждения и сжатие остаются у Меркурия. Claude Code живёт в отдельном необязательном
  сервисе — модуле [`mercurius-claude-code`](skills-mcp.md#модули-сервисы-mcp-и-скиллы) (`services/claude-code/`,
  профиль compose `claude-code`).
- **Сервис отвечает приложению тем же Messages API, что и Anthropic:** в приложении это тот же `AnthropicClient` с
  адресом сервиса (`CLAUDE_CODE_URL`) и токеном модуля (`CLAUDE_CODE_TOKEN`). Внутри сервиса между Claude Code и
  `api.anthropic.com` стоит шлюз допуска: наружу уходит только первый запрос к модели — один вызов приложения даёт
  ровно один запрос к API.
- **Чей вход:** только подписка владельца, один вход на экземпляр.
- **Без профиля ничего не меняется:** адрес и токен модуля пусты — провайдер `claude:` не предлагается, его моделей
  нет в каталоге, команда `/claude` говорит, что модуль не включён и как включить. Профиль включается по решению
  владельца на каждом экземпляре отдельно.
- **Модели и роли:** каталог — модели, которые дал аккаунт, описанные каталогом OpenRouter (окно, модальности);
  ролей и моделей по умолчанию нет — `claude:`-модель работает, только когда владелец внёс её в
  [список категории](#списки-моделей-по-категориям).
- **Цена:** 0 за токен в выборе модели, как у `chatgpt:`; в трассе — оценка «по прайсу» с пометкой, что это не счёт.
- **Одновременно** — не больше `CLAUDE_CODE_MAX_CONCURRENT` процессов Claude Code (по умолчанию 4, около 250 МБ
  каждый); остальные вызовы ждут по порядку прихода.
- **Рассуждение в истории:** подписанные блоки рассуждения не хранятся и в историю не возвращаются; вернуться к
  этому после замера — [открытый вопрос](decisions.md#нужно-проверить-или-доделать).

#### Вход в подписку Claude

Два способа (решение владельца 2026-11-23).

- **Основной — `/claude login`** в личном чате владельца: агент присылает ссылку, владелец открывает её и отвечает
  кодом командой `/claude code <код>` (код можно и следующей строкой); это сообщение удаляется из чата и в историю
  беседы и трассы не попадает — и на экземпляре без модуля. Вход ведёт сам Claude Code в сервисе и хранит его
  в своём каталоге (`storage/claude-code/`); приложение файлы входа не читает и не обновляет. Ожидание кода — до 15
  минут. `/claude` — каким входом идёт работа, план и лимиты; `/claude logout` — убрать вход. Только владелец и
  только личный чат.
- **Второй — токен `claude setup-token`:** настройка `CLAUDE_CODE_OAUTH_TOKEN` в `.env` или в чате (секретная:
  значение лежит в хранилище секретов, заданное в чате важнее `.env`). Приложение передаёт токен сервису с каждым
  запросом, сервис его не хранит. Заданный токен важнее входа через `/claude login` — так выбирает сам Claude Code.
  Токен из чата начинает действовать после перезапуска (`/set` секретной настройки).
- Вход по ключу API и облачный вход (Bedrock, Vertex) сервис подпиской не считает: ключи из окружения процесса Claude
  Code убираются, чтобы подписка молча не стала оплатой по ключу.

#### Сеть модуля Claude

Решение владельца 2026-11-23: один маршрут на оба плеча. Порядок выбора: `VLESS_URI` → `CLAUDE_CODE_PROXY`
(`http://…`, `socks5h://…`, как у `TELEGRAM_PROXY`; пуст — [`DEFAULT_PROXY`](agent-loop.md#прокси-по-умолчанию)) → напрямую.

- Шлюз допуска открывает соединение с `api.anthropic.com` через маршрут; TLS кончается у Anthropic, токен подписки до
  прокси не доходит.
- Собственные обращения Claude Code (вход, обновление токена, лимиты) идут через маленький CONNECT-прокси сервиса на
  loopback, который соединяет через тот же маршрут и только с хостами Anthropic. При прямом маршруте его нет.
- Неверное значение маршрута — сервис не стартует; молчаливого прямого выхода нет.

#### Лимиты подписки и переход на модель категории

Решения владельца 2026-11-23.

- **Лимит кончился** — сервис отвечает 429 со временем открытия окна. Приложение снимает провайдера `claude:` с
  выбора до этого времени и берёт другую модель **только из списка той же категории**; модель вне списка не
  вызывается никогда. Нет другой модели в списке — запуск завершается ошибкой лимита, владельцу уходит одно
  сообщение на окно со временем сброса.
- **Доплата сверх плана** — настройка `CLAUDE_CODE_EXTRA_USAGE`: `stop` (по умолчанию) — при исчерпанном окне запрос
  в подписку не идёт; `notify` — идёт, владельцу одно сообщение на окно, что началась доплата; `allow` — идёт молча.
  Порог `CLAUDE_CODE_EXTRA_USAGE_RESERVE_PERCENT` останавливает раньше первого платного запроса. Не удалось узнать
  состояние лимита при `stop` — отказ. Режима «спросить» нет: его роль играет переход на модель категории.
- **Нужен вход** (401 от сервиса) — одно сообщение владельцу, провайдер снят с выбора на 10 минут (потом проверяется
  снова) или до входа через `/claude code`.

Как сделано в приложении (2026-11-23):

- Провайдер `claude:` есть, пока задан `CLAUDE_CODE_TOKEN`; вызовы идут клиентом Messages API пакета `llm` на адрес
  модуля, каталог — `/v1/models` модуля, описанный каталогом OpenRouter, с ценой 0 (Р8). Каталог запрашивается только
  после входа. Ролей по умолчанию нет (У7): модели идут в работу из списков категорий, в том числе медиа.
- С каждым вызовом модулю уходят токен `CLAUDE_CODE_OAUTH_TOKEN` (если задан) и слово владельца о доплате; настройки
  `CLAUDE_CODE_EXTRA_USAGE` и `CLAUDE_CODE_EXTRA_USAGE_RESERVE_PERCENT` читаются при каждом вызове.
- Снятие с выбора (`ProviderPauses`) общее для подписок: вызов снятого провайдера падает сразу, без запроса;
  `FallbackModels` берёт следующую модель того же списка категории (сначала списки основных и сильных моделей) у
  работающего провайдера, а при её отсутствии не переключает. Исчерпанное окно снимает с выбора **модель**, а не всю
  подписку: у планов бывают окна отдельных моделей (неделя Opus), остальные модели идут дальше. Снятие по лимиту
  отменяется сразу, как только владелец меняет `CLAUDE_CODE_EXTRA_USAGE` или порог. Повторы `RetryingClient` такой 429 не повторяют.
- Кеш промпта: шлюз модуля приводит запрос CLI к виду, который повторяет следующий запрос беседы (дата — в
  сообщение окружения, напоминания CLI перед репликой убраны, результаты инструментов восстановлены, метка — на
  последний повторяющийся блок). После первого вызова беседы из кеша читается 94–99% промпта (замер 2026-11-24).
- Риски, принятые вместе с подпиской (2026-11-24): формат stream-json и поведение CLI за шлюзом — внутренние
  интерфейсы CLI, поэтому версия закреплена и меняется только с проверкой ([порядок обновления](../services/claude-code/BRIEF.md#обновление-claude-code));
  вызов `-p` может расходовать окно плана быстрее интерактивного Claude Code — какие категории отдавать подписке,
  решает владелец списками; процесс CLI — около 110 МБ и 3–8 с на вызов, частые дешёвые вызовы на подписку лучше не
  ставить.
- Отложено: сообщение владельцу о начале доплаты при `notify` (сейчас `notify` для сервиса равен `allow`, состояние
  видно в `/claude`); оценка вызова «по прайсу» в трассе.

#### Что не берём для подписки Claude

- **Прямые запросы с токеном подписки под видом Claude Code** (так делает ядро hermes-agent,
  [конспект](../docs/notes/hermes-agent.md)): это выдача себя за официальный клиент — риск для аккаунта владельца.
- **Чтение, копирование и обновление файлов входа своим кодом:** вход принадлежит Claude Code.
- **Claude Code в образе приложения:** тяжёлое и необязательное — модулем.
- **Claude Agent SDK и Managed Agents как цикл агента:** цикл, инструменты и память у Меркурия свои.

### Google по подписке

Решения владельца 2026-11-26. Модели плана Antigravity (подписка Google) — провайдер `antigravity:`, через
официальный клиент `agy` (Antigravity CLI) в отдельном необязательном модуле `mercurius-antigravity`
(`services/antigravity/`, профиль compose `antigravity`, настройки `ANTIGRAVITY_*`, команда `/antigravity`).
Состояние (2026-11-27): модуль и его подключение в приложении сделаны и проверены на подставном `agy`; на настоящем
`agy` 1.5.18 проверено только то, что видно без входа. Вход владельца, проверка протокола на своей версии и выбор
между stream-json и ACP ждут владельца ([«Ждёт владельца»](history.md#ждёт-владельца)). Устройство сервиса — в его
брифе ([mercurius-antigravity](../services/antigravity/BRIEF.md#устройство)).

- **Условия Google это запрещают, риск принял владелец.** Условия Antigravity (раздел 6) и FAQ, прочитанные
  2026-11-26, называют доступ к сервису через стороннее программное обеспечение и обёртку `agy` в приложение
  нарушением, за которое аккаунт Antigravity и Gemini CLI может быть приостановлен или закрыт. У Claude было иначе:
  там владелец записал, что подписка такое использование разрешает. Владелец выбрал: модуль делается, выключен по
  умолчанию, включает его владелец экземпляра на своём экземпляре, понимая риск; при первом входе `/antigravity`
  показывает предупреждение со ссылкой на условия и продолжает после явного согласия. То же предупреждение — в README
  модуля. Отдельный аккаунт Google риск не снимает, только ограничивает потерю.
- **Ключ API — не здесь.** Разрешённые пути (ключ AI Studio, Vertex) — встроенные провайдеры
  ([Провайдеры Gemini и Vertex](#провайдеры-gemini-и-vertex)). Модулю подписки ключ не нужен и в него не передаётся:
  сервис отказывается стартовать с унаследованными `GEMINI_API_KEY`, `GOOGLE_API_KEY`,
  `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT`.
- **Имя.** Провайдер назван по продукту, а не `gemini:`: план даёт ещё модели Claude и GPT-OSS. Они входят в
  каталог `antigravity:` — всё, что показывает `agy models`.
- **Способ.** `agy` служит только моделью: один вызов модели — один промпт, инструменты исполняет Меркурий.
  Транспорт (`agy` в режиме stream-json, один процесс на вызов, или ACP-сервер) выбирается после разведки.
- **Аккаунт.** Отдельный аккаунт Google, выданный владельцу под эту работу. Вход в подписку вручную делает
  владелец — и во время разработки. Файлы входа исполнитель не читает и не копирует.
- **Цена** в выборе модели — 0 за токен, как у `claude:` и `chatgpt:`.
- **Ресурсы.** Процесс `agy` занимает до ~400 МБ (по данным плагинов hermes); предел одновременных процессов и
  `mem_limit` контейнера задаются по замеру.
- **Среда `agy`.** Официальный бинарь не изменяется, штатные механизмы входа и идентификации клиента сохраняются.
  Владелец решил, что `agy` работает в полноценной пользовательской среде (пользовательский контекст, терминал,
  системная совместимость, каталог вызова, обнаружение инструментов через MCP, устойчивость сессии); что именно
  нужно `agy`, устанавливает разведка, спецификации среды пока нет. Модель интерактивной пользовательской сессии
  (события ввода, времена операций, ожидания, подтверждения, порядок шагов, согласование частей, терминал или
  каналы) сделана как драйвер запуска, в котором `agy` разговаривает как с человеком, — сейчас это вход
  ([Сессия agy](../services/antigravity/BRIEF.md#сессия-agy)). Владелец уточнил 2026-11-27: её назначение —
  верная работа с интерактивным CLI, а не сокрытие чего-либо. Граница записана там же: задержек «под человека» и
  набора по клавишам нет, на вопросы `agy` сервис не отвечает — их решает владелец.
- **Бережная работа с подпиской** — требование к модулю: малый предел одновременности и очередь, никаких своих
  повторов поверх повторов `agy`, отказ до запуска при исчерпанной квоте, один аккаунт и один вход без ротации,
  закреплённая выпущенная версия `agy`, частые дешёвые вызовы — провайдерам по ключу, остановка провайдера до
  действия владельца при ответе Google о проверке аккаунта или условиях.

#### Как сделано: подписка Google в приложении

- **Провайдер — не профиль.** `antigravity` входит в `ModelRef::SUBSCRIPTIONS`: ключа в `.env` у него нет, провайдер
  есть, пока задан `ANTIGRAVITY_TOKEN`; ролей по умолчанию нет — модели идут в работу, когда владелец внёс их в
  списки категорий.
- **Клиент** — `AntigravityClient` пакета `llm` ([Antigravity](../packages/llm/BRIEF.md#antigravity)): Chat
  Completions сервиса, две попытки. К сервису приложение ходит напрямую по внутренней сети, без маршрута моделей.
- **Каталог** — `GET /v1/models` сервиса: цена 0, окно — предел одного сообщения `agy` (60 000 токенов у Gemini,
  120 000 у остальных — по наблюдениям плагинов, не проверено), поэтому приложение сжимает историю заранее. Каталог
  запрашивается после входа.
- **Команда `/antigravity`** (только владелец, только личный чат): без аргументов — вход, квота по группам, что
  снято с выбора; `login` — предупреждение о пункте 6 условий Google со ссылкой, ссылка входа выдаётся только после
  `/antigravity login accept`; `code <код>` — сообщение с кодом удаляется из чата и не попадает в историю, и на
  экземпляре без модуля тоже; `resume` — вернуть модели в выбор; `logout` — снять вход: команды выхода у `agy` нет,
  поэтому модуль удаляет его файлы входа, не читая их, и паузы прежнего аккаунта снимаются (2026-11-27; повод — на B
  Google не пустил аккаунт, а `login` при уже сделанном входе отвечал только «не вышло»). `login` при сделанном входе
  теперь говорит, что сначала `logout`. `agy` ждёт код 60 секунд — владельцу об этом сказано в тексте со ссылкой. Ссылку `agy` показывает только
  терминалу, поэтому шаг входа в сервисе идёт под псевдотерминалом ([Вход](../services/antigravity/BRIEF.md#вход)).
- **Снятие с выбора.** 429 со временем сброса — модель снята до сброса (окна плана — по группам моделей, остальные
  группы работают). 401 — пауза 10 минут и одно сообщение владельцу. 403 «Google просит владельца аккаунта
  действовать» — отдельная причина `ProviderPauses::ACCOUNT`: провайдер снят, пока владелец не вернёт его
  `/antigravity resume`; через 10 минут агент к плану сам не возвращается. Нарушение правил вызова (422) клиент не
  повторяет.
- **Модуль** — профиль compose `antigravity`, том `storage/antigravity` (700), `ANTIGRAVITY_UID`/`GID`; ключи Google
  в сервис не передаются. `Doctor` и тема `modules` показывают его здоровье, версию CLI, вход и маршрут.
- **Знания агента о себе** — темы `models`, `modules`, `commands`; в системный промпт ничего не добавлено.

#### Что не сделано для подписки Google

- Прогрев запасного процесса и передача картинок и видео — отдельные задачи после замера и проверки на настоящем `agy`.
- Оценка «по прайсу» в трассе — общая отложенная задача трёх подписок.
- Список хостов выхода `agy` — короткий и точный, по тому, что видно без входа; настоящий список дополняется
  после входа владельца (`ANTIGRAVITY_EGRESS_HOSTS`).
- Проверка, не разворачивает ли `agy` `@путь` из текста: до неё модуль нельзя включать там, где агент читает
  недоверенные источники ([Что не проверено](../services/antigravity/BRIEF.md#что-не-проверено)).
- Спецификация среды `agy` сверх сделанного (см. [Среда agy](../services/antigravity/BRIEF.md#среда-agy)).

#### Что не берём для подписки Google

- Прямые запросы с токеном подписки к API Google под видом `agy` — выдача себя за официальный клиент.
- Чтение, копирование, симлинк файла входа в чужой HOME: вход принадлежит `agy` и живёт в томе модуля.
- Ротацию аккаунтов: FAQ прямо называет её неподдерживаемой.
- Режим, где `agy` исполняет инструменты (`--dangerously-skip-permissions`).
- Долгоживущий `agy` на беседу и `--conversation`: в нём остаются результаты инструментов, и история расходится с
  историей Меркурия.

### Как сделано: провайдер OpenAI

Проверено на сервере 2026-11-16: приложение поднялось с двумя провайдерами через VLESS, каталог OpenAI — 32 модели с
ценами (идентификаторы ролей по умолчанию `gpt-6-luna`, `gpt-6.1-terra`, `gpt-6.1-sol` в нём есть); воркер на
`openai:gpt-6-luna` ответил (запуск #63), расход записан как оценка по ценам каталога.

- **Код:** пакет `llm` — `OpenAIClient`, `OpenAICatalog`, общий `ChatCompletions`; Меркурий — `LlmSettings` с двумя
  ключами, `ModelRoles` с ролями по провайдерам, выбор по профилю во всех провайдерах, `ProviderRouter` с оценкой
  стоимости и именем модели с провайдером.
- **Найдено ревью и исправлено:** `reasoning_effort` шёл моделям без рассуждения (у OpenAI — 400) — теперь его
  получают только модели, у которых он есть в `supported_parameters` каталога, как у hermes; оценка стоимости
  записывалась как фактическая; в каталог попадали модели только для `/v1/responses` (codex, `-pro`); беседа,
  открытая с провайдером без ключа, падала на каждом запуске; неудачная первая загрузка каталога ждала сутки;
  исчерпанный баланс OpenAI повторялся как превышение частоты; при равной цене выигрывал OpenRouter с его комиссией.
- **Отложено:** модель, у которой нет ключа, по-прежнему видна в таблице ролей (`all()`), хотя используется замена
  по умолчанию.

#### Надёжность инструментов и решения о модели

- Часть с инструментами не получает модель, которую каталог OpenRouter считает плохо вызывающей инструменты: при
  обновлении каталога второй запрос `GET /models?min_tool_success_rate=0.9` даёт модели, чьи вызовы проходят свои
  схемы не реже 90% раз; остальные модели провайдера помечаются `model_catalog.tool_reliable = false`. Нет ответа —
  ничего не известно и никто не отсеивается. Модель, названная прямо, этим отсевом не проходит.
- Каждое решение о модели привязано к запуску (`routing_decisions.run_id`): смена после отказа называет свой запуск,
  выбор до старта запуск забирает при старте; `/trace` показывает причины. Цена вызова хранится с признаком
  уверенности (`llm_calls.cost_status`: сообщена OpenRouter, оценена по каталогу, неизвестна).
